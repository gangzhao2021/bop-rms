# `@bop/feature-control`

## Current storage boundary

The [current manifest](./src/module.manifest.ts) declares `bop_feature_control` with immutable control, dependency, operation and kill-switch versions. Later scoped persistence does not turn the WP-0120 pure minimum into a generic Policy Engine or real Phase capability evidence. Consult [the candidate register](../../../docs/runbooks/project-candidate-register.md) and [WP-2421](../../../docs/spec/work-packages/WP-2421.md) for the current continuation. Historical administration output with Unconfirmed coverage must not grant authority.

Owns the WP-0120 provider-neutral minimum contract for Release Flags、Kill Switches、exact
Brand/Store scope、deterministic basis-point rollout、shutdown policy、bounded recovery and
evaluation records.

## Contract

- Every definition has a strict `module.capability.variant` key、owner、purpose、explicit default、
  review/expiry、half-open UTC effective interval and positive version.
- Exact Store definitions override their same-key Brand definition only inside that Brand.
- Rollout consumes an opaque precomputed bucket; raw Actor、Customer、device and network identity
  never enters this package.
- One immutable evaluation drives the frontend visibility hint and authoritative backend decision.
  Frontend hiding is never authorization.
- Active Kill Switches block new work and return the caller-owned in-flight policy. Business Domains
  remain responsible for safe pause、termination、compensation and completed facts.
- State changes require an exact `@bop/permission` decision and an injected unit of work that
  atomically commits the next immutable control version with a bounded `@bop/audit` record.
- Recovery evidence is exact scope/version bound、time bounded and required for progressive or full
  reopening.

The original WP-0120 minimum owns no database object or runtime grant; the later module manifest owns its declared persistence. That minimum creates no generic Policy Engine、production route、
Section 88 Screen、Provider/WAF/cloud flag service、real Tenant/control fact or deployment.

## Current Store capability continuation

The current service consumes complete current owner definitions under the Brand source barrier, an explicit accepted mapping from the Registry capability key to the owning control key, and held current dependency/trigger receipts. Missing or expired facts fail closed. Store overrides, including Disabled definitions, take precedence only in their exact Store; an expired Store override does not inherit an enabled Brand definition. One decision drives the backend guard and frontend visibility hint. An observation is not a reusable grant.

The owning administration writer appends control/dependency versions, the operation and Audit in one transaction, with current authority on original replay. The new forward migration validates exact dependency parent scope and permits a stable dependency ID across immutable versions. Selected Product Create/Detail/Edit and Store capability mappings are explicit immutable repository configuration. The initial-Draft owning writer now records version1 with Unsatisfied dependencies and SaveDraft/0/1 original recovery; it requires a separately held current change/scope/field authority and creates no effective capability. Other mappings, real trigger facts, ordinary initial-creation composition and complete administration UI remain separately required; isolated test composition does not configure a Store.

## Verification

Run `pnpm feature-control:acceptance` from the repository root.

The normal composition can supply an empty evidence set only when complete owner definitions declare no dependencies. A declared dependency, including a stored Satisfied Future Trigger, is refused by that fallback. No static mapping or empty-source fallback enables an unconfigured control.
