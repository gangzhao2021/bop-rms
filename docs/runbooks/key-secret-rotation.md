# Key and secret rotation procedure

Authority: Handoff 87.8 and the [KMS/Audit/Archive policy](../security/kms-audit-archive-evidence-policy.json). Use the [evidence template](key-secret-rotation-evidence-template.md). This guide authorizes no live account or credential change.

1. Security coordinator names applicable approval, operator, purpose/environment, current version and dependent services/archives/holds. Identify safe restricted key/version references, decrypt/verify consumers, rollout sequence, stop conditions and alerts. A missing dependency or recovery path stops rotation.
2. Preserve purpose/environment separation and dedicated P256 sign/verify keys. Symmetric keys use annual automatic rotation; asymmetric keys rotate annually or on compromise with verify-only `kid` overlap. Validate old retained signatures/decryption as well as new writes before changing dependent consumers.
3. Secrets Manager rotates at 90 days or shorter; nonrotatable secrets receive 180-day review. Use dual-read/single-write version transition. Pepper overlap is at most 24 hours, or use announced global revocation. Record the chosen accepted path and affected Session/recovery behavior; never expose secret material in evidence.
4. Validate authorized new reads/writes, retained historical reads/verifications, consumer convergence and unusual-decrypt/access alerts. On failure stop advancement, retain required reading/verifying capability and escalate. Do not blindly resume old writes or revoke a version while dependencies still require it; the environment's approved recovery decision controls that action.
5. Deletion needs two-person approval, a minimum 30-day deletion window and confirmation that archive/hold dependencies do not block it. An active dependency blocks deletion. Preserve linked correction/refund/void history and applicable retention; rotation is not authority to rewrite append-only evidence.
6. Record actual version transition, overlap bounds, verification, alerts, reviewer and unresolved consumers in restricted storage. Daily Audit chain/signature and source-manifest/archive verification continue; verifier failure freezes high-risk exports. Quarterly cross-tenant-safe restore sampling remains separately evidenced.

The policy's control list and static tests express accepted requirements. They do not prove rotation, historical decryptability, retention, alert delivery or deletion approvals occurred.

## Pilot secret files (WP-2423, DEC-PILOT-SECRETS)

Decision: [pilot hosting integrations](../spec/design/pilot-hosting-integrations.md). A Pilot (real Store) installation reads every key from one folder the hosting mounts, named by `secretsDirectory` in `<runtime>/hosting.json`. InternalTest keeps its generated local key files and never reads this folder.

**Delivery.** One value per file, owned by the pilot user, mode `0400` (or `0600`), at most 16 KB; a trailing newline is ignored. Typical sources: AWS Secrets Manager or SSM Parameter Store written to files by the host agent, an ECS/Kubernetes secret volume (links inside the folder, such as `..data`, are followed; links leaving it are refused), systemd `LoadCredential`, or a deploy script. The folder must not be writable by group or others. Values are never logged; errors name files only.

| File                                                                               | Format                                                | Used for                         | Rotation                                                                                             |
| ---------------------------------------------------------------------------------- | ----------------------------------------------------- | -------------------------------- | ---------------------------------------------------------------------------------------------------- |
| `guest-session-key`                                                                | 64 hex                                                | guest session cookies            | replace; open guest sessions end, guests rescan                                                      |
| `guest-binding-key`                                                                | 64 hex                                                | guest table binding              | replace; seated phones rescan and re-enter the join code                                             |
| `guest-abuse-pepper`                                                               | 64 hex                                                | guest request limits             | replace any time (limits restart)                                                                    |
| `pickup-derivation-key-v<N>`, `pickup-selector-key-v<N>`                           | 64 hex, in pairs                                      | pickup codes                     | add `v<N+1>` pair; the newest issues, all verify; remove the old pair after its orders are collected |
| `merchant-encryption-key-v<N>`                                                     | 64 hex                                                | staff session encryption         | add `v<N+1>`; the newest encrypts, all decrypt; remove the old one after staff sessions expire       |
| `merchant-selector-key`                                                            | 64 hex                                                | staff session lookup             | replace; staff sign in again                                                                         |
| `catalog-cursor-key`                                                               | 64 hex                                                | product list paging              | replace any time (open lists reload)                                                                 |
| `staff-pin-pepper-v<N>`                                                            | 64 hex                                                | staff PINs                       | add `v<N+1>`; PINs set before keep verifying; remove the old version only after every PIN was reset  |
| `store-device-key`                                                                 | 64 hex                                                | registered store tablets         | replace; every tablet is registered again                                                            |
| `staff-pin-choice-key`                                                             | 64 hex                                                | tablet lock screen               | replace any time                                                                                     |
| `dining-key`                                                                       | 64 hex                                                | table join codes                 | replace between services; open tables issue new join codes                                           |
| `qr-signing-key`, `qr-signing-kid`                                                 | P-256 PKCS#8 PEM; kid `[A-Za-z0-9._-]`                | table QR signatures              | see below                                                                                            |
| `qr-previous-public-key`, `qr-previous-kid`, optional `qr-previous-compromised-at` | SPKI PEM; kid; UTC instant `YYYY-MM-DDTHH:MM:SS.sssZ` | codes signed by the previous key | see below                                                                                            |

No two files may hold the same value. A missing or unusable file stops a Pilot start before any service runs: the supervisor prints `PILOT_NOT_READY Secrets: PILOT_SECRETS_UNAVAILABLE missing: …; unusable: …` and refuses (`PILOT_CAPABILITY_MISSING`). Check before starting: `node tooling/environment/pilot-secrets.mjs check <runtime>` (`PILOT_SECRETS_COMPLETE` when ready). A rotated file takes effect when the services restart (use the planned-update procedure in the single-store runbook).

**First values.** `node tooling/environment/pilot-secrets.mjs generate <new private folder>` creates every missing value (0400) and a QR key with kid `store-qr-<date>`; it never overwrites and never prints a value. Upload each file as its own secret to the managed store and delete the folder, or, on a self-hosted machine, use it as the mounted folder (keep an encrypted copy off the host, like the off-site backup key).

**Table QR key switch.** To rotate: move the current public key and kid to `qr-previous-public-key`/`qr-previous-kid` (`openssl pkey -in qr-signing-key -pubout`), put a new key and a new kid in `qr-signing-key`/`qr-signing-kid`, restart. New and replaced codes use the new kid; old codes keep working (Overlap) until reprinted on Table QR codes ("Replace", then print). If the old key may have leaked, also write `qr-previous-compromised-at` (now): every old code stops at once, so replace and print all codes in the same visit. Moving from InternalTest to a Pilot key always counts as compromised (the test key lived in a local file), and a change of `customerOrigin` in `hosting.json` also requires replacing and reprinting every code.
