## Acceptance and owner contract

Add the pure Ordering transition used inside a future serialized initial-selection transaction.
Closed input captures exact Brand/Store/Dining Session, current authorized Guest/Participant references,
UTC observation, and owner-supplied Customer Cart history. History must include terminal, effectively
expired and legacy Carts for that Session, not merely WP-2314's eligible-current query. At most two
rows are needed to distinguish none/unique/ambiguous; ambiguity denies instead of selecting a winner.

One exact-scope Qr/Web DineIn Cart with active lifecycle is selected unchanged, including creator,
item attribution, version and deadlines. Another Participant selects the same Cart; selection grants
no item-edit authority. Existing expired/abandoned/legacy history denies and cannot silently create a
replacement. Zero history requires an explicit owner-generated Cart reference, Qr/Web source and
current versioned/digested lifecycle policy; no Store defaults. Create an empty version1 Cart with
the acting Guest as immutable creator and exact existing Dining Session association. Policy validity
is inclusive-from/exclusive-until. Malformed/extra/accessor/noncanonical/time-overflow inputs deny.

Return a frozen Create/Select decision and exact expected owner version (0 requires the writer to verify absence).
This pure decision performs no authorization, I/O, commit, lease or idempotency storage. The future
application command must resolve current Identity/public Dining purpose-Cart authority before
historical retries and recheck before response. The writer must serialize exact Session selection,
recheck absence/version, and atomically append operation/Audit with any new Cart; stable operation
intent and response-loss recovery belong to that command. These obligations are not asserted by a
caller-supplied history array. No foreign Domain query, new Identity binding, Closing lease or Order
authority follows from empty Cart allocation.
