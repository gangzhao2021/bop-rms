# WP-2142 — Loyalty Program versioning, lifecycle simulation and publish

## Authority and scope

- Handoff Sections 33.4–33.12 define Brand-scoped Loyalty Program identity, immutable Versions,
  earning/activation, reservation/redemption, refund reversal, expiry, Tier and Reward rules.
- Section 88.14 defines `LOY-PROGRAM-LIST` and `LOY-PROGRAM-EDITOR`; Sections 88.21–88.24 define
  validation, approval, publication, projection and error behavior.
- This WP adds runtime-inactive Domain/Application contracts and strict Merchant pages. No accepted
  Customer & Loyalty persistence namespace exists, so database/outbox adapters remain ports.

## Acceptance criteria

1. Stable Program identity is Brand-scoped; configuration changes append a Draft Version and never
   overwrite a Published Version or historical Points/Tier/Expiry facts.
2. Versions cover eligibility, earn/activation, redemption, expiry, Tier, Reward/Entitlement,
   refund reversal, Store/channel/order scope, effective period and customer copy.
3. Exact non-floating integer points and bounded rules support deterministic Earn → Activate →
   Reserve → Redeem/Release, refund reversal, expiry and Tier/Reward lifecycle simulation.
4. Validation fails closed on non-conservation, ambiguous effective versions, invalid Tier ordering,
   invalid expiry/reservation interaction, Pricing-owned monetary calculation or Points-as-tender.
5. Publish/schedule requires validated simulation evidence, distinct Approver, Expected Version and
   idempotency. Suspend is explicit; history is retained.
6. Both canonical pages use strict, permission-trimmed projections and all registered states; stale
   or partial projections are read-only.
