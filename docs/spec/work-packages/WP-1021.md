## Purpose

Define the smallest first-Pilot Catalog structure that proves:

1. Category is a Brand-scoped Aggregate Root and Category is never a Menu Section；
2. Category supports stable identity、Brand-unique code、plain localized content、Draft/Active/
   Inactive/Archived lifecycle、ordered parent/child structure and optional Store applicability；
3. Category tree operations prevent self-parent、cross-Brand parent、cycles and depth above three；
4. Menu is a Brand-scoped Aggregate Root with one complete Draft structure snapshot；
5. Menu owns stable Menu Section Entities and Sellable Placement relationship records；
6. a Section may reference zero or more Categories while remaining independent display structure；
7. a Placement references only the WP-1020 `Sku` Sellable type and expresses presentation/order,
   never price、inventory、purchase authority or a UI component；
8. one-level Menu inheritance is enforced without flattening or copying a Base Menu；
9. Category/Menu mutations require exact Tenant/Actor/Permission/Audit、expected aggregate
   version and idempotent operation reference；and
10. publishing、approval、effective periods、Store Availability、Option、Pricing、Customer query、
    Projection、API/UI/Event and real Catalog evidence remain out of scope.

## Ownership and boundaries

- `@rms/catalog` owns Category、Menu、Menu Section and Sellable Placement.
- Category is Master Data. Menu Section is display structure. Neither identity is interchangeable.
- SKU Sellable identity is consumed through the WP-1020 public Catalog contract；Menu does not
  query Product/SKU private persistence.
- Category parent facts and Menu child records commit only through their owning aggregate.
- Tenant Context derives Brand. Optional Store references are validated through injected public
  Tenant contracts；Catalog never reads Tenant private tables.
- Permission grants authority and Audit records accepted mutations. Neither grants Category、
  Store、Menu、Sellable or inheritance facts.
- Menu Draft is not Published、Scheduled、Effective or Customer-visible. WP-1024 owns publication.
- WP-1023 owns effective Store Availability. Placement structure never means available or
  purchasable.
- Pricing owns money；Inventory owns balances；Recipe owns ingredients；Media owns assets；
  Ordering owns historical line snapshots.
- Localized Category/Menu display content is business configuration, not PII. HTML/Markdown、
  external URLs、customer/staff notes、legal/allergen assertions and unrestricted text are absent.

## Adopted decisions

1. **Category root —** stable Category ID、Brand、normalized code、aggregate version、lifecycle、
   localized name/optional description、parent、sort order and exact optional Store references.
2. **Tree depth —** root level is `1`; the first version supports at most level `3`.
3. **Tree concurrency —** create/update/move/reorder compare Category aggregate version；move also
   consumes a repository-supplied current ancestor/subtree view and sibling ordering fact.
4. **Tree safety —** parent must share Brand；self-parent、cycle、missing parent、duplicate sibling
   order and a resulting subtree deeper than three fail closed.
5. **Archive —** Active Category with Active children cannot archive without an injected complete
   impact decision. This minimum implementation exposes no cascade archive.
6. **Codes —** Category/Menu/Section codes normalize uppercase and are unique in their owning
   scope. Archived codes are not silently released.
7. **Localization —** default locale must resolve to 1–120 plain normalized characters；
   description is optional plain text up to 500 characters. Markup、URL and operational note fail.
8. **Store applicability —** Category keeps a deterministic unique list of opaque Store
   references. Empty means Brand-wide；it does not assert Store existence without injected
   validation.
9. **Menu root —** stable Menu ID、Brand、normalized code、aggregate version and one mutable Draft
   Menu Version. Published/Superseded/Archived rows are not created by this WP.
10. **Menu scope —** the Draft declares deterministic Store、Channel and Order Type reference
    sets. Empty Store set may express Brand-wide structure but never availability.
11. **Section —** stable Section ID/code、localized name、sort order and zero-or-more unique
    Category references. Section references do not mutate Category.
12. **Placement —** stable Placement ID、Section、`Sku` Sellable reference、Presentation Role、
    sort order、pin flag and optional plain localized display-name override.
13. **Placement uniqueness —** ordinary placement uniqueness is
    `(Section,Sellable,PresentationRole)`；special presentation uses an explicit different role.
14. **Presentation Role —** closed values are `Standard`、`Featured`、`Promotional`、`Sponsored`
    and `Hidden`; no frontend component name is stored.
15. **Inheritance —** a Derived Menu may reference one same-Brand Base Menu；a Derived Menu cannot
    be a Base and a Base cannot itself be Derived. No second-level resolution or copy is allowed.
16. **Complete Draft replacement —** Menu mutation replaces the complete Section/Placement
    snapshot at expected Menu aggregate version；partial merge/last-write-wins is forbidden.
17. **Idempotency —** operation reference + deterministic intent digest replays the same intent；
    changed intent conflicts. Repository conditional commit is the final version guard.
18. **Persistence —** one forward migration extends `rms_catalog` with Category and Draft Menu
    structure tables、forced Brand RLS、stable-identity guards and append-only minimal operation
    history.
19. **No event/screen claim —** canonical future commands/events/routes remain acceptance context.
    This WP adds no Event Catalog record、Projection、HTTP route or UI.
20. **External Evidence —** no Pilot Category、Store assignment、Menu、Sellable placement、
    translation、approval or production fact is available or claimed.
21. **Hard stop —** Category/Menu identity collapse、depth/cycle ambiguity、Menu child independent
    write、multi-level inheritance、Published/effective claim、client-trusted Brand/permission、
    missing expected version/idempotency/audit/RLS、price/inventory/purchase authority、PII/free
    note/external URL、allowlist-external file or invented evidence stops implementation.

## Risks, rollback and next action

- Category/Menu Section identity collapse causes ownership and display drift；contracts keep them
  distinct.
- Menu structure mistaken for availability authorizes stale purchase；Draft and Placement are
  explicitly non-authorizing.
- Tree/inheritance recursion can create cycles or unbounded resolution；depth is closed at three
  for Category and one inheritance edge for Menu.
- Free-form display content can leak sensitive or unsafe assertions；strict plain localized text
  only is accepted.
- Rollback before merge is deletion of this brief plus bounded index edits. After merge,
  correction is forward documentation/implementation；accepted evidence history is never
  rewritten.
- Next allowed action is readiness exact-head pinned-Linux CI and Section 91 review.
