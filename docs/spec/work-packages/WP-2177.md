# WP-2177 — Recall Case, Scope Calculation, Containment, Notice and Disposition

## Authority and scope

- Handoff Sections 40.1–40.4, 40.10, 40.18–40.25, 40.29, 87.11.2, 88.16 and
  88.21–88.30 define Recall Case coordination, versioned scope, closure gates, owner actions,
  restricted notification and the canonical Screen contract.
- Exact local predecessor: verified WP-2176 commit `8e4ed1f`.
- Compliance owns the Recall/Withdrawal requirement, Case-bound scope revisions, coordination and
  verification. Trace projection calculates affected scope. Inventory owns Hold/Transfer Block/
  Dispose; Catalog/Ordering own availability/admission; Procurement owns buying/receiving blocks;
  Task and Notification own work/notice outcomes. Historical Orders are never rewritten.
- Section 50 grants no Compliance schema or migration namespace. This WP adds no database object or
  runtime adapter and does not claim durable production operation.

## Acceptance contract

1. Recall revisions pin Tenant/Brand/Store, stable Recall and Case identity, Recall/Withdrawal type,
   source/notice snapshot reference and digest, severity, Requirement Version, affected effective
   period, immutable recorded time and closed lifecycle.
2. Scope calculation consumes an authorized Trace Run and returns stable Supplier/Item/Lot/Batch/
   Product/SKU/Store references plus Customer/Fulfillment aggregate counts only. Expected/traced/gap
   counts reconcile exactly; any Gap makes coverage `Partial` and blocks closure.
3. Lifecycle is `ScopeAssessment | Containment | Notification | Disposition | Verification | Closed |
Cancelled`. Revisions are append-only with exact expected version and preserve source facts,
   affected references and owner outcomes.
4. Containment invokes explicit idempotent owner ports and records opaque Inventory, transfer,
   Catalog availability, Ordering and Procurement outcome references. Recall Hard Blocks cannot be
   manager-overridden and Compliance never writes foreign facts.
5. Task creation and notice approval/issuance use explicit owner ports. Notifications expose only
   aggregate Customer/Fulfillment scope and opaque content/outcome references; no Customer identity,
   contact, message body or Provider payload enters Compliance contracts, Events, UI or logs.
6. Disposition records are scoped, immutable and reference the Inventory/Procurement/Operations
   owner outcome. Compliance never edits Stock Ledger, PO, receipt, Order or Payment history.
7. Closure requires complete Trace coverage, all mandatory containment outcomes, resolved notice,
   recorded disposition, current independent `Passed` Verification and active Case scope. Failed or
   unable Verification returns the Recall to Disposition; no ordinary override can close it.
8. Only committed initiation and closure publish `RecallInitiated` and `RecallClosed`, with safe
   Case/Recall/scope/Requirement/severity/time facts and no affected-object or Customer identifiers.
9. `RECALL-CASE` at `/app/compliance/recalls/:id` exposes Section 88 fields/actions and explicit
   loading/denied/offline/stale/conflict/error/not-found states. Strict UI contracts accept safe
   codes, references, digests and aggregate counts only.
