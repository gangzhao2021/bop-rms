## Owning facts and boundaries

Reservation & Waiting owns Reservation identity, append-only revisions, Reservation status,
Capacity Hold reference / expiry, confirmed capacity claim, applicable Pricing / Payment policy and
payment references, check-in and Dining seating handoff references. Dining owns actual Table and
Session; Pricing owns amounts and policy calculation; Payment owns authorization, capture, void and
refund outcomes; Notification owns delivery; Identity / Customer own profile truth. Reservation
stores only the minimum confirmed contact snapshot and controlled assistance request required for
the booking purpose.

## Acceptance contract

1. Create pending Reservation, revise atomically, confirm, check in, cancel, mark no-show and record
   Dining seating handoff are strict idempotent Commands with Tenant, Brand, Store, Actor, purpose,
   `dining.operate`, exact expected version, append-only Audit and minimal future Event records.
2. Reservation retains one stable identity and append-only revisions. Critical revisions require a
   new unexpired Capacity Hold before the original claim is released; failure leaves the current
   revision unchanged. Seated is terminal for Reservation mutation and can only follow a Dining
   result reference.
3. Deposit status is separate from Reservation status. Reservation stores only owner-issued policy
   and Payment references / controlled outcome; it never calculates money, captures, voids, refunds
   or infers Provider finality. Capacity expiry may expire an unmet Pending reservation but never
   rewrites Payment facts.
4. `RES-CALENDAR`, `RES-LIST`, `RES-DETAIL` and contextual `RES-CREATE-EDIT` implement every Section
   88 field, filter, action and mandatory state. Contact search / display is permission-minimized;
   all commands remain visibly disabled without an authorized command-capable BFF.
5. Handoff Section 50 authorizes no Reservation schema or migration namespace and the accepted
   Module registry classifies `@rms/reservation-waiting` as non-critical. Persistence, outbox,
   Payment / Dining / Notification adapters and live projections therefore remain injected ports;
   this WP must not invent database or external-service authority.
