## Purpose

Define the smallest first-Pilot Catalog source aggregate that proves:

1. Product is a Brand-scoped Aggregate Root with stable opaque identity、normalized
   Brand-unique code、registered type、lifecycle and monotonic aggregate version；
2. Product Version is a complete immutable configuration snapshot；this WP creates and updates
   one optimistic-concurrency Draft and never mutates a Published snapshot；
3. SKU is a Product-owned Entity with its own stable identity/lifecycle and cannot be mutated
   outside the Product Aggregate；
4. SKU code is Brand-unique；unit quantity is positive decimal text and never binary float；
5. Variant selection is a closed, deterministic ordered set and is unique inside Product；
6. Sellable is a Catalog public abstraction, not an Aggregate or table；v0.1 resolves a Product
   SKU to opaque Sellable ID/type/Brand/lifecycle/unit/tax reference without price or inventory；
7. Product and SKU lifecycle transitions follow Sections 11.4 and 12.2, including no direct
   Active/Suspended → Archived and no Archived → Active；
8. Product/SKU creation、Draft update and lifecycle action require exact Tenant/Actor/
   Permission/Audit、expected aggregate version and idempotent operation reference；
9. persistence enforces Brand scope、optimistic version、append-only operation history and forced
   RLS in the Catalog-owned schema；and
10. Category、Menu、Option、Availability、Publishing workflow、Projection/UI/API、Pricing、
    Inventory、Recipe、Allergen/legal content and real Catalog evidence remain out of scope.

## Ownership and boundaries

- `@rms/catalog` solely owns Product、Product Version、SKU and their Catalog lifecycles.
- SKU is never promoted to a separate Aggregate Root. Every SKU mutation commits through one
  Product expected aggregate version.
- Sellable is a discriminated public value. WP-1020 supports only `Sku`; Bundle/Gift Card/
  Membership/Service/Deposit remain unavailable until their owning WPs.
- Tenant Context derives Brand. Caller-supplied Brand mismatch fails closed before persistence.
- Permission decides authority and Audit records accepted mutations. Neither grants Catalog facts.
- Publishing owns approval/effective publication. WP-1020 Draft never claims Published,
  Scheduled, Approved or externally visible Menu content.
- Pricing owns money/tax calculation; Catalog stores only an opaque tax classification reference.
  Inventory owns balance/availability；Recipe owns ingredients；Media owns assets.
- Ordering/history consumes an immutable future Sellable snapshot；it never depends on current
  mutable Catalog names. No Ordering table is read or written here.
- Product names are business configuration, not PII. Preparation/customer notes、HTML/Markdown、
  secrets、external URLs and legal/allergen assertions are absent from this minimum contract.

## Adopted decisions

1. **Initial aggregate —** create one Product in `Draft` with one Draft Product Version and zero or
   more Draft SKUs.
2. **Product types —** the minimum registered types are `PreparedFood` and
   `NonAlcoholicBeverage`; age-restricted、gift/stored-value and service types fail closed.
3. **Codes —** Product/SKU codes normalize to uppercase and match
   `[A-Z][A-Z0-9_-]{0,63}`. Brand uniqueness is repository/database authoritative.
4. **Localization —** default locale is canonical BCP-47-shaped text and must have a localized
   name of 1–120 normalized plain-text characters. No HTML/Markdown or free-form operational note.
5. **Draft snapshot —** content is exact Product Version ID、base version (nullable)、default
   locale、localized names、tax reference (nullable)、ordered SKU snapshot and Draft status.
6. **Draft update —** replaces the complete Draft snapshot at expected Product aggregate version；
   partial merge/last-write-wins is forbidden.
7. **SKU identity —** stable SKU ID/code/product/brand/created facts never change. Unit semantics
   change requires a new SKU.
8. **Unit quantity —** canonical positive decimal string, maximum six fractional digits；no
   `number` money/quantity representation.
9. **Variant values —** exact ordered `(dimensionReference,valueReference)` pairs, unique by
   dimension, and no unknown/duplicate/accessor-bearing structure.
10. **Lifecycle —** Product and SKU transitions are pure policies. Suspended may resume；
    Discontinued may reactivate only through a new Product Version and injected impact approval,
    which is not implemented here；Archived restore returns only Draft/Discontinued.
11. **Sellable eligibility —** `Active` SKU under `Active` Product is Catalog-eligible；this is not
    Store/time/Menu/price/inventory availability and never authorizes purchase.
12. **Expected version —** every mutation compares a positive Product aggregate version and
    increments exactly once.
13. **Idempotency —** create/lifecycle use operation reference + deterministic intent digest；
    Draft update also has an operation reference. Same intent replays；changed intent conflicts.
14. **Failure ordering —** validate closed input、scope、permission and current state before
    mutation. Database unique/version constraints remain the final concurrency guard.
15. **Database —** first Catalog migration creates `rms_catalog.product`、
    `rms_catalog.product_version`、`rms_catalog.sku` and
    `rms_catalog.product_operation_record`; no Category/Menu/Option/Sellable table.
16. **Snapshot immutability —** non-Draft Product Version rows are database-immutable. This WP
    writes Draft only；future publication uses forward-only new versions/status actions.
17. **RLS —** all Catalog tables use forced Brand RLS through `platform_helpers.current_brand_id()`
    and require Store context to be null for Brand master-data writes.
18. **Operation history —** append-only operation record keeps minimal operation/digest/result
    references. It contains no localized payload or unrestricted notes.
19. **No event claim —** Event names remain future Catalog Publishing/API acceptance. WP-1020 does
    not add outbox payload or claim a published event.
20. **No screen claim —** Section 88 governs later UI/API WPs. No route、component、Projection、
    search index or realtime consumer is added.
21. **External Evidence —** no Pilot Product/SKU、tax classification、barcode、Media、allergen、
    approval、traffic or production fact is available or claimed.
22. **Hard stop —** SKU as independent Aggregate、price/inventory/Recipe/Order ownership、
    Published claim、client Brand/permission trust、binary float、mutable published snapshot、
    missing expected version/idempotency/audit/RLS、PII/free text/external URL、allowlist-external
    file or invented evidence stops implementation.

## Risks, rollback and next action

- Treating SKU as a root breaks Product concurrency；all writes use the Product aggregate version.
- Treating Catalog eligibility as availability authorizes stale purchase；Sellable output is
  explicitly non-authorizing until Menu/Availability/Quote/Ordering WPs.
- Mutable Product Version rows can rewrite history；only Draft is replaceable and later statuses
  are immutable.
- Free-form preparation/allergen/legal text can leak sensitive or unsafe assertions；it is absent.
- Rollback before merge is deletion of this brief plus bounded index edits. After merge,
  correction is forward documentation/implementation；accepted evidence history is never
  rewritten.
- Next allowed action is implementation exact-head pinned-Linux CI and Section 91 review.
