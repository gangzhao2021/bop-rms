# WP-2197 — Platform Tenant / Region / Lifecycle Operations

## Authority and scope

- Handoff Sections 50.7, 87 and 88.18 define cross-Brand Platform access and the canonical
  `PLT-TENANT-LIST` / `PLT-TENANT-DETAIL` screens.
- Exact local predecessor: verified WP-2196 commit `1bdc804`.
- `@bop/tenant` owns Tenant/Brand identity and the immutable Platform Tenant administration
  versions. Store, Provider, health, incident, plan, capability, policy, Support Case, Export,
  Restore and Audit facts stay with their owning Domains and are consumed only through approved
  references or projections.

## Acceptance contract

1. Platform pages are not Merchant super-admin pages. Every query and command requires a named
   Platform Actor, exact permission, purpose code, valid Support Case reference and full Audit;
   Tenant impersonation and unrestricted database browsing are prohibited.
2. `PLT-TENANT-LIST` `/platform/tenants` exposes exact Tenant ref/approved display name, region,
   lifecycle, plan/capability metadata, Store count and owner-projected health/open incident with
   exact ref/name, status, region and health filtering.
3. `PLT-TENANT-DETAIL` `/platform/tenants/:id` exposes only non-sensitive configuration,
   regions/environments, capability metadata, owner Store/provider health, Support Case, data and
   retention policy, and Audit references. It never exposes secrets, credentials, unrestricted
   object IDs, raw database access or private source tables.
4. Onboarding, configuration, suspension and restore use immutable versions, expected version,
   idempotency, exact command permission and append-only operations. A Tenant/Brand must already be
   resolved by the owner contract; client-supplied identity or scope is never authority.
5. Onboarding approval and platform capability changes require independent approval and accepted
   evidence. Activation additionally requires the owning Tenant lifecycle contract. Missing,
   expired, revoked or mismatched external evidence blocks without being invented.
6. Service suspension requires an explicit impact assessment, independent approval, recent MFA and
   owner lifecycle confirmation. Restore is only a controlled request in this WP; completion remains
   gated by the approved Restore workflow and evidence.
7. Diagnostic access is only a navigation/action intent here. WP-2198 owns Support Case assignment,
   time-bound diagnostic grants, action evidence, expiry and revocation; WP-2197 never manufactures
   those facts.
8. Immutable Tenant administration, normalized capability metadata and operation history use forced
   Platform-context RLS requiring actor, purpose and Support Case session context. The BFF must set
   that context only after application authorization.
9. UI actions fail closed for partial/stale/offline/denied/conflict states and retain explicit
   production warning, purpose, case and recent-MFA status without placing those values in URLs or
   analytics.
10. This WP creates no real Tenant, region allocation, plan, capability, Store/provider health,
    incident, Support Case, approval, onboarding, suspension, export, restore or external mutation.
