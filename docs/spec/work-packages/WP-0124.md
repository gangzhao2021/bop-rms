## Purpose

Add a provider-neutral、synthetic `@bop/notification` minimum contract that proves:

1. Notification Requests originate from an immutable Event reference instead of a business Module
   directly invoking an Email/SMS/Push provider；
2. a request carries only opaque recipient、template/content and source references plus exact Tenant
   scope、purpose、priority、locale、channels and timing metadata；
3. exact scope + source Event + logical notification + recipient deduplicates repeated requests；
4. transactional and marketing preference evidence is separate and cannot substitute for the other；
5. preference、suppression and Pilot channel enablement resolve before any adapter call；
6. provider-neutral Email/SMS/Push adapter contracts use normalized opaque delivery references and
   never return or persist Provider payload；
7. adapter timeout becomes explicit `Unknown`; resend creates a new immutable attempt and never
   rewrites or silently assumes the prior attempt failed；
8. delivery failure/retry cannot change or roll back the source business fact；and
9. malformed、cross-Tenant、replayed、suppressed、disabled-channel or adapter-failure inputs return
   stable bounded outcomes without exposing recipient、content、identity or Provider data.

WP-0124 supplies the Notification Request / Provider Adapter minimum in Handoff Section 44.6.4.
Actual transactional Email delivery remains Feature F17.2 / WP-1720–1724.

## Governing decisions

1. **Predecessor —** WP-0123 is integrated and post-merge verified at
   `814f53e4baad28a8e0dd82ef6f1a8cd06ba06cdf`.
2. **Owner —** `@bop/notification` owns Notification Request、preference/suppression decision、
   channel route、logical deduplication key、delivery attempt metadata and adapter contract only.
   Source Domains own business facts；Publishing owns immutable templates/content；Identity/Privacy
   owners retain recipient contact and consent facts.
3. **Independent capability —** Notification remains separate from Workflow、Approval and Task.
   Their failure cannot silently change another capability or the source business outcome.
4. **Event source —** every request binds one immutable source Event reference/type/occurred-at and
   exact Tenant scope. This WP does not subscribe to Eventing、read Outbox or claim Consumer evidence.
5. **Opaque data —** core records contain UUIDv7 references、stable codes、`sha256:` digests、
   locale and canonical instants only. Recipient address、template body、rendered content、tracking
   data and Provider payload never enter the core Domain.
6. **Purpose separation —** `Transactional` and `Marketing` are distinct preference purposes.
   Evidence for one never authorizes the other. First Pilot marketing delivery is disabled.
7. **Channels —** adapter contracts enumerate Email、SMS and Push as required by Section 48.3.12.
   Section 86 enables only transactional Email for the first Pilot；SMS and Push remain disabled
   without a future accepted trigger.
8. **Latest evidence —** route resolution consumes injected immutable preference and suppression
   evidence valid at the explicit evaluation instant. Missing、stale、wrong-purpose、wrong-recipient、
   wrong-scope or contradictory evidence fails closed.
9. **Deduplication —** the logical key is exact Tenant scope + source Event + notification code +
   recipient reference + purpose. The unit-of-work port enforces one request per key and idempotency.
10. **Request lifecycle —** immutable request outcomes are `Accepted` or `Suppressed`; suppression
    records a bounded reason and performs no adapter call. A request is not proof of delivery.
11. **Delivery attempts —** attempts are append-only、strictly sequenced and bound to one accepted
    request/channel/route/content digest. Results are `Accepted`、`Rejected` or `Unknown`.
12. **Unknown/resend —** timeout or ambiguous provider acknowledgement is `Unknown`; an explicit
    resend uses a new attempt/reference/sequence and retains the prior attempt unchanged.
13. **Adapter boundary —** the injected adapter receives only the normalized request required for
    the chosen channel. It returns a bounded result and optional opaque provider-attempt reference；
    raw response、status body、headers、recipient/content or Provider error text are prohibited.
14. **Source isolation —** request or delivery failure is non-critical consumer behavior and cannot
    roll back、cancel、complete or otherwise mutate the source business fact.
15. **Privacy Governance gap —** no accepted `@bop/privacy-governance` package exists yet. This WP
    represents preference/suppression/contact resolution only through injected ports and immutable
    opaque evidence；it does not invent consent、PII、retention or deletion facts.
16. **Publishing boundary —** template/content references must be immutable published references
    with digest/version evidence. This WP does not author、render or publish content.
17. **Telemetry —** only stable channel、purpose、priority、operation、outcome and reason codes may
    be labels. Tenant、Store、Actor、recipient、event、request、template、content、attempt and
    provider references are excluded.
18. **No persistence/API/UI —** no table、migration、RLS、repository adapter、route、Screen、
    navigation or Projection.
19. **No provider/external mutation —** no SES/SNS、domain/DNS/DKIM/SPF/DMARC、Production Access、
    suppression list、credential、real recipient/template/message、external resource or deployment.
20. **External Evidence —** SES regional/production access、verified domain、deliverability、
    bounce/complaint、load、recovery、staging and production evidence remains
    `NOT AVAILABLE / NOT CLAIMED`.
21. **Hard stop —** business-fact ownership、recipient PII、template/rendered body、Provider payload、
    marketing/SMS/Push enablement、implicit consent、silent retry/Unknown coercion、mutable attempts、
    source-business mutation、Event Consumer claim、persistence、production API/UI、Provider/resource
    or allowlist-external tracked file stops implementation.
