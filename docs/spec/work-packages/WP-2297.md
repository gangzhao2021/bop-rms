## Acceptance and design

Add a read-only reserve operation to the public Dining admission service. Capture its closed
Guest/admission/operation/request-time input before awaiting dependencies. Authorize the exact
current ContextOnly DineIn Guest before reading owner facts. Validate fixed Brand/Store, current
internal Table, coherent original Join and original Guest/hash, Active Session/Participant and
Active unconsumed admission with the existing pure eligibility transition. Return only a frozen
narrow owner receipt containing operation/admission/Guest, Brand/Store/internal Table and assignment,
Dining Session/Participant/version and evaluated time. Do not consume, resolve consumption history,
write Audit, expose capability/hash/history or manufacture public mapping/validity.

Share current-authority validation with consumption within the existing service without changing
consumption's original-operation recovery or exact writer validation. A reservation is a current
observation, never a lease or write authorization: consumption must always revalidate atomically.
After consumption, Closing or Move, reservation denies obsolete eligibility. Exact current Guest
and owner coherence remain required on all paths. No evidence TTL or public/internal Table identity
is inferred; later API composition must provide authoritative mapping and finite validity.
