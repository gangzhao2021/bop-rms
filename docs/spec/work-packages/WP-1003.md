## Purpose

Add the smallest Identity-owned, provider-neutral server-side Guest Session contract that proves:

1. only server-resolved, currently allowed Customer entry evidence can create a Guest Session；
2. the browser receives one 256-bit opaque `__Host-bop-guest` credential and a separate
   session-bound CSRF credential, while persistence receives only keyed hashes；
3. one immutable Session is bound to exactly one Brand、Store、public Store/Table context and
   channel, without Customer Profile creation or Merchant authority；
4. idle expiry is four hours, absolute expiry is 24 hours, and an Order-closure binding shortens
   validity to at most two hours after closure；
5. fixation and every binding change rotate both browser and CSRF credentials atomically, and the
   former selector becomes immediately unusable；
6. Dine-in remains `ContextOnly`: a Guest Session cannot join/create/host a Dining Session or
   execute a Dining Order command without WP-1006's separate active credential；
7. revocation、expiry、scope drift、stale admission evidence、version conflict and dependency
   failure fail closed without an identifier oracle；and
8. the server-side record contains no raw Cookie、CSRF、QR token/signature、IP/device value、
   Customer contact、Provider Token or unrestricted payload.

WP-1003 owns the Guest Session context and lifecycle only. WP-1004 owns the public QR resolution
transport/error/recovery contract. WP-1005 owns Order Resume and Pickup Proof capabilities.
WP-1006 owns Staff-started Dining Session admission and copied-QR abuse behavior. WP-1020 onward
owns Menu/Cart/Order behavior.

## Ownership and trust boundaries

- `@bop/identity` owns Guest Session identity, lifecycle, browser credential boundary, rotation,
  revocation and persistence contract.
- `@rms/dining` remains the owner of QR/Table and Dining Session truth. Identity never imports RMS
  packages or private Dining types.
- `@rms/store` remains the owner of public Store and operating-status truth. Identity never
  evaluates Store hours.
- An injected server-side entry-admission port composes verified WP-1002 QR context, WP-1001 Store
  availability and the applicable abuse decision. The client cannot provide an `Allowed` fact.
- `packages/database` provides isolated-test plumbing only. Identity remains the write owner of its
  table through the Module and database-access manifests.
- Future API/BFF composition may serialize the fixed Cookie descriptor and no-store response, but
  no production route is registered in this WP.

The Guest Session is an authorization input for its exact journey scope, not a Customer account,
Merchant Actor, Permission, Dining credential, Order reference credential or cross-Store lookup.

## Adopted decisions

1. **Identity owner —** extend existing `@bop/identity`; do not create a Customer or RMS Session
   owner and do not widen `AuthenticationSession`, which remains workforce/Actor based.
2. **Separate aggregate —** add one `GuestSession` aggregate with a distinct
   `GuestSessionReference`, status `Active | Revoked | Expired`, positive version and immutable
   rotation/revocation facts.
3. **Server admission only —** creation accepts a bounded opaque entry request reference and calls
   one injected admission port. Only exact `Allowed` evidence can proceed. The evidence is a
   strict immutable server record, never a browser DTO.
4. **Admission evidence —** the record binds one internal Brand/Store reference, public Store
   reference, optional public Table reference, `DineIn | Pickup`, normalized locale, source QR
   reference/revocation version, evidence reference, evaluated instant and validity instant.
   The admission port atomically consumes the per-request same-origin entry proof once；the static
   QR itself remains reusable context and never becomes that proof.
5. **No BOP-to-RMS dependency —** Identity validates the closed primitive evidence shape and opaque
   references. The Application composition supplying it remains responsible for calls to public
   Store/Dining contracts.
6. **Admission freshness —** evidence must be valid strictly after creation time and its evaluated
   instant cannot be in the future. Missing、denied、ambiguous、expired or malformed evidence is
   uniformly unavailable.
7. **Raw credentials —** an injected cryptographic generator returns exact 32-byte random values
   encoded as 43-character unpadded base64url for the browser Session and CSRF credentials.
   Deterministic strings exist only in synthetic tests and are never production randomness claims.
8. **Keyed selectors —** an injected environment-keyed HMAC-SHA-256 port derives distinct fixed
   32-byte selector hashes for Session and CSRF purposes. Raw credentials and pepper never enter a
   record、log、metric、URL or database.
9. **Cookie —** the descriptor is exactly `__Host-bop-guest; Secure; HttpOnly; SameSite=Lax;
Path=/`, with no `Domain`. Cookie serialization/transport remains WP-1004.
10. **CSRF —** CSRF is session-bound and rotates with the Session. It may be returned only by a
    future same-origin no-store bootstrap for page memory and never enters a Cookie or browser
    persistence.
11. **Initial creation —** a client-supplied fixation candidate is ignored. Identity creates a
    fresh public Session reference and both fresh credentials through injected ports.
12. **Exact scope —** a record stores internal Brand/Store references only for server
    authorization plus customer-safe public Store/Table、channel and locale context. It stores no
    unrestricted Tenant、Customer、Cart、Order or Dining object.
13. **Dine-in denial —** initial Dine-in state is exact `ContextOnly`; the record contains no
    Dining Session/Participant/Host/join credential. WP-1006 must rotate/bind through a separately
    accepted command before any Dine-in write.
14. **Pickup scope —** Pickup may establish Store context, but it still grants no Cart/Order read
    or write. Later owning WPs must bind exact Cart/Order references through rotation.
15. **Timeouts —** active Guest Session uses `4h` idle and `24h` absolute half-open expiry.
    Background/SSE/polling activity never extends idle time.
16. **Order closure —** a future exact Order binding may record a canonical closure instant and
    closure expiry exactly two hours later. Effective validity is the earliest of idle、absolute
    and closure expiry.
17. **Rotation —** QR/Store/Table/channel/locale、Cart/Order、Dining admission、risk or other
    binding change requires a new Session reference、Session credential and CSRF credential.
    The old record is revoked atomically with reason `BindingChanged` or `Rotated`.
18. **Dine-in Batch rule —** submitting one Batch is not checkout and must not rotate an otherwise
    unchanged authorized Dine-in Guest Session. Final Dining Session checkout/closure or another
    binding change does rotate/revoke it.
19. **Revocation reasons —** use a closed set:
    `Rotated | BindingChanged | Logout | StoreUnavailable | QrRevoked | OrderClosed |
DiningSessionClosed | RiskChanged | Administrative`.
20. **Resolution —** hash the presented browser credential, resolve at most one record, validate
    status、idle/absolute/closure expiry and current immutable binding evidence, then return only a
    server-safe Session context. Unknown and expired credentials are indistinguishable.
21. **Expected version —** rotate/revoke requires positive expected version. Persistence performs
    the old-row terminal update plus new-row insert atomically; no last-write-wins or restore exists.
22. **Idempotency —** create/rotate/revoke mutations carry an opaque UUIDv7 operation reference.
    A repeated exact operation returns the original bounded result；different intent under one
    operation reference is a conflict.
23. **No invented concurrent identity —** no Customer/device correlation or arbitrary active
    Guest-Session cap is invented. The accepted Guest Session create/rotate budget remains an
    injected admission concern and later load evidence may trigger a separate reviewed cap.
24. **No fingerprinting —** IP/device parsing、keyed abuse buckets、WAF and rate budgets are
    injected/gated. No raw or derived cross-Customer device profile is stored by Identity.
25. **Persistence —** add forward migration
    `0200_006_create_guest_session.sql` with one `bop_identity.guest_session` table. It stores
    selector hashes、strict scope/binding fields、UTC lifecycle facts and versions only.
26. **Tenant defense —** every row carries exact `brand_id` and `store_id`. Forced RLS uses the
    accepted Tenant Context helpers for runtime access；PUBLIC is revoked. No login/runtime role,
    broad grant, `SECURITY DEFINER`, trigger or dynamic SQL is created.
27. **No secrets/ciphertext need —** unlike Merchant OIDC Sessions, a Guest record contains no
    Provider token bundle, so no encrypted-secret column or KMS call is introduced. Selector
    peppers remain external secrets.
28. **Retention —** expired/revoked raw selector hashes are eligible for scheduled deletion after
    the recovery window; a minimal Audit/revocation fact may remain per policy. No cleanup job is
    implemented in this WP.
29. **Telemetry —** labels are limited to operation、outcome and stable reason. Raw credential、
    selector/hash、CSRF、QR/public/internal references、locale、time、version and admission evidence
    are prohibited.
30. **Uniform errors —** malformed public command shape is `InvalidRequest`; every
    valid-shaped-but-denied Session/admission/dependency outcome is `GuestSessionUnavailable`;
    expected-version/idempotency conflicts remain bounded internal command conflicts.
31. **No Customer Profile —** Guest creation never creates/merges a Customer Profile, User,
    Loyalty Account, contact or consent fact.
32. **No external evidence —** no real Cookie、QR、Store/Table、IP/device、KMS/HMAC pepper、
    Customer traffic、load、staging or production evidence is available or claimed.
33. **Hard stop —** BOP-to-RMS import、client-trusted admission、raw credential/hash leakage、
    Customer PII、Merchant authority、Dine-in join/Host/order authorization、unforced scoped table、
    production API/UI、Provider/resource or allowlist-external tracked file stops implementation.

## Public candidate contract

The implementation candidate adds:

- `GuestSession`
  - opaque Session reference and positive version；
  - exact active/revoked/expired lifecycle；
  - internal Brand/Store authorization scope；
  - customer-safe public Store/Table/channel/locale context；
  - source QR/revocation evidence and `ContextOnly` Dine-in state；
  - created/last-seen/idle/absolute/optional closure expiry；
  - immutable rotation and revocation facts.
- `GuestSessionService`
  - `create` from injected current admission evidence；
  - `resolve` from a keyed browser selector；
  - `rotate` for an explicit server binding change；
  - `revoke` with expected version and idempotency.
- `GuestSessionStorePort`
  - atomic create/resolve/rotate/revoke and idempotency behavior.
- `GuestSessionCredentialPort`
  - 256-bit raw credential generation and purpose-separated keyed hashing.
- `guestSessionCookie`
  - exact browser Cookie descriptor, without transport registration.

The browser-facing issue result contains raw Session/CSRF credentials only at the immediate
application boundary. The persisted/public Domain record never contains them.

## Risks, rollback and next action

- Guest Session scope can become a cross-Store bearer capability；selectors are opaque/keyed,
  records are exact Brand/Store scoped, forced RLS is required and every binding change rotates.
- Static QR context can be mistaken for Dine-in admission；Dine-in remains exact `ContextOnly`
  until WP-1006 supplies a separate active credential.
- Session telemetry can become Customer tracking；identifiers, scope, locale, time and raw
  abuse/device evidence are prohibited.
- Rollback before merge is deletion of this brief plus bounded index edits. After merge, correction
  is a forward documentation/implementation change；accepted evidence history is never rewritten.
- Next allowed action is implementation exact-head pinned-Linux CI followed by Section 91 review.
