## Purpose and bounded outcome

WP-1601 consumes the existing public `KitchenItemReady.v1` fact through
`fulfillment.kitchen-item-ready:v1` and applies one append-only Fulfillment-owned Ready transition:

1. independently authorize the exact Brand / Store / Order / Batch / Item event;
2. lock and resolve the Fulfillment-owned current state without reading Kitchen private tables;
3. accept only a full-quantity Ready fact for one exact Pending Fulfillment Item;
4. record one immutable Ready result and operation, increment the Aggregate version and derive the
   post-transition phase as `Ready` only when every Item is Ready; and
5. atomically persist the result, operation, Audit and generic Inbox completion. Same Event and
   semantic redelivery converge while changed identity/content fails closed.

`KitchenOrderReady.v1` is a public Kitchen consistency hint, not a Fulfillment state authority. It
is not required to derive Ready after the exact Item vector is complete and is not activated by this
WP. Existing consumer catalog registration remains reserved for a later runtime composition.

No non-Kitchen `Mark Item Ready` Command, Pickup proof, Handoff Record, Completed transition,
`FulfillmentCompleted` Event, Ordering Projection, UI/API/SSE/Worker or production activation is
introduced. These remain later lifecycle increments.

## Closed Domain and screen contract

- Owner: `@rms/fulfillment` and `rms_fulfillment`; Kitchen owns Ready production and Ordering owns
  Order identity. Cross-Domain access is public Event only.
- Source: strict `KitchenItemReady.v1`; full quantity must equal the locked Fulfillment Item ordered
  quantity. Inventory, queue state, Kitchen Ticket UI or `KitchenOrderReady` never substitutes.
- Transition: `Pending -> Ready` per Item exactly once. Aggregate version increments by one for each
  new Item result; aggregate phase remains `Pending` until all Items are Ready, then becomes `Ready`.
- Idempotency: generic Inbox plus permanent source Event and Kitchen Ready-result identities. The
  first accepted source provenance is retained.
- Time and privacy: strict UTC, indirect identifiers only, no Customer/contact/address/note,
  health/allergen narrative, Money, Payment/Provider or arbitrary payload.
- Existing `FUL-PICKUP-QUEUE` and `FUL-FULFILLMENT-DETAIL` contracts remain future composition.
  This WP creates no Projection, route or client state.

## Acceptance criteria

- Exact authorized Item Ready changes only the matching Pending Item to Ready with full quantity.
- The Aggregate phase becomes Ready only after the last exact Item result and never becomes
  Completed.
- Missing, duplicate, stale, future, malformed, partial, over-quantity, cross-scope or mismatched
  source fails before an effect.
- Same Event, semantic redelivery, concurrency and commit-unknown recovery cannot duplicate a
  result, operation, Aggregate version or Audit.
- Persistence proves append-only behavior, forced RLS, exact quantities, uniqueness and cross-Store
  denial.
- Focused and root checks, security/privacy review, exact-head and exact-main Linux CI pass.
