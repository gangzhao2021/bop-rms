## Goal and bounded responsibility

Deliver the smallest Eventing reliability increment:

1. materialize the stable, business-agnostic Domain Event Envelope and `Append Event in Transaction` contract in `@bop/eventing`;
2. create the shared technical control table `platform_eventing.outbox_event`;
3. prove a synthetic business write and its Outbox event commit or roll back atomically in one caller-owned PostgreSQL transaction;
4. preserve default-deny schema privileges、Tenant isolation、minimal payload and deterministic migration/runtime verification.

The eventing package does not generate IDs、open transactions、commit、roll back or own business facts. The caller supplies an already-open transaction and application-generated UUIDv7 identifiers. The package performs one parameterized insert only. A failure is returned to the caller so the caller can roll back the complete business transaction.

## Accepted contract

### Public envelope

The pre-publication envelope contains:

- `eventId`: application-generated UUIDv7;
- stable PascalCase `eventType`;
- positive `schemaVersion`;
- `occurredAt`: UTC instant;
- `producerModule`: canonical `@bop/*` or `@rms/*` identity;
- `tenantId` and optional `storeId`;
- `aggregateType`、`aggregateId` and positive `aggregateVersion`;
- `correlationId` and optional `causationId`;
- either an Actor reference or the `System` actor classification;
- a JSON-object payload containing stable IDs and the minimum business fact;
- an explicit redaction classification and required JSON-object replay metadata.

The generic contract does not define a concrete business Event or payload schema. Before any producer is added, WP-0035 must register the Event type/version、payload schema、compatibility rule、consumer contract、retention and replay semantics. Secrets、credentials、payment data、health/allergy facts and unnecessary PII are prohibited.

Section 80.6.3 is the later naming authority: `schemaVersion` / `schema_version` supersedes the older generic `eventVersion` label. `publishedAt` is absent before publication and remains nullable in the Outbox until WP-0031 publishes the event.

### Table

`platform_eventing.outbox_event` is a shared infrastructure technical control record owned by `shared-infrastructure/eventing`, not a business Module table. It stores the exact envelope fields plus:

- server-recorded `recorded_at`;
- `available_at`;
- nullable `published_at`;
- non-negative `attempt_count`, initially zero;
- nullable stable `last_error_code`.

Event facts are inserted once and retained. WP-0030 exposes no update or delete operation. The bounded delivery-state columns exist for the future WP-0031 dispatcher and WP-0033 retry/dead-letter implementation; their mutation contract is not implemented here.

The table uses the accepted `platform_helpers.uuid_v7` domains, exact constraints, PUBLIC denial, `ENABLE ROW LEVEL SECURITY` and `FORCE ROW LEVEL SECURITY`. Its policy uses `platform_helpers.current_brand_id()` and `current_store_id()` with transaction-local server-resolved context. Missing or invalid context denies rows/writes for an ordinary non-owner runtime. No runtime role、grant、login or bypass authority is created.

Tenant-scoped indexes lead with `brand_id`. WP-0030 adds only:

- the UUIDv7 primary key on `event_id`;
- a partial publishable index on `(brand_id, available_at, recorded_at, event_id)` where unpublished;
- aggregate-order lookup on `(brand_id, aggregate_type, aggregate_id, aggregate_version, event_id)`;
- correlation lookup on `(brand_id, correlation_id, recorded_at, event_id)`.

These are contract indexes, not production query-plan evidence.

## Risks、recovery and external evidence

- Risk: a generic envelope becomes an ungoverned payload bag. Control: JSON-object shape、explicit classification、no concrete producer and mandatory WP-0035 registration before first producer.
- Risk: shared infrastructure becomes a cross-Domain write path. Control: a single parameterized Outbox insert and no API that writes business tables.
- Risk: delivery metadata is mistaken for permission to build a dispatcher. Control: no claim/lease/update API in this WP.
- Risk: RLS is mistaken for primary authorization. Control: application authorization remains mandatory；RLS is defense in depth.
- Risk: applied migration rollback damages retained Events. Control: before application, normal Git revert；after application, reviewed forward-fix or separately approved restore only.

External Evidence remains gated and unclaimed: actual API/Worker/Migration roles and grants、RDS compatibility、production query plans/volume/partitioning/retention、payload size threshold/object-storage reference、Event Catalog consumer approvals、staging apply、backup/restore and production authorization.
