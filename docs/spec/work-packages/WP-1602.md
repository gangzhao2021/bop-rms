## Purpose and bounded outcome

WP-1602 composes WP-1005's closed Pickup Proof capability policy with the Fulfillment-owned Ready
Aggregate. It owns:

1. strict proof-generation planning for one exact Ready Pickup Fulfillment, accepting only an
   already purpose-hashed `PickupProofCapability`; raw QR/PIN material never enters Fulfillment;
2. generation `1` issuance and exact `n + 1` regeneration, with a fresh capability reference and
   selector hash and an append-only invalidation fact for the prior generation;
3. strict verification against current Store, Fulfillment, generation, Ready state, capability
   version, expiry and purpose-separated selector hash; and
4. append-only proof generation, invalidation, successful verification and operation persistence
   under forced Store RLS. A successful verification is evidence only for WP-1603's future
   authorized handoff command.

No raw proof generator or hasher, HTTP/UI/notification/abuse adapter, Handoff Record, handed-over
quantity, Fulfillment completion, Event, Projection, Manager Override, live grant or production
activation is introduced.

## Closed Domain contract

- Owner: `@rms/fulfillment`; reusable grammar and maximum lifetime remain owned by
  `@bop/public-capability`.
- Source: an exact locked Fulfillment source must be `Pickup` and `Ready`, contain only full-ready,
  zero-handed-over Items, and carry the authoritative last-ready instant and aggregate version.
- Issuance: first generation is exactly `1`; candidate status/version are `Active`/`1`, candidate
  Store/Fulfillment/Ready instant must equal the source and expiry must remain valid at observation.
- Regeneration: exact next generation, fresh capability reference/hash, same proof kind and public
  display reference, and prior active generation invalidation are mandatory. History is never
  updated or deleted.
- Verification: only the latest non-invalidated generation is eligible. The exact WP-1005 policy
  evaluates Ready, Store, Fulfillment, generation, version, selector and expiry. Public errors are
  bounded and non-oracular.
- Authority: proof validity does not confer `fulfillment.pickup.complete`, quantity mutation,
  already-completed bypass or Manager Override. It produces no lifecycle transition.
- Time: canonical UTC instants and WP-1005's integral maximum 60-minute lifetime. Money is absent.

## Acceptance criteria

- First issue requires exact Ready scope and generation `1`; Pending, stale version, mismatched
  scope/Ready instant, expired candidate and malformed input fail without an effect.
- Regeneration requires exact `n + 1`, fresh capability/hash and append-only prior invalidation;
  old generation and selector cannot verify afterward.
- Verification requires current Ready Store/Fulfillment/generation/version/hash and unexpired
  capability. It returns only a bounded validated evidence record, never completion authority.
- Persistence proves no raw credential column, exact selector grammar, current-generation
  uniqueness, immutable history, forced RLS and cross-Store denial.
- Capability and Fulfillment tests, migration/tenant regressions, architecture gates, root format /
  lint / typecheck / build, security/privacy review, exact-head and exact-main CI pass.
