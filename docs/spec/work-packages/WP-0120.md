## Purpose

Begin Feature F01.2 with a provider-neutral、synthetic `@bop/feature-control` contract that proves:

1. Release Flags and Kill Switches are separate control types with explicit owner、purpose、default、
   scope、review/expiry and version;
2. exact Store controls override their same-Brand control while never crossing a Brand boundary;
3. deterministic percentage rollout consumes a precomputed opaque bucket and never raw Actor、
   Customer、device or network identity;
4. one effective evaluation drives both a frontend visibility hint and the authoritative backend
   execution decision, while frontend hiding never grants or enforces authority;
5. Kill Switch modes can block new work、request a safe pause or request immediate termination while
   preserving an explicit policy for already-running transactions;
6. activation and recovery require accepted Permission evidence and an Audit append before success;
   and
7. malformed、ambiguous、expired or conflicting controls fail closed with stable bounded reason
   codes and no Tenant、Actor or control-state oracle.

This WP creates no production route、Screen、database object、Provider integration or operational
control. Later WPs own persistence、publishing/effective-period integration and Section 88 UI.

## Governing decisions

1. **Exact predecessor —** implementation starts only after WP-0109 exact-head CI、authorized
   squash merge、post-merge exact-main CI and branch/resource cleanup. Baseline
   `9763aadf914e2aa90592f6f7e1c85b0ede13c5a2` satisfies that gate.
2. **Domain owner —** `@bop/feature-control` owns Release Flag、Kill Switch、scope/rollout、
   recovery policy and bounded evaluation record. It does not own Tenant、Permission、Audit、
   business transactions or caller configuration.
3. **No generic Policy Engine —** the accepted shared policy fields are implemented as a narrow
   Feature Control contract. This WP does not introduce a DSL or absorb Permission、Workflow、
   Pricing or Domain policy semantics.
4. **Control key —** keys use the accepted `module.capability.variant` form, lower-case ASCII
   segments and a closed maximum length. Unknown fields、wildcards and whitespace fail validation.
5. **Control kinds —** the exact kinds are `ReleaseFlag` and `KillSwitch`. A record cannot change
   kind after creation under the same control ID.
6. **Required metadata —** every control has an opaque control ID、key、positive version、owner
   reference、bounded purpose code、exact scope、default state、review time and optional expiry.
   Free-text operational reasons and PII are excluded.
7. **Tenant scope —** scope is exactly one Brand or one Store within that Brand. Store evaluation
   requires exact Brand + Store Tenant Context; Brand evaluation may apply to that Brand's Store
   context. No global all-Tenant control or client-supplied Brand inference exists.
8. **Store precedence —** an exact Store control overrides its same-key same-Brand control. Two
   equally applicable records at the winning scope/version are an invalid conflict and fail closed.
9. **Percentage rollout —** Release Flag rollout is `0..10000` basis points. Evaluation accepts an
   injected integer bucket in `0..9999`; it does not accept or hash raw identity. A bucket below the
   configured rollout basis points is enabled and deterministic for identical inputs/version.
10. **Default behavior —** Release Flags declare an explicit default. A validated definition may
    use that default when no scoped override is currently applicable. Malformed、ambiguous or
    conflicting candidate data never falls back to an enabled default and instead denies backend
    execution.
11. **One evaluation —** the immutable result contains the effective control ID/version/scope、
    backend decision、frontend visibility hint、stable reason code and evaluated-at instant. The
    hint is presentation-only and cannot authorize backend execution.
12. **Kill modes —** exact active modes are `BlockNew`、`SafePause` and `Terminate`. Any active Kill
    Switch denies new operations. The mode and caller-owned shutdown policy describe the requested
    handling of in-flight work; Feature Control never rewrites or directly mutates business facts.
13. **In-flight policy —** every Kill Switch definition declares one closed in-flight policy:
    `AllowToComplete`、`ReachSafeCheckpoint` or `CompensateAndStop`. Each business Domain remains
    responsible for applying that policy safely to its own transaction/state machine.
14. **Recovery policy —** recovery is explicit and versioned: `Manual`、`AutomaticAfterValidation`
    or `Progressive`. Progressive recovery uses bounded basis-point stages and cannot silently jump
    to fully open.
15. **Recovery validation —** `BeginRecovery` requires a validated recovery checklist/result from
    an injected caller-owned validator. Missing、failed、stale or scope/version-mismatched evidence
    denies without changing effective control.
16. **Permission —** create/change、activate、begin-recovery and complete-recovery operations consume
    exact accepted `@bop/permission` decisions for their operation and scope. Feature Control never
    treats ownership、Tenant Context or frontend visibility as a grant.
17. **Atomic Audit —** every state-changing operation constructs a bounded `@bop/audit` append
    request and passes the next immutable control version plus that request to one injected
    unit-of-work port. Success is reported only when the port atomically persists both; Audit or
    persistence failure fails closed. No direct Audit private-table access or fabricated evidence
    is accepted.
18. **Evaluation record —** evaluation returns a bounded immutable record for caller telemetry/
    audit composition. It contains no raw rollout subject、Actor reference、Cookie、Token、IP、
    free text or business payload and is not persistence evidence.
19. **Time boundary —** this minimum contract validates UTC instants and half-open
    `[effectiveFrom, effectiveUntil)` applicability. It does not schedule/publish definitions or
    claim the reusable Effective Period owner reserved for WP-0122/WP-0123.
20. **No cache authority —** callers may cache only by exact Brand/Store、key、definition version
    and evaluation bucket, with bounded expiry. Cache is never the source of truth and is outside
    this WP's implementation.
21. **No database change —** no Feature Flag/Kill Switch table、migration、RLS policy、runtime role、
    grant or production seed is added. Persistence is a later bounded increment.
22. **No production API/UI —** `FEATURE-FLAG-LIST` remains Phase 2 / WP-2193. No route、navigation、
    Screen、frontend state or deployment is added.
23. **No external mutation —** no Provider、WAF、cloud flag service、credential、real Tenant、
    operational Kill Switch or external resource is created or changed.
24. **Privacy/telemetry —** stable reason/mode/result codes may be logged or measured; Tenant、
    Store、control、Actor and rollout-subject identifiers are not metric labels and no PII/secret is
    logged.
25. **External Evidence remains a gate —** real production controls、runtime authorization/audit、
    load、incident、recovery drill、staging and production evidence is
    `NOT AVAILABLE / NOT CLAIMED`.
26. **Hard stop —** any need for persistence/migration、new shared Policy Engine、raw identity
    hashing、cross-Domain private query、production route/UI、Provider/credential/resource、
    real operational activation、weakened deny behavior or allowlist-external tracked file stops
    implementation for exact review.
