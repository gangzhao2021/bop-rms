## Goal and bounded responsibility

Deliver, only after later authorization, the smallest business-agnostic relay that:

1. runs from `apps/worker` and asks `@bop/eventing` to claim a bounded Outbox batch for one server-authorized Brand context;
2. publishes each claimed immutable Event envelope through a transport-neutral adapter;
3. records a successful transport acknowledgement as `published_at`;
4. recovers an expired lease after process loss and accepts the unavoidable at-least-once duplicate window;
5. preserves per-Aggregate ordering while explicitly providing no broader order;
6. exposes safe structured operational signals without logging Event payloads or sensitive identifiers.

WP-0031 owns dispatch mechanics, not Domain Event meaning、consumer effects、retry policy、dead-letter policy、trace rollout、Event Catalog or realtime delivery.

## Ownership and runtime boundary

### `shared-infrastructure/eventing` and `@bop/eventing`

`platform_eventing.outbox_event` remains a shared technical control record owned by `shared-infrastructure/eventing`. `@bop/eventing` remains the sole business-agnostic public contract for Outbox persistence and dispatch:

- it owns typed claim、publish-result and lease-release contracts;
- it owns parameterized SQL against `platform_eventing.outbox_event`;
- it reconstructs and validates the existing public envelope;
- it exposes no ORM row、database client、SQL fragment、transport SDK type or concrete broker type;
- it does not choose Tenant scope、authenticate a Worker、enumerate Brands、own the Worker process or define a concrete business Event;
- it mutates only delivery-control columns explicitly accepted for WP-0031. Immutable Event facts and payload remain unchanged.

WP-0030's caller-transaction `appendEventInTransaction` remains unchanged and does not acquire dispatch behavior.

### `apps/worker`

`apps/worker` remains a lifecycle/composition root. It owns:

- startup、readiness、bounded polling coordination and graceful shutdown;
- receipt of a server-authorized bounded Brand work list;
- one transaction-local Tenant Context per Brand claim/complete operation;
- fair scheduling between authorized Brand contexts;
- composition of `@bop/eventing` with one injected transport adapter;
- cessation of new claims on shutdown and bounded draining of already claimed work.

The Worker does not contain SQL、Event schema rules、business routing、consumer logic、retry/dead-letter policy or broker-specific code. A forced stop may leave leases to expire; it must not mark an unacknowledged Event published.

### Transport adapter

The Eventing contract defines a narrow outbound port equivalent to:

```text
publish(envelope, dispatchContext) -> acknowledged | typed failure
```

`acknowledged` means only that the configured transport accepted responsibility according to its future adapter contract. It does not mean a consumer processed the Event. The adapter receives the immutable public envelope plus non-secret dispatch metadata; it cannot update Outbox state directly.

WP-0031 uses a deterministic synthetic adapter for contract、concurrency and failure-injection evidence. It does not select、install、configure or integrate pg-boss、Kafka、SNS/SQS、EventBridge、Redis、a streaming platform or any external broker. The accepted pg-boss baseline remains a future compatibility input; choosing it as the Outbox transport requires a separately accepted adapter contract and evidence.

## Accepted dispatcher contract

The Owner accepted the following complete contract on `2026-07-23`.

### Lease and claim

Add delivery-control columns through one forward-only Eventing migration:

- nullable `lease_token` using the accepted UUIDv7 domain;
- nullable `lease_owner` as a validated opaque operational instance reference;
- nullable `lease_expires_at timestamptz`;
- a constraint requiring all lease fields to be either present together or null;
- a partial claim index aligned with the accepted per-Brand unpublished query.

The opaque owner reference is never a hostname、user、account、pod ARN or credential and is not exposed outside restricted operational diagnostics. The unique random `lease_token`, rather than `lease_owner`, authorizes conditional complete/release.

For exactly one Brand context, one short database transaction:

1. sets validated transaction-local Brand and optional Store context from server-resolved authority;
2. selects eligible head-of-line rows using `FOR UPDATE SKIP LOCKED`;
3. orders candidates by `available_at, recorded_at, event_id`;
4. limits the batch;
5. atomically writes a fresh lease token、opaque owner、expiry and increments `attempt_count`;
6. commits before any transport call.

Eligibility requires:

- `published_at IS NULL`;
- `available_at <= database statement time`;
- no active lease, or `lease_expires_at <= database statement time`;
- `last_error_code IS NULL` for WP-0031;
- no earlier unpublished Event for the same Brand / Aggregate ordering key.

Database time is authoritative. No external I/O occurs while row locks or a database transaction are held. `SKIP LOCKED` is a throughput mechanism, not proof of fairness.

Accepted initial bounded configuration:

- total claim batch maximum: `100`;
- per-Brand claim maximum per scheduler turn: `25`;
- lease duration: `30 seconds`;
- idle poll interval: `1 second`;
- graceful-drain deadline: `25 seconds`;
- adapter call concurrency maximum: `10`.

All values are validated positive integers with safe compiled defaults. The implementation accepts bounded overrides only through an injected Worker composition-root configuration object；it does not read arbitrary environment keys inside `@bop/eventing` or the dispatcher. Binding deployment configuration to that object remains outside this WP, and malformed or out-of-range input fails construction.

### Fairness、expiry and crash recovery

The Worker rotates the starting Brand cursor on every scheduler pass and permits at most the per-Brand maximum before advancing. Empty、slow or backlogged Brands cannot permanently monopolize the batch. Fairness is best effort across the explicitly authorized in-memory Brand list; it is not global FIFO or a latency SLA.

An expired lease is reclaimable by another Worker using a new token. Completion or release is a conditional update on `brand_id + event_id + lease_token + published_at IS NULL`; a stale Worker gets a stable lost-lease result and cannot overwrite the current claimant. Clock authority is PostgreSQL, not the Worker host.

The Worker does not renew leases in WP-0031. The accepted lease duration must therefore exceed the accepted adapter-call deadline plus bounded local overhead. A timeout、process crash、lost database acknowledgement or lease expiry may cause another publish. Shutdown stops claims first, waits only to the drain deadline and leaves unfinished rows for expiry recovery.

### At-least-once publication and duplicate window

For each claimed Event:

1. validate the reconstructed envelope;
2. call the injected transport adapter outside a database transaction;
3. after a positive acknowledgement, open a short transaction in the same Brand context;
4. conditionally set `published_at` to database time and clear the matching lease;
5. retain the Outbox record.

The database mark cannot be atomic with an unspecified external transport acknowledgement. A crash or timeout after transport acceptance but before the conditional success update republishes the Event after lease expiry. A lost acknowledgement can do the same. This is the explicit duplicate-publication window and is why the system guarantees at-least-once, never exactly-once, publication. Consumer idempotency belongs to WP-0032.

No path marks success before transport acknowledgement. If the conditional success update loses the lease, the dispatcher reports a sanitized lost-lease result and does not overwrite another claim. `published_at` records successful channel acceptance, not consumer completion.

### Aggregate ordering

The ordering key is:

```text
brand_id + aggregate_type + aggregate_id
```

Only the earliest unpublished row by `aggregate_version, event_id` for that key may be leased. At most one row for an Aggregate may be in flight. A lower-version unavailable、leased or failed row blocks later rows for that Aggregate. The `event_id` tie-breaker is deterministic but does not invent a second business order when multiple Events legitimately share an Aggregate version.

This guarantees dispatch order only within one Aggregate as observable from accepted `aggregate_version`. It does **not** guarantee:

- global order;
- order between Brands、Stores、Aggregate types or Aggregate IDs;
- order between independent Events with the same Aggregate version beyond the technical `event_id` tie-breaker;
- transport arrival or consumer-completion order;
- order across retries、replay or multiple downstream transports;
- strict FIFO fairness between Workers or batches.

The dispatcher must not skip a failed head-of-line Event to publish a later Event for the same Aggregate. Resolution belongs to WP-0033.

## Tenant、RLS and least-privilege contract

- The production Worker uses a dedicated non-login-derived runtime identity and separate `pg` pool from API、Migration and reporting identities. The actual role/login is established externally; migrations do not create it.
- The Worker role is non-owner、has no `BYPASSRLS`、cannot create schema/functions/roles and receives no schema-wide or table-owner privilege.
- The later owning grant is limited to required `USAGE` / helper `EXECUTE` plus `SELECT` on the exact Outbox columns and column-level `UPDATE` on accepted delivery-control columns. It cannot insert Events through the dispatcher contract、update envelope/payload facts or delete rows.
- Every claim、complete and release transaction sets server-resolved `bop.brand_id` and optional `bop.store_id` with `SET LOCAL`. Missing、invalid、stale or unauthorized context denies by default. Pool-level `SET` and an all-Tenant RLS bypass are prohibited.
- Cross-Brand operation iterates one authorized Brand context per transaction. There is no unrestricted cross-Brand query、super-Tenant toggle or caller-supplied Brand trust.
- Store-scoped rows require the matching Brand and Store context under the existing policy. The accepted design iterates authorized Store contexts for Store rows and a Brand context for Brand-only rows. Brand-wide dispatch does not imply access to every Store row, and no broad Brand-worker RLS exception is permitted.
- Application authorization and the authorized Brand-work source remain primary controls; RLS is defense in depth. Tenant existence、work entitlement or row counts from another Brand must not leak through errors、timing diagnostics or conflict detail.

## Attempt、failure and WP-0033 boundary

Accepted semantics:

- `attempt_count` counts actual handoffs to the transport adapter, not polls、row locks or validation-only failures. It increments atomically when a lease is acquired for an intended adapter call.
- A positive acknowledgement clears the lease and `last_error_code` and sets `published_at`.
- A typed adapter failure conditionally records one stable sanitized `last_error_code` and clears the lease.
- WP-0031 does not calculate backoff、advance `available_at` after failure、apply maximum attempts、classify poison messages、retry a row carrying `last_error_code`、create a dead-letter record、skip an Aggregate head or expose an operator retry/discard action.
- Consequently, a failed row is parked by `last_error_code IS NOT NULL` until WP-0033 supplies an accepted retry/dead-letter transition. This fail-closed behavior prevents a tight retry loop and makes the pre-WP-0033 dispatcher unsuitable for production traffic.
- Crash/lease-expiry recovery with no recorded adapter failure remains WP-0031 because it is lease recovery, not retry policy. Reclaim increments `attempt_count` because another adapter invocation may occur.
- Envelope validation failure is a stable non-publishable error and is parked without calling the adapter. Whether validation-only parking increments `attempt_count` requires the Owner to accept the exact definition above.

Error codes are closed, stable, non-sensitive categories such as transport timeout、transport rejected、invalid envelope and lost lease. Raw exception text、SQLSTATE detail、endpoint、payload fragments and Provider responses never enter `last_error_code`.

## Security、privacy and observability review

### Data flow and classification

1. PostgreSQL returns one Tenant-scoped Outbox row to `@bop/eventing`.
2. `@bop/eventing` validates and reconstructs the public envelope in Worker memory.
3. The Worker passes it to the injected transport adapter.
4. Only sanitized outcome metadata returns to PostgreSQL delivery-control columns.
5. Logs、metrics and traces receive allowlisted operational metadata, never the envelope body.

`payload_json`、`replay_metadata_json`、Actor references、Tenant/Store/Object IDs、free text and any indirect identifiers are at least internal/restricted according to their registered Event classification. Credentials、secrets、tokens、complete payment data、health/allergy facts and unnecessary PII remain prohibited Event content. WP-0031 does not weaken WP-0030 validation or create a payload exception.

### Logging and telemetry

Allowed structured log fields are bounded values such as environment、service、module、operation、result code、safe error code、attempt number、batch count、duration bucket and lag summary. A server-validated correlation reference may appear only where the accepted observability contract permits it.

Prohibited in logs、traces、metrics、fixtures、screenshots and ordinary errors:

- `payload_json` or `replay_metadata_json`, whole envelopes or serialized database rows;
- secrets、tokens、credentials、connection strings、SQL text、bind values or transport endpoint details;
- raw exception messages、Provider/broker response bodies or stack output in customer-visible errors;
- Actor/Customer identity、email、phone、address、notes、payment or health/allergy facts;
- unrestricted Event、Aggregate、Tenant、Brand、Store、Actor、Session or lease-owner identifiers.

Metrics use bounded labels only: environment、service、operation、result/error category and Event type only after WP-0035 registration confirms bounded cardinality. Tenant/Store/Event/Aggregate/Correlation IDs and free text are prohibited metric dimensions.

Required local instruments are:

- claimed、acknowledged、failed、lost-lease and expired-lease counters;
- claim、adapter-call and completion duration;
- oldest eligible Outbox age / publish lag and unpublished count as bounded aggregates;
- current in-flight count and graceful-drain result;
- readiness degradation when database access or required adapter readiness is unavailable.

Alert thresholds、production exporter、cross-runtime trace propagation、retention and dashboard routing remain WP-0040–0045 / External Evidence. Observability failure must not change a committed source transaction or falsely mark an Event published.

## Rollback and recovery

- Before an implementation migration is applied, a normal reviewed Git revert removes the unintegrated code.
- Applied migration bytes and Outbox history are immutable. Recovery is a new reviewed forward-fix migration or an independently approved restore; never down、repair、baseline、mark-applied、force、checksum bypass、table truncation or applied-file edit.
- Runtime rollback stops the Worker from taking new claims. Already acknowledged but unmarked Events remain in the explicit duplicate window; active leases expire and become reclaimable. Rollback must not clear leases broadly、set `published_at` manually、delete retained Events or skip a failed Aggregate head.
- A transport adapter rollback is allowed only when its owning later contract proves compatibility and acknowledgement semantics. No external transport exists in this WP to roll back.
- Outbox recovery runbook creation/update is not silently included; if implementation requires it, the Owner must add the exact documentation path to the allowlist.

## Accepted Owner decision record

The composite authority did not uniquely determine the following implementation-significant choices. The Owner explicitly accepted all ten recommendations on `2026-07-23`:

1. **Lease persistence and fencing** — Recommended: add token、opaque owner and expiry columns; conditional completion uses the token. Impact: enables crash recovery without holding locks across I/O, but adds one forward migration and mutable delivery metadata.
2. **Batch、fairness and timing bounds** — Recommended: total `100`、per Brand `25`、lease `30s`、poll `1s`、drain `25s`、adapter concurrency `10`, with bounded validated overrides. Impact: determines lock/load、duplicate and shutdown behavior; production tuning remains External Evidence.

4. **Aggregate head selection** — Recommended: earliest unpublished `aggregate_version,event_id`, one in flight per Brand/Aggregate, and unavailable/failed lower rows block later rows. Impact: preserves the only authoritative order at the cost of head-of-line blocking.
5. **Cross-Brand authorization source** — Recommended: a server-controlled bounded Brand/Store work list outside Outbox, rotated fairly; never discover Tenants by bypassing RLS. Impact: preserves least privilege, but its owning contract does not yet exist and must be named.
6. **Store-scoped RLS behavior** — Recommended: iterate authorized Store contexts for Store rows and a Brand context for Brand-only rows, without a broad Brand-worker RLS exception. Impact: strongest isolation but more transactions and requires an authorized Store work list.
7. **Worker grants** — Recommended: exact non-owner SELECT plus column-level delivery UPDATE and helper access, with no INSERT/DELETE/payload mutation/BYPASSRLS. Impact: least privilege; actual role and grant application remain External Evidence.
8. **Transport acknowledgement port** — Recommended: transport-neutral positive acknowledgement/typed failure port and synthetic adapter only. Impact: closes dispatcher logic while deferring broker choice, but WP-0031 cannot claim production readiness.
9. **Lease renewal** — Recommended: exclude renewal in WP-0031 and require adapter deadline below lease/drain bounds. Impact: smaller contract; long or uncertain transports increase duplicates and must fail closed.
10. **Implementation paths and dedicated command** — Recommended: the bounded allowlist above、one `0000_011` migration and `pnpm outbox-dispatcher:acceptance`. Impact: makes evidence executable; exact filenames must be closed before implementation.
