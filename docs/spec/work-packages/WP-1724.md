## Closed SES/SNS event contract

The adapter accepts only bounded SNS `Notification` or `SubscriptionConfirmation` envelopes using
Signature Version `2`, the exact configured `ca-central-1` Topic ARN/account and an exact approved
SNS certificate HTTPS host/path. A certificate-verification port must validate the chain and
SHA-256/RSA signature over the canonical SNS string before any Message parsing or mutation.

Notification Messages admit one SES destination and only Delivery, Permanent/Transient Bounce or
Complaint. The destination exists in memory only while a recipient resolver maps it to an opaque
same-purpose Notification recipient reference. The atomic Inbox port uniquely accepts the SNS
Message ID and applies immediate suppression/case intent for Permanent Bounce or Complaint; soft
Bounce remains bounded retry evidence. Persisted normalized evidence excludes address, Provider
payload, rendered content and headers.

A verified SubscriptionConfirmation calls only the scoped confirmation port with the exact
configured Topic ARN and signed token. The application never follows `SubscribeURL` or
`UnsubscribeURL`. Retention is an opaque approved Policy reference; application code cannot invent
or shorten the schedule.

## Acceptance and verification

- forged signature, Signature Version 1, wrong Topic/account/Region, invalid certificate URL,
  malformed payload and cross-purpose recipient resolution fail before Inbox;
- valid Provider Event is normalized and uniquely accepted before success; Permanent Bounce and
  Complaint atomically suppress and open an operational case intent;
- Subscription confirmation never follows message URLs and invokes only the scoped port;
- normalized evidence/log/runbook examples contain no recipient address, raw payload or secret;
- Notification tests, format/lint/typecheck/build, architecture and security/privacy review are
  required locally; external AWS/deliverability evidence remains unclaimed.
