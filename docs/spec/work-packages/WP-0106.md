## Responsibility and intended increment

WP-0106 proves that one protected Merchant request can be composed through the accepted public
boundaries without granting authority from a Provider claim、client-supplied Tenant value or Identity
fact:

1. an injected transport adapter supplies an opaque Session reference;
2. the Identity public port resolves the current Session and its usability is revalidated;
3. only an active Workforce User authenticated through the accepted provider-independent OIDC method
   becomes the authenticated Actor input to WP-0103;
4. WP-0103 derives exact Brand / Store Tenant Context from the route resource plus active
   Membership / Store Assignment;
5. the API composition root loads the permission-owned policy snapshot and the exact active
   Membership / Store Assignment evidence for that context;
6. WP-0105 materializes normalized evidence and the unchanged WP-0104 evaluator decides the exact
   action and scope;
7. only `Allow` advances to a synthetic handler. Every unknown、malformed、expired、revoked、
   ambiguous、unscoped or denied state fails closed with a bounded `401` or `403`.

No production or application business route is registered because WP-0105 deliberately seeds no
business action. Acceptance uses an isolated synthetic Express route and synthetic in-memory ports.

## Domain and module boundary

- Identity remains the sole owner of Actor and Session lifecycle. The API may resolve/revalidate a
  Session through `IdentitySessionPort`; it may not inspect a Provider payload or mint/rotate/revoke
  the Session.
- Tenant and Membership remain the owners of Brand、Store、Membership and Store Assignment facts.
  The API uses only their public ports and WP-0103 context.
- Permission remains the sole owner of policy facts、materialization and evaluation. The API neither
  mutates nor invents a Grant.
- `apps/api` is only the transport/composition root. It owns request-private orchestration、closed
  denial responses and synthetic integration acceptance, not business rules or persistence.
- There is no cross-Domain private import、foreign-table query、new Repository、migration、Event、
  Audit writer、Projection or UI contract.

## Recommended Owner Decisions

The Owner's blanket authorization adopts these decisions unless exact implementation evidence proves
an accepted boundary conflict:

1. **Scenario boundary —** implement provider-independent orchestration only; no Cognito SDK、
   OIDC endpoint、Cookie or token handling.
2. **Session selector boundary —** accept an opaque Session reference only through an injected
   request adapter. WP-0106 does not define its Cookie/header transport.
3. **Current-state authority —** always call `IdentitySessionPort.resolveSession` and
   `assertSessionUsable` at the request observation time; never trust a cached/client Actor snapshot.
4. **Actor eligibility —** require active `User + Workforce + Oidc` Actor with a non-null opaque
   Actor reference. Other account/method kinds fail authentication.
5. **Authentication denial —** missing、malformed、unknown、revoked、expired or invalid Session
   returns one bounded `401 authentication_required` response without existence detail.
6. **Tenant authority —** reuse unchanged WP-0103 route-resource resolution. Query、body and custom
   Brand/Store headers never grant scope.
7. **Membership authority —** active Membership and Store Assignment are re-resolved through the
   public Membership port for policy materialization; ambiguity or drift fails closed.
8. **Permission authority —** use only the WP-0105 `PermissionPolicyPort` snapshot and
   `materializePermissionEvidence`, then the unchanged WP-0104 `evaluatePermission`.
9. **Exact action —** the integration middleware receives one server-configured exact
   `BusinessAction`; a request cannot choose or alter it.
10. **Store-write gate —** a Store-required integration rejects a Brand-only or absent Store scope
    before business handling.
11. **Policy absence —** missing、invalid or internally inconsistent policy materialization is a
    bounded `403 permission_denied`; no empty-policy allow fallback exists.
12. **Deny precedence —** `ExplicitDeny` remains authoritative over Explicit Allow and Role Grant;
    the API adds no alternate evaluator.
13. **Decision privacy —** the public denial body does not reveal Actor、Session、Tenant、Role、
    Grant、policy version or evidence. Internal request state is non-enumerable and cleaned on
    completion.
14. **No permission self-grant —** neither Identity output nor a Session/Provider claim can produce
    action evidence. Only Permission-owned facts can allow.
15. **No application route —** test via a synthetic isolated route until an owning business WP
    registers a real action and resource.
16. **No persistence —** add no table、migration、database access manifest、runtime grant、cache or
    Session store.
17. **No BFF security claim —** Cookie flags、CSRF、Origin / Fetch Metadata、PKCE、state、nonce、
    refresh rotation and token encryption remain WP-0107 acceptance, not a WP-0106 pass.
18. **No revocation workflow claim —** WP-0106 proves current-session denial only; global
    revocation、invite、MFA and recovery remain WP-0108.
19. **No object authorization claim —** aggregate/resource ownership beyond exact Tenant scope and
    Store switch remain WP-0109.
20. **Synthetic-only evidence —** all identifiers、Actors、Stores、policies and Sessions are
    synthetic. No real employee、Tenant or Provider fact enters source or evidence.
21. **Observability boundary —** errors remain closed and no raw request、Session、Actor、policy or
    Provider value is logged、measured as a label or returned.
22. **Concurrency —** simultaneous requests keep Session、Tenant and Permission state isolated; no
    module-global current Actor/context exists.
23. **Rollback —** before integration use reviewed Git revert. No data or external resource rollback
    exists because WP-0106 creates none.
24. **Future trigger —** any need for a Cookie/token parser、Cognito claim、Session persistence、
    concrete business action、object lookup or allowlist-external tracked file stops this WP for an
    exact Owner Decision or the owning later WP.

## Risks、security/privacy review and rollback

- **Authentication confusion:** an injected selector separates transport from Identity resolution;
  every request revalidates the canonical Session and closed Actor kind.
- **Tenant escalation:** only route resources plus active Membership / Assignment create context;
  request headers/body/query and Provider claims are non-authoritative.
- **Permission escalation:** Identity and API cannot construct a grant. The permission-owned snapshot
  and unchanged deny-first evaluator are the only allow path.
- **Stale or mixed request state:** request-private symbols、cleanup and concurrency tests prevent a
  global Actor/context.
- **Information disclosure:** all failures collapse to bounded public codes; raw Session、Actor、
  Membership、Tenant、Role、Grant、policy and Provider data are absent from output/log assertions.
- **Premature security claim:** this WP explicitly does not claim Cookie、CSRF、OIDC、token storage、
  MFA/recovery or complete cross-Tenant browser security.
- **Rollback:** Git revert before or after merge removes only API composition/tests/docs/script
  changes. There is no database、credential、cloud or external state.

Readiness security/privacy finding counts: Blocker `0`、High `0`、Medium `0`、Low `0`.
Residual risks are the intentionally deferred BFF/session/CSRF controls in WP-0107、revocation/MFA in
WP-0108、object/cross-Tenant integration in WP-0109 and Process-enforced GitHub Free governance.
