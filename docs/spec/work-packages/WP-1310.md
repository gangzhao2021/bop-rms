## Purpose

Close the public application contracts that connect authoritative Payment outcomes to Ordering and
that compensate an already-paid Order which Ordering proves cannot be fulfilled. Ordering consumes
`PaymentSucceeded.v1`, owns the mutually exclusive confirmation or paid-without-fulfillable
disposition and alone publishes `OrderConfirmed.v1`. Payment consumes only Ordering's public
unfulfillable disposition, opens a Critical case, reconciles Provider truth, initiates an idempotent
full original-method refund when safe, publishes `PaymentRefunded.v1` only from Provider-confirmed
truth and keeps the case Open until independent Operations reconciliation is also present.

This Work Package is contract-first. Current Ordering acceptance/cancellation/capacity-finality
producers, durable Inbox/Outbox/disposition/case/refund adapters, scheduler, real Stripe and Interac
reader flows do not exist and are neither invented nor claimed as runtime evidence. The contracts,
state machines, Event Catalog entries and synthetic acceptance matrix are executable; live F13.1
activation remains gated.

## Closed execution contract

### Ordering payment-outcome consumer

1. `@rms/ordering` owns consumer `ordering.payment-outcome:v1`, Order confirmation, Kitchen-release
   eligibility and `OrderConfirmed.v1`. Payment never writes an Order or publishes an Ordering Event.
   The consumer accepts only strict Store-scoped `PaymentSucceeded.v1 | PaymentFailed.v1` from
   `@rms/payment`. Success carries an exact Payment transaction, Intent, Attempt and Order, positive
   decimal CAD amount, Captured evidence and canonical terminal instant; failure carries the same
   identities plus only the canonical bounded reason/retry disposition. Provider/private/raw fields
   are prohibited.
2. Processing is strict parse, System consumer authorization, exact Inbox replay/conflict and then
   an Ordering-owned public source lookup. A caller-owned Ordering local transaction atomically
   records the Inbox result and disposition effect; only `Confirmed` appends `OrderConfirmed` to its
   Outbox. This contract does not authorize a cross-Domain transaction or private-table access.
3. The immutable public source is bound to Brand, Store, Order, Batch, Submission, Payment
   Transaction/Intent/Attempt, source Payment Event, positive source version, checkpoint, SHA-256
   digest and evaluated UTC instant. Its closed disposition union is:
   `Confirmed | AwaitingAcceptance | PaidWithoutFulfillableOrder`. The unfulfillable reasons are
   `CapacityExpired | SubmissionCancelled | OrderNoLongerFulfillable` and always carry
   `kitchenReleaseDisposition: Blocked`.
4. Submitted, PaymentPending, OrderCreated, a Payment projection or WP-1309 Acceptance evidence by
   itself can never mean Confirmed. `AwaitingAcceptance` returns retry-required and creates neither
   Order confirmation nor compensation. `PaidWithoutFulfillableOrder` creates no `OrderConfirmed`
   and leaves one stable replayable Ordering public disposition for Payment. Missing, malformed,
   ambiguous, stale or cross-scope source evidence fails closed. PaymentFailed records only one
   idempotent local no-confirmation outcome and performs no confirmation-source lookup,
   `OrderConfirmed`, compensation disposition or refund work.
5. Same Event and same canonical fact replay the original result. Same identity with changed
   content, source version or digest conflicts. The `Confirmed` and
   `PaidWithoutFulfillableOrder` branches are mutually exclusive. PaymentFailed can never be
   aliased to success, confirmation or compensation.
6. Ordering results are `OrderConfirmed | AwaitingOrderAcceptance | CompensationRequired |
PaymentFailedRecorded`.
   Errors are limited to `ORDER_PAYMENT_OUTCOME_INPUT_INVALID |
ORDER_PAYMENT_OUTCOME_PERMISSION_DENIED | ORDER_PAYMENT_OUTCOME_CONFLICT |
ORDER_PAYMENT_OUTCOME_SOURCE_UNAVAILABLE | ORDER_PAYMENT_OUTCOME_DEPENDENCY_UNAVAILABLE`, with
   bounded messages that do not reveal object existence.

### `OrderConfirmed.v1`

7. `OrderConfirmed.v1` is owned and produced only by `@rms/ordering`, Store-scoped,
   `indirect_identifier`, additive, idempotently replayable and a business record. Its consumers are
   `kitchen.confirmed-order:v1` and `fulfillment.confirmed-order:v1`.
8. Its exact payload is `confirmationReference`, `orderReference`, `orderBatchReference`,
   `sourceSnapshotDigest` and `confirmedAt`. Envelope causation is the exact PaymentSucceeded Event;
   aggregate identity/version comes from the exact Ordering source. It contains no Payment amount,
   Payment/Provider identity, Customer data or transaction snapshot. Kitchen release remains
   impossible when this Event is absent.

### Paid-without-fulfillable compensation

9. `@rms/payment` owns service/job `payment-paid-without-fulfillable-compensation:v1`, the Critical
   case, refund operation/fact and `PaymentRefunded.v1`. Input is only the strict Ordering public
   `PaidWithoutFulfillableOrder` disposition; no client amount, method, reason, approval, Provider
   object or free text is accepted.
10. The sequence is strict input, authorization, one immutable non-financial Payment identity lookup,
    permanent operation replay/conflict, Attempt-scoped fenced lease, one authoritative clock, exact
    Payment terminal/cumulative-refund source, stable Critical Open case and claim, Provider
    retrieve-before-decision, optional refund, Provider retrieve-after-mutation, append-only
    receipt/fact/Event composition and operation commit. The identity lookup returns only exact scope,
    original Payment Transaction/Intent/Attempt, `Test | Live`, positive version and digest so the
    environment-bound operation can be resolved before any financial source read; the later full
    source must match that identity exactly. A mutation response is never terminal refund truth.
11. Case, operation and action references are permanent for the exact environment, original Payment
    Transaction/Attempt, Order, reason and purpose. Their stored request/action fingerprints bind the
    exact Ordering disposition and Payment identity/source digests; changed evidence under the same
    permanent identity conflicts and cannot mint a second financial action. The target is the captured
    CAD amount returned cumulatively through the original method. The server derives each mutation as
    `captured - Provider-confirmed refunded`; confirmed plus pending claims can never exceed captured.
    Negative, zero, over-refund, cross-scope, changed-content and conflicting concurrent claims fail
    before Provider mutation.
12. OnlineCard and TerminalCard may call the existing Provider refund port after the exact claim.
    TerminalInterac without exact Store-scoped, named authorized Staff, approved reader and fresh
    single-use in-person evidence returns `InPersonActionRequired`, retains the Critical Open case
    and performs zero generic background refund calls. This WP does not invent that evidence or a
    reader adapter.
13. Every decision retrieves Provider truth first. Every attempted mutation, returned failure or
    throw is followed by reconciliation retrieval when available. Only verified webhook or strict
    Provider retrieval proving cumulative `refundedAmount == capturedAmount`, with exact context,
    method, CAD amounts, monotonic time and evidence digest, may compose a Provider-confirmed refund
    fact and `PaymentRefunded.v1`. Already fully refunded performs zero mutation. Partial, Pending,
    Unknown, unavailable, stale, malformed or cross-scope truth stays Open and is never guessed.
14. Stable Provider keys survive retries, failover and commit-unknown. Retry after any possible
    external effect retrieves and reconciles before considering mutation; it cannot create a second
    financial action. The WP-1308 admission Kill Switch is intentionally absent from compensation,
    Provider-truth ingestion and replay.
15. Case closure requires two independent append-only receipts in either order: an exact
    Provider-confirmed full original-method refund fact and an authorized Operations reconciliation
    receipt bound to that exact refund fact/digest, Actor, scope, purpose, time and Audit. Refund-only,
    Operations-only, early acknowledgement, Task completion or mutation response leaves the case
    Open. Exact duplicates replay; conflicting evidence fails closed.
16. Results are `InPersonActionRequired | RefundPending | ReconciliationRequired |
AwaitingProviderConfirmation | AwaitingOperationsReconciliation | Closed`. Errors are limited to
    `PAYMENT_COMPENSATION_INPUT_INVALID | PAYMENT_COMPENSATION_PERMISSION_DENIED |
PAYMENT_COMPENSATION_LEASE_UNAVAILABLE | PAYMENT_COMPENSATION_OPERATION_CONFLICT |
PAYMENT_COMPENSATION_SOURCE_UNAVAILABLE | PAYMENT_COMPENSATION_DEPENDENCY_UNAVAILABLE`, with one
    safe message.

### Refund Event and exception projection source

17. `PaymentRefunded.v1` is owned and produced only by `@rms/payment`, Store-scoped, classified
    `payment`, additive, idempotently replayable and a business record. Consumers are
    `payment.status-projection:v1` and `operations.order-exception:v1`.
18. Its exact payload is `refundReference`, `compensationCaseReference`,
    `paymentTransactionReference`, `paymentIntentReference`, `paymentAttemptReference`,
    `orderReference`, positive decimal `amountMinor`, `currencyCode: CAD`,
    `refundKind: PaidWithoutFulfillableOrderCompensation` and `providerConfirmedAt`. It is composed
    exactly once from Provider-confirmed cumulative full refund; Operations reconciliation is not an
    Event prerequisite but remains mandatory for Case closure.
19. Payment exposes a strict exception projection source covering the existing WP-1307
    reconciliation differences, WP-1309 `CaptureDeadlineExceeded` receipts and WP-1310
    `PaidWithoutFulfillableOrder` cases without aliasing their meanings. The public shape is limited
    to safe internal references, kind, severity, state, refund/Operations disposition and canonical
    instants. Raw Provider evidence, external IDs, evidence digests, amount, Actor, Guest, Customer,
    Staff or reader details are not exposed.
20. Raw Provider payload, PAN/CVV/client secret/fingerprint, Guest/contact/allergy data and
    unnecessary PII are prohibited from Events, Tasks, public errors, logs, URLs and analytics.
    Metrics may use only bounded operation/outcome/reason/method buckets, never Tenant, Order,
    Payment, case, Actor or Guest identifiers as labels. Audit is Restricted and contains only exact
    scope, purpose, safe internal references, reason and key digest.
21. This WP adds no migration, SQL, database manifest/config/count change, Provider SDK/HTTP/UI,
    scheduler, real producer, reader/location, credential, external resource, deployment or non-local
    data action. The injected repositories, transaction, source, lease, exception, reconciliation,
    Provider and event ports define required runtime behavior without claiming it currently exists.

## Risks, rollback and boundaries

- Risk: Payment success or arrival time is treated as Ordering confirmation. Mitigation: only the
  exact Ordering-owned Confirmed source composes OrderConfirmed; absent/ambiguous evidence retries.
- Risk: Provider response, Task or Operations click becomes refund truth. Mitigation: only verified
  webhook/retrieval full-refund evidence composes PaymentRefunded, and Case close requires a second
  exact audited Operations receipt.
- Risk: retry or Interac worker creates a second/invalid financial action. Mitigation: permanent
  evidence-bound claims/keys, retrieve-before-mutation and an explicit in-person Interac gate.
- Rollback: remove the new public contracts/services, Event registrations, manifest metadata and
  generated catalog artifacts. No database or financial rollback exists because this WP introduces
  no persistence implementation or external action.
- External Evidence: real Ordering acceptance/cancel/capacity-finality producer; durable Inbox/
  Outbox/disposition/case/refund/reconciliation adapters; scheduler/lease and immediate handoff;
  Stripe API/SDK/account/key; approved Terminal Location/reader and Interac in-person flow;
  Permission/Audit/Operations grants and process; Customer receipt/status; telemetry/incident drills;
  PCI/entity/privacy/legal evidence and deployment all remain gated and unclaimed.
- Authorization boundary: local code, synthetic tests, branch/PR/CI and the user-authorized squash
  merge only. No credential, Provider/cloud, deployment or non-local data mutation.
