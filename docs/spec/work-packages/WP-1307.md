## Purpose

Create Payment's first bounded, idempotent reconciliation job. It compares approved internal
Payment facts with normalized Provider retrieval or settlement evidence, records immutable checks,
heals an eligible unresolved attempt only through the existing authoritative Payment terminal
service, and opens a stable exception for every unexplained difference without rewriting source
facts or Ordering.

## Closed execution contract

1. Job identity is `payment-reconciliation:v1`. Exact run input carries run/idempotency reference,
   `Operational | DailySettlement` mode, Brand/Store scope, System or named Actor, purpose,
   scheduled/cutoff instants and an explicit maximum candidate count of `1..100`.
2. Authorization and the caller-owned scheduler lease are proven before any candidate read or
   Provider call. Duplicate run identity returns the identical committed result; different content
   under the same identity fails closed. Concurrent runs cannot claim the same candidate.
3. Operational selection is limited to unresolved `Pending | Unknown`, explicitly mismatched or
   overdue attempts due no later than the run cutoff. The selection source supplies only approved
   Payment references, exact CAD Money, method/capture mode, normalized internal state, last
   observed time and Provider Intent reference. It never supplies raw webhook/Provider payload.
4. Each Provider retrieval uses WP-1301's strict `RetrievePaymentIntent` request with exact
   environment, Brand, Store, Attempt and operation scope. Returned context, Provider Intent,
   method, capture mode, CAD amounts and observation time must match the candidate/run boundary.
5. Provider Failure or `Unknown` is recorded as `Unavailable | Unresolved` with bounded safe codes
   and retry disposition. Timeout alone never becomes Payment success/failure and never closes an
   existing exception.
6. Matching non-terminal or terminal evidence records `Matched`. A previously unresolved internal
   attempt with exact Provider `Captured | Failed | Cancelled` truth may invoke one injected
   idempotent terminal-observation sink using source `ProviderRetrieval`; only the existing WP-1305
   service may create terminal facts/Events. The reconciliation job never writes them directly.
7. State, requested/captured/refunded amount, currency or terminal-fact conflict records
   `Difference` and opens/reuses one stable `StateMismatch | AmountMismatch | RefundMismatch |
TerminalConflict` exception. It cannot silently mutate Order, Intent, Attempt, observation,
   terminal fact, Outbox, Audit or Projection source.
8. `DailySettlement` consumes only a separately authorized normalized settlement feed containing
   safe settlement reference, Store, Business Date, CAD internal/provider captured/refunded totals
   and evidence time. Missing live settlement evidence is `Unavailable`, never an invented zero or
   successful reconciliation.
9. Run, check and exception persistence is one caller-owned atomic repository operation after all
   bounded comparisons finish. Counts, amounts, candidate identities and outcome totals must
   reconcile before commit. A failed commit leaves no partial success claim.
10. Every check and exception is append-only. Resolution, assignment, write-off, Provider fetch UI,
    refund reconciliation and the `PaidWithoutFulfillableOrder` compensation/exception projection
    remain WP-1310/1901 scope; this WP only creates Open source records.
11. A bounded authorized Payment reconciliation query contract supports exact Store, run/payment/
    settlement reference, outcome, exception and checked-at filters with deterministic cursor
    ordering. It exposes safe normalized amounts/states, last checked time and Open exception
    reference; raw evidence and Provider messages are absent.
12. Operational scheduling declares a maximum 15-minute interval and daily settlement cadence.
    Actual external scheduler deployment, Stripe SDK/account, settlement/balance feed and live
    timing evidence remain External Evidence gates and are not claimed by repository tests.
13. Tables force Store RLS and grant no PUBLIC access. Logs/metrics/analytics/URLs receive only run,
    safe internal reference, result/reason code, count and duration; credentials, Provider payload,
    payment identifiers, evidence digest and unnecessary PII are prohibited.

Allowlist:

- Payment reconciliation contracts, job/query services and injected ports, exports, unit tests and
  package docs;

  isolated database acceptance;

filter/cursor enforcement, append-only results, forced Store RLS, no PUBLIC grants, frozen install,
Payment/Event/Inbox/Projection regressions, architecture/security gates and exact CI.
