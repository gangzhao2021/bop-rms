## Problem and bounded outcome

WP-0103 proves a server-authoritative Workforce Actor and Brand/Store Tenant Context, but Membership and Store Assignment deliberately grant no business permission. Command handlers need one stable contract that can answer whether an exact business action is authorized without trusting frontend visibility、route identifiers or raw Role/Grant storage.

WP-0104 creates the smallest executable `@bop/permission` Phase 0 boundary:

- a strict business-action and resource-scope request over an immutable Tenant Context;
- normalized policy evidence accepted only from a server-side policy source;
- deterministic precedence `Explicit Deny > Explicit Allow > Role Permission > Default Deny`;
- a fail-closed immutable decision with stable safe reason and bounded explanation/audit descriptor;
- synthetic unit and contract evidence for scope、precedence、ambiguity、invalid input and privacy.

It creates no Role、Permission Catalog item、Grant/Override repository、database schema/table/migration、API middleware/route、frontend capability、Workflow/Approval rule、real workforce/Tenant fact、Provider/cloud resource or production action.

## Ownership and boundaries

`@bop/permission` owns authorization evaluation semantics and the public decision/explanation contract. Identity owns Actor；Tenant owns Brand/Store and Tenant Context；Membership owns Membership/Store Assignment；WP-0105 will own Role/Grant/Override facts and persistence；Audit owns append-only records.

The evaluator consumes only public immutable Tenant Context plus normalized policy evidence. It never reads another Domain's private table、accepts a client assertion as authority、changes a business Aggregate、writes Audit or infers Permission from Membership/Assignment. A Command Handler still performs Actor validation、Tenant resolution、resource-scope validation、business invariant、Audit and Event in the Section 52.6 order.

## Adopted Recommended Owner Decisions

1. **One owning Module —** create exact Phase 0 module `permission` / `@bop/permission`.
2. **Evaluation-only increment —** WP-0104 owns request、decision、explanation and pure evaluation semantics; `Manage Role / Grant / Override` remains WP-0105.
3. **Server-authoritative context —** evaluation requires a valid frozen `TenantContext`; raw Actor/Brand/Store headers、route strings、email、Provider subject or frontend state are rejected as authority.
4. **Workforce boundary —** the accepted Tenant Context already proves an active Workforce User. The evaluator revalidates the public contract and fails closed on malformed or mutable input.
5. **Exact action syntax —** a business action is a bounded lower-case dot-delimited identifier. WP-0104 invents no concrete action or Permission Catalog entry.
6. **No wildcard semantics —** evidence matches one exact action. Prefix、glob、regex、implicit page-to-action and unknown-action fallback are prohibited.
7. **Closed resource scope —** requests use exact `Brand` or `Store` scope derived from Tenant Context. A Store request must match the context Store exactly; Brand context cannot request a Store action.
8. **Scope inheritance —** exact Brand-scoped evidence may apply within the same Brand's Store context; Store-scoped evidence applies only to the exact Store. No cross-Brand or sibling-Store match exists.
9. **Normalized evidence only —** the evaluator accepts immutable synthetic `ExplicitDeny | ExplicitAllow | RolePermission` evidence produced by a trusted server-side policy source. The public type is not a persistence model or frontend payload.
10. **Actor binding —** Explicit Deny/Allow evidence must bind the exact Actor and Tenant scope. Role Permission evidence must carry an opaque role reference and exact Tenant scope; WP-0105 proves assignment and activity.
11. **Policy snapshot —** every evaluation carries an opaque bounded policy snapshot reference and positive version supplied by the future WP-0105 owner. Missing/invalid snapshot fails closed.
12. **Canonical instant —** applicability uses the Tenant Context's server-resolved UTC instant. A candidate's effective interval is inclusive-from/exclusive-until and invalid/expired evidence never grants access.
13. **Final precedence —** matching user Explicit Deny wins over every allow; otherwise Explicit Allow wins; otherwise Role Permission allows; otherwise Default Deny.
14. **Deny ambiguity —** malformed、duplicate-conflicting or scope-inconsistent evidence fails closed with a stable denial. Evaluation never chooses by array order.
15. **Default deny —** zero applicable evidence returns `Deny / DEFAULT_DENY`; absence is not an error and reveals no candidate count or foreign-scope existence.
16. **Immutable result —** result is exactly `Allow | Deny`, stable reason code、action、scope kind、policy snapshot reference/version and a bounded explanation source. It exposes no raw Role/Grant/User identifier.
17. **Explanation minimization —** explanations reveal only the winning source class and safe reason. They contain no names、emails、raw Actor/Brand/Store/Role/Grant values、free text or rejected foreign-scope detail.
18. **Audit descriptor, not Audit write —** high-risk denial or override composition may consume the bounded descriptor later. WP-0104 performs no Audit persistence and cannot silently ignore an owning Audit failure.
19. **Business rules stay outside —** amount、time-of-day、Workflow state、Approval requirement and Aggregate invariant are separate Command/Workflow checks. They are not generic Role conditions.
20. **Frontend is advisory only —** UI trimming may consume a decision reference later, but frontend state and hidden buttons never authorize an action.
21. **No object-level shortcut —** exact business resource ownership remains WP-0109/owning Domain. Tenant-scope permission does not prove an object belongs to that scope.
22. **No cache authority —** this pure contract creates no cache or Session snapshot. Any future cache must key exact Actor/Tenant/policy version and fail closed on invalidation.
23. **Stable safe errors —** invalid contract input throws only bounded codes/messages; authorization denial is a normal decision and never echoes input.
24. **No Event or persistence widening —** no Event Catalog entry、Outbox、schema、table、migration、runtime role、grant or credential is added.
25. **Privacy classification —** Actor/Tenant/policy references are at least `indirect_identifier`; logging、URLs and analytics are prohibited; fixtures are synthetic only.
26. **Future composition —** WP-0105 supplies authoritative Role/Grant/Override evidence; WP-0106–0109 own integration、BFF/session composition、revocation、Store switch and object/cross-Tenant negative evidence.

## Security、privacy、risk and rollback

- **Client forges evidence:** the contract is server-only, validates strict immutable input and is never a request-body schema；API composition remains later.
- **Cross-Tenant privilege:** exact Tenant Context、Actor binding and Brand/Store scope matching fail closed；foreign-scope evidence never reveals existence.
- **Deny bypass:** precedence is exhaustive and order-independent；malformed/conflicting input denies rather than being ignored.
- **Role becomes workflow engine:** candidate conditions are limited to scope/effective period；amount、state、approval and business invariants remain owning Domains.
- **Stale authorization:** policy snapshot/version is explicit；real invalidation/cache/session behavior remains WP-0105/0108.
- **Explanation leakage:** only stable codes and source class are returned；raw references and candidate counts are excluded from logs/URLs/analytics.
- **Audit omission:** descriptor production is testable, but real high-risk Audit composition is not claimed until its owning integration WP.
- **Rollback:** before shared integration, Git revert removes the dependency-free contract package. No database、external resource or production data rollback exists in this WP.
