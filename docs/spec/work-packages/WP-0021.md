## Migration、verifier and failure contract

Migration order is exact as listed。Every file uses the Section 94 header、one-schema ownership、UTF-8 / LF / final newline、byte-exact SHA-256、fully qualified SQL、one migration per transaction and immutable history。No file creates a table、view、sequence、function、trigger、extension、role、login、policy or seed。

The optional independent verifier is read-only and does not become a Migration Runner command。It checks expected / unexpected schemas、owner、PUBLIC ACL、dangerous default privileges and unexpected objects；it never performs DDL、repair、adopt or baseline。Format is `foundation:<schema-or-object> [<CODE>] <message>` sorted by schema/object、code、message。

Closed diagnostics：`FOUNDATION_SCHEMA_MISSING`、`FOUNDATION_SCHEMA_UNEXPECTED`、`FOUNDATION_SCHEMA_OWNER_MISMATCH`、`FOUNDATION_SCHEMA_PUBLIC_PRIVILEGE`、`FOUNDATION_OBJECT_UNEXPECTED`、`FOUNDATION_CORE_HISTORY_MISSING`、`FOUNDATION_CORE_OBJECT_UNEXPECTED`、`FOUNDATION_CONFIG_UNSAFE`、`FOUNDATION_CONNECTION_FAILED`、`FOUNDATION_INTERNAL`。Exit `0` is compliant / help；`1` is schema / owner / ACL / object violation；`2` is usage / configuration / TLS / connection / read / internal failure。

Failure rolls back the current migration and history insert。Concurrent execution、uncertain connection loss and no automatic retry remain Section 94 behavior。Recovery is forward-fix or independently approved restore；never down、repair、baseline、mark-applied、force、checksum bypass or applied-file modification。
