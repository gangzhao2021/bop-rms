## Goal and acceptance contract

Create one bounded, actionable inventory for a future Ontario Pilot integration decision without
creating, collecting or implying any real evidence.

1. The inventory identifies the accepted Pilot planning baseline and explicitly labels every
   planning-only value as non-operational.
2. Each readiness item has one stable ID, accountable owner role, required evidence outcome,
   repository dependency, current state and exact unblock condition.
3. States are controlled as `Blocked — source unavailable`, `Blocked — evidence unavailable`,
   `Ready for owner action`, `In review`, `Accepted` or `Not applicable`. This WP initializes no
   external item beyond a blocked state.
4. The matrix covers source authority, corporate/legal, premises/Store, food safety, tax/fiscal,
   Payment, privacy, accessibility, staffing/operations, devices/network, platform/security,
   communications and production go/no-go boundaries already named by accepted repository sources.
5. Evidence references must be opaque controlled references with owner, version, validity/expiry
   and review status. Evidence bytes, secrets, unrestricted object IDs, payment data, health facts
   and unnecessary PII must never be added to this inventory or Git.
6. Local verification is recorded separately from external readiness. A passing build, demo,
   synthetic fixture or GitHub workflow cannot satisfy a legal, professional, Provider, Store or
   production requirement.
7. The canonical Store gate remains blocked. Production PII, Payment, legal receipts, public
   ordering, Provider activation, deployment and real-data seeding remain unauthorized.
8. The document names the next owner actions and the conditions for a later evidence-intake WP; it
   does not execute those actions or infer that unavailable evidence is defective.

  unavailable and require authoritative reconciliation before any evidence-intake decision.

  runtime authority remains with the owning Domain, Live Gate and independently authorized
  production process.
- Risk: sensitive evidence is committed. Mitigation: store only controlled metadata/reference
  requirements and prohibit evidence bytes, secrets and personal/payment data.
- Risk: local green checks imply operational readiness. Mitigation: maintain separate local and
  external sections and keep the Pilot gate blocked.
- Rollback: revert the single documentation-only integration. No runtime or external state exists
  to unwind.
