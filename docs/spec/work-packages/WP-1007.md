## Purpose

Define the smallest first-Pilot closeout slice that proves:

1. only current server-authorized Staff or the exact current Host may request or cancel Closing；
2. `Active → Closing` immediately locks admission of every new Order Batch；
3. Cancel Closing returns to `Active` only when injected Ordering/Payment evidence proves no
   irreversible payment、capture、settlement or reconciliation conflict；
4. Dining may close independently after every associated Batch has a terminal execution outcome；
5. every unpaid or indeterminate Order/Batch creates or resolves the same Store-scoped Manager
   exception Task idempotently before Dining becomes `Closed`；
6. unresolved Ordering facts remain `Open` after Dining closes and retain the Dining reference；
7. `Paid | ProviderConfirmedRefund | AuthorizedWriteOff | OtherControlledFinal` are accepted only
   as server-issued owning-Domain finality evidence, never as a client-selected state；
8. Dining cannot execute、approve or account for a Write-off, mutate an Order/Payment/Task private
   table, or claim Provider/accounting finality；and
9. no Order aggregate、Payment adapter、Task database、Projection/UI、Table cleaning workflow or
   real operational evidence is implemented.

WP-1007 owns the Dining phase transition、new-Batch lock policy、close preconditions and
Task-composition boundary only. WP-1220 onward owns Order/Batch facts. WP-1301 onward owns Payment
and Provider finality. WP-1809 owns the Order Exception Workbench and 15-minute visibility
projection. WP-2112 owns Floor Board、Table cleaning and move/merge/split behavior.

## Ownership and trust boundaries

- `@rms/dining` remains sole owner of Dining Session phase/version and Table-assignment reference.
  It consumes only public, immutable Ordering/Payment closure summaries through an injected port.
- `@bop/task` remains sole Task owner. Dining may request one exact Store-scoped exception through
  a public idempotent port and validate the returned public Task record；it never writes Task
  storage or marks source business completion.
- Ordering remains sole owner of Order/Batch phase、payable balance and Closure Status. Payment
  remains sole owner of capture/refund/Provider reconciliation and financial finality.
- Permission and Tenant Context decide Staff authority. Host authority is exact current
  Dining-bound Guest/Participant evidence supplied by the server, not a caller boolean.
- Audit records accepted begin/cancel/finalize intents. Dining cannot grant permission or rewrite
  Audit history.
- Order/Payment/Task references are Internal opaque facts. No amount、PAN、Payment secret、
  Provider payload/reference、customer/contact、allergy/health or free-text reason crosses this
  boundary.
- Every public denial is bounded and non-oracular. Trusted adapters may retain stable reason codes
  without Store/Table/Session/Order existence detail in Customer output.

## Adopted decisions

1. **Canonical phases —** WP-1007 exports only `Active → Closing`、guarded
   `Closing → Active` and invariant-satisfied `Closing → Closed`. It creates no Reopen command.
2. **Batch lock —** only `Active` admits a new Batch. `Closing | Closed | Cancelled` deny before
   Ordering mutation；client optimistic state is never authoritative.
3. **Begin authority —** named Staff requires exact Tenant/Brand/Store/Actor、Permission、
   operation reference、expected Dining version and Audit. Exact current Host requires current
   Dining-bound Guest Session/Participant evidence for that Session and Store.
4. **Cancel authority —** same Staff/Host rule. Cancel additionally requires a fresh server
   reversibility decision `Reversible`; `Irreversible | Indeterminate | Unavailable` fails closed.
5. **Cancel meaning —** Cancel Closing unlocks future Batch admission by returning to `Active`; it
   does not cancel/refund/reverse any Order or Payment and cannot erase a started attempt.
6. **Closure evidence —** one closed object contains exact Dining Session、Store、evidence
   version/time and a deterministic list of associated opaque Order summaries.
7. **Execution finality —** every associated Batch must be `Fulfilled | Rejected | Cancelled`.
   Pending/Accepted/Kitchen-active/unknown evidence blocks Dining close rather than creating a
   financial Task for non-final work.
8. **Financial classes —** exact classes are `Settled`、`ProviderConfirmedRefund`、
   `AuthorizedWriteOff`、`OtherControlledFinal`、`Unpaid` and `Indeterminate`.
9. **Write-off boundary —** `AuthorizedWriteOff` must carry an opaque owning-Domain finality
   reference and valid decision time. No amount、threshold、approval chain、MFA detail or accounting
   mutation is represented. The caller cannot supply this class directly.
10. **Unresolved class —** `Unpaid | Indeterminate` keeps the Order `Open` and requires one
    exception Task. Dining may then close independently only after every required Task receipt is
    accepted.
11. **Task identity —** deterministic Task intent is exact purpose
    `DINING_UNPAID_BATCH_EXCEPTION` + Store + Dining Session + Order + closure evidence version.
    Exact replay returns the existing Task；changed intent conflicts.
12. **Task shape —** Store scope、source type `DINING_SESSION`、opaque source reference/digest、
    exception type、Manager Queue assignment、Critical severity/priority and due/SLA references are
    server configuration/evidence. No free-form body or customer/payment detail is added.
13. **Task finality —** creating/acknowledging/assigning a Task never changes Order/Payment/Dining
    source truth. Task resolution requires a later opaque completion reference from the owning
    Domain and is owned by Task/Order exception composition.
14. **Visibility boundary —** required Task creation is synchronous evidence before close.
    `merchant_order_exception_v1` visibility within 15 minutes belongs to WP-1809 and is not
    claimed without that Projection.
15. **Ordering independence —** Dining close never changes Order Closure Status. An unpaid,
    refund-pending or exception-bearing Order remains `Open` until Ordering's Section 24.9
    invariants pass.
16. **Table boundary —** this WP emits no Table cleaning/availability mutation. WP-2112 consumes
    `Closed` through its own public contract.
17. **Join invalidation —** begin Closing makes every outstanding Join capability unavailable
    through the already accepted Session-phase evaluation. No raw credential is required.
18. **Expected version —** begin/cancel/finalize use exact positive expected Dining version and
    compare-version persistence. Conflicts refresh source state；no last-write-wins.
19. **Idempotency —** every mutation uses opaque operation reference plus deterministic intent
    hash. Same intent returns the prior result；changed intent conflicts.
20. **Failure ordering —** exception Tasks are ensured before the final Dining close commit.
    Orphan prevention relies on deterministic retry；a Task may safely remain open while Dining is
    still Closing, but Dining can never be Closed without all required Task receipts.
21. **No cross-Domain private access —** Dining imports only public BOP contracts and injected
    public evidence；no Ordering/Payment private table or implementation path.
22. **Closed contracts —** missing/extra/symbol/accessor/array/non-plain/malformed values fail
    closed；returned records are immutable.
23. **No screen implementation —** Section 88 is acceptance context. No route/component,
    Projection, realtime consumer or analytics event is added.
24. **No external evidence —** no real Staff/Host/Order/Batch/Payment/Provider/Task/Store、
    accounting approval、MFA、traffic or production fact is available or claimed.
25. **Hard stop —** client-selected Paid/refund/write-off、Dining financial mutation、close with
    non-terminal Batch、close without required Task、Task completion used as source finality、
    cross-Store evidence、free-form/PII/Payment data、allowlist-external tracked file or invented
    External Evidence stops implementation.

## Risks, rollback and next action

- Closing without an immediate Batch lock accepts late work；phase admission is server-side.
- Treating Task creation as Order finality can hide unpaid debt；source finality remains
  Ordering/Payment-owned.
- Client-selected Write-off enables financial bypass；only opaque owning-Domain evidence is
  accepted and no financial Command exists here.
- Cross-Domain atomicity is intentionally not fabricated. Tasks are idempotently ensured before
  close so partial failure leaves a visible Task and retryable Closing Session, never a silently
  closed unresolved Session.
- Rollback before merge is deletion of this brief plus bounded index edits. After merge,
  correction is forward documentation/implementation；accepted evidence history is never
  rewritten.
- Next allowed action is readiness verification followed by exact-head pinned-Linux CI and
  Section 91 review. Implementation starts only from the verified readiness squash on `main`.
