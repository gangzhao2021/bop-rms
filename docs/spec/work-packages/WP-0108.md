## Responsibility and bounded intended increment

WP-0108 composes four Identity-owned, provider-neutral workforce security workflows over the
already accepted WP-0102、WP-0105 and WP-0107 contracts:

1. create and atomically consume a single-use, 24-hour workforce invitation only after an approved
   pending/active Membership and required Store Assignment exist;
2. track only TOTP enrollment/challenge status and provider evidence references while the real
   Provider owns verifier material and the TOTP seed;
3. execute controlled account recovery through approved identity-proofing/break-glass evidence,
   revoke all Sessions and rotate the recovered Session boundary;
4. consume global logout、Membership disable、Store Assignment removal、Role removal、credential
   reset/compromise and recovery invalidation evidence through one idempotent actor-wide Session
   revocation command.

The candidate is a local/synthetic contract and PostgreSQL acceptance increment. It does not create
or call Cognito、SES、KMS、Secrets Manager、WAF or another AWS resource; send email; establish a real
workforce identity; issue a real temporary credential; perform production recovery; or enable a
production route.

## Ownership、trust boundaries and data classification

- `@bop/identity` owns invitation、MFA status、recovery case、revocation request and Authentication
  Session mutation facts. It never owns Membership、Store Assignment、Role or Permission.
- `@bop/membership` remains the owner of Membership/Store Assignment state and supplies only its
  existing bounded invalidation evidence. `@bop/permission` remains the owner of Role Assignment
  state. Because Membership already depends on Identity, Identity never imports either package.
  The existing `apps/api` composition boundary validates their public evidence and calls the strict
  Identity command; no component queries another Domain's private tables.
- Provider ports may invite/disable a provider subject、start/verify/reset TOTP and issue a
  one-time temporary credential only in future infrastructure. Provider objects and raw responses
  never enter Domain contracts.
- Notification is a future public adapter port. Local acceptance records only a deduplicated,
  opaque dispatch request; it sends no message. WP-0124 owns the reusable Notification contract.
- Audit is an injected public port using the accepted WP-0042 contract. Identity persistence is not
  an Audit substitute, and audit failure prevents a security workflow from reporting success.
- Corporate email is `personal`. Invitation selectors、temporary credentials、TOTP seed/code、
  recovery proof、Provider token/subject and Session/Cookie/CSRF values are `credential` or
  `Restricted`. None may enter URLs、logs、analytics、metrics、traces、fixtures or public failures.
- Tests use deterministic synthetic addresses and opaque references only. Email is normalized for
  verification/routing, never used as Actor、Tenant、Brand、Store、Role or Permission authority.

## Adopted Recommended Owner Decisions

1. **Invite-only workforce —** public self-signup remains disabled. Invitation requires a named
   Actor plus approved Membership and any required Store Assignment evidence before issuance.
2. **Invitation lifetime and use —** one 24-hour invitation per exact Actor + Membership intent;
   the browser receives only a 256-bit opaque selector, persistence stores its keyed HMAC-SHA-256
   hash, and acceptance consumes it atomically once. Expired、replayed、revoked、email-mismatched or
   scope-mismatched invitations fail with one uniform denial.
3. **Email is verification, not authority —** acceptance verifies the intended normalized corporate
   email through the Provider port, then resolves all authorization from Actor/Membership/Store/
   Permission owners. Email cannot select or widen scope.
4. **Provider-neutral invite —** the local port returns only canonical success/unknown/denied
   outcomes and opaque evidence references. No Provider user object、temporary password or delivery
   payload persists.
5. **No reusable bootstrap —** first Owner creation、one-shot deployment task、real approvers and
   seed-path disablement remain WP-2040 External Evidence. No default password、hidden superuser or
   bootstrap endpoint is introduced.
6. **TOTP only —** password-capable privileged workforce must reach `TotpVerified` before business
   action. SMS MFA and email-only recovery are invalid. Medium-risk and recent-MFA enforcement
   remains compatible with Section 87.6.
7. **Provider owns verifier material —** BOP stores factor status、verified/reset timestamps、
   optimistic version and opaque Provider/Audit references only. TOTP seed、shared secret、QR
   payload and submitted code never persist or appear in logs/errors.
8. **Enrollment/challenge rotation —** successful TOTP completion calls the accepted WP-0107
   `MfaCompletion` rotation; previous Session selector and CSRF are immediately unusable. A recent
   MFA fact is server time on the same rotated Session and expires after exactly 15 minutes.
9. **Recovery is controlled —** one recovery case requires declared purpose、identity-proofing
   evidence、an active authorized approver and bounded expiry. Owner、Finance and Platform Admin
   require a distinct active privileged approver or explicit two-person break-glass evidence.
10. **Admin-only Provider recovery —** self-service email/SMS recovery is forbidden. After approval,
    Identity revokes every active Session before requesting a one-time Provider temporary
    credential; Provider timeout/unknown is not success.
11. **Recovery rotation and notification —** recovery resets factor status, revokes all former
    Sessions with reason `Recovery`, and any continuing browser context must be a new rotated
    Session. A deduplicated security-notification request and Audit record are mandatory outputs.
12. **Uniform errors and rate bounds —** invite acceptance、MFA and recovery expose finite generic
    outcomes with bounded timing. Per-selector/Actor and coarse client-risk attempt limits use
    server time and opaque counters; they disclose neither account nor factor existence.
13. **Actor-wide revocation command —** one strict command carries Actor、reason、idempotency、
    correlation、purpose、observed time and source evidence reference. It revokes all active
    Sessions atomically and reports the already-revoked set deterministically on replay.
14. **Accepted reasons —** `GlobalLogout`、`MembershipDisabled`、`StoreAssignmentRemoved`、
    `RoleRemoved`、`CredentialReset`、`CredentialCompromised`、`Recovery` and `Administrative`
    map to the unchanged WP-0100/WP-0107 closed revocation reasons. No caller-supplied free text
    enters persistence.
15. **Cross-Domain evidence —** Membership invalidation uses the exact existing
    `MembershipAccessInvalidation`. Role removal uses an exact public Role Assignment transition
    snapshot, not a new fabricated Domain Event. The API composition layer verifies Actor/scope/
    effective-state consistency and maps only the closed reason/evidence reference into Identity;
    ambiguity fails closed.
16. **Idempotency and concurrency —** the request ID is unique; the request row and all Session
    revocations commit in one transaction under optimistic/fenced writes. Replays return the
    original bounded result; concurrent Session creation cannot escape the completed cutoff.
17. **Cutoff semantics —** completion revokes every Session created at or before the command's
    database-observed cutoff. A security workflow may additionally disable Provider login before
    the transaction and must recheck/revoke any racing Session before re-enable; local authority
    remains denied while Provider state is unknown.
18. **Audit ordering —** commands record Actor performing the action、target Actor、purpose、
    reason、scope、correlation/idempotency and bounded result. No email、proof document、TOTP value、
    token or selector appears in the Audit payload.
19. **Persistence —** add forward-only migration
    `migrations/0200-bop-identity-tenancy/0200_005_create_workforce_identity_security.sql` with
    exact Identity-owned tables `workforce_invitation`、`workforce_mfa_status`、
    `workforce_recovery_case` and `session_revocation_request`.
20. **Database constraints —** UUIDv7 references、positive versions、UTC instants、finite enums/
    opaque references、single-use shapes、expiry ordering、approval separation and unique
    idempotency are constrained. No raw secret、unbounded JSON Provider payload or unrestricted
    object ID exists.
21. **Least privilege —** PUBLIC access is revoked. No runtime login/role/grant、BYPASSRLS、
    `SECURITY DEFINER`、trigger、dynamic SQL or production credential is added.
22. **Pre-Tenant boundary —** these are Identity security-control tables keyed by Actor and opaque
    Membership/scope evidence references. They do not grant authorization and cannot query
    Membership/Permission private tables.
23. **Forward-only recovery —** before migration use reviewed Git revert. After application,
    migration bytes and security history are immutable; correction uses a reviewed forward fix,
    never down/repair/delete/history reset.
24. **No production route —** orchestration is exercised through injected ports and synthetic tests
    only. `apps/api/src/app.ts`、server startup、environment/IaC and production adapters are excluded.
25. **Future split —** WP-0109 owns Store switch、object authorization and complete cross-Tenant
    negative composition. WP-0124 owns reusable notification delivery. WP-2040 owns real Cognito/
    SES/KMS/Secrets Manager/WAF and first-Owner execution evidence.
26. **Hard stop —** any need for a real Provider/email call、SDK/dependency、production route、
    credential/IaC/external resource、real workforce fact、new cross-Domain private query、
    allowlist-external tracked file or weakened control stops implementation for exact review.

## Security/privacy findings、risks and rollback

Readiness findings: Blocker `0`、High `0`、Medium `0`、Low `0`.

- **Account enumeration:** every public invite/MFA/recovery failure is uniform and rate bounded.
- **Invitation theft/replay:** only a keyed selector hash persists; single consumption、exact
  Actor/email/scope binding and 24-hour expiry are mandatory.
- **MFA secret disclosure:** Provider owns verifier material; BOP stores no seed、QR payload or code.
- **Recovery takeover:** identity proof、active approval、privileged separation、global revocation、
  Audit and notification are one controlled workflow; email alone is never sufficient.
- **Cross-Domain authority theft:** Identity accepts only strict public evidence and owns no
  Membership/Role mutation or private-table read.
- **Revocation race:** database cutoff、idempotency and fenced mutation must prove no old Session
  remains authoritative after completion.
- **Provider uncertainty:** local Session denial is authoritative. Timeout/unknown cannot reactivate
  local access or be reported as a successful credential reset.
- **Rollback:** before migration use reviewed Git revert. After migration, append/transition through
  an approved forward fix; never delete security history or down-migrate. No external rollback
  exists because this WP creates no external resource.

Residual risk is explicitly deferred to WP-0109 Store/object/cross-Tenant composition、WP-0124
notification delivery、WP-2005 production database roles and WP-2040 real Cognito/SES/KMS/
Secrets Manager/WAF/deployment evidence.
