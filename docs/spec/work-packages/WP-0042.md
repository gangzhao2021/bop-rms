## Problem and bounded intended outcome

The repository has a foundation `platform_audit` schema but no Audit Record table or `@bop/audit` contract. Existing business and Eventing specifications require critical writes、high-risk denials、overrides、imports/exports and corrections to be auditable, while ordinary logs and Domain Events are not the Audit source of truth.

A future, separately authorized WP-0042 implementation would deliver the smallest audit foundation:

1. a business-agnostic append contract accepting a caller-owned PostgreSQL transaction;
2. one append-only `platform_audit.audit_record` technical control table;
3. explicit Brand and optional Store scope、Actor classification、Action、authorized target reference、classified before/after references or deltas、reason、correlation and immutable time facts;
4. fail-closed validation、least privilege、forced RLS defense in depth and synthetic transaction/Tenant evidence;
5. linked corrective records without Update/Delete of retained history.

This readiness brief does not choose or implement the unresolved details below. It records a candidate contract and executable decision/verification matrix for Owner acceptance、modification or rejection.

## Domain、ownership and collaboration boundary

- The capability is the shared BOP Audit service exposed as the future `@bop/audit` public contract.
- `platform_audit.audit_record` is a shared technical governance record in a dedicated platform schema, not a business Aggregate、Domain Event log、application log、Projection or generic cross-Domain Repository.
- Each business/Application Command remains responsible for authorization、expected version、idempotency and its own Domain mutation. It may append Audit and Outbox evidence in the same caller-owned transaction.
- Audit never writes another Domain's private table and never infers permission、Tenant、Store、Actor、purpose or classification from IDs.
- Audit failure for a required action returns a stable failure to the caller so the complete business transaction can roll back. It is never silently downgraded to an application log.
- Query、Explorer、Export、hash-chain、signature、archive and verifier capabilities remain outside this WP unless a later explicit Owner Decision changes the boundary.

## Candidate implementation contract

This section is a bounded candidate only. Every unresolved choice is governed by the `PROPOSED / PENDING OWNER ACCEPTANCE` register below.

### Candidate append input

- application-generated UUIDv7 `auditId`;
- required `brandId` and optional `storeId`;
- explicit Actor classification plus the minimum authorized Actor reference;
- nullable `impersonationReference`, which must remain null while impersonation is not an accepted capability;
- stable `actionCode`;
- stable `targetType` and authorized opaque `targetId`;
- classified before/after reference or bounded summary JSON objects;
- stable `reasonCode` and an optional bounded note only if explicitly accepted;
- trusted WP-0041 `correlationId`;
- caller-supplied UTC `occurredAt`;
- source-channel classification and only approved device/network references;
- data classification and retention-policy reference;
- optional `correctsAuditId` for a linked corrective record.

The server records `recordedAt`. The contract accepts a caller-owned transaction and performs parameterized Audit persistence only. It does not create IDs、open/commit/roll back a transaction、write a business table、append an Outbox Event、authorize a user or expose an ORM entity.

### Candidate persistence invariants

- insert-only Audit facts; no public Update/Delete/Upsert;
- duplicate `auditId` rejects rather than replacing history;
- correction is a new linked Audit Record;
- forced Brand/optional Store RLS with transaction-local server-resolved context;
- PUBLIC denial and no advance runtime role/login/grant;
- no Secret、Token、Cookie、Session、PAN/CVV、raw credential、Provider payload、health/allergy fact、unrestricted object ID、unnecessary PII or arbitrary request body;
- no database trigger that attempts to manufacture business meaning from another Domain's private row;
- no hash、signature、daily digest、KMS、S3 Object Lock or archive object owned by WP-0046.

## Recommended Owner Decisions

1. **Owning component and database ownership — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend `@bop/audit` as the public capability and `shared-infrastructure/audit` as the only declared owner of `platform_audit.audit_record`. Business modules call the public append contract and never write the table directly. Impact: fixes the long-lived owner and architecture-test declaration.
2. **Scope model — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend required `brand_id` plus nullable `store_id`; when Store is supplied it must belong to the same resolved Brand context. Do not admit global/unscoped Audit rows in WP-0042. Impact: closes RLS、index and Tenant-partition semantics without inventing future platform-operator scope.
3. **Actor model — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend a closed Actor classification (`User` / `System` / `Service`) with an opaque UUIDv7 reference where applicable; Actor identity remains a reference, not copied PII. Keep `impersonation_reference` null until a future accepted impersonation IDR. Impact: prevents ambiguous or PII-bearing Actor payloads.
4. **Action and target references — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend bounded stable codes and opaque UUIDv7 target references, with no polymorphic foreign key or cross-Domain existence query. Each caller validates the target it owns. Impact: preserves Domain ownership while enabling authorized correlation.
5. **Before/after representation — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend JSON objects containing only classified field keys and safe reference/delta values, not full entity snapshots. Require explicit size ceilings and reject prohibited fields; exact ceilings remain part of Owner acceptance. Impact: balances explainability、storage and privacy.
6. **Reason and note policy — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend required stable `reason_code` for corrective/high-risk actions and no generic free-text note in the foundation contract. A future owning workflow may add a separately classified bounded evidence reference. Impact: avoids an uncontrolled PII/Secret text sink; rejecting this recommendation requires exact note size、classification、retention and masking rules.
7. **Time contract — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend caller-supplied UTC `occurred_at` plus database-recorded UTC `recorded_at`; do not resolve Business Date in Audit and do not silently rewrite caller time. Exact acceptable skew/late-record policy requires Owner acceptance. Impact: distinguishes action time from durable recording time.
8. **Transaction and failure semantics — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend one parameterized insert in a caller-owned transaction; required Audit failure fails the Command transaction. Audit opens no transaction and performs no external call. Impact: supplies atomic critical-write evidence without making Audit the business write owner.
9. **Idempotency and conflict semantics — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend application-generated UUIDv7 `audit_id`; retry reuses the same ID and a duplicate rejects. No `ON CONFLICT DO NOTHING` or mutable idempotency record is added. Impact: prevents a conflicting replay from being mistaken for recorded evidence.
10. **Correction and controlled redaction — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend only linked append-only correction in WP-0042 through `corrects_audit_id`; no row Update/Delete、payload rewrite or physical redaction. Policy-driven redaction/anonymization and legal-hold interaction require a future Privacy/Audit-integrity WP and explicit legal evidence. Impact: preserves history without pretending the retention/privacy conflict is solved.
11. **Retention metadata — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend immutable classification and retention-policy/version references, with no deletion job、archive lifecycle or hard-coded universal expiry in WP-0042. Impact: records why a fact is retained while leaving WP-0046/archive and legal schedules gated.
12. **Privilege and RLS contract — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend default deny、forced RLS、no PUBLIC privilege、no production/runtime role or grant creation, and synthetic non-owner acceptance using transaction-local Brand/Store context. A future deployment WP owns actual principals/grants. Impact: proves defense in depth without fabricating runtime identity evidence.
13. **Read/query boundary — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend WP-0042 expose append and linked-correction contracts only; authorized trail queries、field masking、Explorer、Export and `/app/audit` remain later screen/query WPs. Impact: avoids an unrestricted cross-Domain read API before object-specific permission and field masking exist.
14. **Hash-chain/partition boundary — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend no physical PostgreSQL partitioning、per-Tenant sequence、hash/signature/digest/KMS/S3/archive/verifier object in WP-0042. WP-0046 owns the tamper-evident chain and archive design through a forward migration after its exact partition/concurrency contract is accepted. Impact: keeps WP-0042 to one append table but requires WP-0046 to add its own ordering material.
15. **Outbox/Event boundary — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend the generic Audit append does not emit an Event automatically. An owning business Command separately appends its approved Event in the same caller transaction when required. Impact: prevents recursive/unregistered Audit events and preserves Event Catalog ownership.
16. **Migration identity and recovery — PROPOSED / PENDING OWNER ACCEPTANCE.** Recommend next immutable migration `migrations/0000-platform/0000_014_create_audit_record.sql`, forward-only after `0000_013`; before application use Git revert, after application use reviewed forward-fix/restore only. Impact: binds the candidate to the accepted global migration order.

### Accepted exact closure values

- before/after summaries are plain JSON objects, each at most `16,384` UTF-8 bytes and together at most `32,768` bytes；maximum depth `8`、maximum `128` cumulative fields、field names at most `64` characters and string values at most `2,048` characters；
- `occurredAt` is canonical ISO-8601 UTC `Z` and may not exceed database current time by more than five minutes；historical values have no lower bound and are never rewritten；
- `User` and `Service` require an opaque UUIDv7 Actor reference；`System` has none；impersonation remains null；
- stable codes use `^[A-Z][A-Z0-9_]{0,127}$`；target type uses `^[A-Z][A-Za-z0-9]{0,127}$`；retention policy version is a positive integer；
- classification is exactly `Public | Internal | Confidential | Restricted`；
- raw IP is not retained；an approved optional device/network reference is opaque UUIDv7；
- summaries reject prohibited Secret、Token、Cookie、Session、credential、PAN/CVV、raw Provider payload、health/allergy and arbitrary request-body content；there is no free-text note.
