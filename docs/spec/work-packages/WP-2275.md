## Bounded transaction and assignment decision

Add Dining-owned current Session, current Join capability and append-only start-operation tables.
The initial Session retains WP-1006's supplied Table assignment version. For an empty Table, the
exact assignment evidence is its current aggregate version. Atomic start verifies that version,
Published/Available/empty Table and current scope/time, then occupies the Table and advances its
aggregate version once. The new Session retains the original assignment version; these are distinct
facts. Later configuration revisions do not rewrite assignment. WP-2112 Move continues to assign the
target's next aggregate version; this WP adds no Move or Closing writer.

The owner adapter exposes only resolveStartOperation/start and a scoped current Session reader.
Operation lock then Table lock/row (matching WP-2272), exact expected version, Session/capability
creation, Table occupation, immutable operation append and public Audit append form one transaction.
One active/closing Session per scoped Table is also constrained in PostgreSQL. Same-key/same-intent
converges on the original; changed intent or competing Table writers conflict. Lost acknowledgement
resolves from immutable history; Audit failure rolls back every owner fact. Current Staff permission
remains mandatory in the service and is not inferred by storage.

Only a purpose-separated selector hash and bounded capability metadata are stored; raw invitation,
human code and pepper never persist. Capability rows are a future owner lifecycle foundation; this
WP performs initial INSERT only. Join/regeneration/expiry/reuse lookup, Participant/admission,
credential recovery and live transport remain separate owning implementations. No selector-based
lookup is exposed, so no claim about reused human-code history is invented.
