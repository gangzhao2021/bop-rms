# WP-2220 — Durable Cart Item Presentation Snapshots

## Authority and readiness

Baseline: verified local WP-2219 `d04ad5e`, clean branch `codex/wp-2220`. Owner authorizes continued
implementation and verified local commits/successor branches; remote publication and deployment
remain excluded. Composite Handoff 0.5.3 Sections 24.2, 24.5, 44.9, 50, 52, 56, 87–97;

The next HTTP mutation increment needs durable original labels: current operation records store only
aggregate facts. Preparing labels after commit can yield ambiguous failure; rebuilding on retry can
change the original response. This package supplies that prerequisite without enabling HTTP writes.

## Scope

Ordering owns an optional versioned presentation snapshot on each new Item operation. It contains
only public Brand/Store labels, Pickup service mode and exact Item/Option display names. Quantities,
notes, scope, lifecycle and versions remain in the existing immutable aggregate snapshot. Money,
Quote claims, credentials, private attribution and extra fields are prohibited. DineIn remains gated.

An optional preparation port runs after authorization/Catalog validation and before persistence.
Validate and freeze its output against the candidate aggregate. Store it in a nullable additive JSON
column in the same transaction as Item, Cart, operation and Audit. Existing records stay untouched.
Authorized exact retries return the stored snapshot without calling preparation again. When a caller
requires presentation, legacy records with no snapshot fail closed; do not manufacture historical
labels. Preserve expected-version, 24-hour idempotency, session reauthorization and conflict replay.

Non-goals: HTTP activation, source wiring, Quote-absence mutation guards, Pricing, lifecycle writes,
DineIn visibility, UI/browser work and production evidence. A snapshot alone is not an unquoted view.

## Acceptance

1. Strict public-only snapshot parsing enforces exact Item/Option identity, valid labels, bounded
   arrays and Pickup scope; rejects malformed/accessor/extra-field or mismatched input.
2. Preparation failure commits no mutation. Applied/replayed results preserve original snapshots;
   retry skips source preparation and still enforces authorization, intent and expiry.
3. PostgreSQL atomically persists snapshots, retains null legacy records and original replay across
   fresh adapters. Rollback and existing concurrency/RLS/Audit evidence remain valid.
4. Frozen install, affected checks, migration/ownership and complete local verify pass. Final diff,
   documentation and resource cleanup are reviewed.

## Security, contract and handoff review

Snapshot data is public display evidence associated with a Restricted operation record. It adds no
copy of Customer Note, actor/session attribution, money, Quote, credential or Provider data. Exact
keys and bounded labels/arrays prevent additional payloads. The immutable aggregate remains the sole
source of Item quantity, options and note; matching Item/Option order is required. Existing forced
Brand/Store RLS, Audit transaction and 24-hour replay rules remain unchanged. No unaccepted security
finding was identified within this scope.

Preparation is an explicitly supplied owner contract; synthetic labels in acceptance establish
persistence behavior only. A later HTTP composition must bind real public sources before calling it,
and establish durable Quote-aware mutation evidence under the Cart lock. A stored label snapshot
alone must never be interpreted as evidence that Quote is absent. Existing API methods remain
unavailable; no browser/visual/remote CI/production test result is claimed.

The final diff contains 14 allowed files, no lockfile/dependency changes and one additive nullable
column. Historical migration bytes remain unchanged. An upgrade must apply the new migration before
using the updated adapter; this package performs no live migration. The new column preserves the
existing append-only operation rules and adds no new table or foreign Domain access.
