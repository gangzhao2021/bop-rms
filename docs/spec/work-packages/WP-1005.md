## Purpose

Define the smallest provider-neutral Public Capability contract that proves:

1. an `orderReference` is an unguessable public routing/display reference but never a bearer
   credential；
2. an Order Resume token is a separate 256-bit single-use credential with a 30-minute maximum
   lifetime, purpose/Order/Store scope, keyed-hash persistence and atomic-consume requirements；
3. Pickup Proof is either a 128-bit opaque proof or six-digit human code bound to one Store、
   Fulfillment、generation and Ready state, valid for at most 60 minutes and invalidated by
   regeneration、completion or cancellation；
4. raw capabilities are prohibited from URLs sent to servers、logs、events、analytics、ordinary
   persistence、screenshots and fixtures outside synthetic tests；
5. public references、resume credentials and Pickup Proofs cannot cross Store、Order、Fulfillment
   or purpose boundaries and do not grant Merchant、Order mutation、Payment、Kitchen or Fulfillment
   completion authority；and
6. no Ordering/Fulfillment aggregate、database、HTTP endpoint、notification、Customer screen、
   abuse bucket、WAF、Provider or production adapter is implemented in this WP.

WP-1005 owns the reusable credential grammar and closed policy/evidence contract only.
`@rms/ordering` remains the future owner of Order facts and public Order-reference issuance.
`@rms/fulfillment` remains the future owner of Pickup readiness、generation、verification and
handoff facts. Identity remains the owner of Guest Session creation/rotation. WP-2048 owns the
atomic abuse bucket and enumeration security matrix. WP-1723 owns notification-worker minting and
fragment delivery. The later HTTP/PWA packages own same-origin consume and fragment scrubbing.

## Ownership and trust boundaries

- Candidate `@bop/public-capability` is a cross-cutting BOP contract module. It owns only closed
  value-object grammar、maximum lifetime policy、purpose separation and fail-closed evaluation.
- The module owns no database schema/table、aggregate、HTTP route、worker、event、notification、
  projection or screen.
- Calling Domains retain their facts. A future Ordering adapter supplies exact internal
  Store/Order scope；a future Fulfillment adapter supplies exact Store/Fulfillment/generation/Ready
  evidence. The contract never queries either Domain's private storage.
- Raw Order Resume and Pickup credentials are `Restricted credential` data. Public Order
  references are customer-safe only inside an already-authorized exact Order scope and remain
  prohibited telemetry labels.
- Keyed hashes are purpose-separated selector evidence, not public identifiers. Pepper material is
  supplied by a future managed credential adapter and never enters this contract、record or error.
- Generic public failures are deliberately non-oracular. Detailed mismatch/status/replay reasons
  are internal policy outcomes only and cannot be returned to a Customer.

## Adopted decisions

1. **New BOP contract module —** candidate package is exact `@bop/public-capability`, generated by
   the accepted Module Generator, Phase 1, no synchronous dependencies and no database ownership.
2. **No universal capability service —** the package exports immutable contracts and pure policy
   evaluation only. It is not a runtime service boundary and cannot own another Domain's facts.
3. **Public Order reference —** exact canonical unpadded base64url encoding of 16 random bytes
   (`22` characters). It is at least 128 bits、opaque、case-sensitive and contains no timestamp、
   Store/Order number、Tenant or checksum metadata.
4. **Reference is not authorization —** every Order/Receipt query still requires an exact active
   Guest Session authorized for the same Store and Order, or a successfully consumed Order Resume
   credential. Reference possession alone returns no existence fact.
5. **Resume raw credential —** exact canonical unpadded base64url encoding of 32 random bytes
   (`43` characters). Plaintext may exist only in trusted mint/delivery memory and consume-request
   memory.
6. **Resume selector —** persistence accepts only a purpose-separated keyed hash (`64` lowercase
   hex characters) plus positive pepper version. It never accepts or derives a raw token.
7. **Resume scope —** exact purpose `OrderResume`、internal Store reference、internal Order
   reference and public Order reference. A token cannot choose or replace any scope value.
8. **Resume lifetime —** canonical UTC instants；`expiresAt` is strictly after `issuedAt` and no
   later than 30 minutes. The contract contains no sliding extension.
9. **Resume lifecycle —** exact `Active | Consumed | Revoked | Expired`. Consumption requires
   matching purpose/scope/hash evidence、Active status and `observedAt < expiresAt`.
10. **Atomic consume boundary —** pure evaluation may return only a closed authorization decision
    and the next immutable record. A future owner must persist compare-version + consume + sibling
    revoke + Guest Session set/rotate in one accepted transaction. WP-1005 does not claim that
    adapter.
11. **Sibling rule —** consuming one resume credential must atomically revoke every active sibling
    for the same Order/purpose. At most two unexpired siblings may coexist after an unknown send.
    The contract exposes the stable sibling-scope key and limit, not notification behavior.
12. **Resume redirect —** after future successful atomic consume, the only allowed navigation is a
    server-derived clean `/orders/:orderReference` path. No absolute/relative client redirect input
    is accepted by this contract.
13. **Fragment delivery boundary —** future links are
    `https://<customer-host>/resume#t=<token>`. WP-1005 contains no URL builder/parser. WP-1723
    owns delivery and the PWA owns immediate `history.replaceState`.
14. **Pickup proof kinds —** exact `Opaque` 16-byte/22-character credential or `HumanCode`
    six ASCII digits. No variable-length、alphanumeric or formatted short code is accepted.
15. **Pickup selector —** storage accepts only a purpose-separated keyed hash and positive pepper
    version. Raw proof is never stored in the capability record.
16. **Pickup scope —** exact internal Store and Fulfillment references、positive generation and
    purpose `PickupHandoff`. Public Order reference may be attached only as a routing display fact,
    never as verification evidence.
17. **Pickup readiness —** verification can succeed only with caller-supplied exact
    `Ready` evidence for the same Store/Fulfillment/generation. `Pending | Completed | Cancelled`
    fail closed.
18. **Pickup lifetime —** `expiresAt` is strictly after `readyAt` and no later than 60 minutes.
    Completion/cancellation ends validity earlier without rewriting expiry.
19. **Regeneration —** new generation must equal prior generation + 1, uses a fresh proof
    reference/hash and invalidates the prior generation. Reusing a proof reference、hash or
    generation fails closed.
20. **Pickup completion authority —** valid proof is evidence for a future authorized Staff
    command only. It cannot bypass quantity、Fulfillment state、Store scope、staff permission、
    already-completed checks or required Audit.
21. **Manager Override —** remains a future Fulfillment command requiring reason、recent step-up、
    permission and Audit. WP-1005 exports no override boolean or bypass result.
22. **Closed evaluation —** external decision is only `Allowed | Unavailable`. Internal reason
    codes are bounded for trusted tests/adapters and must never become public response detail or
    telemetry labels.
23. **Canonical closed input —** objects reject missing、extra、symbol、accessor、array、
    non-plain prototype and malformed primitives. All returned records are frozen.
24. **No binary floating point time arithmetic —** instants are canonical UTC strings and
    duration checks use integral milliseconds within fixed limits.
25. **No abuse implementation —** WP-2048 owns `5/hour` resume and Pickup failure budgets plus
    `security.abuse_bucket`. This contract exposes no IP/device/contact input and cannot invent
    `Retry-After`.
26. **No external evidence —** no real Order、Store、Fulfillment、Customer、email、resume link、
    Pickup proof、KMS/pepper、WAF、browser、load、staging or production fact is available or
    claimed.
27. **Hard stop —** raw capability persistence/logging/event/URL、reference-as-auth、
    cross-Store/scope acceptance、non-atomic consume claim、Pickup completion bypass、new database、
    HTTP/UI/notification/Provider code、PII、allowlist-external file or invented External Evidence
    stops implementation.

## Public candidate contract

The implementation candidate adds:

- opaque branded value objects and strict parsers for public Order reference、raw resume token、
  opaque Pickup proof、human Pickup code、selector hash、canonical instant and UUIDv7 scope；
- immutable `OrderResumeCapability` and `PickupProofCapability` record contracts containing only
  internal scope、hash evidence、policy version/lifecycle and timestamps；
- pure constructors/evaluators for resume validity/consume and Pickup validity/regeneration；
- stable internal decision reasons for trusted adapters/tests, with one public `Unavailable`
  mapping requirement；and
- exported fixed policies: resume maximum `30` minutes、maximum `2` active siblings、Pickup maximum
  `60` minutes.

No credential generator、hasher、database、transaction、API、Cookie/Session mutation、notification、
URL/PWA、abuse limiter、Fulfillment completion or Manager Override is added.

## Risks, rollback and next action

- Treating `orderReference` as a bearer credential creates enumeration and cross-Order disclosure；
  every query still needs exact Session/consumed-capability authorization.
- Logging or persisting raw resume/Pickup credentials defeats single-use secrecy；only
  purpose-separated keyed hashes may persist.
- Non-atomic resume consume can replay or leave siblings active；the owner adapter must consume、
  revoke siblings and rotate/set Guest Session in one transaction before an end-to-end claim.
- Pickup proof without exact Ready/generation/Store/Fulfillment evidence can bypass handoff
  controls；the contract fails closed and grants no completion authority.
- Rollback before merge is deletion of this brief plus bounded index edits. After merge, correction
  is a forward documentation/implementation change；accepted evidence history is never rewritten.
- Next allowed action is implementation exact-head pinned-Linux CI and Section 91 review, followed
  by authorized squash merge、post-merge exact-main verification and branch cleanup.
