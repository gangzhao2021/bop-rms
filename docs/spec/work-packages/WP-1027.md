## Authority resolution

The canonical Feature F10.2 backlog names WP-1027 `Merchant Catalog Management API`. Older WP-1024
notes called it a publish screen/UI boundary. The explicit backlog title is the higher and more
specific authority for this WP, so this implementation adds transport contracts only and does not
invent UI work.

## Purpose

Implement the smallest Merchant Menu management API that proves:

1. Menu list queries are bounded、cursor-based and status-filtered through a named Catalog read
   model contract；
2. Submit Review、Approve、Publish and Archive are explicit action routes, never arbitrary target
   state mutation；
3. every route first passes an injected Merchant authentication、Tenant Context and Permission
   chain；
4. every mutation carries one UUIDv7 Idempotency Key、one exact `If-Match` version and server time；
5. the Catalog public Application service remains the final authority for permission、Audit、
   evidence、idempotency、concurrency and lifecycle rules；and
6. responses serialize only stable allowlisted management DTOs.

## Adopted boundaries

- Brand scope is explicit in `/api/v1/merchant/brands/{brandId}/catalog/menus` routes so the
  existing route-derived Tenant Context chain can resolve and revalidate it.
- List limit defaults to `50` and is bounded to `1–100`; cursor is opaque and filter status is a
  finite lifecycle allowlist. No SQL-like query、arbitrary sort or export is accepted.
- Action request bodies are closed. `action` / `targetState` cannot be caller supplied. Publish is
  the only action that accepts an Effective Period.
- `Idempotency-Key` must be one UUIDv7 and `If-Match` must be one quoted positive version.
- This transport composes the WP-1024 Menu publication contract. It does not bypass or duplicate
  Catalog authorization and Audit logic.
- Product/SKU/Option/Availability Domain commands already exist behind public Application
  interfaces but new bulk/import routes are excluded；Section 88 assigns Import Jobs jointly to
  WP-2000. Merchant UI remains WP-1802.

## Implementation surface

- API Merchant Catalog router with one menu-list resource and four lifecycle action resources；
- injected authorization and Catalog management ports；
- safe cursor/filter/header/body parsers、finite error mapping and allowlisted DTO serialization；
- registered request-correlation/core-telemetry route templates and server composition option；and
- root/API acceptance wiring with synthetic HTTP coverage.

## Acceptance

- authorization denial stops before Catalog is called；
- missing/duplicate/malformed idempotency or expected-version headers fail closed；
- open query/body fields and target-state mutation are rejected；
- route-derived action and server time are passed unchanged to Catalog；
- Applied and Already Applied results remain distinguishable；
- conflict、denial、not-found、stale and unavailable states map to stable non-reflective errors；and
- adapter-only fields、raw errors、credentials、UI and External Evidence are never returned.
