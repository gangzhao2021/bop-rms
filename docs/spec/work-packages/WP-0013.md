## Evidence contract

The Module access evidence is pure literal and contains version, exact Module identity, table-governance records, and access records using Section 92 closed vocabularies. Evidence cannot add ownership. Duplicate/case-conflicting schema or table owners, reserved-schema claims, missing/extra governance, identity/layout mismatch, non-owner write/DDL, unowned target, invalid read pattern, computed target, path escape, symlink, and unsupported real persistence assets fail closed.

The platform registry is the only non-business shared-schema authority. Business Modules cannot claim `platform_*` or `public`; `packages/database` receives no business fact ownership.

## Acceptance and evidence map

1. **Authority and identity:** Section 92/ADR-0029/IDR-0042 are referenced; discovery reuses WP-0010–0012 and rejects Manifest/package/Layer/layout mismatch.
2. **Business ownership:** one legal Module schema/table passes; duplicate/case-conflicting schema and table ownership fail.
3. **Governance completeness:** each owned table has exactly one matching classification/write-owner/read-pattern/retention/PII record; missing or extra records fail.
4. **Owner access:** owner read/write of its own table through the accepted pattern passes.
5. **Cross-Module protection:** foreign write/DDL and writes to unowned business targets fail.
6. **Read boundaries:** Public Query Contract has no direct foreign-table target; approved view/Event Projection/Reconciliation rules pass only for the accepted principal and destination.
7. **Shared infrastructure:** finite legal uses pass; reserved claims, public-table access, and shared-schema escape attempts fail.
8. **Static safety:** non-literal/dynamic targets, unknown fields, duplicate set values, path/case escape, symlinks, and unreadable roots fail closed.
9. **Staged enforcement:** real persistence/Drizzle/pg/raw SQL/migration/Repository/schema/model/connection/seed assets produce `UNSUPPORTED_DATABASE_ASSET`.
10. **Determinism:** path/line/code/message ordering, repeated output, and exit codes `0|1|2` are stable.
11. **Root and CI integration:** focused check is discoverable, root `pnpm verify` invokes it, and the sole `bootstrap / verify` workflow invokes the same finite check.
12. **Baseline health and scope:** existing Manifest/Generator/Import Boundary/Screen Registry/guidance, all root tests, forced uncached workspace tasks, PostgreSQL and five-service lifecycles, structured files, graph, diff/security/scope review, and cleanup pass.
