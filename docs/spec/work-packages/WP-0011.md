## Bounded goal and responsibility

Create the deterministic repository Module Generator and its synthetic tests. The Generator accepts Layer, Module Name, Package Name, Phase, Allowed Dependencies, future Database Schema Name metadata, and an accountable Owner role. It validates the resulting declaration with the single WP-0010 `module.manifest.ts` contract, JSON Schema-backed validator, and semantic validator before resolving or writing a target.

Module Name is an unscoped kebab-case logical name. Package Name must be exactly `@bop/<moduleName>` for Layer `BOP` or `@rms/<moduleName>` for Layer `RMS`. Layer, namespace, and slug must agree. The target is derived, never caller-selected: `packages/bop/<moduleName>` or `packages/rms/<moduleName>`.

The Generator owns only a skeleton: the later Section 56.4 directory set, `src/module.manifest.ts`, `src/index.ts`, `package.json` with export/dependency/test entries, `tsconfig.json`, and a rendered copy of the accepted Module README template. Empty Manifest collections remain empty; database schema is inert future ownership metadata; Owner is supplied by the caller. The Generator does not infer Domain facts, create an ADR, or invent an owner. A new ADR remains conditional on a separately identified architecture decision.

The output is deterministic and fail-closed. Existing or partial targets, case collisions, symlink parents, unsafe/escaping names, absolute or parent traversal, invalid/private scopes, unknown inputs, and Manifest identity conflicts fail without overwrite. A repeated run against the same target is an error and preserves the existing bytes; the same input in two clean synthetic roots produces byte-identical trees.
