## Purpose

Add a provider-neutral、synthetic `@bop/task` minimum contract that proves:

1. a Task tracks work that must actually be completed without owning or implying the source
   Domain's business result；
2. every Task binds an exact Tenant/Brand/Store scope、opaque source reference、type、severity、
   priority、due date and immutable creation metadata；
3. assignment supports exactly one current User、Role、Position or Queue target while preserving
   append-only assignment history；
4. eligible Actors can claim Role、Position or Queue work, while exact User assignment remains
   restricted to that User；
5. Create、Assign、Claim、Complete、Fail and Cancel enforce Permission、expected version、
   idempotency and atomic Audit composition；
6. terminal transitions are immutable and repeated completion with the same command is idempotent；
7. overdue work can append a bounded escalation record and Notification intent without a clock、
   worker、real delivery or source-business mutation；
8. Task Completion records only an opaque completion reference and never asserts that the owning
   Domain accepted or completed its business action；and
9. malformed、cross-Tenant、unauthorized、stale-version、ineligible、replayed or terminal inputs
   fail with stable bounded outcomes and privacy-safe telemetry.

WP-0125 supplies the BOP Task minimum lifecycle in Handoff Section 44.6.4. Task Inbox/Detail
Projections、production routes and owning-Domain resolution flows remain later Screen/Domain work.

## Governing decisions

1. **Predecessor —** WP-0124 is integrated at
   `bf672b512c6872a661300bc68b579f8129061e83`. Exact-head run/job
   `30487691046 / 90697383204` passed in `9m47s`; post-merge run `30488366739` passed on unchanged
   merge SHA in rerun job `90700441380` after the first runner-local startup attempt stopped before
   repository checks.
2. **Owner —** `@bop/task` owns generic executable work metadata、current assignment、
   assignment history、claim metadata、due/escalation metadata and Task terminal outcome only.
   The source Domain owns its business facts、allowed resolution action and final result.
3. **Independent capability —** Task remains separate from Workflow、Approval and Notification.
   Task completion、failure、cancellation or delivery failure cannot silently change another
   capability or source-business outcome.
4. **Scope —** each Task and every command carry exact Tenant、Brand and Store references. Missing,
   mismatched or cross-scope input fails closed before authorization or mutation.
5. **Opaque data —** core records use UUIDv7 references、stable codes、`sha256:` digests and
   canonical instants only. No employee name/contact、free-form task body、source payload、
   customer data、notification content or Provider payload enters this package.
6. **Assignment targets —** `User`、`Role`、`Position` and `Queue` are the only target kinds.
   There is exactly one current target；assignment changes append history rather than rewriting it.
7. **Claim eligibility —** User-targeted work may be claimed only by that Actor. Role、Position and
   Queue claims require injected, exact-scope Membership eligibility evidence valid at the command
   instant. Task does not own workforce scheduling or availability.
8. **Lifecycle —** the minimum lifecycle is explicit、monotonic and versioned. Terminal
   `Completed`、`Failed` and `Cancelled` records cannot be reopened or overwritten in this WP.
9. **Completion boundary —** `Complete` records an opaque completion reference and result code.
   It is not proof that the source Domain completed、accepted or changed its business state.
10. **Idempotency —** each mutating operation requires one stable key. The unit-of-work port binds
    scope + operation + Task + key + request digest and commits state plus Audit atomically.
11. **Expected version —** Assign、Claim、Complete、Fail、Cancel and escalation reject stale
    expected versions. Repeated same-command completion resolves to the original committed result.
12. **Authorization —** injected Permission evidence must match Actor、action、scope、purpose and
    current command. Assignment eligibility does not replace Permission.
13. **Audit —** every accepted mutation composes one append-only Audit entry in the same unit of
    work. Audit contains stable references/codes only and never source payload or personal data.
14. **Due/escalation —** explicit overdue evaluation compares a supplied UTC instant with `dueAt`.
    Escalation appends an immutable bounded record and opaque Notification intent. No implicit
    clock、scheduler、worker or automatic reassignment exists.
15. **Notification boundary —** escalation may request Notification through an injected contract.
    Notification rejection/failure cannot roll back、complete、fail、cancel or otherwise mutate the
    source business result.
16. **Source access —** Task stores only an opaque source reference、source type and safe snapshot
    digest. It never queries another Domain's private table or executes the source resolution.
17. **Screens —** Section 88 `TASK-INBOX` and `TASK-DETAIL` remain canonical, but this WP adds no
    route、UI、Projection、search、comment body or navigation record.
18. **Telemetry —** only stable operation、target kind、status、severity、priority、outcome and
    reason codes may be labels. Tenant、Store、Actor、Task、source、assignment、membership、
    completion、Audit and Notification references are excluded.
19. **No persistence/API/UI —** no table、migration、RLS、repository adapter、route、Screen、
    navigation or Projection.
20. **External Evidence —** no real workforce directory、production permission grant、
    Notification provider、load、recovery、staging or production evidence is available or claimed.
21. **Hard stop —** source-business ownership、free-form/PII payload、implicit cross-scope
    assignment、eligibility-as-permission、mutable history、terminal reopening、Task completion as
    business completion、automatic worker/delivery、private-table access、persistence、production
    API/UI、external resource or allowlist-external tracked file stops implementation.
