## Resolved contract and hard gate

Section 88 makes the Customer Payment screen active only after the Provider IDR. The accepted
Payment packages deliberately provide no Provider SDK/API implementation, public Guest HTTP
adapter, client-secret delivery, browser confirmation or public Payment-status query. The existing
status projection requires an internal Store-scoped Actor permission and cannot be exposed or
reinterpreted as a Customer contract.

WP-1704 therefore closes the browser contract without inventing that missing authority. It adds the
two canonical clean routes and a strict injected controller boundary for `Pending`, `Failed`,
`Unknown` and authoritative `Succeeded + Order reference`. The real browser runtime remains
explicitly Provider-unavailable, performs no Payment network request and enables no card, cash,
manual-entry, Terminal or redirect action. A future approved public adapter may inject the same
closed controller contract without changing screen semantics.

One page-memory operation reference may be established only immediately before an approved create
attempt. Unknown outcome retains it and retry reuses exactly that operation; deterministic failure
or malformed output never becomes success. The clean result route reads only page memory, never
query parameters, fragments, Provider callback fields or the Order reference as authorization.
Refresh or direct navigation without that context fails closed. No Payment amount is accepted from
the browser; no Provider/UI secret, raw result or internal exception is rendered, logged or stored.
