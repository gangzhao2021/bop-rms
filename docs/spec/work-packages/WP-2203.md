## Goal and acceptance contract

Turn the existing manual Merchant showcase browser evidence into one repeatable, fail-closed local
and GitHub acceptance command without changing the application being tested.

1. One root command starts the exact local demo entry through a Playwright-managed, loopback-only,
   strict-port web server and executes Chromium with one worker and zero retries.
2. The command verifies these 13 accepted routes at `1440x900` and `390x844`: `/app`; Store list,
   detail, setup and service; Menu list and editor; Order queue and detail; Kitchen board and work
   item; Compliance dashboard; and sanitized non-production Support Cases.
3. Every development route renders its expected existing page identity and the visible local
   synthetic/read-only notice, has no application API `fetch` / XHR, makes no non-loopback request,
   emits no uncaught page error or error-level console message, and has no horizontal overflow.
4. At least one accepted linked path is exercised through user-visible navigation instead of only
   direct URL entry; keyboard focus remains visible and the primary main/navigation landmarks remain
   available where the accepted Screen contract requires them.
5. A production build made with `VITE_BOP_LOCAL_DEMO=1` still excludes the bounded demo module and
   fixture markers. Its browser preview remains signed out or unavailable on the same covered entry
   routes and never displays the synthetic demo notice or fixture authority.
6. Development and production preview processes use finite startup/test timeouts, do not reuse an
   unknown CI server, are stopped on success or failure, and leave neither owned port listening.
7. The unique `bootstrap / verify` workflow installs only Chromium plus required Linux libraries and
   runs the root acceptance command. Browser download, startup, assertion and cleanup failures fail
   the job; no retry may convert a failure into acceptance.
8. Browser traces, screenshots and reports are untracked diagnostics only, contain synthetic data,
   and are retained only on failure. No credential, token, real Tenant/Store/Actor, payment data,
   health/allergy fact or unnecessary PII is introduced.

## Risks, rollback and external boundary

- Risk: browser installation increases clean-runner time and network exposure. Pin one Playwright
  version and one Chromium engine, keep a single worker and remain inside WP-2202's finite 45-minute
  job budget; timeout is a failure, not a reason to weaken assertions.
- Risk: Vite HMR or font assets can create noisy transport observations. Permit only loopback Vite
  assets and its local development transport; reject application API and non-loopback traffic.
- Risk: selector-heavy tests become brittle. Prefer roles, accessible names, Screen IDs and visible
  accepted labels over CSS structure or snapshots.
- Rollback: revert the WP-2203 commit to remove the test dependency, scripts, browser suite and CI
  step without changing the WP-2200 / WP-2201 application behavior.
- External Evidence: no real Tenant, Brand, Store, Actor, credential, Provider result, business fact
  or production activation is required, introduced or claimed.
- Owner approval covers this brief plus bounded local implementation and verification on
  `codex/wp-2203`. Commit, push, PR publication, merge, deployment and Provider actions require
  separate explicit authorization.
