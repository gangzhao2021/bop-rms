## Intended complete scope

A Product Version publication is Product-owned versioned child configuration, with
expected Product aggregate and publication revision, original-intent operation UUID,
Tenant/Brand/Actor/purpose/fine action/current Phase, append-only history and Audit /
Outbox in one owning transaction. Full content snapshot stays private to Catalog;
minimal reference graphs are public and explicitly distinct from eligibility.

Actions: Validate, SubmitReview, Approve, Reject, Publish, SchedulePublish,
ReschedulePublish, CancelScheduledPublish, ActivateScheduled, and owning Supersede.
Reject returns Draft/changes requested with immutable prior review preserved.
Validation pins all 12 checks from 68.9, exact snapshot, scope, effective period,
current cross-domain impact and policy; Hard Errors never override. Warning override
needs actual current policy, Actor and Reason. Approver must differ from submitter.
No caller boolean/evidence object supplies authority. ActivateScheduled requires
current scheduler authority and all current validations, not a stale approved token.
Original committed replay does not re-run present configuration mutations; current
caller authority remains mandatory. Failed unknown response recovers original result.

Scopes cover Brand default, Store, Store Group, Region, Channel and Order Type,
plus channel/order-type qualifiers and explicit UTC/IANA effective period. Use the
accepted context priority and reject ties/ambiguous overlaps; topology/membership
facts come from public Tenant contracts, not invented fixtures in a normal runtime.
Effective ranges are half-open and never a guessed default. Future source reads retain
scheduled/cancelled/rescheduled/published/superseded records independently, full stored
coverage and current authority/fences, without claiming operational stock applicability.

Current relational Product supports only one mutable Draft; replaceDraft pins the
same version ID and single Draft unique constraint. Publishing therefore requires
an immutable content snapshot for that same Version ID, a guarded frozen version,
and a real successor Draft with a fresh Version ID before later edits. Stable SKU
identities survive successor Drafts; do not rewrite past publication/transaction facts.
Forward migrations only, original 1100_001 and all existing migrations immutable.
Review/approval pin source/configuration revisions; later edits invalidate them.
Any source-root revision/event/history changes must reconcile existing Product
operation/source receipts and recorded Draft readers, never counterfeit completeness.
This is required implementation work, not an excuse to expose fake Published graphs.

All source changes acquire Catalog Product source barrier before Product/Version locks
and collaborate in the same physical RC UoW. Child publication state, Product snapshot,
Audit, Outbox and source generation commit atomically. Append-only compensations for
cancel/reschedule/supersession; no UPDATE of history or silent schedule overwrite.
Fenced normal writers/readers, RLS/minimal roles, current permission/scope/field checks,
refresh/freshness and original replay must be verified in actual isolated PostgreSQL.

Normal command/query API, effective/future public sources, Product timeline/projections
and accepted CAT-PRODUCT-REVIEW flow must consume these facts. UI evidence requires
rendered browser journeys/screenshots. Missing real IAM/topology/provider facts remain
explicit gates; unconfigured runtime fails closed. Finish repository-completable scope,
