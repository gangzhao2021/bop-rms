## Owning facts and boundaries

Ordering owns Cart, Order, Batch and submission idempotency. Catalog/Menu owns public-effective
Sellables; Pricing owns Quote, tax and Money; Dining owns Dining Session eligibility; Food Safety
owns structured allergen evidence; Payment owns Payment Attempt, Terminal and Provider outcome.
Staff Order Entry is a thin orchestration contract over those owners. It cannot create a POS-only
truth model, accept browser-authored financial facts, claim Payment success or persist customer
contact or allergy / health detail.

## Acceptance contract

1. Every action carries Tenant, Brand, fixed Store, named Staff Actor, purpose, operation reference,
   observed time and the fixed `Pos` source channel. Authorization proves both `ordering.operate`
   and explicit `ordering.order.create_staff` before an idempotency or shared-contract read.
2. Create Cart, configure, requote, attach an eligible Dining Session, record structured allergen
   review, submit and start Terminal payment invoke injected owner contracts. The strict input has no
   price, tax, currency, lifecycle status, cash or manual-success override.
3. Submit requires a current owner-issued Quote and allergen readiness, persists named created /
   submitted Actor and `Pos` source evidence, and duplicate operation replay returns the same single
   Order / Batch. Terminal start is cashless and can return only `Pending`, never success finality.
4. `OPS-ORDER-ENTRY` implements fixed Store / service context, public-effective Menu filtering,
   Sellable configuration, staff Cart / Quote, optional eligible Dining Session / verified Customer
   reference, structured allergen review, Terminal handoff, and every mandatory state. Mutations stay
   disabled without an authorized command-capable BFF.
5. Section 50 already assigns Cart / Order tables to Ordering. This orchestration adds no owning
   fact, schema, migration, Event Catalog entry or Provider adapter; persistence and every
   cross-domain operation remain injected ports.
