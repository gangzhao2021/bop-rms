# WP-2240 - Same-Origin Guest Binding Credential Transport

## Authority and scope

Owner authorizes sustained implementation and verified local commits. Baseline46c3bd8, branch
codex/wp-2240-binding-http. WP-1003, WP-1205 and WP-2234–2237 govern credential transport,
current authorization and initial Pickup activation. Composite authority is unchanged.

Add same-origin POST BFF prepare/activate/complete handlers around the real Identity service public
interface. Browser input contains only operation and credential proofs, never Cart/Store/Session IDs
or time authority. Candidate Session credential is delivered only in a Secure, HttpOnly, SameSite=Lax,
Path=/ host cookie. Its name is operation-specific so concurrent preparations cannot overwrite one
another. CSRF and purpose-separated recovery proof use no-store credential JSON and remain ephemeral
page memory, consistent with existing Customer transport. They are never Cart DTO fields.

Prepare leaves the active Guest cookie unchanged and creates no Cart. Activate acknowledges candidate
Cookie/CSRF/proof and publishes the active Guest cookie only after the Identity/Ordering service
finishes. Complete accepts that operation's candidate cookie, or the active Guest cookie when the
success headers already arrived, with candidate CSRF. Thus loss of response headers or body can be
retried explicitly without reusing revoked credentials. Clear only the matching staged cookie on
successful publication; failed/unknown results cannot write or clear credential cookies.

Staged cookies have no Max-Age/Expires attribute; no Web Storage, IndexedDB or service-worker
storage is introduced. Identity's preparation/Session deadlines continue to govern authority. Page reload/browser-close recovery
after losing in-memory CSRF/proof is not implemented here. No claim of general basket recovery or
DineIn transport. Full PWA orchestration and production composition remain separate work.

## Acceptance

1. Exact origin/fetch metadata, JSON, CSRF and Idempotency-Key validation; duplicate/malformed
   credential cookies and unknown body keys deny before the service. Bounded no-store errors.
2. Strict output validation before headers; raw Session credentials never appear in JSON/errors.
   No cross-operation cookie fallback, foreign cookie scope, insecure descriptor or substituted
   operation/credential result. Distinct concurrent preparations retain distinct cookie names.
3. Optional application injection registers fixed bounded telemetry templates; absent composition
   stays unavailable. Real HTTP tests and real Identity/Ordering PostgreSQL composition prove
   interrupted activation and repeated completion using the original candidate.
4. Frozen offline install, affected API types/lint/tests, Cart PostgreSQL suite, full pnpm verify,
   pnpm test:integration, secret scan and final scope/LF/diff/privacy review.

No migration, dependency, UI/Screen change, external service mutation or production activation.
Store/QR and policy evidence in integration tests is synthetic. Local commits only; no main merge,
push/deploy or remote CI claim. Local results follow.

## Remaining integration work

PWA orchestration must retain the original operation and candidate proof during explicit foreground
retry, distinguish a lost preparation response from uncertain activation, and preserve context when
credentials change. Preparation expiry, page refresh and cancellation require explicit recovery
semantics before enabling the complete browser journey; a failed completion does not prove that
activation never occurred. No automatic reconnect mutation replay. Current-Cart safe DTO composition,
DineIn shared ownership, production Store/policy configuration and external evidence remain separate
work. This package does not claim that the entire project or general basket recovery is complete.
