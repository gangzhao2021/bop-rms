# WP-2150 — Delivery Task queue, dispatch and assignment

## Authority and scope

- Handoff Sections 34.41–34.52 define idempotent Delivery Task creation after Planned Delivery,
  separate execution/assignment states, one active TTL Offer, append-only Attempts, pinned Dispatch
  Policy/Route Plan, bounded retry and worker availability. Section 88.10 defines
  `FUL-DELIVERY-DISPATCH` at `/operations/delivery`.
- This WP extends `@rms/fulfillment` with runtime-inactive Delivery contracts and ports. Existing
  Pickup persistence remains unchanged; no live worker/provider, scheduling, location or migration
  evidence is invented.

## Acceptance criteria

1. One Store-scoped Task is created idempotently only from a complete Planned Delivery source; Pickup,
   Pending, cancelled or incomplete source is rejected.
2. Execution and Assignment status remain independent. One failed Assignment Attempt cannot make the
   Task Failed.
3. At most one active Offer exists; TTL, sequence, assignment version, pinned policy/route versions,
   target and idempotency remain immutable.
4. Late accept, stale version, parallel offer and exhausted automatic retry fail closed or open an
   explicit dispatch exception without overwriting history.
5. Worker/provider candidates consume owner-issued availability/capability evidence; Identity and
   scheduling facts are referenced, not copied.
6. Strict queue UI provides canonical lanes, filters and actions with stale/read-only behavior.
