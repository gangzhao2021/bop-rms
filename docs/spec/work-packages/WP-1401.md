## Purpose and bounded outcome

WP-1401 introduces the minimum Kitchen-owned business aggregate behind the WP-1400
`OrderConfirmed.v1` intake boundary:

- exactly one `KitchenTicket` for an exact Store-scoped Order Batch;
- one initial `KitchenWorkItem` for each exact Ordering source item;
- an immutable Kitchen execution snapshot containing display, quantity, customer-note,
  Station-routing and Recipe/Preparation evidence;
- append-only creation action, Restricted System Audit and `KitchenWorkCreated.v1` Outbox
  evidence in the same Kitchen-local transaction; and
- the first `rms_kitchen` schema migration with forced Brand+Store RLS.

The increment remains runtime inactive. WP-1402 owns the real Station-routing and
Recipe/Preparation-plan producer. WP-1401 accepts only a strict injected plan in synthetic tests;
it does not infer a Station, inspect current Catalog/Recipe state or register a live Worker.

## Authority resolution

1. The Handoff contains `Feature F14.1 — Kitchen Order Intake`; it contains no `F14.2`.
2. The later frozen `OrderConfirmed.v1` contract supersedes Section 26.2's older
   `OrderBatchReleasedToKitchen` wording. WP-1401 does not introduce a second release Event.
3. Ordering alone owns Order, Batch, confirmation and immutable transaction-snapshot facts.
   Kitchen never reads `rms_ordering`, imports private Ordering paths or adds cross-schema foreign
   keys.
4. Kitchen owns Ticket, Work Item, creation action and Kitchen execution snapshot facts.
5. Section 26.3 requires a released Kitchen snapshot. A Work Item is not created unless the
   injected plan supplies exact Station-routing and Recipe/Preparation evidence. Placeholder or
   guessed facts are prohibited.
6. Customer note remains part of the Section 26.3 Kitchen snapshot, subject to the later Section
   87.11.2 rule: NFC plain text, at most 240 Unicode code points and four lines, with control and
   bidirectional-override characters rejected. It is Restricted possible-health data, is never
   interpreted as allergy accommodation, ingredient deletion or safety approval, and never enters
   an Event, Audit summary, log, URL, analytic label, screenshot or non-synthetic fixture.
7. WP-1407 owns structured allergen assistance and named-operator acknowledgement. WP-1401 cannot
   authorize Kitchen Start or make a food-safety claim.

## Closed execution contract

1. **Input boundary.** The Kitchen intake adapter implements WP-1400's existing injected
   `intakes.resolveByIdentity` and `intakes.accept` port. Its only command input is a strictly parsed
   `ConfirmedOrderIntakeReceipt` plus the caller-owned `ConsumerTransaction`. The adapter never
   receives the raw Ordering Event or its Payment causation reference.
2. **Authorization ordering.** The existing WP-1400 raw registration and facade paths strictly
   parse and authorize `ConsumeConfirmedOrder / CreateKitchenIntake` before calling `intakes`.
   WP-1401 does not duplicate or bypass that authorization. The Ordering-owned source-query service
   independently authorizes `ResolveConfirmedOrderKitchenSource / CreateKitchenWork` for the exact
   Brand, Store, Order, Batch, confirmation, source Event, aggregate version and purpose before it
   reads its injected source.
3. **Ordering source evidence.** Add a strict, accessor-safe, deeply frozen public
   `ConfirmedOrderKitchenSourceEvidence`. It binds an evidence reference, Brand, Store, Order,
   Batch, confirmation, source Event, positive source aggregate version, Ordering snapshot digest,
   captured UTC instant no later than the confirmed instant, positive evidence version and
   canonical SHA-256 evidence digest.
4. **Lossy item projection.** Source evidence contains one to 100 unique items. Each item contains
   only Order Item and Batch references, stable ordinal, quantity `1..999`, Product/Product Version,
   SKU and Menu Version references, localized display-name snapshot, selected Option references,
   quantities and localized names, bounded customer note and an immutable line digest. Pricing,
   tax, Money, Quote, Cart, Customer/Guest, contact, Staff/Actor/Participant and Payment/Provider
   fields are prohibited.
5. **Source authority.** The Ordering query revalidates every requested scope/reference/version/
   digest against the returned evidence and recomputes its canonical evidence digest. Missing,
   malformed, stale, cross-scope or ambiguous evidence fails closed. No Kitchen effect, plan read,
   Audit or Event occurs.
6. **Injected execution plan.** Kitchen resolves a strict `KitchenWorkPlan` only after exact source
   evidence. The plan port receives a deeply frozen, deliberately lossy planning projection with
   exact scope, evidence anchors, item/Product/SKU/Menu/Option references and quantities, but no
   customer note, localized display narrative, health or free text. Kitchen alone retains the full
   source snapshot. The plan binds the same scope, Order, Batch, confirmation, source-evidence
   digest and item set, plus a plan reference, positive version, generated UTC instant no earlier
   than either the confirmation or source-evidence capture, and canonical digest.
7. **Plan item.** The plan contains exactly one entry for each source item and no extra/duplicate
   entry. Each entry binds the Order Item, split ordinal `1`, opaque Station reference, routing-rule
   reference/version/digest, one Preparation reference/version/digest representing the frozen
   Recipe/Preparation plan, one to 32 NFC normalized plain-text preparation instructions with
   bounded length. It contains no Customer, health, Money or Provider data. After strict plan
   validation, Kitchen—not the plan producer—computes the final execution-snapshot digest over the
   complete immutable Work Item display/note/source plus Station/routing/preparation content.
8. **No partial aggregate.** A missing, incomplete, malformed, cross-scope or changed plan produces
   zero Ticket, Work Item, action, Audit and Outbox mutation. WP-1401 never creates an unrouted or
   placeholder Work Item.
9. **Ticket aggregate.** A new `KitchenTicket` is Store scoped and binds stable Ticket, Brand,
   Store, Order, Batch, confirmation, WP-1400 source Event, source aggregate version, Ordering
   snapshot/evidence digests, plan digest, correlation reference and created UTC instant. It starts
   at aggregate version `1` and status `Open`.
10. **Work Item entity.** Every source item produces one stable Work Item under the Ticket. It binds
    Order Item, ordinal `1`, exact required quantity, completed quantity `0`, initial status
    `Queued`, Station and preparation/routing snapshots, display/options/customer-note snapshot,
    execution digest and created UTC instant. `Ready` is not a Work Item status. WP-1401 exposes no
    Accept, Start, Complete, Cancel or Ready transition.
11. **Stable identity.** Reference ports derive Ticket from Brand+Store+Batch, Work Item from
    Ticket+Order Item+ordinal, creation action from Ticket+purpose, and Event/Audit from the same
    stable creation effect. References never depend on a job/run identifier or wall-clock bucket.
    Canonical fingerprints bind all exact source and plan content under those stable references.
12. **Authoritative time.** For a new creation attempt, the adapter reads one injected authoritative
    UTC instant only after exact receipt/source/plan checks. Caller/Event time does not select a
    branch. New action, aggregate, Audit and Event creation use this instant; stored source facts
    retain their own validated instants. A complete durable effect is instead strictly reparsed and
    replayed with zero source, plan or clock read because the persisted Kitchen Snapshot is the
    immutable post-intake authority.
13. **Three semantic keys.** Persistence resolves by scoped source Event, confirmation and Batch.
    All keys must be missing or resolve to the same exact stored creation effect. Split keys,
    malformed stored data or changed content is a conflict.
14. **Replay.** Same Event and exact semantic replay return the original WP-1400 receipt and stored
    Ticket with zero second action/Audit/Event. A different Event ID representing an otherwise
    identical semantic fact retains the original Ticket and original source Event reference.
    Before the first commit, or between competing creation attempts, changed Ordering evidence,
    plan, customer note, Station, preparation, quantity, version or digest conflicts under the same
    stable identity. After a complete effect is durable, current external source/plan state is not
    reread and can never rewrite or invalidate its immutable Kitchen Snapshot; malformed or changed
    persisted snapshot content still conflicts.
15. **Atomic creation.** One Kitchen-local transaction atomically completes the generic Inbox and
    persists the intake binding/Ticket, all Work Items, one append-only creation action, one Audit
    and one `KitchenWorkCreated.v1` Outbox row. Mandatory Audit or Outbox failure rolls back the
    whole transaction. The action independently records System actor with no actor reference,
    purpose/reason, `EVENT_CONSUMER` source channel and `Restricted` classification; it does not
    rely on Audit as its business-history source. No cross-domain transaction or table write is
    allowed.
16. **Commit unknown and concurrency.** The repository returns `Created`, `AlreadyCreated` or
    `Conflict` with the complete stored effect. Both success receipts are strictly reparsed and
    exact-compared. A retry resolves the permanent semantic keys before mutation. Concurrent
    consumers converge on one Ticket/item set/action/Audit/Event; no changed result is adopted.
17. **Audit.** The first creation produces one descriptor-safe `@bop/audit` record with System actor,
    exact Brand+Store, action `KITCHEN_TICKET_CREATED`, target Ticket, reason
    `ORDER_CONFIRMED`, original correlation, source channel `EVENT_CONSUMER`, classification
    `Restricted` and the approved retention code/version. Summaries contain only bounded status and
    item count; no note, names, Station, preparation text, evidence digest or foreign identity.
18. **Event.** `KitchenWorkCreated.v1` is owned and produced by `@rms/kitchen`, Store scoped,
    idempotent, `indirect_identifier`, business-record retention and consumed by
    `kitchen.queue-projection:v1`. Payload is strict and minimal: `kitchenTicketReference`, Order,
    Batch, confirmation, Work Item count, aggregate version and createdAt. Envelope aggregate is
    `KitchenTicket`, aggregate ID is Ticket, occurredAt equals createdAt, actor is System,
    correlation comes from the intake and causation is the `OrderConfirmed` Event. No item snapshot,
    note, Station, preparation, health, Money or Payment reference enters the Event.
19. **Bounded public result/error.** The creation result is immutable and includes only original
    intake receipt, Ticket reference, Work Item count and `Created | AlreadyCreated`. Closed errors
    are `KITCHEN_TICKET_INPUT_INVALID | KITCHEN_TICKET_PERMISSION_DENIED |
KITCHEN_TICKET_CONFLICT | KITCHEN_TICKET_DEPENDENCY_UNAVAILABLE`, with one safe message
    `kitchen ticket creation is unavailable`. No existence, data or dependency detail is exposed.
20. **Privacy and telemetry.** Module classification becomes
    `indirect_identifier,personal,health`; fixtures are synthetic only and logs/URLs/analytics are
    prohibited. Metrics may use bounded outcome/reason labels only—never Brand, Store, Order,
    Ticket, Item, Station, note, digest or other object references.
21. **Persistence.** Migration `1500_001` creates `rms_kitchen.kitchen_ticket`,
    `kitchen_work_item` and append-only `kitchen_action_record`. Every table carries Brand+Store;
    every unique/FK/index needed for identity or lookup leads with scope. There is no cross-schema
    FK, role/login/grant or private Ordering access.
22. **RLS and immutability.** All three tables enable and force RLS using exact current Brand and
    Store helpers, revoke PUBLIC, deny missing/wrong context and prevent cross-tenant unique/upsert
    leaks. Ticket/source/snapshot identities and Work Item execution snapshots are immutable;
    aggregate/status/version columns remain capable of future expected-version transitions. The
    Work Item table permits only the Section 26.4 closed states `Queued | Held | In Progress |
Completed | Cancelled`, positive versions and completed quantities within the required
    quantity; WP-1401 creation still writes exactly `Queued`, version `1` and completed quantity
    `0`. Creation action rows are append-only.
23. **Runtime boundary.** No API, UI, Worker registration, transport adapter, scheduler, feature
    flag, Provider SDK/call, credential, deployment or non-local database action is in scope.
    Runtime composition remains absent until the real Ordering query, WP-1402 plan source and all
    listed live gates are proven.
