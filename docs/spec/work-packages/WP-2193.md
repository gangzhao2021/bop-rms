# WP-2193 — Capability / Feature Flag Dependency and Effective-period Administration

## Authority and scope

- Handoff Sections 48.3.15–48.3.18, 56.23, 88.7 and 88.21–88.30 define Feature Control
  ownership, effective-period behavior and the canonical Merchant screens.
- Exact local predecessor: verified WP-2192 commit `0f1b562`.
- `@bop/feature-control` owns Release Flag, Kill Switch and Store Capability administration.
  Domain configuration remains with its owning Domain; Feature Control stores only controlled keys,
  scope, dependency/evidence references and immutable evaluation/publication metadata.

## Acceptance contract

1. Administrative definitions are immutable by version and explicitly include owner, purpose,
   Brand/optional Store scope, default/effective value, source, lifecycle, review/expiry and bounded
   effective period.
2. Brand definitions may be overlaid only by an exact same-Brand Store definition. Resolution is
   deterministic, retains its source and fails closed for missing, overlapping, expired or malformed
   definitions.
3. Capability dependencies identify required/conflicting capabilities or Future Trigger IDRs.
   Publish is blocked unless every requirement has compatible evidence and every Future Trigger is
   accepted; the API cannot turn missing evidence into success.
4. Draft, submit, independently approve, publish/schedule and disable operations require exact
   scope, purpose, permission, expected version, idempotency and append-only Audit evidence.
5. Persistence is append-only and forced Brand/optional-Store RLS prevents cross-Tenant access.
6. `STORE-CAPABILITY` and `FEATURE-FLAG-LIST` expose source, dependency impact, effective period,
   status/expiry/owner and complete loading/empty/denied/not-found/offline/stale/conflict/error
   states. Frontend hiding never grants backend execution.
7. This WP creates no real flag, capability, approval, Future Trigger acceptance, publication,
   production evaluation, external mutation or cross-Domain configuration value.
