## Purpose

Implement the smallest first-Pilot Catalog model that proves:

1. Option Set is one Brand-scoped Aggregate Root with one complete mutable Draft Version；
2. Option is a stable Option Set-owned Entity and cannot be written independently；
3. selection minimum/maximum、repeat and per-option/total quantity rules are satisfiable；
4. Option conflict references remain inside the owning Option Set and self-conflict is denied；
5. triggered Option Set references are same-Brand graph facts and self/cyclic graphs fail closed；
6. Product Option Binding is a Product Version-owned child that references one exact Option Set
   Version without copying Option definitions；
7. the same Option Set can be bound more than once only with distinct Binding ID and Purpose；
8. enabled/default Option scope、hard-limit override、SKU include/exclude and channel scope are
   explicit and validated；and
9. publication、approval、effective Availability、Pricing、Inventory/Recipe behavior、API/UI、
   Projection/Event and real Catalog evidence remain absent.

## Adopted boundaries

- Option Set lifecycle is `Draft | Archived`; only Draft Version content is created here.
- Option lifecycle is `Draft | Active | Inactive | Archived` within the owning Draft snapshot.
- Display Style is `SingleChoice | MultiChoice | Quantity`; it does not select a UI component.
- Counts use non-negative safe integers. A maximum must cover the minimum. Repeat-disabled sets
  force per-option maximum `1`; total quantity cannot be lower than minimum or per-option max.
- Localized content is bounded plain business configuration. HTML、Markdown、URL、notes、PII and
  allergen/legal assertions fail closed.
- Product Binding can tighten but never loosen referenced Option Set limits. Defaults must be
  enabled、eligible、non-conflicting and within the effective rule.
- Include and Exclude SKU scopes are disjoint and reference only Product-owned SKUs.
- Operation reference + deterministic intent digest provides replay；changed intent conflicts.
  Repository conditional commit remains the final aggregate-version guard.
- Persistence adds only Catalog-owned `1102` tables with forced Brand RLS、stable identity rules、
  exact foreign keys and append-only operation history.
- WP-1023 owns Store Availability. WP-1024 owns publication/effective immutable versions. Pricing、
  Inventory and Recipe own their facts and are not represented as local truth here.

## Implementation surface

- synthetic tests for strict parsing、authority、idempotency、selection satisfiability、trigger/

No REST route、screen、Projection、Event、Published state、price、inventory balance、Recipe modifier、
real Store/Product/Option fact、external resource or deployment is added.

## Risks and next action

- An Option treated as an independent Aggregate can drift from its Version；ownership and foreign
  keys prevent independent mutation.
- Binding copied Option content makes historical validation ambiguous；Binding stores only stable
  references and exact Version identity.
- An unsatisfiable or cyclic rule graph can block ordering；local validation plus injected complete
  trigger-graph validation fail closed.
- Next action is exact-head pinned-Linux CI and Section 91 review. Merge、post-merge verification
  and cleanup remain external and are not claimed.
