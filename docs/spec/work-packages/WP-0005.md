## Goal

Provide a deterministic, local-only Docker Compose environment for PostgreSQL `18.4`. Prove safe secret handling, localhost connectivity, accepted initialization settings, health, restart persistence, scoped clean reset, and clean re-creation without changing application readiness or implementing later database work.

## Scope and files

- Root Compose definition pinned to the exact accepted PostgreSQL patch image and OCI digest.
- A tracked environment template with no credential and an ignored local secret-file path.
- WP-bounded PostgreSQL lifecycle documentation and automated verification under `tooling/postgres/`.
- The existing unique GitHub Actions job `bootstrap / verify`, extended with finite, self-cleaning Compose verification.
- This brief, the specification index, and only the ignore/documentation updates required by the local environment.

No application package, Domain package, Screen Registry entry, UI component, database driver, ORM, migration, schema, seed, fixture, or production infrastructure is in scope.

## PostgreSQL and Compose contract

- PostgreSQL is exactly `18.4`; floating tags such as `latest` or `18` are prohibited. The Compose image includes a reviewed OCI digest, and verification records the actual pulled image identity.
- The database port binds only to `127.0.0.1`; no LAN/public bind is allowed.
- Compose explicitly defines its project, PostgreSQL service, project-scoped container, network, named volume, port, and connection-based healthcheck.
- Initialization uses encoding `UTF8`, deterministic `C` collation and character classification, server/session timezone `UTC`, and `DateStyle` `ISO, YMD`.
- Machine identifier ordering never depends on locale behavior. User-facing ICU collations and their lifecycle belong to later migration/read-model work.
- The named volume persists across an ordinary restart. Clean reset removes only resources labeled and named for the selected WP-0005 Compose project.
- Local Compose is not production RDS, deployment, backup/restore, HA, DR, or production-readiness evidence.

## Security boundary

- No real password, token, credential, PII, Provider data, Store data, or production data may be committed, logged, passed on a command line, emitted by health output, or uploaded as a CI artifact.
- Compose requires an explicit local password-file path and fails with a clear error when it is missing. The actual secret file and local `.env` remain Git-ignored and should have Linux mode `0600`.
- CI and lifecycle tests create short-lived synthetic credentials outside tracked files, mount them as Docker secrets, scan output for disclosure, and delete them on exit.
- Commands may create, inspect, restart, and remove only the selected WP-0005 Compose project. Existing containers, networks, and volumes from other projects are never stopped, removed, or modified.
- API `/ready` remains truthful: database stays `not_configured` / not ready until a later authorized application-integration WP establishes a real connection.

## Local lifecycle and rollback

The bounded lifecycle documentation must provide exact commands for config validation, start, status, logs, stop, restart, and clean reset.
