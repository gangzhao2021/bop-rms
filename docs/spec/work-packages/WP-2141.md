# WP-2141 — Customer duplicate / merge evidence review

## Authority and scope

- Handoff Sections 33.1–33.3 and 33.15 assign Brand-specific Customer Profiles and the
  `CustomerProfilesMerged` fact to Customer & Loyalty while Identity and transaction Domains retain
  their own facts.
- Section 42.17 requires Tenant and Brand isolation. Section 88.14 defines contextual
  `CRM-MERGE-REVIEW`; Sections 88.21–88.24 define approval, projection, search and failure behavior.
- This WP adds a local runtime-inactive contract, Aggregate and strict Merchant page. It does not
  create a database namespace because no accepted Customer & Loyalty migration ownership is present.

## Acceptance criteria

1. A review is created only for two distinct Profiles in the same Tenant and Brand from exact,
   independently validated evidence. Empty evidence, broad fuzzy matching and cross-Brand candidates
   fail closed.
2. The review freezes conflicting fields, linked account / transaction references, consent evidence,
   impact and rollback references without copying raw contact values.
3. Approval requires `customer.merge.approve`, a validated approval and an Actor distinct from the
   requester. Rejection is explicit and version checked.
4. An approved review emits `CustomerProfilesMerged` with both Profile IDs retained and explicit
   guarantees that transaction facts and historical Actors were not rewritten.
5. `CRM-MERGE-REVIEW` strictly parses its purpose-scoped projection, trims evidence by field
   permission, supports exact contact / Profile-reference lookup only and becomes read-only when
   stale or partial.
6. All required page states are represented and no raw contact, credential, payment or unrestricted
   personal data enters routes, logs, analytics, fixtures or error payloads.
