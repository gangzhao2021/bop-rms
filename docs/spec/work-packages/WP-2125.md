## Owning facts and boundaries

Inventory owns a Transfer request, its immutable revisions, dispatch / receipt facts, In Transit
quantity, discrepancy and linked Stock Movements. Source and destination are separately authorized
Stock Scopes. Dispatch and receipt append facts; neither edits an earlier quantity or makes In Transit
disappear by overwrite.

## Acceptance contract

1. Define a versioned Transfer Aggregate with distinct source / destination Scopes, immutable line
   revisions, Item / lot / expiry, exact requested / dispatched / received / in-transit / discrepancy
   quantities, owner, dates, lifecycle and append-only timeline.
2. Create / revise authorizes both Scopes before Item / Balance reads, rejects equal or foreign
   Scopes and server-rebinds lifecycle, lot / expiry, Unit conversion, Balance version and negative
   policy. Revision is allowed only before dispatch.
3. Submit / approve enforce exact permissions, expected version and independent approval. Dispatch
   and receive support partial quantities, prevent over-dispatch / over-receipt and preserve explicit
   remaining and In Transit quantities.
4. Dispatch / receive validate atomic adapter results containing exact Audit, updated Aggregate and
   immutable `Transfer` Movements. Discrepancy and cancel-remaining are appended with controlled
   reasons and cannot rewrite dispatch / receipt history.
5. Implement `INV-TRANSFER-LIST` at `/operations/inventory/transfers` and `INV-TRANSFER-DETAIL` at
   `/operations/inventory/transfers/:id`; keep `INV-STOCK-TRANSFER` registry-only as the historic
   alias. Cover required filters, fields, actions, freshness and mandatory states.
6. Section 50 assigns no Inventory schema and the Event Catalog contains no Transfer event.
   Persistence, snapshots, projection and atomic Ledger posting remain injected; no migration or
   Event is invented.
