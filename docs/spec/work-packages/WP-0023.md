## Goal and bounded responsibility

Prove, against a synthetic Aggregate Root in a unique isolated local PostgreSQL database, that the accepted compare-and-swap persistence pattern prevents a stale writer from overwriting a committed update:

```sql
UPDATE <synthetic_aggregate>
SET <changed_fields>,
    version = version + 1,
    updated_at = <transaction_time>,
    updated_by_actor_id = <validated_actor>
WHERE id = <validated_id>
  AND version = <expected_version>
RETURNING version;
```

The test observes one returned row as success and zero returned rows as the persistence-level stale-version signal. It proves that the winner remains durable、the stale write is not applied、the version advances exactly once and a later retry using the current version can succeed.

This WP adds integration evidence only. It does not create a production database object、migration、runtime helper、Repository abstraction、HTTP endpoint or UI behavior. Section 52.8 remains the future API contract for `ETag`、`If-Match` and `409 AGGREGATE_VERSION_CONFLICT`; this WP does not pretend that a database row count is already an HTTP response.

## Accepted exact implementation contract

### Test fixture and lifecycle

1. Extend only the existing `packages/database/test/integration.mjs` isolated PostgreSQL suite. Do not create a reusable fixture library or change dependency / package / workflow configuration.
2. Create a uniquely named synthetic schema and Aggregate Root table inside a WP-owned isolated test database after the accepted WP-0020 through WP-0022 migrations have applied.
3. The synthetic row contains only `id uuid`、`version bigint not null`、`created_at timestamptz not null`、`updated_at timestamptz not null`、`created_by_actor_id uuid`、`updated_by_actor_id uuid` and a non-sensitive synthetic value used to observe the winning write.
4. Start at version `1`. Treat PostgreSQL `bigint` values as exact strings at the Node boundary; never coerce a version through binary floating-point or JavaScript `number`.
5. Use synthetic UUIDv7-shaped identifiers and synthetic values only. No Tenant、Brand、Store、Customer、Employee、Provider、payment、allergy / health、credential or other PII fact is permitted.
6. The existing isolated database teardown remains the cleanup owner. No shared developer database、staging、production or external Provider is contacted.

### Concurrency scenarios

1. Two independent PostgreSQL clients read the same row and version `1`.
2. The first client updates with expected version `1`, returns version `2` and commits its synthetic value、timestamp and actor.
3. The second client attempts a different update with the stale expected version `1`, returns zero rows and must not change any value、timestamp、actor or version.
4. A scoped reread observes the winner and current version `2`. The test does not generalize this reread into authorization、existence-disclosure or API error-mapping policy.
5. A retry using expected version `2` succeeds exactly once and returns version `3`.
6. A successful compare-and-swap that is rolled back leaves the committed row and version unchanged.
7. A missing ID and a stale version both produce zero updated rows at the SQL boundary. Future owning Repository / API work must distinguish not-found from conflict without leaking an unauthorized resource; WP-0023 records but does not implement that policy.

The test must use bounded waits and deterministic synchronization. It must not rely on timing races、unbounded sleeps or a last-write-wins assertion. PostgreSQL errors and test output must remain redacted under the existing connection contract.
