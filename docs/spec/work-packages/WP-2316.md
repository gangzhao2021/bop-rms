## Owner transaction and acceptance

Implement a scoped PostgreSQL writer using WP-2315's decision. Capture closed options/command before
awaits. Serialize scoped operation then Dining Session with bounded transaction advisory locks. A
new operation reads complete Customer Session Cart history, including expired/terminal/legacy rows,
with a bounded two-header query and a shared root-row lock. Reuse the existing aggregate reader in
the same transaction. Unique current eligible history selects unchanged; ambiguity or unusable history
denies. Only absent history creates an empty version1 Cart from explicit current policy and generated
reference. No Store lifecycle values are invented.

Add one immutable dining_cart_operation table, not a second association table. Preserve exact command
scope, Guest/Participant and minimal original Cart/version/action/time receipt; never copy Cart notes,
credentials or item snapshots. A scoped partial unique Create index prevents a second protocol-created
Cart for that Session. A scoped Cart/Dining Session foreign key prevents wrong association. Validate
the observed Cart version/source/lifecycle and original creator for Create at operation insertion.
Forced Store RLS, PUBLIC revocation and update/delete/truncate rejection preserve history. Add only
the necessary Cart association unique key and Customer Session history lookup index. Root migration
1300_012 is forward-only; existing migrations remain byte-identical. Catalog count becomes101.

Create/select, operation and public Audit append commit atomically. Existing Cart creator, items,
version and deadlines never change on selection. Complete canonical command fields identify intent;
retry observation, generated candidate and current policy are excluded. Exact original retry within
24 hours returns its historical receipt without new Cart/operation/Audit; changed/expired reuse denies.
Current authority is still required by the future caller. Original receipt is neither a current Cart
view nor a Closing/item-write lease. Lost commit acknowledgement can recover through the original key.

Audit uses the existing System actor pattern; Guest/Participant attribution remains in immutable
operation fields. Require exact scope, operation correlation, OrderingCart target, bounded Create/Select
action, authorized-selection reason, CUSTOMER_PWA source and Restricted classification, without
summaries, correction or network data. Runner owns bounded transaction/connection/context cleanup.
