## Owning facts and boundaries

Inventory owns Inventory Item identity, units / conversions, tracking and lot / expiry policy,
negative-stock policy, Storage requirements, lifecycle and scoped Reorder Policy. The immutable Stock
Ledger owns quantity facts; its Stock projection is rebuildable. Catalog owns SKU, Recipe owns usage,
Procurement owns Supplier Offering / price, and Accounting owns its ledger. This WP cannot post a
Movement, create opening balance, alter a Purchase Order or invent a Supplier mapping.

## Acceptance contract

1. Establish canonical `@rms/inventory` ownership with strict Item create / update / lifecycle and
   Reorder Policy commands carrying Tenant, Brand, Actor, purpose, permission, expected version,
   idempotency and Audit evidence before reads or writes.
2. Validate stable code, localized name, Item type, base Unit / compatible decimal conversion,
   tracking / lot / expiry / negative-stock policy and controlled policy changes. Lifecycle is
   action-only; Restore returns Archived to Inactive, and history is append-only.
3. Quantity is never accepted by an Item mutation. Identity queries may omit Stock Scope; any
   quantity, reorder, quantity sort / filter / export or stock action requires exactly one explicit
   Store / Site / Location scope and returns value + Unit + freshness from a rebuildable projection.
4. Implement the primary Section 88 surfaces: `INV-STOCK-OVERVIEW`, `INV-ITEM-LIST`,
   `INV-ITEM-DETAIL`, `INV-ITEM-CREATE` and `INV-ITEM-EDIT`, with embedded/contextual links for
   policy, history, picker/import/export and later Movement workflows. All mandatory Inventory and
   universal states are represented; mutation buttons remain disabled without an authorized BFF.
5. Section 50 does not assign Inventory tables or a migration namespace. Persistence, Ledger,
   authorized usage / supplier feeds and imports remain injected ports; no migration or Event
   Catalog publication is allowed in this WP.
