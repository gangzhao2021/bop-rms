## Outcome and closed semantics

WP-1406 publishes two Kitchen-owned facts:

- `KitchenItemReady.v1`: one Order Item has one immutable full-quantity Kitchen Ready result.
- `KitchenOrderReady.v1`: every Order Item represented by the exact Kitchen Ticket has an immutable
  Ready result after applying the current Ready transition.

`KitchenOrderReady` is explicitly a Kitchen preparation fact. It is not Ordering acceptance or
completion, Fulfillment Ready/Completed, Pickup handoff, Payment, output completion or Customer
notification. Kitchen never writes another Domain's state. Fulfillment may consume the public
facts idempotently in its own later Work Package.

Ready remains an OrderItem/Ticket result, never a Work Item status. Partial Work Item completion,
final Work Item completion with Expo enabled, queue projection state and realtime hints cannot emit
either Ready Event. Manual Expo Ready and automatic Ready create the same public semantics.

## Exact public Event contracts

Both Event types are stable, version `1`, Store-scoped, owned and produced by `@rms/kitchen`,
classified `indirect_identifier`, retained as business records and replay-safe. The Event envelope
Actor is `System`: named operator accountability remains in the mandatory immutable Audit and is
not copied to public consumers.

`KitchenItemReady.v1` uses aggregate type `KitchenOrderItemReadyResult`, aggregate ID equal to the
immutable Ready-result reference and aggregate version `1`. Its closed payload is:

```text
{ kitchenTicketReference, orderReference, orderBatchReference,
  orderItemReference, readyResultReference,
  readyQuantity, requiredQuantity, readyAt }
```

`KitchenOrderReady.v1` uses aggregate type `KitchenTicket`, aggregate ID equal to the Ticket and
aggregate version equal to the committed Ticket version. Its closed payload is:

```text
{ kitchenTicketReference, orderReference, orderBatchReference,
  readyItemCount, itemCount, readyAt }
```

For both Events, `occurredAt == readyAt`, correlation is the original command correlation and
causation is the exact manual Ready operation or automatic Ready child operation. Event references
are independent server UUIDv7 values and cannot alias scope, source, operation, result, Ticket,
Order, Batch or Order Item references. Quantities/counts are bounded positive safe integers. Item
Ready requires `readyQuantity == requiredQuantity`; Order Ready requires
`readyItemCount == itemCount`.

No payload contains Customer/health/allergen/note, Product/Option/Recipe/Station/preparation,
Actor/Session/permission, Payment/Provider, contact, display text, arbitrary narrative, internal
digest, Ticket snapshot or Work Item vector.

## Atomic publication and Order readiness proof

The existing WP-1404 lifecycle transaction is the sole producer. Before committing a Ready result,
its exact locked Kitchen source includes Order/Batch identity and a complete, sorted Ticket
readiness vector with one entry per distinct Order Item. Each entry has only Order Item reference,
required quantity and nullable immutable Ready-result proof fields. The current target must be the
only prospective transition in that vector.

The application substitutes the newly composed Ready result into the current target, then:

1. always composes exactly one `KitchenItemReady.v1`;
2. composes `KitchenOrderReady.v1` only when every Ticket entry is now fully Ready;
3. creates one append-only Kitchen Ready publication record binding the Ready result, exact Event
   references and semantic digests; and
4. passes the Ready result, publication record, public envelope(s), Audit(s), operation(s) and
   mutation to the existing repository `commit` boundary once in the same transaction.

Any identity, source-vector, event composition, Outbox or publication-row failure rolls back the
Ready result and remains replayable. An existing Ready operation replay returns the original effect
and emits nothing again. The scoped Ready-result uniqueness, publication Ready-result uniqueness,
Outbox Event identity and Ticket lock prevent duplicate Item/Order facts. A different Event ID for
the same Ready result is not accepted as equivalent application state.

The complete vector is authoritative Kitchen owner data, not a Projection. It must exact-match the
Ticket's source Order Items under the same lock. Missing, duplicate, extra, cross-scope, wrong-
quantity, false-null/false-present, future-time or aliased evidence is dependency corruption with
zero write. `KitchenOrderReady` is omitted, not inferred, when any other Item remains unready.

## Persistence boundary

Forward-only migration `1500_004_create_kitchen_ready_publication.sql` creates only
`rms_kitchen.kitchen_ready_publication`. One append-only, forced-RLS row per Ready result binds:

- Brand, Store, Ticket, Order, Batch, Order Item and Ready-result references;
- Item Event/Outbox reference and semantic digest;
- optional Order Event/Outbox reference and semantic digest as one all-null/all-present group;
- committed Ticket version, full item quantity, Ticket item count, correlation, causation and UTC;
- exact data classification and retention code.

All keys and foreign keys are Brand/Store leading and Kitchen-local. There is no cross-Domain FK,
payload JSON, Customer/health column, mutable status or update/delete path. No production adapter,
Worker registration or runtime activation is claimed; the repository port defines the atomic write
shape and database acceptance proves the durable constraints.

Kitchen repository transaction -> generic Outbox -> authorized consumers. Public Events are
indirect identifiers only. Tenant/Store scope is derived from the locked source and cannot be
supplied independently by a consumer or browser.

Abuse evidence must cover extra/symbol/accessor/proxy input, wrong source scope/identity/version,
duplicate/unsorted/aliased vector entries, partial quantities, stale/future time, public payload
