## Purpose

Add a provider-neutral、synthetic `@bop/effective-period` minimum contract that proves:

1. immutable configuration/release references can carry exact Effective From/Until timing without
   transferring caller-owned configuration payload；
2. UTC instants、IANA time zone、local date-time and explicit UTC offset round-trip consistently,
   including daylight-saving gaps/ambiguities；
3. periods are half-open `[Effective From, Effective Until)`, with From required and Until optional；
4. exact configuration family + Tenant scope rejects ambiguous overlap while allowing adjacency；
5. an explicit evaluation instant resolves zero、one or conflict, never silently chooses among
   multiple effective versions；
6. historical resolution is reproducible from immutable candidate metadata and an explicit instant；
7. Schedule/Renew creates immutable activation and optional expiry intents with exact Permission、
   accepted approval evidence、positive expected version、idempotency and atomic Audit；and
8. malformed、stale、cross-Tenant、replayed、conflicting or unavailable inputs return stable bounded
   denial without exposing configuration or identity data.

WP-0123 completes Feature F01.2 acceptance that a Published Configuration can resolve its current
effective Version. It does not implement generic configuration overlay priority from Handoff
Section 48.3.18.

## Governing decisions

1. **Predecessor —** WP-0122 is integrated and post-merge verified at
   `02516889ec494c78e4913560d1112cf82c953aa1`.
2. **Owner —** `@bop/effective-period` owns timing metadata、period validation、overlap validation、
   effective resolution and schedule intent contracts only. The caller Domain/Publishing owns
   configuration schema、payload、validation、Release and business priority.
3. **Opaque version —** candidates contain only UUIDv7 family/configuration/release/snapshot
   references、`sha256:` digest、stable configuration/purpose codes、exact Tenant scope and timing.
4. **Exact scope —** every candidate is one Brand or one Store within that Brand. No global scope、
   client-derived Brand、Store Group/Region/Channel/Order Type priority or cross-scope fallback.
5. **Canonical time —** stored instants are canonical UTC. Each boundary also carries IANA time
   zone、local date-time and explicit UTC offset that must round-trip to the same instant. Floating
   local time、host default zone and implicit DST choice are invalid.
6. **Boundary semantics —** From is inclusive；Until is exclusive and must be later than From.
   `Until = null` means open-ended. Derived states are `Scheduled`、`Effective` and `Expired`;
   they are never persisted as mutable truth.
7. **Overlap —** overlap validation is exact family + scope. Adjacent half-open periods are valid；
   any intersecting or duplicate period is a conflict. This minimum has only fail-closed `Reject`
   policy and invents no precedence.
8. **Resolution —** caller supplies exact family/scope candidates and an explicit UTC instant.
   Zero match returns unavailable；one returns its immutable version reference；more than one
   returns conflict. No “latest wins”、array-order or clock-dependent fallback.
9. **Historical reproducibility —** resolution record includes query instant、candidate-set digest、
   selected version/reference or stable reason. It contains no payload and never queries mutable
   caller tables.
10. **Schedule/Renew —** Schedule creates a new immutable timing version and deterministic
    activation/optional expiry intents. Renew creates another version；it never extends or edits
    history in place.
11. **Approval —** injected accepted approval evidence is bound to exact family/version/scope、
    period digest、Actor and validity window. This WP does not implement Approval workflow.
12. **Permission —** exact Schedule and Renew actions require accepted `@bop/permission` evidence.
    Ownership or approval alone is never a grant.
13. **Atomic Audit —** one unit-of-work port atomically enforces expected version/idempotency,
    writes the immutable timing version and schedule intents, and appends bounded `@bop/audit`.
14. **Task/Notification boundary —** Handoff reminder dependency is represented only by opaque
    intent references/ports until WP-0124/0125. No Task、Notification、clock、queue、worker or
    delivery result is fabricated.
15. **Event boundary —** timing records may later source events, but this WP publishes no Event and
    fabricates no Outbox result.
16. **Privacy/telemetry —** only stable operation/status/reason codes may be labels. Tenant、Store、
    Actor、family/version/release/snapshot/digest/intent IDs and local date-time are excluded.
17. **No persistence/API/UI —** no table、migration、RLS、repository adapter、route、Screen、
    navigation、projection or deployment.
18. **No external mutation —** no Provider、credential、real approval/configuration/schedule、
    external resource or operational activation/expiry.
19. **External Evidence —** real scheduler、reminder、load、recovery、staging and production evidence
    remains `NOT AVAILABLE / NOT CLAIMED`.
20. **Hard stop —** payload/overlay ownership、implicit time zone、ambiguous overlap winner、
    mutable status/history、Approval/Task/Notification implementation、event claim、persistence、
    production API/UI、Provider/resource or allowlist-external tracked file stops implementation.
