## Acceptance and design

Add three fixed same-origin POST BFF endpoints for Dining binding prepare/activate/complete.
Preparation accepts only admissionReference, parsed through Identity's existing public parser;
operation and CSRF use exact headers. Require exact HTTPS Origin, same-origin/cors Fetch
Metadata, JSON, no query and unambiguous credential cookies/headers. Identity and Dining
public composition retain all authority and effects; API implements transport only.

Stage candidate Session solely in Secure HttpOnly SameSite=Lax Path=/ operation-specific
__Host-bop-guest-dining-candidate cookies distinct from Pickup's purpose. Candidate CSRF and
recovery proof use no-store JSON for ephemeral page memory only. Preparation does not replace
main Session. Activation requires exact candidate possession; success publishes main Session and
clears only its own stage. Completion accepts exact staged candidate or already-published main
Session. Unknown failures never clear cookies or imply rollback; bound raw Session never appears
in JSON, URLs, errors or telemetry. Fixed telemetry routes, optional app/server injection and
unconfigured-unavailable behavior are required. No runtime provider or browser activation.

Actual PostgreSQL composition acceptance injects lost Identity activation acknowledgement after
committed Dining consumption and Identity binding. HTTP recovery after preparation expiry must
work both with retained candidate cookie and with only successfully-published main cookie;
no duplicate consumption/history/Audit. This is synthetic local HTTP and database evidence,
not a real browser, TLS interception or production packet-loss test.
