## Purpose

Apply the existing provider-neutral WP-0120 Kill Switch decision to Payment's first real new-work
boundary. A fresh exact-scope decision must permit a new online Payment Intent before Ordering
preparation, Payment claim or Provider invocation. Active, recovering-blocked, missing, malformed or
unavailable control evidence fails closed without hiding an already committed idempotent result or
blocking authoritative Payment truth and recovery paths.

## Closed execution contract

1. Feature Control remains the sole owner of Kill Switch definitions, scope, rollout, activation,
   Audit and recovery. Payment owns only the safe application of the evaluated decision to its own
   state machine; it never reads Feature Control private persistence or mutates a control.
2. The only key introduced by this WP is `payment.provider.admission`. It is a `KillSwitch`, not a
   Release Flag or general Payment configuration. The Payment module manifest declares that exact
   key and the public `@bop/feature-control` dependency.
3. WP-1308 applies the key to the currently implemented `CreatePaymentIntent` admission boundary.
   WP-1309 and WP-1310 must separately define safe in-flight capture, cancel, refund and compensation
   behavior; this WP does not guess those state transitions.
4. Permission and exact Guest Session / Brand / Store authorization are resolved first. A denied or
   malformed authorization performs no Payment, Feature Control, Ordering, Audit or Provider read.
5. After authorization, Payment computes the permanent operation digest and resolves its own
   operation record before evaluating the Kill Switch. An exact committed replay remains readable
   when the switch is active or unavailable and never creates another Attempt or Provider call.
   A changed replay remains an idempotency conflict.
6. A genuinely new operation reads one authoritative server clock instant after authorization and
   exact replay resolution, then requests one evaluation for the exact key, action, Brand, Store and
   that current UTC instant. It never evaluates against the caller-carried request instant. The
   evaluation request contains no operation, Guest, Actor, Payment or raw rollout-subject reference;
   the Feature Control adapter owns its precomputed opaque bucket. The command accepts no client
   control key, definition, bucket, state, mode, version or decision.
7. Payment accepts backend execution only from an immutable, internally consistent WP-0120
   `KillSwitch` evaluation whose effective Brand scope matches the authorized Brand or whose Store
   scope matches the exact authorized Brand + Store. Key, version, scope kind, evaluation instant,
   backend result, reason and bounded evaluation record must agree.
8. Only `KILL_INACTIVE` and `KILL_RECOVERY_ALLOWED` may admit new work. `KILL_ACTIVE` and
   `KILL_RECOVERY_BLOCKED` deny it. `CONTROL_UNAVAILABLE`, a Release Flag result, missing effective
   control, stale/scope-mismatched/mutable/extra evidence, a frontend/backend mismatch or dependency
   failure fails closed. All such outcomes map to one bounded Payment-disabled error so callers do
   not receive an active-versus-unavailable control oracle. Frontend visibility is never
   authorization.
9. Every active mode blocks new Payment work. `BlockNew`, `SafePause` and `Terminate` plus their
   in-flight policy are returned only as bounded internal control evidence; no mode permits a new
   intent and no public error reveals control ID, owner, version, scope, rollout or recovery detail.
10. An admitted decision is checked before Ordering preparation, Audit composition, Payment claim or
    Provider invocation. A denied/unavailable decision leaves no new Payment or Ordering fact and
    performs no Provider call.
11. The Kill Switch never rewrites or deletes an Intent, Attempt, Provider observation, terminal
    fact, reconciliation result, Audit or Event. Existing `Processing | Unknown` operations remain
    recoverable through WP-1307 reconciliation rather than being declared failed by the switch.
12. Verified webhook acceptance, terminal truth mapping, status projection and reconciliation are
    recovery/source-truth paths and are not disabled by `payment.provider.admission`. Blocking them
    would hide a charge or prevent recovery and is prohibited.
13. This WP creates no table, migration, Feature Control store, production route/UI, Stripe SDK,
    Provider configuration, scheduler, capture/cancel/refund action or real operational control.
14. Logs, metrics, errors, URLs and analytics may expose only the Payment action and stable bounded
    allow/deny/unavailable reason. Control identifiers, Tenant/Store identifiers as metric labels,
    rollout subject/bucket, Actor/Guest identity, Provider data, Payment method detail, secrets and
    unnecessary PII are prohibited.

## Risks, rollback and boundaries

- Risk: gating idempotent replay would hide a committed external outcome. Mitigation: exact replay
  resolution precedes the new-work gate and never reinvokes Provider.
- Risk: a UI hint or malformed cross-Store result grants execution. Mitigation: backend decision and
  all exact key/scope/version/reason invariants are revalidated; invalid evidence denies.
- Risk: a broad switch blocks truth/recovery processing. Mitigation: only the new-intent admission
  path is gated; webhook, terminal and reconciliation services remain unchanged.
- Rollback: remove the Payment integration and manifest/dependency declaration while preserving all
  previously committed Payment facts. No data rollback or history edit exists.
- External Evidence: real persisted controls, runtime Permission/Audit composition, activation and
  recovery drills, Stripe account behavior, production telemetry and incident evidence remain
  gated and unclaimed.
- Authorization boundary: local code, synthetic tests and repository documentation only. No real
  control activation, credential, Provider/cloud mutation, deployment or non-local data action.
