# WP-2151 — Delivery Detail, address / promise snapshot and controlled revision

## Authority and scope

- Handoff Sections 34.17–34.40 define immutable operational snapshots, append-only Fulfillment
  Revision, critical revalidation, requested/confirmed windows and capacity evidence. Section 88.10
  defines `FUL-DELIVERY-DETAIL` at `/operations/delivery/:id`.
- This WP extends `@rms/fulfillment` with runtime-inactive snapshot/revision contracts and a strict
  field-masked detail UI. It does not invent a real address, geocode, Customer contact, price,
  Provider acceptance or capacity result.

## Acceptance criteria

1. The original address/promise snapshot is immutable and keeps stable Address, geocode, contact,
   fee/tax, requested/confirmed window and capacity evidence references.
2. Revisions are append-only, exact-version and reasoned; rejected revisions preserve the current
   effective snapshot and their validation evidence.
3. Critical address/window/verification changes require fresh Address, service-area, ETA, Pricing,
   Capacity and, when applicable, Provider/Manager/Order-amendment evidence.
4. Terminal Task/Fulfillment phases and revisions at/after cutoff fail closed. In-progress critical
   revision requires Manager and current Provider/Task acceptance.
5. The Delivery Detail projection exposes only masked address/contact data and safe references, with
   stale/partial views read-only and commands permission/purpose scoped.
