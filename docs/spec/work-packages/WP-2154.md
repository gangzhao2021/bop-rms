# WP-2154 — Delivery Exception Workbench / reroute / cancellation / support

## Authority and scope

- Handoff Sections 34.73–34.90 define delay/completion/custody exceptions, reattempt, return,
  disposition and final-failure evidence. Section 88.10 defines `FUL-DELIVERY-EXCEPTION` at
  `/operations/delivery/exceptions`.
- This WP adds runtime-inactive exception/remedy contracts to `@rms/fulfillment` and a strict
  operational workbench. It coordinates owning-domain facts without deciding Refund, Order cancel,
  Kitchen remake, Inventory replacement/disposal or Customer compensation.

## Acceptance criteria

1. Exceptions are append-only with lifecycle/severity separate, one active completion exception per
   Task, explicit owner/SLA/customer-impact and normalized reason evidence.
2. Reattempt/reroute requires a new sequence, address/instruction/customer availability, window,
   capacity, freshness, assignment and proof-policy evidence; it never creates a new Task.
3. Return-to-Store and disposition remain separate; only validated return and owner-issued downstream
   action finality permit resolution/finalization.
4. Cancelled-by-Ordering, Delivered-on-Reattempt and final Failed resolutions require their owning
   final facts. Exhaustion cannot be inferred from one failed attempt or unresolved exception.
5. Workbench filters/actions are permission, purpose, expected-version and freshness gated; safe refs
   only, stale/partial views read-only, and support handoff never exposes unnecessary PII.
