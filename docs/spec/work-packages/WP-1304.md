## Purpose

Durably accept one already verified Stripe Event before acknowledging delivery. Enforce one
Provider Account + Provider Event ID receipt, preserve bounded restricted raw evidence, and expose
a transaction-owned Inbox processing boundary whose successful effect and completion marker commit
together. Duplicate, delayed and out-of-order delivery must not duplicate a later Payment effect.

## Closed execution contract

1. Input is exactly WP-1303's `VerifiedProviderWebhook`; this WP accepts no signature header,
   secret, route-supplied Tenant scope, browser status, client amount or unverified Provider object.
2. The service copies and revalidates the immutable verified envelope and raw bytes before a write.
   Provider/environment/account/Brand/Store/Event identity, timestamps and SHA-256 evidence digest
   must agree; invalid or mutated evidence fails closed.
3. Payment owns one immutable `provider_webhook_record` and separately erasable restricted raw
   evidence. Acceptance persists both atomically before a success acknowledgement. No Payment,
   Order, ledger, Event or Projection fact is changed by receipt acceptance.
4. The database uniqueness key is Provider + environment + Provider Account + Provider Event ID.
   The route/account input is not a Tenant key. Concurrent first delivery creates exactly one
   receipt; a same-key/same-digest delivery is `Duplicate`; same-key/different-digest is a security
   conflict and never replaces accepted bytes or metadata.
5. `Accepted` and matching `Duplicate` return a transport-neutral `Acknowledge` result suitable for
   Provider `2xx`. Dependency failure, invalid evidence and identity/digest conflict return no
   acknowledgement. The Controller never waits for Payment mapping and never equates receipt with
   financial success.
6. Raw evidence is Restricted, non-queryable through public contracts and expires 30 days after
   receipt unless a separately authorized hold exists. The immutable receipt/dedupe fact expires no
   earlier than 90 days. Cleanup may erase only expired raw bytes; it never deletes or rewrites the
   receipt, normalized Payment, Audit or legal-hold fact.
7. Processing uses a stable Payment webhook Consumer identity and a caller-owned transaction. The
   processor receives one immutable receipt plus an owned raw-byte copy; a successful mapper effect
   and completion marker commit atomically. Failure rolls both back and remains replayable.
8. Completion uniqueness is receipt + Consumer identity. Concurrent or repeated processing returns
   the existing completion and never re-runs a committed mapper effect. Events are independent: no
   arrival-order cursor or Provider timestamp may block an older/later event.
9. Manual/system replay calls the same processing boundary. It never edits the accepted payload,
   clears completion, manufactures a new Provider Event ID or bypasses idempotency. Eligibility,
   retry scheduling, dead-letter UI and operator permission remain later work.
10. Audit/telemetry expose only bounded scope references, safe state/reason codes, timestamps and
    evidence digest. Raw payload, signature, secret, Provider message, PAN/payment-method detail,
    PII and exception text are prohibited from logs, errors, metrics, analytics and public output.
11. WP-1305 owns mapping verified evidence into authoritative PaymentSucceeded/PaymentFailed facts
    and Events. WP-1306+ own projection, reconciliation and operational screens. This WP supplies
    only the idempotent Inbox boundary and a synthetic mapper acceptance proof.
12. No public HTTP deployment, Stripe API call, real account/credential, Provider retrieval,
    Payment state mutation, Order progression, ledger, refund, reconciliation job, UI or production
    retention execution is authorized.
