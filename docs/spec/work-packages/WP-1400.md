## Purpose

Create the smallest Kitchen-owned, contract-first consumer for the frozen Ordering-owned
`OrderConfirmed.v1` business fact. The new Phase-1 `@rms/kitchen` package validates the exact
producer contract, declares consumer `kitchen.confirmed-order:v1`, authorizes the System intake,
coordinates Store-scoped Inbox idempotency and delegates one immutable confirmed-order intake
receipt to an injected Kitchen-local transaction port.

This Work Package is runtime-inactive. It introduces no Kitchen Ticket、Work Item、Station、routing、
queue、Kitchen Event、migration、database adapter、Worker registration or live Store / Payment flow.
WP-1401 owns the first Ticket / Work Item Aggregate and persistence increment; WP-1402 owns Station
routing. The contracts and synthetic acceptance matrix are executable without claiming those later
facts exist.

## Closed execution contract

### Module and consumer identity

1. New Module `@rms/kitchen` is owned by the Kitchen Engineering Owner. Its synchronous code
   dependencies are limited to public `@bop/eventing` and `@rms/ordering` exports. It owns future
   schema metadata `rms_kitchen` but owns zero tables in WP-1400.
2. The Module Manifest consumes only `rms.ordering.order-confirmed.v1`, publishes no Event, owns no
   Job, Feature Flag or Kill Switch and classifies its bounded fields as `indirect_identifier`.
3. Consumer registration is exact: name `kitchen.confirmed-order:v1`, version `1`, Event
   `OrderConfirmed@1`, owner `@rms/kitchen`, Tenant scope `store`, ordering `none`, side effect
   `accept_confirmed_order` and replay safety `true`.
4. Ordering is `none` because Kitchen subscribes to only one Ordering Aggregate Event subset and
   cannot require unconsumed Order versions to arrive. Independent confirmed Batches tolerate
   delivery reordering while exact Batch/confirmation semantic keys prevent duplicate intake.

### Strict intake and authorization

5. Input is `unknown` until parsed by the integrated public `parseOrderConfirmedEnvelope`. The
   consumer accepts only the exact Ordering producer, System actor, Store scope, `Order` aggregate,
   `aggregateId == orderReference`, positive aggregate version, exact confirmation/Order/Batch
   references, canonical SHA-256 source digest and `occurredAt == confirmedAt` UTC binding.
6. Parse succeeds before durable side effects. The application coordinator `service.consume` then
   requires an injected System authorization for action `ConsumeConfirmedOrder`, purpose
   `CreateKitchenIntake` and the exact Brand、Store、Order、Batch、confirmation、source Event and
   observed UTC instant before it invokes generic Inbox. The public Consumer Registration handler
   does not trust that facade: on a first delivery it independently performs the same strict parse →
   System authorization → process sequence inside the shared transaction. Both paths delegate to one
   authorized internal handler; `service.consume` calls it after its own authorization and does not
   authorize twice. Denial or dependency failure leaves no durable Inbox or Kitchen effect. A
   completed duplicate skips the public handler under the accepted WP-0032 contract.
7. The immutable Kitchen intake receipt binds consumer name/version, source Event reference, Brand,
   Store, Order, Batch, confirmation, source aggregate version, source snapshot digest, confirmed UTC
   instant, correlation and one canonical `semanticEventBindingDigest` formatted exactly as
   `sha256:<64 lowercase hex>`. The application computes that digest transiently from the canonical
   input `{ consumerName, consumerVersion, sourceEventWithoutEventId }`, where
   `sourceEventWithoutEventId` is the normalized projection of every parsed envelope and payload
   field except `eventId`, which the receipt stores separately as `sourceEventReference`. The digest
   therefore covers consumer identity and Event type/version/time/producer/scope/Aggregate/version/
   correlation/causation/System actor/payload/classification/replay metadata and makes a different
   delivery Event ID replayable only when the complete causal business fact is otherwise identical.
   The receipt does not copy `causationId`: the immutable retained source Event remains its authority,
   while the non-reversible digest covers the causal binding. It contains no Item, Customer, Guest,
   Staff, note, allergy/health, Payment, Provider or money field.

### Transaction, idempotency and recovery

8. The caller supplies one Kitchen-local `ConsumerTransaction`. The Kitchen port is explicit:
   `resolveByIdentity({ brandReference, storeReference, sourceEventReference,
confirmationReference, orderBatchReference, transaction })` simultaneously resolves the source
   Event、scoped confirmation and scoped Batch keys and returns only `NotFound |
Resolved(receipt: unknown) | Conflict`. `NotFound` means no key resolves; `Resolved` means one or more
   keys resolve to the same receipt; keys that resolve to different receipts are always `Conflict`.
   `accept({ receipt, transaction })` returns only `Created(receipt: unknown) |
AlreadyAccepted(receipt: unknown) | Conflict`. The persistence port never receives the full envelope
   or its Payment-event causation reference. Every success receipt remains `unknown` until strict
   parsing and the applicable exact comparison succeed.
9. The `service.consume` coordinator performs strict parse and authorization, exact multi-key
   `resolveByIdentity` preflight, the generic WP-0032 Inbox operation with the authorized internal
   handler, then an exact `resolveByIdentity` postcondition in the same Kitchen-local transaction.
   The internal handler calls `accept`; `Created` must equal the attempted receipt in every field.
   `AlreadyAccepted` must return the original receipt with every event-ID-independent semantic field
   and `semanticEventBindingDigest` exact; it retains the original `sourceEventReference` and creates
   no Event-ID alias or second effect. Inbox completion without one exact resolved effect、an effect
   without the matching Inbox path、multi-key disagreement or a commit-unknown drift fails closed.
   No transaction spans Ordering and Kitchen and no foreign Repository or table is queried.
10. The handler returns `completed` with no `resultHash`, so accepted WP-0032 persists
    `consumer_inbox.result_hash = null`. `semanticEventBindingDigest` remains only on the Kitchen
    receipt; Order/Batch/confirmation/full-Event fingerprints are not copied into the generic Inbox
    discriminator.
11. Primary delivery idempotency is exact `consumerName + eventId`. Semantic uniqueness is exact
    `Brand + Store + confirmationReference` and exact `Brand + Store + orderBatchReference` so one
    confirmed Batch cannot later materialize a second Ticket.
12. WP-0030 makes one Event ID an immutable Event fact and WP-0032 intentionally lets a completed
    `ConsumerDeliveryWorker` duplicate return from Inbox before the business handler. Therefore the
    raw Worker path proves only zero second effect for that Event ID; it does not inspect content,
    prove equality or rerun authorization. Event equality is the upstream WP-0030 invariant and
    completed-duplicate suppression is the WP-0032 delivery-idempotency invariant. This does not
    weaken the public registration handler's independent parse and authorization on first delivery.
13. A different Event ID reusing the same confirmation or Batch semantic key returns the original
    receipt only when the normalized envelope differs solely by `eventId`, every persisted semantic
    receipt field and the event-ID-independent `semanticEventBindingDigest` are exact, and all
    resolved keys identify that original receipt. It retains the original `sourceEventReference` and
    creates no alias or second effect. Any other changed scope、Order、version、digest、time or causal
    envelope field conflicts.
14. A possible commit-unknown retry re-enters the coordinator, resolves all identities and verifies
    the exact receipt before any new attempt. Changed/unavailable evidence or Inbox/effect drift
    fails closed.
15. Temporary dependency failure maps to platform `CONSUMER_TEMPORARY_FAILURE` and relies on the
    existing Eventing retry / dead-letter contract. Schema、authorization or semantic rejection is
    non-retryable and uses a bounded safe code. WP-1400 creates no scheduler、timer、lease or custom
    retry store.
16. Public service results are limited to `Accepted | AlreadyAccepted`. Public errors are limited
    to `KITCHEN_CONFIRMED_ORDER_INPUT_INVALID | KITCHEN_CONFIRMED_ORDER_PERMISSION_DENIED |
KITCHEN_CONFIRMED_ORDER_CONFLICT | KITCHEN_CONFIRMED_ORDER_DEPENDENCY_UNAVAILABLE`, with bounded
    messages that reveal no object existence.

### Ownership, privacy and non-goals

17. Ordering owns confirmation truth and Event retention; Eventing owns Inbox/retry controls;
    Kitchen owns only its consumer and immutable intake receipt contract. WP-1400 creates no mutable
    Aggregate、expected-version write、Outbox Event or human Command.
18. Event ID、Order、Batch、confirmation、correlation and digests are indirect identifiers. They are
    prohibited from logs、URLs、analytics、metric labels、screenshots and non-synthetic fixtures.
    Causation remains only in the retained immutable source Event and is never copied into the
    Kitchen intake receipt. Metrics may use only bounded consumer/version/outcome/error buckets.
19. Source Event retention, Inbox completion metadata and immutable receipt provide this System intake's
    correlation trail. Ticket creation Audit、Outbox and lifecycle behavior must be closed by
    WP-1401 rather than invented here.
20. No migration、SQL、database catalog/config/count、database-access manifest、Ordering producer
    change、Event Catalog schema/generated artifact change、API/UI、Worker composition、Provider SDK、
    credential、external resource、deployment or non-local data action is authorized.

## Acceptance and evidence map

1. Producer compatibility: the integrated WP-1310 canonical envelope passes; extra fields、
   accessors、custom prototypes、wrong producer/type/version/actor/scope/aggregate/time/digest fail
   before a port observes the value.
2. Registry: `ConsumerRegistry` accepts the exact registration and rejects an unknown consumer、
   Event or schema version; Module Manifest/Event Catalog consumer identity remains aligned without
   changing the frozen Event schema.
3. Authorization: `service.consume` checks the exact action/purpose/scope exactly once before Inbox
   and delegates to the already-authorized internal handler without authorizing twice. On a direct
   first delivery, the public registration handler independently strict-parses、authorizes and only
   then processes; deny/throw rolls back the processing marker, makes zero `accept` call and persists
   zero Inbox completion or Kitchen effect.
4. Port contract: `resolveByIdentity` checks all three identities simultaneously; no match is
   `NotFound`, one shared receipt is `Resolved`, and keys resolving to different receipts are
   `Conflict`. `Created` and `AlreadyAccepted` receipt values remain `unknown` until strict parsing;
   `Created` is exact in every field and `AlreadyAccepted` is exact on the event-ID-independent
   semantic projection. The `accept` port receives only the strict receipt and shared transaction,
   never the source envelope.
5. Happy path: one caller-owned transaction records one Inbox completion and one exact receipt;
   receipt `semanticEventBindingDigest` is `sha256:<64 lowercase hex>`, the handler returns completed
   without `resultHash` and Inbox `result_hash` is `null`.
6. Same-ID replay: under the separate WP-0030 immutable Event and WP-0032 Inbox invariants, a raw
   Worker completed duplicate skips its handler and produces zero second effect. Tests do not claim
   that the raw path checks equality or authorization. Through `service.consume`, strict parse、
   authorization、effect preflight and postcondition are tested around the generic Inbox operation.
7. Semantic replay: a different Event ID with the same scoped confirmation or Batch and an otherwise
   identical normalized envelope returns the original receipt, retains its original
   `sourceEventReference`, creates no alias/second effect and stores a new Inbox completion with null
   `result_hash`. Any change other than `eventId`, or multiple keys resolving to different receipts,
   conflicts before a new effect.
8. Scope: missing Store、cross-Brand/Store、foreign Order/Batch/confirmation、wrong aggregate and
   malformed version/digest all fail closed without object-existence leakage.
9. Recovery: temporary failure rolls back and retries; commit-unknown redelivery executes the same
   preflight → generic Inbox → postcondition sequence, resolves one exact receipt and never creates a
   second effect. Inbox/effect drift fails closed.
10. Ordering: independent confirmed Batches succeed in either delivery order without requiring an
    unconsumed Ordering Aggregate version.
11. Boundary/privacy: tests prove zero Ticket/Work Item/Station/routing/queue/Event/migration/private
    query; the receipt excludes causation and Payment identity; only its non-reversible semantic
    digest covers the transient causal binding; generic Inbox stores no fingerprint; and Payment、
    Provider、Customer、note、allergy/health、secret or identifier-bearing telemetry fields are
    prohibited.
12. Contract chain: Eventing Inbox regression、existing Event Catalog tests、complete Ordering
    producer regression and Kitchen consumer acceptance all pass on the same candidate.

## Risks, rollback and boundaries

- Risk: `OrderConfirmed.v1` is treated as an Item snapshot or current Ordering tables are queried.
  Mitigation: retain only its opaque exact binding; WP-1401 must use a separately closed public
  snapshot Query.
- Risk: replay or a second Event produces duplicate later Ticket work. Mitigation: WP-0030 immutable
  Event identity、WP-0032 delivery idempotency、confirmation/Batch semantic uniqueness、canonical
  receipt comparison and commit-unknown recovery; raw Worker duplicate behavior is not overstated.
- Risk: absent WP-2045 is silently represented as live security acceptance. Mitigation: keep it an
  explicit live / Phase-1 gate and make this Module runtime-inactive.
- Rollback: remove the new Kitchen package、root acceptance script/workspace importer and WP-1400
  documentation. No database or business-data rollback exists because this WP creates no migration,
  persistent adapter or external effect.
- Authorization boundary: local documentation/code、synthetic tests、branch/PR/CI and the already
  user-authorized squash workflow only. No credential、Provider/cloud、deployment or non-local data
  mutation.
