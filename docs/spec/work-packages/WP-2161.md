## Acceptance contract

1. The new RMS module has a valid Manifest, public contract and architecture coverage before
   business implementation. It depends only on the BOP Publishing contract and never imports a
   source RMS Domain or private table.
2. Report Definition mutations require exact Tenant / Brand / optional Store scope, Actor, purpose,
   permission, expected aggregate version, idempotency, validation evidence and append-only Audit /
   Outbox composition. Certification requires a distinct authorized approver.
3. Every Report Version pins approved Dataset and Metric Version references, dimensions, typed
   filters, sort, visualization/table layout, row limit, Business Date/timezone semantics,
   freshness, access/export policy and effective period. Expressions, SQL, remote URLs and free-form
   recipient data are prohibited.
4. Schedule definitions pin the published Report Version, timezone, cadence, safe format and
   recipient scope reference. This WP persists scheduling intent only; WP-2162 owns Report Runs and
   artifacts, and Notification/Output owns delivery.
5. `RPT-REPORT-CATALOG` and `RPT-REPORT-BUILDER` expose exact scope, certification, owner, last-run
   summary, schedule state, lineage validation and sampled-preview metadata. Every Section 88 state
   is represented; unavailable runtime clients are visibly read-only and cannot simulate success.
6. Brand/Store RLS, append-only versions/operations/schedules, ownership metadata, migration and
   isolated database acceptance pass without inventing production data or external evidence.
