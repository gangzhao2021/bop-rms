## Acceptance

Prepared -> Acknowledged -> Activated records carry explicit DiningSessionBinding purpose,
exact admission/operation, current ContextOnly DineIn predecessor, fresh DiningBound candidate,
public context, candidate Session/Participant identity, hashed recovery proof, revision and times.
Candidate is never installed in live storage by this contract. Its fresh credentials must be
acknowledged with all three proofs while the predecessor remains current, before activation.

Activation accepts only the exact current Dining admission evidence for the predecessor Guest,
admission/operation, Store/public Table and candidate Session/Participant, evaluated after
acknowledgement and valid now. Produce an immutable owner-local CAS/Audit plan to revoke the
predecessor, install the same candidate and advance the preparation. No actual write is performed.

Completion authenticates the active candidate and its CSRF, never the consumed recovery proof
or revoked predecessor, including after preparation expiry. It preserves exact Dining binding.
It proves Identity credential continuity only; current Dining authorization remains a separate
public gate for every later command. No Host flag or Ordering authority is created.

Preparation expiry is explicit server-policy input, bounded by current predecessor deadlines
and the existing fifteen-minute technical ceiling. No production TTL or admission expiry is
invented. All command/record/evidence shapes are closed; accessor/nonplain/malformed inputs and
nonboolean proof comparisons deny with fresh bounded errors. Hashes remain hashes only.
