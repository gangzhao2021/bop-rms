## Problem and intended outcome

WP-0034 owns the immutable transport-neutral Correlation / Causation Context, but no HTTP adapter currently creates one trusted root per request or joins a Request to a distinct application Command and its emitted Event. WP-0040 owns a closed structured logger, but it does not yet accept bounded HTTP request fields.

WP-0041 delivers only:

1. a server-generated UUIDv7 `requestId` and independent WP-0034 UUIDv7 root `correlationId` for every Express request;
2. immutable explicit request-local storage with cleanup and no ambient authorization;
3. generated `X-Request-ID` and `X-Correlation-ID` on every response;
4. explicit Request → Command and Command → Event correlation helpers;
5. closed structured logging fields for validated `requestId`、bounded `durationMs`、bounded `statusCode` and accepted trusted correlation;
6. one synthetic PostgreSQL acceptance path through the existing Outbox and Consumer contracts.

## Accepted contract

### Inbound trust and HTTP behavior

- Raw browser、public client、query、body、Provider callback、proxy、`X-Request-ID` and `X-Correlation-ID` values are never trusted、continued、reflected or logged.
- Direct requests create two independent application-owned UUIDv7 values: one request attempt identifier and one correlation root. A future trusted-upstream adapter requires a separate accepted inventory、authentication/threat model and External Evidence.
- Every response carries the generated identifiers as headers. Existing health/readiness and WP-0036 Realtime bodies remain unchanged; general business response envelopes remain future endpoint-WP work.
- Stable safe errors never return Stack、SQL、headers、Cookie、Token、payload、Provider data or raw input.

### Explicit request-local and lineage behavior

- The Express adapter stores one frozen context directly on the request through a private immutable key and removes it on response finish/close.
- No `AsyncLocalStorage`、module-global mutable context、OpenTelemetry baggage or hidden ambient authorization exists.
- A Command receives its own UUIDv7. An Event emitted by that Command retains the request correlation and sets `causationId` to that immediate `commandId`.
- Retry、replay、redelivery、commit-unknown reconciliation and Consumer processing preserve existing lineage exactly.
- Request、correlation、Command and Event identifiers grant no Tenant、Store、Actor、permission or object access.

### Structured logging

- The closed logger schema adds only validated `requestId`、integer `durationMs` from `0` through `86,400,000`、HTTP `statusCode` from `100` through `599`, and the already accepted trusted correlation context.
- HTTP completion uses one closed event name and stable bounded result codes. Method、URL、query、headers、IP、Session、Token、Tenant、Store、Actor、object identifiers、free text、body、payload、SQL and bind values are absent.
- Logger validation/write failure remains isolated from HTTP and business completion.
