## Purpose

Close Feature F01.1 with a provider-neutral、synthetic API composition that proves:

1. a Tenant-scope permission does not authorize an object until the owning Domain supplies exact
   server-side object scope evidence;
2. Brand-owned objects may be used only inside the same Brand context, while Store-owned objects
   require the exact Brand and Store;
3. missing、unknown、forged、cross-Brand and sibling-Store objects fail with one bounded public
   denial and no existence oracle;
4. Store switch is a state-changing server command that authorizes the current Session and CSRF,
   resolves the target Store through the Tenant owner, re-evaluates active Membership and exact
   Store Assignment, then rotates Session and CSRF authority;
5. the former Session selector is unusable after a successful switch, while denial performs no
   rotation and grants no authority; and
6. the complete negative matrix composes accepted WP-0100–0108 public contracts without a
   cross-Domain private query or new generic repository.

This WP creates no production endpoint or UI. It provides a bounded composition contract and
acceptance evidence for later route/UI work.

## Governing decisions

1. **Exact predecessor —** implementation starts only after WP-0108 exact-head CI、authorized
   squash merge、post-merge exact-main CI and branch/resource cleanup. Baseline
   `05b1b87308f26b23bfd2efbbdea81cce0198d328` satisfies that gate.
2. **Existing owners remain authoritative —** Identity owns Session/rotation; Tenant owns
   Brand/Store facts; Membership owns Membership/Store Assignment; Permission owns action policy;
   each future business Domain owns its object and object-state facts.
3. **Composition location —** API remains the transport/composition root. No Domain may import
   another Domain's private persistence or reverse the accepted dependency graph.
4. **Object reference is not authority —** a client route/body object ID is only a lookup request.
   Authorization consumes a server-side result from an injected owning-Domain resolver.
5. **Resolver boundary —** the resolver accepts the already authenticated immutable Tenant Context、
   exact parsed business action and requested opaque object reference, then returns either one
   frozen exact scope evidence or `null`. It does not return a business object payload.
6. **Object evidence shape —** evidence carries the requested object reference、scope kind、exact
   Brand、optional exact Store and positive object version. Unknown fields、mutable evidence、
   malformed UUID/version or a mismatched returned object reference deny.
7. **Brand object semantics —** a Brand-scoped object matches the exact Brand context and may also
   match a Store context within that same Brand. It never matches another Brand.
8. **Store object semantics —** a Store-scoped object matches only the exact Brand and exact Store
   context. Brand-only context、sibling Store and cross-Brand context deny.
9. **Object state remains owned —** the injected resolver returns evidence only when the owning
   Domain's object-state preconditions permit the requested operation. WP-0109 does not invent one
   universal lifecycle vocabulary or bypass a Domain Command's expected-version/state checks.
10. **Permission remains mandatory —** exact object scope does not grant an action. Routes compose
    object-scope middleware with the accepted WP-0104/0105 deny-first Permission middleware and
    Domain Command validation.
11. **Query isolation —** the owning resolver is expected to query inside transaction-local
    server-resolved Tenant Context/RLS. It must not perform an unrestricted object lookup and then
    disclose a mismatch.
12. **Uniform denial —** missing、unknown、malformed、stale、mismatched、cross-Brand and
    sibling-Store object inputs produce the same `403 object_access_denied` response. Raw
    exception、object、Tenant or conflict detail is not exposed.
13. **Private request state —** resolved object scope is attached as a non-enumerable request-local
    value and removed on response finish/close, matching the Tenant Context cleanup pattern.
14. **Store request is not authority —** the requested target Store reference is parsed strictly,
    but no context changes until the server loads the active Store and its parent Brand and resolves
    one active exact Membership plus Store Assignment.
15. **Current Session authorization —** switch first calls the accepted same-origin/session-bound
    CSRF authorization boundary. Cookie/CSRF values remain opaque inputs and are never returned in
    errors、logs or evidence.
16. **Target re-evaluation —** the server derives Brand from the Tenant-owned Store fact; it does
    not accept a client Brand as truth. Inactive/missing Store or Brand、missing/ambiguous/inactive
    Membership or Store Assignment denies.
17. **Cross-Brand switch —** switching to a Store in another Brand is allowed only if the same
    current Workforce Actor independently has an active Membership and exact Store Assignment in
    that Brand. There is no broad “all tenants” toggle.
18. **Rotation order —** validation completes before rotation. Successful switch rotates with
    reason `StoreContextElevation`; the former Session/CSRF authority becomes unusable atomically.
    Denied validation performs no rotation.
19. **Rotated result validation —** the composition validates that the rotated Session is active、
    belongs to the same Actor、references the former Session as its predecessor and advances
    version. Invalid adapter output denies and is not presented as success.
20. **Returned context —** success returns only the rotated opaque Cookie mutation and the minimum
    canonical frozen Actor/Brand/Store Tenant Context. It does not return Membership、Role、
    Permission evidence、Provider identity or Token.
21. **No persisted authorization shortcut —** the returned Store Context supports navigation and
    Session rotation evidence only. Every later business request still resolves route resources、
    Membership/Store Assignment、Permission and object state server-side.
22. **Concurrency —** simultaneous switches from one selector allow at most the store adapter's
    single expected-version rotation winner. Losers deny; no forked Session authority is accepted.
23. **Revocation interaction —** revoked、expired、idle-expired、recovered or globally invalidated
    Sessions fail at the current Session authorization boundary. WP-0109 does not reopen WP-0108
    lifecycle policy.
24. **No audit fabrication —** synthetic tests may observe bounded calls/reasons. A real Audit
    adapter、real workforce/Tenant facts and production operational evidence remain gated.
25. **No database change —** the accepted Session、Tenant、Membership and Permission contracts
    already provide the required composition facts. No table、migration、RLS policy、runtime role or
    generic object persistence is added.
26. **No production route/UI —** `apps/api/src/app.ts`、server startup、Merchant frontend、Section 88
    Screens and Store-switch UI remain unchanged. Later route/UI WPs consume this contract.
27. **No dependency change —** implementation uses only current workspace/Node dependencies. No
    package or lockfile change is expected.
28. **Privacy and telemetry —** no raw Cookie、CSRF、Token、email、IP、object payload、PII or
    free-text reason is logged. Tenant/Store/object identifiers are not metric dimensions.
29. **External Evidence remains a gate —** real Cognito、KMS、Secrets Manager、WAF、workforce、
    Tenant/Store、staging/load/penetration and production evidence is `NOT AVAILABLE / NOT CLAIMED`.
30. **Hard stop —** any need for a new Domain/table/migration、cross-Domain private query、generic
    object repository、production route/UI、new dependency/lockfile、real Provider/credential/fact、
    external resource、weakened uniform denial or allowlist-external tracked file stops
    implementation for exact review.
