## Problem and bounded outcome

Identity proves who an authenticated Actor is；Tenant owns Brand/Store identity；Membership proves where a Workforce Actor may operate. The repository does not yet compose those public facts into a server-authoritative request context or safely bind that context to one database transaction.

WP-0103 creates the smallest executable Tenant Context boundary:

- a strict permission-free `TenantContext` owned by `@bop/tenant`;
- API middleware that consumes only an injected authenticated Actor and route parameters、revalidates active Brand/Store and resolves exactly one active Membership/Store Assignment;
- stable default-deny HTTP behavior without echoing Tenant、Actor、Session or object identifiers;
- a parameterized PostgreSQL transaction helper that applies exact Brand and optional Store with transaction-local settings only;
- synthetic positive/negative evidence for missing/wrong/ambiguous/inactive scope、request cleanup、pool reuse、parallel/failure paths and the complete current forced-RLS table registry.

This WP does not implement Role、Permission、Grant、explicit deny/allow、object authorization、real login/Cognito/BFF/Session/Cookie/CSRF、Store switch UI、Customer QR context、Platform support/break-glass、runtime role creation、migration、real Tenant/Employee data、Provider/AWS resource or production action.

## Ownership and trust boundaries

`@bop/tenant` owns the resolved Tenant Context value and its strict shape. `@bop/identity` remains the Actor authority；`@bop/membership` remains the authority for Workforce Brand Membership and Store Assignment；neither Brand/Store identity nor Membership alone grants a business action.

`apps/api` is only the composition root. It may read route parameters as requested resources but may not accept Brand/Store authority from headers、query、body、Role claims or Provider attributes. It invokes the public Identity、Tenant and Membership contracts, attaches the resolved context as a non-enumerable request-local value and never adds business rules.

`@bop-rms/database` owns only the generic PostgreSQL transaction mechanism. It accepts a previously resolved opaque scope、validates its UUIDv7 shape、uses parameterized `set_config(..., true)` inside `BEGIN`/`COMMIT`, rolls back on failure and always releases the connection. It does not resolve Tenant facts、Permissions or business objects.

## Adopted Recommended Owner Decisions

1. **One context owner —** extend the existing `@bop/tenant` public root with `TenantContext`; do not create another business Module.
2. **Permission-free value —** context contains exact Actor、Brand、optional Store、scope kind and server resolution instant only. It contains no Role、Permission、Grant、deny/allow、email、Provider subject、Token or Session secret.
3. **Workforce-only middleware —** accept only a strict active Workforce `User` Actor from an injected authenticated-actor resolver. Missing authentication returns stable `401`; invalid/inactive/non-Workforce authority fails closed.
4. **No real authentication —** the injected resolver is a port/test seam. WP-0106–0108 own Cognito、BFF、Session Store、Cookie、CSRF、MFA and revocation integration.
5. **Route resource only —** requested Brand/Store comes only from configured Express route parameters after route matching. Brand/Store headers、query and JSON body are never authorization inputs.
6. **Closed route scope —** each middleware instance is configured for exact `Brand` or `Store` scope. A Store-scoped route requires Store；a Brand-scoped route cannot silently elevate to Store.
7. **Store derives Brand —** a Store-scoped request resolves the public Store and derives its immutable Brand. If a route also contains Brand, both must match exactly.
8. **Active organization facts —** Brand and Store must exist through the public Tenant port and have lifecycle `Active`; Draft、Suspended、Archived、unknown or ambiguous facts deny.
9. **Exact server time —** use an injected server UTC canonical instant for deterministic tests and runtime `now`; client time never affects scope.
10. **Exact Membership —** Actor + derived Brand + instant must resolve exactly one active Membership through the public Membership port/resolver. Zero or multiple matches deny without revealing which fact exists.
11. **Exact Store Assignment —** Store scope additionally resolves exactly one active Assignment owned by that Membership at the same instant. Parent-inactive、zero、multiple or mismatched assignment denies.
12. **No implicit fallback —** no default Brand、last Store、first Membership、single-row shortcut、email domain、Provider group or route-only authorization exists.
13. **Strict context construction —** `@bop/tenant` revalidates the public Identity Actor、Brand and optional Store objects；all inputs are closed、plain and accessor-safe.
14. **Request-local storage —** middleware attaches context through a private symbol as non-enumerable/read-only and deletes it on response finish/close. Missing context access throws a stable internal code.
15. **Safe HTTP errors —** only closed `authentication_required` / `tenant_context_denied` responses are emitted；no raw exception、database detail、Actor/Tenant/Store/Membership ID or existence distinction is returned.
16. **No automatic logging —** middleware and transaction helper add no identifier-bearing log、metric or span dimension. Existing Correlation ID remains the safe diagnostic join key.
17. **Middleware mounting —** public health/readiness/realtime routes remain unchanged. Future protected routes explicitly mount the correct Brand/Store middleware before Permission evaluation.
18. **Permission remains mandatory later —** successful Tenant Context means “where this Actor has active membership,” not “what this Actor may do.” WP-0104 must still decide the action and WP-0109 the object.
19. **Transaction-local only —** every scoped database operation runs inside an explicit transaction and sets `bop.brand_id` plus `bop.store_id` (empty string for no Store) using parameterized `set_config` with `is_local=true`.
20. **Persistent SET prohibited —** no session-level `SET`、connection-string option、pool hook、global variable or AsyncLocalStorage value may establish RLS authority.
21. **Fail-closed missing context —** absent/invalid settings leave helper functions null/error and forced-RLS returns zero rows or denies writes；the helper never invents a scope.
22. **Pool cleanup —** commit、rollback、callback failure、database failure and release paths prove the next borrower receives no Tenant setting.
23. **Parallel isolation —** simultaneous Brand/Store transactions on separate pooled connections remain exact and cannot observe one another's rows.
24. **Prepared and reused connection evidence —** prepared statements and max-one-connection reuse are exercised across different contexts to prove scope is evaluated per transaction.
25. **No nested transaction claim —** helper owns one top-level transaction. Nested savepoint composition is rejected/not exposed in this increment rather than silently reusing a foreign transaction.
26. **Callback error preservation —** business callback errors trigger rollback and remain the caller-visible error；connection/acquire/context/commit failures map to stable safe infrastructure codes.
27. **Current RLS registry closure —** acceptance enumerates the exact 14 current forced-RLS tables and fails on drift. Existing dedicated positive/negative suites are composed for Audit、Eventing、Tenant、Operating Entity and Membership tables.
28. **No migration or grants —** existing helpers and RLS policies are reused unchanged. No schema/table/policy、login、runtime role、credential、`BYPASSRLS` or broad grant is created.
29. **Synthetic fixtures only —** tests use opaque UUIDv7 values and synthetic labels；no real Customer、Employee、Store、email、Session、Provider or production record.
30. **Background jobs later —** the generic transaction helper supports one explicit scope per transaction, but Worker orchestration、support access、cross-Tenant jobs and reporting are owned by their later WPs.
31. **External Evidence stays gated —** real Session authority、production pool configuration、runtime grants、load/performance and multi-Tenant production evidence are not represented as passed.
32. **Future extension requires review —** Customer public Store context、Platform context、Brand-less global actions、multi-Store operation or cross-Tenant support requires the owning accepted contract and cannot widen this middleware silently.

## Security、privacy、risk and rollback

- **Arbitrary route ID becomes authority:** the route identifies only a requested resource；active Store/Brand、Membership and Assignment must all resolve server-side.
- **Identity grants business access:** Identity supplies only an active Workforce Actor. Tenant Context grants no action；Permission evaluation remains mandatory.
- **Store crosses Brand:** Store's public immutable Brand is authoritative；optional Brand route value must match；Membership and Assignment are resolved against the same Brand.
- **Ambiguity chooses first:** existing exact resolvers deny zero/multiple results；middleware never sorts or picks a fallback.
- **Context leaks through request/pool:** request symbol is deleted on finish/close and PostgreSQL context is transaction-local with rollback/release/reuse/parallel evidence.
- **Persistent session scope:** session-level `SET` and connection hooks are prohibited；acceptance inspects executed SQL and post-transaction settings.
- **Existence/PII leakage:** all denial paths return generic stable errors and no identifiers are logged、echoed、placed in metrics or stored in analytics.
- **Permission confusion:** context types contain no action、Role or grant and docs/tests assert the explicit WP-0104 boundary.
- **Rollback:** before shared integration, Git revert removes the provider-neutral code. No migration or external resource exists. After consumers adopt the public context, compatibility follows additive public-contract evolution；database helper changes require pool-leak regression before release.
