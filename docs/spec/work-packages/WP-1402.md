## Purpose and bounded outcome

WP-1402 replaces WP-1401's synthetic final-plan test double with the smallest
real Kitchen-owned work-plan producer. The producer validates exact,
version-pinned Recipe preparation evidence and exact Kitchen Station/routing
evidence, applies one closed Phase-1 single-Station rule, and returns the
existing immutable `KitchenWorkPlan` consumed by WP-1401.

The bounded outcome is deliberately a pure planner:

- every exact Ordering source item receives one Recipe-owned preparation
  snapshot and one Kitchen-owned Station/routing snapshot;
- one active Store Station handles every prepared item only when its declared
  capabilities cover all preparation requirements;
- the same receipt, source and evidence produce the same plan reference,
  timestamp, version and digest across retries and concurrent attempts; and
- missing, ambiguous, malformed, stale, cross-scope or incapable evidence
  produces no plan and therefore no Ticket, Work Item, action, Audit or Event.

WP-1402 creates no Station or Routing Rule authoring Aggregate, database table,
migration, API, UI, Event, Audit record, Worker registration or Recipe business
implementation. Real configuration and Recipe adapters remain gated evidence
sources. The existing WP-1401 Ticket transaction remains the only business
mutation in this path.

## Resolved authority, precedence and ownership

1. **Release fact.** The integrated `OrderConfirmed.v1` contract remains the
   later accepted release fact for F14.1. WP-1402 does not revive the older
   `OrderBatchReleasedToKitchen` wording or create a second release Event.
2. **Kitchen ownership.** Handoff Section 26.7 makes Kitchen the owner of Store
   Station, Routing Rule, the route decision and Work Item formation. The
   planner and its consumer-side routing evidence contract therefore remain in
   `@rms/kitchen`.
3. **Recipe ownership.** Sections 29.1, 29.6 and 29.7 make Recipe the owner of
   Recipe versions, Preparation Steps, instructions and required capabilities.
   WP-1402 accepts a strict, injected Recipe-owned evidence boundary; it does
   not create `@rms/recipe`, reconstruct Recipe from Catalog, or implement
   Recipe selection/modifier/business rules inside Kitchen.
4. **Phase-1 minimum.** Section 44.12 expressly permits a single Station and
   defers complex Routing. Section 44.17.2 defers multi-Station Routing. The
   only WP-1402 selector is therefore the closed
   `{ kind: "AllPreparedItems" }` selector for one exact Store Station.
5. **Unavailable selectors.** WP-1401's accepted planning source contains SKU
   and selected Option references but no Category, Order Type or Recipe Step
   graph. Section 26.7 says routing may use those facts; it does not require
   them in this minimum. WP-1402 does not add them, query current Catalog or
   Ordering, or infer them from other fields.
6. **Snapshot authority.** The routing and Recipe configuration effective at
   the exact accepted release instant is frozen into the existing WP-1401
   Station/routing and Preparation snapshots. Later configuration changes
   cannot rewrite a durable Ticket.
7. **Persistence boundary.** Section 50.21's Phase-1 Kitchen mapping contains
   the three tables already delivered by WP-1401. Those tables already retain
   the plan, Station/rule and Preparation snapshot fields. WP-1402 adds no
   source configuration table or projection and does not change the database
   ownership manifest.
8. **Operational and safety boundary.** WP-1403 owns the Kitchen Queue
   Projection, WP-1404 owns lifecycle Commands, WP-1405 owns realtime hints,
   WP-1406 owns Ready Events, WP-1407 owns structured allergen assistance and
   named-operator acknowledgement, and WP-1408 owns KDS continuity. Producing a
   plan does not authorize Start, Ready, Fulfillment or a food-safety claim.

## Closed execution contract

### Internal integration and authorization

1. The planner is an internal implementation of WP-1401's existing
   `KitchenTicketCreationPorts.plans.resolve({ receipt, source })` port. It is
   not a public facade, HTTP handler, Worker registration or independently
   invocable business Command.
2. WP-1400 and WP-1401 already strict-parse and authorize the System intake
   before the plan port is reached: `ConsumeConfirmedOrder / CreateKitchenIntake`, followed by the Ordering-owned
   `ResolveConfirmedOrderKitchenSource / CreateKitchenWork` query. WP-1402
   reparses its receipt and planning-source input but does not duplicate that
   authorization or introduce a second Permission decision.
3. Evidence-port request metadata is a least-privilege authorization intent,
   never authentication proof:

   - the Station request contains only System actor with null actor reference,
     action `ResolveKitchenStationRoutingEvidence`, purpose
     `CreateKitchenWork`, Brand, Store and `effectiveAt`; and
   - the Recipe request contains only System actor with null actor reference,
     action `ResolveRecipePreparationEvidence`, purpose `CreateKitchenWork`,
     Brand, Store, `effectiveAt`, source-evidence reference/version/digest and
     the complete lossy `KitchenPlanningSource.items` set.

   Neither request contains Order, Batch, confirmation, correlation, source
   Event, Ordering snapshot, Customer note, localized display narrative or
   health data. Each owning adapter must strict-parse its request and use the
   trusted runtime/service identity to final-authorize the exact action,
   purpose and scope before reading its source. Deny or authorization failure
   performs zero source read and returns no evidence. These are internal
   owner-read intents, not human Permission seeds or a new public planner
   authorization result. A future standalone facade, endpoint or human action
   requires a brief refresh with an explicit Permission and error mapping.

4. The existing WP-1401 boundary maps a thrown plan dependency to
   `KITCHEN_TICKET_DEPENDENCY_UNAVAILABLE`; WP-1402 does not claim a new public
   planner `PERMISSION_DENIED` or reveal whether a Station, rule or Recipe
   exists. Invalid or non-unique evidence returns no plan. No cause detail
   enters an error, log, URL, metric label or analytic payload.

### Exact release and source binding

5. `effectiveAt` is exactly `receipt.confirmedAt`. It is both the accepted
   release instant and the only instant at which Recipe and Station/routing
   evidence is resolved. Caller time, wall-clock time, Event-processing time
   and current mutable configuration cannot select a branch.
6. The receipt and `KitchenPlanningSource` must agree exactly on their five
   shared business identities: Brand, Store, Order, Batch and confirmation.
   The receipt's Ordering `sourceSnapshotDigest` and the planning source's
   `sourceEvidenceDigest` are deliberately different anchors and must never be
   equated or aliased. The planning source preserves the independently
   validated source-evidence reference/version/digest supplied by WP-1401 and
   remains one to 100 contiguous, uniquely identified items. Any shared-scope
   mismatch returns no plan before an evidence port is called.
7. Evidence values remain `unknown` until strict parsing. Parsers are exact,
   accessor-safe and deeply freeze accepted data. Extra or symbol keys, custom
   prototypes, accessors, non-enumerable substitutions, mutable collections,
   non-canonical references/digests/instants/text and duplicate set members are
   rejected without executing an accessor.

### Recipe preparation evidence

8. The injected preparation port returns one strict
   `KitchenPreparationEvidenceSet` for the exact request. The set binds:

   - one evidence reference, positive evidence version and canonical SHA-256
     evidence digest;
   - exact Brand, Store and `effectiveAt`;
   - exactly one item for every planning-source item and no extra or duplicate
     item; and
   - no Customer note, localized display narrative, Customer/Guest/Staff,
     health/allergen narrative, Money, Payment or Provider field.

9. Every preparation-evidence item binds the exact Order Item, source ordinal,
   source quantity, Product, Product Version, SKU, Menu Version, source-line
   digest and complete selected Option reference/quantity set from the planning
   source. It also contains:

   - one opaque Preparation reference and positive Preparation version;
   - one opaque Recipe-owned Preparation digest anchor whose canonical
     SHA-256 shape is validated but whose owner binding is not recomputed or
     interpreted by Kitchen;
   - one to 32 NFC-normalized plain-text instructions using the existing
     maximum of 500 Unicode code points per instruction; and
   - zero to 32 sorted, unique, opaque required Station-capability references.

10. `preparationDigest` remains an opaque Recipe-owned version anchor; Kitchen
    validates its shape but neither recomputes nor interprets its owner
    binding. After final authorization, the Recipe-owning adapter guarantees
    that the Preparation reference/version/digest, instructions and required
    capabilities form one published and effective Recipe-owned fact. Kitchen
    recomputes only its consumer-side Preparation-set evidence digest over the
    fixed-order record `{ evidenceReference, evidenceVersion, brandReference,
storeReference, effectiveAt, normalizedItems }`. Every normalized item includes its exact
    source binding, opaque Preparation reference/version/digest, instructions
    and required capabilities. Missing, extra, duplicate, cross-scope,
    future-time, malformed or changed evidence returns no plan.

### Station and routing evidence

11. The injected Kitchen configuration port returns one strict
    `KitchenStationRoutingCandidateSetEvidence` bound to an evidence reference,
    positive evidence version, canonical evidence digest, exact Brand, Store
    and `effectiveAt`. Its candidate array is bounded to zero through 100
    entries, normalized by Routing Rule reference and rejects duplicate Rule
    references.
12. A candidate contains exactly these business fields:

    - Station reference, positive Station version and status
      `Active | Inactive`;
    - zero to 32 sorted, unique, opaque Station-capability references;
    - Routing Rule reference, positive Routing Rule version and status
      `Active | Inactive`;
    - the exact selector `{ kind: "AllPreparedItems" }`;
    - the exact target Station reference; and
    - a canonical Routing Rule digest.

13. The Routing Rule digest is recomputed over Brand, Store, `effectiveAt`,
    rule reference/version/status/selector, target Station reference and the
    selected Station reference/version/status/capabilities. Changing a Station
    version or capability therefore changes the retained rule digest even
    though the existing WP-1401 snapshot intentionally exposes no separate
    Station-version field.
14. The candidate-set evidence digest is recomputed over the fixed-order record
    `{ evidenceReference, evidenceVersion, brandReference, storeReference,
effectiveAt, normalizedCandidates }`. Every reference array, capability
    set and normalized evidence set uses lowercase canonical UUID strings in
    code-unit/ASCII ascending order with fixed field order; locale comparison,
    current-locale behavior and insertion order are prohibited. Resolution
    requires exactly one candidate, one active Station, one active rule, an
    exact target-to-Station match and full capability coverage for every
    preparation item. Zero or multiple candidates, an inactive object, target
    mismatch or any required capability absent from the Station returns no
    plan. There is no fallback, priority, wildcard, hidden tie-break or guessed
    default.

### Deterministic plan composition and replay

15. The output uses the unchanged WP-1401 `KitchenWorkPlan` and
    `KitchenWorkPlanItem` contracts. It contains exactly one item per source
    item, no extra/duplicate item, `splitOrdinal: 1`, the accepted Station and
    Routing Rule reference/version/digest, and the exact Preparation
    reference/version/digest/instructions.
16. The planner derives `planReference` from the purpose
    `KitchenWorkPlan` plus exact Brand, Store, Order, Batch and confirmation
    only. It never uses random data, a job/run ID, wall-clock bucket,
    configuration version or evidence digest as identity. The returned value
    must be a canonical UUIDv7 and distinct from every receipt, source,
    evidence, item, Product, SKU, Menu, Option, Preparation, Station and
    Routing Rule reference observed in the attempt; any namespace collision
    returns no plan.
17. `planVersion` is exactly `1` and `generatedAt` is exactly
    `receipt.confirmedAt`. The planner does not call a clock. It computes
    `planDigest` through the existing canonical
    `createKitchenWorkPlanDigestBinding` and the injected SHA-256 port.
18. The same receipt, planning source and evidence must return a byte-identical
    plan across repeat, concurrent and possible commit-unknown attempts.
    Changed Recipe, Station or rule evidence retains the stable plan reference
    but changes the plan digest, so WP-1401's accepted pre-commit conflict and
    post-commit immutable-snapshot replay behavior remains authoritative.
19. A complete durable WP-1401 Ticket remains the post-intake authority. Its
    replay performs zero planner, Recipe, routing-source, reference or digest
    dependency call and can never be rewritten by current configuration.

### Privacy, effects and public boundaries

20. The planning source is already deliberately lossy. Customer note and
    localized display names stay inside WP-1401's Kitchen execution snapshot
    composition and never cross either WP-1402 evidence port. Recipe
    instructions are configuration narrative, not Customer narrative; they
    must contain no secret, personal/health data or external locator.
21. The final Ticket remains `Restricted` because WP-1401 may retain a bounded
    possible-health Customer note. WP-1402 adds no new PII class, Event field,
    Audit summary, log, URL, metric label, analytic field, screenshot or
    non-synthetic fixture.
22. Plan resolution is a read/derive step and creates no independent business
    fact. It has no expected-version mutation, Idempotency Key, transaction,
    repository commit, Audit or Outbox Event. WP-1401 atomically records the
    accepted immutable plan only when it creates the Ticket.
23. No API, UI, Queue Projection, Worker composition, scheduler, Feature Flag,
    Kill Switch, Provider call, credential, external resource, deployment or
    non-local database action is in scope.

  Event, business-data or external-effect rollback.
- Authorization boundary: this bounded candidate changes only the exact twelve
  implementation paths above. Commit, push, PR, merge, deployment,
