## Purpose

Verify a bounded Stripe webhook delivery against untouched raw bytes before JSON interpretation.
Resolve the direct-account Test/Live endpoint configuration, enforce the five-minute timestamp
window, support a bounded current/next signing-secret overlap, and emit only a strict verified
Envelope plus raw-evidence bytes for WP-1304's durable Inbox boundary.

## Closed execution contract

1. The internal adapter command accepts exactly Provider, environment, provider-account reference,
   received UTC instant, one `Stripe-Signature` header and an owned copy of the untouched raw body.
   It accepts no Tenant, financial, Payment status, Event ID, secret or parsed Provider object from
   a caller.
2. Input is bounded before configuration access: raw body is non-empty and at most 1 MiB; the
   signature header is ASCII, at most 8 KiB and has finite entry/signature counts. Ambiguous
   timestamps, malformed schemes, duplicate timestamp fields and invalid hex fail closed.
3. A server-side endpoint registry resolves the direct Stripe account and exact Test/Live
   Brand/Store scope plus signing-secret material. Route/account input never authorizes Tenant scope.
   Missing, mismatched or malformed configuration fails before JSON parsing.
4. Stripe `v1` HMAC-SHA256 is checked in constant time over exact
   `timestamp + '.' + untouched raw bytes`. At least one supplied `v1` signature must match one
   eligible configured secret. JSON is never parsed before that match.
5. The signature timestamp must be within an inclusive five-minute window of server `receivedAt`;
   both stale and future timestamps fail. A zero/disabled tolerance is not configurable.
6. Secret rotation permits `Current` plus at most one `Next` secret. Next verifies only inside an
   explicit UTC overlap of at most seven days. Secret material is copied, validated, zeroed after
   use, never returned, persisted, logged, audited, hashed into general telemetry or echoed in an
   error.
7. Only after verification may the adapter parse minimal Stripe Event envelope fields. It requires
   canonical Event ID/type/created/livemode and exact Test/Live agreement. Provider payload remains
   opaque raw evidence and never enters the Payment Aggregate or Canonical Domain contract.
8. The verified result includes Provider/account/Brand/Store scope, safe Event reference/type,
   Provider/received timestamps, raw SHA-256 evidence digest, matched secret slot and an immutable
   owned raw-body copy. It includes no signature header, secret, Provider message or parsed data
   object.
9. Every attempt emits one bounded Restricted security/audit observation after configuration
   resolution. Failures expose only stable safe codes; verifier/audit exceptions are normalized and
   raw request material is never placed in errors.
10. No HTTP route, browser credential/CORS, Stripe API client, Payment mutation, durable Webhook
    Receipt/Inbox, Event ID dedupe, `2xx`, asynchronous mapping, retry/replay UI, Provider retrieval,
    Event/Projection or real secret/account evidence is authorized. WP-1304 owns durable acceptance,
    idempotency and response semantics.

## Later boundaries

- WP-1304 atomically persists verified raw evidence/receipt with unique Provider Event ID before
  `2xx`, then provides idempotent, order-independent and replayable Inbox processing.
- WP-1305+ owns authoritative Payment facts/events, projections and reconciliation. A verified
  signature is authenticity evidence only and never Payment success.
- Restricted raw Stripe evidence defaults to 30-day retention; normalized Payment facts follow the
  transaction retention rule. WP-1304 owns enforceable persistence/expiry behavior.
- Production endpoint secrets, account mapping, privacy/PCI/contract facts and operational rotation
  evidence remain External Evidence gates.
