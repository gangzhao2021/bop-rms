## Problem and bounded intended outcome

WP-0040 provides bounded Structured JSON Logging and WP-0041 provides trusted operational lineage, but the repository has no centralized core metric instruments、sanitized error-tracking adapter or OpenTelemetry runtime lifecycle. Existing Realtime counters are injected test callbacks rather than a production telemetry backend. API/Worker failures are logged, but there is no accepted metric series、cardinality budget、OTel SDK startup/shutdown contract or Collector-outage proof.

WP-0044 will establish the smallest truthful operational telemetry increment:

1. centralized low-cardinality operation count、duration and error count instruments;
2. sanitized error tracking through stable codes、existing Pino redaction and OTel status/event metadata without raw exception text;
3. API request/startup/shutdown and Worker startup/shutdown integration;
4. accepted OpenTelemetry API `1.9.1` and Node SDK `0.220.0` runtime boundary;
5. explicit staging/production OTLP-to-ADOT configuration validation;
6. failure isolation、bounded shutdown and synthetic exporter/cardinality evidence;
7. no public metrics endpoint、business KPI、alert route、AWS resource or External Evidence claim.

This is not the complete cross-runtime API → Database → Outbox → Consumer rollout described by IDR-0014 because those runtime adapters are not yet composed in the current applications. It creates the reusable contract and instruments only active runtime paths. Database、Queue/Job、Provider and later business operations must join the same registry in their owning Work Packages.

## Domain、Module and data boundary

- `packages/observability` owns the private technical telemetry contract、validation、instrument creation and OTel SDK lifecycle. It owns no business Domain、Aggregate、Projection or Metric Definition.
- WP-0044 “Core Metrics” are operational service metrics. They are not the Section 38 Business Intelligence Metric Definition/KPI Catalog and cannot define Gross Sales、Net Sales、payment、tax、inventory or other business meaning.
- `apps/api` owns HTTP route-template mapping and API runtime lifecycle integration.
- `apps/worker` owns Worker runtime lifecycle integration.
- Correlation ID remains operational lineage and is not used as an OTel Trace ID、metric dimension or authorization input.
- Tenant、Brand、Store、Actor、Customer、Order、Session、Token、IP、URL、query、header、body、SQL、bind value、Provider payload and free text are prohibited metric dimensions and unrestricted span attributes.
- No telemetry path may query another Domain's private table、mutate a transaction、write an Audit/Event fact or affect business completion.

## Recommended Owner Decisions

**Status for every item: `OWNER PRE-AUTHORIZED AND ADOPTED — 2026-07-28`.**

1. **Owning package —** extend `@bop-rms/observability`; do not create a generic business analytics or provider package.
2. **Metric meaning —** limit WP-0044 to operational runtime metrics. Business metrics/KPIs remain Section 38 and later Reporting/BI WPs.
3. **Accepted SDK pins —** add direct runtime dependencies `@opentelemetry/api@1.9.1` and `@opentelemetry/sdk-node@0.220.0` only. pnpm may resolve the SDK's required transitive graph, but no alternate vendor SDK、SaaS client or AWS SDK is added.
4. **Exporter boundary —** use the Node SDK's OTLP environment contract toward an ADOT Collector. Application code never calls CloudWatch or X-Ray APIs directly and never embeds an endpoint、header or credential.
5. **Environment behavior —** development/test defaults to an injected synthetic/in-memory path or disabled export. Staging/production startup validates explicit OTel enablement and a bounded OTLP endpoint; plaintext is allowed only for loopback/sidecar, otherwise HTTPS is required.
6. **Core instruments —** create exactly `bop.operation.count`、`bop.operation.duration` in milliseconds and `bop.error.count`. No process-wide arbitrary instrument factory is exported.
7. **Closed attributes —** allow only environment、service、module、operation、result code and optional registered route template. Configuration owns finite allowlists; unknown names/values fail closed before export.
8. **Initial operations —** instrument `http_request`、`api_startup`、`api_shutdown`、`worker_startup` and `worker_shutdown`. Do not fabricate Database、Outbox、Consumer、Job or Provider observations for inactive composition paths.
9. **HTTP route mapping —** export registered route templates such as `/health` rather than raw URL/path/query. Unmatched、parser-rejected and unknown routes collapse to a single `unmatched` value.
10. **Result classification —** use bounded result codes already owned by the runtime (`SUCCESS`、stable HTTP family result and stable startup/shutdown failure codes). Status code、exception message and arbitrary error text are not metric dimensions.
11. **Error tracking —** v0.1 has no independent Error Tracking SaaS. API/Worker failures emit the existing centralized sanitized Pino error record plus `bop.error.count` and an OTel span status/event containing only a stable code. Raw `Error`、message、stack、URL and payload never enter OTel.
12. **Trace separation —** OTel creates its own Trace/Span identifiers. Trusted Correlation/Causation may remain in bounded Pino output but is not a metric label and is not coerced into an OTel identifier or baggage.
13. **Sampling boundary —** application-side instrumentation does not invent a production tail-sampling result. The accepted 10% success / bounded 100% sanitized-error policy remains ADOT configuration External Evidence.
14. **Failure isolation —** metric、span、exporter and shutdown failures never roll back or block an accepted business operation. A safe bounded telemetry failure signal may be logged; raw exporter errors are discarded.
15. **Lifecycle —** initialize telemetry before accepting runtime work and attempt a bounded flush/shutdown after readiness is failed and intake is drained. Repeated shutdown shares one promise and telemetry failure does not reopen readiness.
16. **No scrape endpoint —** do not add `/metrics` or include telemetry status/details in `/health` or `/ready`. CloudWatch/ADOT export remains a private runtime path.
17. **Cardinality evidence —** deterministic tests generate adversarial route/identifier/free-text canaries and a high request count, then prove the exported series remain within the exact finite registry and contain no prohibited value.
18. **Cloud/alert boundary —** create no Collector、CloudWatch、X-Ray、dashboard、alarm、SNS、EventBridge、credential、subscription or paid resource. WP-0045 owns Alert Routing/basic Runbook；WP-2065 and deployment WPs own cloud materialization.

## Risks、controls and rollback

- **Sensitive error export:** only stable codes reach OTel; existing centralized Pino serializer alone handles bounded stack positions.
- **Cardinality explosion:** finite config allowlists and route collapse reject IDs/free text before instrument calls.
- **Telemetry affects transactions:** every observation is synchronous-safe and exception-isolated; exporter/flush failure cannot change business completion.
- **Collector outage/memory pressure:** SDK queues and shutdown are bounded; outage tests prove business flow continues. Production capacity remains External Evidence.
- **Double counting:** one completion guard per operation and idempotent runtime shutdown.
- **Trace/correlation confusion:** identifiers remain separate and are never authorization inputs or metric dimensions.
- **False cloud-readiness claim:** synthetic exporters prove the application contract only; ADOT/CloudWatch/X-Ray routing、retention、sampling、cost and dashboards require real staging evidence.
- **Rollback:** normal reviewed Git revert of code/manifests/lockfile. No schema/data/cloud rollback exists because this WP creates none.
