## Owning facts and boundaries

Inventory owns Waste intent, approval and the immutable `Waste` Stock Movement. Compliance owns a
Food Safety Incident and Kitchen owns its work facts; Inventory may retain only an authorized stable
reference returned by their public contracts. Waste never edits a Balance, Incident or earlier
Movement. Cost is exact server-owned valuation and is field-masked unless separately authorized.

## Acceptance contract

1. Define a versioned Waste Aggregate with explicit Stock Scope, Item / lot / Location, exact
   positive waste quantity and conversion snapshot, controlled reason and source type, authorized
   source / evidence references, Balance version, projected impact, approval requirement, optional
   exact cost summary and append-only decisions.
2. Record authorizes before source, evidence, Balance or valuation reads; rejects foreign facts and
   enforces lifecycle, lot / expiry, conversion and negative-stock policy. Browser input cannot
   author Balance, conversion, cost, threshold or approval policy.
3. Submit follows the server threshold result: no-approval Waste becomes Approved; threshold Waste
   remains Submitted until an independent authorized approver approves or rejects it. Every mutation
   uses exact permission, scope, expected version, Audit and full-intent idempotency.
4. Post accepts only Approved Waste and validates one exact atomic adapter result containing the
   Audit, Posted Aggregate and immutable negative `Waste` Movement linked to the Waste reference.
5. Implement standalone `INV-WASTE-WIZARD` at `/operations/inventory/waste/new`, preserving
   `INV-WASTE-RECORD` only as an alias. Cover item / barcode / lot lookup, quantity / Unit, reason,
   Kitchen / Incident linkage, evidence, permission-masked cost, threshold approval and all states.
6. No Inventory schema or unregistered Event is invented. Compliance / Kitchen lookup, evidence,
   valuation, projection, persistence and atomic Ledger posting remain injected public ports.
