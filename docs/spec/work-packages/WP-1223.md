## Purpose and ownership

Store owns resolution of an explicit UTC instant through one exact, effective, versioned Store
configuration containing the IANA time zone and local Business Day Start. The declared platform
default is `04:00:00` local; a Store override remains explicit. The immutable result retains the
Store scope, Business Date, exact UTC boundary, DST disambiguation and configuration evidence.

Ordering owns allocation of a positive decimal Order Number sequence inside `Store + Business
Date`. `order_number_counter` is the concurrency control record and `order_number_allocation` is
append-only history. WP-1224 must execute counter advancement, allocation and Order creation in one
database transaction; a failed pre-Order transaction therefore consumes no formal number, while a
committed Rejected, Cancelled or Voided Order keeps its allocation forever.

The accepted source defines no prefix, width or Brand display format. This WP therefore uses the
smallest non-invented representation: the positive sequence encoded as canonical base-10 text.

## Decisions and invariants

1. Inputs are closed and runtime-validated. Instants are canonical UTC milliseconds, zones are
   known IANA names, versions are positive and configuration periods are half-open.
2. Business Date never uses UTC midnight. The resolver compares the instant with the Store-local
   boundary for the applicable local calendar date and returns the prior date before that boundary.
3. A nonexistent DST-gap boundary advances to the first valid local instant. An ambiguous overlap
   uses the earlier occurrence. The repeated hour cannot move Business Date backward or reset the
   sequence twice.
4. `PlatformDefault` is valid only with `04:00:00`; other starts must be explicit Store overrides.
   Business Day Start has minute precision and is stored as `time without time zone`.
5. Allocation is unique for Order ID and for both sequence and displayed number within exact Brand,
   Store and Business Date scope. A new Business Date starts at sequence `1`.
6. Allocation retains configuration ID/version/digest, IANA zone, local start, exact UTC boundary,
   disambiguation and allocation instant. No current Store configuration is needed to interpret
   history.
7. Both tables use forced Store RLS and no runtime grant. Allocation history rejects ordinary
   update/delete. Counter mutation is permitted only to the future Ordering repository transaction.
8. No Actor, permission, Audit record, Submission idempotency, Order table/API, Event, Projection,
   Payment, Kitchen, UI, Provider, real Store fact or deployment is implemented. WP-1224 owns the
   authorized atomic Create Order composition.

## Risks, rollback and residual gates

The primary risks are DST ambiguity, counter races, accidental sequence reuse and cross-Store data
access. Deterministic disambiguation, database serialization/uniqueness, append-only allocation and
forced RLS mitigate them. Rollback is a reviewed Git revert/forward-fix before dependent Order rows
exist; no destructive data rollback is authorized. Pilot Store configuration, legal/tax facts,
staging/production evidence and all WP-1224+ capabilities remain gated and unclaimed.
