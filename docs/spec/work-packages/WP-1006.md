## Purpose

Define the smallest first-Pilot Dining admission slice that proves:

1. only a named、authorized Staff Actor can start one active Dining Session for an eligible Table；
2. a fixed Table QR remains context-only and can never join a Session、create a Participant、
   become Host or authorize a Dining Order；
3. joining requires a separate 128-bit invitation credential or six-ASCII-digit human code bound
   to exact purpose、Store、Table、Dining Session and Table-assignment version；
4. a Join credential is valid for at most 15 minutes and is invalidated by successful join、
   regeneration、Session leaving Active or Table reassignment；
5. successful join creates one Session-scoped opaque Participant and one recoverable、
   single-use admission for Identity to rotate the existing Guest Session into exact
   `DiningBound` state；
6. Dine-in authorization requires both the rotated Guest Session and current Dining
   Session/Participant evidence；neither proof alone grants Ordering、Payment or Merchant power；
7. copied-QR and short-code failure decisions are non-oracular and require accepted abuse
   admission/cooldown evidence without collecting raw IP、device or contact data in Dining；and
8. no Guest Self-Start、Convenience Mode、Session Closing、Order Batch、Payment、allergen
   accommodation、production adapter、HTTP/UI or real operational evidence is implemented.

WP-1006 owns the Dining start/join aggregate boundary、short-lived Join capability grammar and
Identity binding transition only. WP-1007 owns Closing and unpaid exception behavior. WP-1028、
WP-1407 and WP-2027 own the remaining allergen safety chain. WP-1220 onward owns Cart/Order Batch.
WP-2048 owns WAF/application enforcement and the atomic `security.abuse_bucket`. WP-2112 owns the
later full Floor Board、Table configuration and move/merge/split experience.

## Ownership and trust boundaries

- `@rms/dining` owns Dining Session、Table Assignment reference、Participant、Host assignment and
  Join lifecycle facts. It receives Table eligibility/current-version evidence through a public
  Application port and never queries Store/Reservation/Identity private storage.
- `@bop/public-capability` owns only canonical raw Join credential grammar、purpose-separated hash
  record grammar、15-minute maximum、generation/lifecycle and pure fail-closed evaluation.
- `@bop/identity` remains the sole Guest Session owner. It consumes one Dining-issued admission、
  rotates Session/CSRF credentials and stores only exact Dining Session/Participant references in
  the new binding. Dining never writes the Identity table.
- Permission decides the named Staff action. Audit records the accepted start/regenerate intent.
  Dining cannot grant itself a Permission or mutate an Audit record.
- The existing fixed QR supplies customer-safe Store/Table context only. The server supplies all
  internal Store/Table/Session scope and current assignment facts.
- Raw Join credentials are `Restricted credential` data. They never enter a persisted
  Dining/Identity record、URL sent to a server、log、event、analytics、screenshot or ordinary
  fixture. Only synthetic tests may hold deterministic values.
- Internal mismatch/replay/abuse reasons are bounded trusted diagnostics. Every Customer-facing
  denial maps to one generic unavailable response with no Store/Table/Session existence oracle.

## Adopted decisions

1. **First-Pilot mode —** exact mode is `StaffStarted`. `GuestSelfStart` and `ConvenienceMode`
   are not enum alternatives、flags or fallback paths in this implementation.
2. **Named Staff authority —** start and regenerate require exact Tenant、Brand、Store、Actor、
   the operation's injected active Permission reference/allowed decision、recent authorization
   evidence where policy requires it、operation reference and Audit composition. This WP does not
   invent a Permission catalog code.
3. **Table start invariant —** exact current Table assignment/version evidence must be eligible
   and contain no active Session. A repeated exact operation is idempotent；changed intent under
   one operation reference conflicts.
4. **Initial phase —** accepted Staff start creates one immutable `Active` Dining Session and one
   active Table Assignment. `Pending` self-start behavior is absent.
5. **Session lifecycle —** the record recognizes canonical `Active | Closing | Closed |
Cancelled` for fail-closed join evaluation, but WP-1006 exports no Closing/Closed command.
6. **One active Session —** one Table cannot be assigned to two Active/Closing Sessions. The
   future store adapter must enforce compare-version uniqueness atomically.
7. **Participant —** successful join creates one opaque UUIDv7 Session-scoped Participant. It
   carries no account/contact/device/IP/profile fact.
8. **Host —** the first successfully joined active Participant becomes Host when no Host exists.
   Later joins do not replace Host. Host transfer is deferred and no client-supplied Host boolean
   is accepted.
9. **Public join kinds —** exact `Invitation` is canonical unpadded base64url for 16 random bytes
   (`22` characters)；exact `HumanCode` is six ASCII digits. A QR payload/reference cannot satisfy
   either grammar by implication.
10. **Selector persistence —** only a purpose-separated keyed HMAC-SHA-256 selector hash (`64`
    lowercase hex) and positive pepper version persist. Raw credential and pepper never enter the
    record.
11. **Join scope —** exact purpose `DiningJoin`、internal Store、internal Table、Dining Session、
    positive Table-assignment version and positive generation. A raw credential chooses no scope.
12. **Lifetime —** canonical UTC `expiresAt` is strictly after `issuedAt` and at most 15 minutes.
    There is no sliding extension.
13. **Lifecycle —** exact `Active | Consumed | Revoked | Expired`. Join succeeds only for Active、
    unexpired、exact-version and exact-hash evidence while the Session is Active and assignment is
    current.
14. **Single use —** successful join returns the next immutable Consumed capability plus
    Participant/admission evidence. A future Dining store performs compare-version + consume +
    Participant/Host + idempotency in one transaction.
15. **Regeneration —** exact next generation、fresh capability reference/hash and Staff authority
    are required. Every prior Active generation for the same Session/Table purpose becomes
    Revoked. Reuse or generation skipping fails closed.
16. **Session/assignment invalidation —** Closing、Closed、Cancelled、Table reassignment or
    assignment-version change makes every outstanding credential unavailable even before its
    stored expiry.
17. **Guest context —** join requires a current `ContextOnly` Dine-in Guest Session with exact
    internal Store and customer-safe Table context. Pickup、wrong Store/Table and already-bound
    sessions fail closed.
18. **Identity admission —** Dining returns one opaque UUIDv7 admission reference containing no
    raw capability. Exact retry can resolve the same admission；changed Guest/session intent
    conflicts.
19. **Identity rotation —** successful binding generates fresh 256-bit Guest Session and CSRF
    credentials, revokes the old record as `BindingChanged`, and creates a new record with exact
    `DiningBound` state、Dining Session and Participant references.
20. **Host ownership —** Identity stores no Host flag. Dining remains source of Host/current
    Participant status.
21. **Dine-in command gate —** a later Ordering adapter must validate both current Identity
    `DiningBound` context and current Dining Session/Participant evidence. WP-1006 creates no Cart、
    Order、Batch or Payment authority.
22. **Batch stability —** future submission of an unchanged Batch does not rotate the Guest
    Session. Session closure or another binding change does.
23. **Default abuse contract —** Join failures require `5 / 10 minutes / Guest Session` and
    `20 / 10 minutes / canonical IP-device scope`, then cooldown/invalidation. The package exports
    these fixed defaults and consumes only an injected `Admitted | Cooldown` result.
24. **Abuse data boundary —** raw IP/device/contact、forwarded chain、keyed abuse hash、bucket row、
    WAF rule、delay and `Retry-After` are absent. WP-2048 supplies them.
25. **Copied-QR denial —** fixed QR context without a separate Join credential is always
    unavailable. Wrong Table/Store/assignment remains indistinguishable from unknown Session.
26. **No public redirect/link builder —** the contract validates in-memory credential values only.
    Later same-origin transport/PWA code owns secure fragment/body handling and immediate
    redaction.
27. **Closed input/output —** objects reject missing、extra、symbol、accessor、array、non-plain
    prototype and malformed values. Returned records and decisions are immutable.
28. **No database-backed Dining claim —** Dining persistence remains a port in this WP. The only
    authorized migration extends Identity-owned `guest_session` for its own binding facts.
29. **No screen implementation —** Section 88 contracts are acceptance context only. No Customer
    or Merchant route/component is added.
30. **No external evidence —** no real Staff、Guest、Store/Table、Dining Session、credential、
    Permission、Audit、IP/device、KMS/pepper、traffic、load、Provider or production fact is
    available or claimed.
31. **Hard stop —** fixed-QR authorization、Guest Self-Start、raw credential persistence、
    cross-Store/Table acceptance、non-idempotent start/join、Dining-to-Identity private write、
    Host client selection、Ordering/Payment authority、raw abuse identifiers、unforced Identity
    scope、PII、allowlist-external tracked file or invented External Evidence stops implementation.

## Risks, rollback and next action

- Treating fixed QR as Join authorization enables copied-Table attacks；a separate exact-scoped
  short-lived credential is mandatory.
- Six-digit code space requires the accepted strict abuse budget；WP-1006 cannot claim protection
  until WP-2048 supplies an atomic adapter, but its contract fails closed without admitted
  evidence.
- Non-idempotent Session start or Join can duplicate occupancy/Participants；future persistence
  must enforce expected-version and operation uniqueness atomically.
- Consuming a Join credential before Identity rotation can strand a Participant；the recoverable
  one-time Dining admission allows exact retry without reusing the credential or creating a second
  Participant.
- Identity binding without current Dining evidence can outlive Session closure/reassignment；
  every protected later command must revalidate both owners.
- Rollback before merge is deletion of this brief plus bounded index edits. After merge, correction
  is a forward documentation/implementation change；accepted evidence history is never rewritten.
- Next allowed action is bounded implementation verification followed by exact-head pinned-Linux
  CI、Section 91 review、authorized squash merge、post-merge exact-main verification and cleanup.
