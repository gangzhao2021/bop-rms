## Acceptance and persistence design

Implement a read-only Ordering adapter for WP-2313's current Cart port. Capture fixed scope and closed
query input before awaits. Exact Brand/Store/Dining Session selects at most two eligible Customer
Cart headers: DineIn, Qr/Web, Active lifecycle, idle/absolute expiry strictly after observation time.
Zero means no currently selectable Cart; more than one means dependency-unavailable, never arbitrary
latest/first selection. Ineligible legacy, terminal, expired and non-Customer rows grant no selection.

Within one bounded read-only owner transaction, establish exact tenant context, select the unique
header, borrow that transaction for the existing public Cart aggregate repository, then reselect and
compare exact ID/version. Validate aggregate scope/Session/source/current lifecycle/time and freeze
it before return. A changed version, disappearance or new ambiguous current selection denies. This is
a current observation, not an atomic lease, uniqueness writer or authorization substitute. The caller
must use WP-2313 current Identity/Dining authorization; the store accepts no credential or Actor input.

Actual isolated PostgreSQL acceptance covers two synthetic currently authorized participants reading
the same persisted Cart through WP-2313, unique/absent/foreign/expired/ambiguous selection, immutable
item attribution, real between-statement version drift, bounded SELECT-only role and connection/context cleanup. Fixture Cart rows and
Identity/Dining providers are explicitly synthetic; no actual public Staff/Join/Identity composition
or production fact is claimed. Public owner repository reads stay in rms_ordering cart/cart_line.
