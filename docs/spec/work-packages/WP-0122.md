## Purpose

Add a provider-neutral、synthetic `@bop/publishing` minimum contract that proves:

1. Publishing owns Draft、Review、Approval、Publish、Archive、Rollback and immutable Release Record；
2. caller Domains retain configuration content ownership and supply only an opaque immutable
   snapshot reference、digest、configuration type/reference and exact Tenant scope；
3. edits create a new Draft/version and never overwrite a Published snapshot；
4. Submit Review、Approve and Publish are sequential、versioned and fail closed；
5. Publish requires current successful validation and accepted approval evidence for the exact
   snapshot/scope/version；
6. rollback creates a new reviewed Release Record pointing to an eligible prior snapshot and never
   rewinds transaction history；
7. exact Permission precedes every state change and next state + Release Record + Audit commit in
   one unit of work；and
8. malformed、stale、ambiguous、cross-Tenant、replayed or concurrent inputs return stable bounded
   denial without exposing configuration content.

WP-0123 owns Effective Period、time zone、Schedule activation/expiry、overlap validation and current
effective-version resolution. This WP neither implements nor simulates those owners.

## Governing decisions

1. **Predecessor —** WP-0121 is integrated and post-merge verified at
   `dfd638e408adff3a32524176c55da40e78c51969`.
2. **Owner —** `@bop/publishing` owns lifecycle and Release Record only. The caller Domain owns its
   configuration schema、validation semantics and payload.
3. **Opaque snapshot —** Publishing accepts UUIDv7 configuration/snapshot references and a
   `sha256:` digest. It never accepts arbitrary JSON、binary、PII or business payload.
4. **Exact scope —** every lifecycle record is one Brand or one Store within that Brand. No global
   publish and no client-derived Brand.
5. **States —** exact lifecycle states are `Draft`、`InReview`、`Approved`、`Published`、`Archived`
   and `Superseded`. Rejected review creates a new Draft revision rather than mutating history.
6. **Versioning —** positive expected version and idempotency are required. Every accepted change
   creates a new immutable lifecycle version；Published/Archived/Superseded records are never edited.
7. **Validation —** Submit Review requires current caller-owned validation evidence bound to exact
   snapshot/digest/scope. Publishing does not interpret business rules.
8. **Approval —** Approve consumes injected accepted approval evidence bound to exact review、
   Actor/scope/snapshot/version. This WP does not implement Approval workflow or private queries.
9. **Publish —** only the exact Approved snapshot may publish. It creates an immutable Release
   Record and supersedes only the caller-supplied exact previous release under one atomic port.
10. **Rollback —** rollback target must be a prior immutable Published/Superseded snapshot in the
    same configuration family/scope. It creates a new Release Record/version after validation and
    approval；it never restores mutable state or alters transactions.
11. **Archive —** archive prevents future configuration use but does not erase Release/Audit
    history or affect completed transactions.
12. **Schedule hard boundary —** Schedule returns explicit unsupported capability in this minimum.
    No clock、job、effective period or overlap logic is fabricated before WP-0123.
13. **Permission —** exact Create Draft、Submit Review、Approve、Publish、Archive and Rollback actions
    require accepted `@bop/permission` evidence. Ownership/reviewer identity is never a grant.
14. **Atomic Audit —** each mutation supplies immutable next records and a bounded `@bop/audit`
    request to one unit-of-work port. Success exists only if all records commit atomically.
15. **Event boundary —** lifecycle records may later source events, but this WP publishes no Event
    and fabricates no Outbox result.
16. **Privacy/telemetry —** only stable operation/state/reason codes may be labels. Tenant、Store、
    Actor、configuration/snapshot/release/digest IDs and free text are excluded.
17. **No persistence/API/UI —** no table、migration、RLS、repository adapter、route、Screen、
    navigation、projection or deployment.
18. **No external mutation —** no Provider、credential、real approval/configuration、external
    resource or operational publication.
19. **External Evidence —** real authorization/approval、scheduler、load、recovery、staging and
    production evidence remains `NOT AVAILABLE / NOT CLAIMED`.
20. **Hard stop —** persistence、payload ownership、Approval/Effective Period implementation、
    direct private query、event claim、production API/UI、Provider/resource、weakened immutability or
    allowlist-external tracked file stops implementation for exact review.
