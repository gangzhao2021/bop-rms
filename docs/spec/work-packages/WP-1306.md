## Purpose

Build Payment's first rebuildable `payment_status_v1` read model from the stable
`PaymentSucceeded.v1` and `PaymentFailed.v1` facts. Expose bounded Store-scoped list/detail query
contracts with explicit checkpoint and freshness while preserving WP-1305 as the sole terminal
transaction authority.

## Closed execution contract

1. Consumer `payment.status-projection:v1` accepts only exact WP-1305 Payment terminal envelopes.
   It validates producer/type/version, Brand/Store, Payment Intent aggregate identity/version,
   occurrence time and every closed payload field before any projection effect.
2. Event Inbox completion and projection generation replacement share one caller-owned transaction.
   A duplicate Event is harmless; a same Payment Intent/same source version with different content
   fails closed; an older checkpoint cannot replace a newer active generation.
3. Projection `payment_status_v1` is Payment-owned, Store-scoped, versioned, generation-switched,
   rebuildable and never writes Intent, Attempt, Provider observation, webhook receipt, terminal
   fact, Audit, Outbox or Ordering state.
4. The active snapshot contains only Payment Transaction/Intent/Attempt/Order references, terminal
   `Succeeded | Failed`, exact success Money or bounded failure reason/retry disposition, terminal
   occurrence time, source Event/checkpoint and projection metadata. Provider Account/Event/object
   IDs, evidence digest, raw payload, payment-method detail, Guest/PII and Provider message are absent.
5. Every result declares projection name/version/generation, source checkpoint, projected-at,
   optional last-rebuilt-at and `Fresh | Stale | Rebuilding | Failed`. Projection freshness never
   authorizes or confirms a transaction action.
6. Rebuild reads an injected authorized exact terminal-fact feed, writes a shadow generation and
   switches active generation atomically. Failure leaves the previous active generation readable;
   counts, stable identities and source checkpoints must reconcile before activation.
7. `GetPaymentStatus` authorizes Tenant/Brand/Store/Actor/purpose before reading by exact Payment
   Intent. `ListPaymentStatuses` authorizes before any read, requires exact Store scope and supports
   bounded exact Payment/Order reference, terminal status and occurred-at range filters with
   deterministic pagination.
8. Query dependencies may return only exact-scope rows and no more than the requested limit.
   Cross-Store, malformed, duplicate, out-of-order or filter-mismatched content fails closed.
9. PAY-PAYMENT-LIST and PAY-PAYMENT-DETAIL retain Section 88 routes, permissions, fields and states.
   This WP supplies backend contracts only. Action hints are non-authoritative; capture, cancel,
   refund and reconcile commands must later reauthorize and re-read source facts.
10. Ordering is a separate `ordering.payment-outcome:v1` consumer and is not implemented here.
    This projection never advances Order, releases Kitchen work or claims commercial confirmation.
11. WP-1307 owns Provider reconciliation runs/checks/exceptions. Provider retrieval, settlement,
    reconciliation status, refunds, kill switch, watchdog, compensation, UI, realtime and exports
    remain absent rather than represented as successful or empty values.
12. Tables force Store RLS and grant no PUBLIC access. Logs/metrics/analytics/URLs receive only
    bounded internal references, checkpoint/freshness/state codes and timing; no credential,
    Provider payload, payment identifier or unnecessary personal data is authorized.
