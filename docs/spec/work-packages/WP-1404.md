## Outcome

WP-1404 closes the first Kitchen execution mutation boundary. It implements
four commands over the authoritative Kitchen Ticket / Work Item Aggregate:

1. `AcceptKitchenWorkItem`;
2. `StartKitchenWorkItem`;
3. `CompleteKitchenWorkItem`; and
4. `MarkKitchenOrderItemReady`.

The title is retained exactly from the canonical backlog. Complete is included
because later accepted Sections 26.1, 26.6, 44.12 and 48.4.6 require it even
though the backlog title abbreviates the command set.

This is a bounded Application / Domain / persistence increment. It creates no
HTTP or BFF route, Session or CSRF adapter, KDS UI, SSE transport, offline
command queue, Worker composition, runtime role or grant, credential, external
resource or deployment. Synthetic context, admission and Expo evidence proves
only the provider-neutral contract; it is not live authority evidence.

Business behavior outside this WP is also closed: Hold, Resume, Cancel, Rework,
Course / Fire, Prioritize, ETA, Exception handling, operator handover,
multi-Station execution, Ticket lifecycle changes and partial Ready are not
implemented or inferred. WP-1404 does not create an offline mutation path or
authorize a stale queue to drive any of those later behaviors.

## Resolved authority, precedence and ownership

1. Kitchen remains the sole owner of Ticket, Work Item execution state,
   lifecycle operations and OrderItem Ready results. The queue projection is a
   read model and never authorizes a command or supplies Expected Version.
2. The Ticket status remains exactly `Open` throughout this WP. No accepted
   authority defines a Ticket `Accepted`, `Completed` or `Ready` state machine,
   so WP-1404 does not invent one. This ruling is limited to WP-1404 and does
   not claim the Ticket can never gain a later accepted lifecycle.
3. Work Item status remains the exact closed vocabulary `Queued`, `Held`, `In
Progress`, `Completed` and `Cancelled`. `Ready` is not a Work Item state.
4. Accept is a per-Work-Item, append-only named-operator claim fact. It keeps
   the Work Item `Queued`; it is not an `Accepted` status.
5. Ready is a unique, append-only result for one OrderItem. It never mutates a
   Work Item into Ready and does not create a Ticket Ready state.
6. WP-1404 adds no mutable `ready_quantity`. The Ready result stores its
   immutable `readyQuantity` and `requiredQuantity`, and Phase 1 accepts only
   the complete case where they are equal. Partial Ready remains deferred by
   Section 44.17.2.
7. WP-1404 owns the four commands and their source facts. WP-1405 owns only
   realtime hints. WP-1406 owns ItemReady / OrderReady public Events and the
   incremental Ready projection trigger. WP-1407 owns structured allergen
   review and acknowledgement; WP-1408 owns stale/offline continuity and
   operator handover.
8. Section 26.1 explicitly requires Kitchen to publish Item preparation
   progress and completion Events, while Section 26.6 defines partial completed
   quantity. Section 52.16 names only the final Completed Event. This bounded
   brief resolves that catalog gap with the narrow
   `KitchenItemProgressRecorded.v1` contract for a partial positive quantity
   delta and reserves `KitchenItemCompleted.v1` for the final delta only. This
   is a candidate contract resolution, not a claim of separate Owner approval.
   A partial delta can never masquerade as an Item-completed fact.

## Exact command and authorization contract

The exact action / purpose pairs are:

| Command    | Authorization action        | Purpose                   | Target    |
| ---------- | --------------------------- | ------------------------- | --------- |
| Accept     | `AcceptKitchenWorkItem`     | `KitchenWorkExecution`    | Work Item |
| Start      | `StartKitchenWorkItem`      | `KitchenWorkExecution`    | Work Item |
| Complete   | `CompleteKitchenWorkItem`   | `KitchenWorkExecution`    | Work Item |
| Mark Ready | `MarkKitchenOrderItemReady` | `KitchenExpoCoordination` | OrderItem |

All four require exact permission `kitchen.operate`.

Every call follows this order:

1. strictly parse and deeply freeze the public command;
2. resolve the current trusted Workforce Session / Tenant Context to one named
   User Actor, active Brand, active Store and server-observed UTC instant, and
   resolve the separately injected immutable server Correlation Context;
3. require caller Actor, Brand, Store and `correlationReference` values to match
   those trusted values exactly; caller values can narrow or prove equality and
   never create correlation or grant access;
4. final-authorize the exact action, purpose, permission, Actor, Brand and
   Store before idempotency lookup or Kitchen source read;
5. begin the caller-owned transaction and install the same trusted snapshot's
   named User `actorReference`, Brand, Store and server-selected purpose as
   transaction-local Tenant / RLS context;
6. acquire the Brand + Store + idempotency-key transaction fence, resolve the
   key inside that fence, then, only for exact NotFound, lock Ticket and Work
   Item rows in a deterministic order and re-read authoritative source state;
7. validate versions, transition, admission / Expo evidence and time; and
8. atomically commit source mutation, lifecycle operation, optional Ready
   result, Confidential Audit and applicable Outbox Event.

Authentication, Membership, Store Assignment or permission denial / failure
performs zero operation lookup, source read, mutation, Audit or Outbox effect.
Switching Store, revoking Membership or revoking permission invalidates the
old scope. Authorization and transaction context must exact-match the same
trusted Actor / Brand / Store snapshot; context mismatch or installation throw
is a dependency failure before operation lookup. There is no ID-only,
cross-Store or projection fallback.

Raw body, header, Provider or client correlation is never durable lineage. The
service uses only the injected trusted `correlationReference` for the first
committed lifecycle operation, effect digest, Audit and Event envelope. Current
attempt correlation is excluded from the stable business-intent digest.
Missing, malformed, throwing or non-equal correlation context fails before
operation lookup/source; parallel requests cannot share or leak a context. A
replay preserves the first operation's stored correlation and never overwrites
lineage with the retry attempt's correlation.

## Transition and quantity matrix

Every parsed source row and committed row satisfies the exact cross-field
invariant: `Queued` has completed quantity `0`; `In Progress` has completed
quantity from `0` through `required - 1`; `Completed` has completed quantity
exactly equal to required. `Held` and `Cancelled` remain immutable in this WP
and preserve the already accepted bounded range from `0` through required;
WP-1404 does not tighten their inherited semantics. Migration 1500_003 adds
this database CHECK to both authoritative Work Item and queue-row storage as
defense in depth. A malformed stored row is a dependency failure with zero
effect, never a state inference.

### Accept

- The Ticket is `Open`; the target Work Item is `Queued` with completed
  quantity `0` and has no existing Accept operation.
- Expected Ticket and Work Item versions are exact.
- One successful Accept increments Ticket aggregate version and target Work
  Item version exactly once. Work Item status and quantities remain unchanged.
- The append-only operation records the named accepting Actor and accepted UTC
  instant. A partial unique key permits one Accept fact per Work Item.
- The committed result publishes `KitchenWorkAccepted.v1` atomically.

### Start

- The Ticket is `Open`; the target Work Item is still `Queued` with completed
  quantity `0`.
- The exact Accept operation, accepting Actor and accepted instant are re-read
  under the source lock. In Phase 1 the starting Actor must be the accepting
  Actor; named-operator transfer / handover remains WP-1408.
- Exact, current `Allowed` Start-admission evidence is mandatory for every
  Start. A well-formed exact `Blocked` decision returns
  `KITCHEN_WORK_PRECONDITION_FAILED`. Missing / unavailable, malformed / extra,
  stale / future, wrong Actor / scope / target / accepted operation / version /
  action / purpose / digest, unsupported `producerContractVersion` or port throw returns
  `KITCHEN_WORK_DEPENDENCY_UNAVAILABLE`. Both use the single safe message and
  perform zero persistence, Event, Audit, narrative or telemetry detail.
- One successful Start increments Ticket and Work Item versions exactly once,
  changes the Work Item to `In Progress`, preserves completed quantity and
  publishes `KitchenWorkStarted.v1` atomically.

### Complete

- The target Work Item must be `In Progress`; Queued, Held, Completed and
  Cancelled items cannot accept a completion delta.
- The source transaction re-reads the exact Accept and Start operations. The
  completing Actor must equal their named claim owner; operator transfer and
  handover remain WP-1408.
- Delta is a positive integer no greater than remaining quantity.
- Every successful delta increments Ticket and target Work Item versions once.
- If cumulative completed quantity remains below required quantity, status
  stays `In Progress` and only `KitchenItemProgressRecorded.v1` is published.
- If cumulative equals required quantity, status becomes `Completed` and only
  `KitchenItemCompleted.v1` is published.
- Cumulative quantity can never exceed required quantity or move backward.
- The source transaction reads the complete sibling Work Item set for the
  OrderItem. If the final delta makes every required sibling Completed, exact
  Expo evidence decides whether to append the Ready result.

### Mark Ready and automatic Ready

- Mark Ready targets an OrderItem, not a Work Item or Ticket status.
- The sole Phase-1 Work Item must be exactly present, `Completed`, and
  have completed quantity exactly equal to required quantity, and be bound by
  the command's one-entry reference / version vector. Missing, extra,
  duplicate, changed, non-Completed or quantity-inconsistent entries fail
  closed.
- Expo `Enabled` requires an authorized named User Mark Ready command. It
  increments Ticket version once and does not change completed Work Item
  versions, states or quantities. Mark Ready re-reads the immutable Enabled
  evidence captured by the final completion operation; it never resolves
  current Store configuration again.
- Expo `Disabled` makes the final completing User command append a System Ready
  result in the same transaction. It shares that Complete command's one Ticket
  / Work Item version increment and is causally bound to the User operation.
- Exactly one Ready result may exist for Brand + Store + Ticket + OrderItem.
  Competing Complete / Mark Ready operations serialize on the Ticket and the
  unique Ready key; they cannot produce two results.
- The Ready result binds the complete sibling vector, vector digest,
  `readyQuantity == requiredQuantity`, Expo evidence, causal operation and UTC
  ready instant. Both quantities are copied exactly once from the sole
  immutable Phase-1 Work Item; they are never summed across preparation tasks.
  A future split/multi-Station model must refresh this contract and define
  allocation before accepting more than one vector entry.
- WP-1404 publishes no Ready Event. Manual and automatic Ready results return
  `projectionPending: true` and the WP-1406 gate.

## Idempotency, replay and concurrency

`idempotencyKey` is the independent Brand+Store-scoped replay key;
`operationReference` is the distinct server-owned Command identity. The
canonical intent digest covers only stable business intent: Actor, Brand, Store,
action, purpose, Ticket / Work Item / OrderItem targets, expected versions and
quantity delta or sibling vector. It excludes operation/Event/correlation IDs,
the current attempt correlation, newly sampled server time and returned
admission / Expo feed values.

The canonical `effectDigest` uses the tagged SHA-256 form over one fixed-field-order,
UTF-8 canonical JSON binding. Common fields are the persisted independent
`idempotencyKey`, server-owned `operationReference`, action, purpose, Actor,
Brand, Store, Ticket / Work Item / OrderItem targets, `intentDigest`, expected and
committed Ticket / Work Item decimal versions, before / after status,
applicable delta / cumulative / required quantities, occurred instant, the
complete exact public result, predecessor operation references, the first
persisted trusted correlation and exact causation. Start additionally binds its opaque admission anchor; final Complete
and Mark Ready bind the captured Expo anchor. Every explicit action binds its
Audit reference plus semantic digest and its applicable Outbox Event reference
plus complete event-semantic digest; absent Event is an explicit null.

An automatic-Ready Complete binding additionally contains the child operation
reference and child `effectDigest`, plus Ready-result reference,
`workItemsDigest`, ready / required quantities and ready instant. The child
binding independently covers its System/action/reason/parent causation, Ready
result bundle and System Audit with an explicit null Outbox Event; it never
recursively includes the parent digest. Mark Ready covers the same Ready-result
business fields directly. Reference arrays use lowercase UUID code-unit order,
versions are decimal strings, and no insertion-order / locale comparator is
allowed. Digests exclude Customer / health / narrative, projection state,
transient dependency detail and their own digest field.

- A currently authorized same-key / same-business-intent replay returns the
  exact durable result with the original operation reference and stored
  correlation lineage. It performs zero source, admission, Expo, reference,
  Domain-clock, mutation, Audit or Outbox call and ignores the retry attempt's
  otherwise-valid new correlation for durable output.
- Same key with changed action, scope, Actor, target, versions, delta, vector or
  other stable business intent is a version / idempotency conflict. Correlation
  change alone is not changed business intent.
- The repository acquires one transaction-scoped serialization fence over the
  exact Brand + Store + idempotency key before lookup, operation-reference
  creation or source read. A waiter re-runs strict lookup inside the fence and,
  for the same business intent, adopts the winner's exact durable result,
  operation reference and original correlation with no source/evidence/clock/
  reference/effect call. The injected fence port receives only that exact tuple
  plus the caller transaction, is held until commit or rollback and cannot be
  replaced by process-local memory. Fence failure is a dependency failure. The
  scoped database unique key remains a defense-in-depth constraint rather than
  the primary race protocol.
- Commit-unknown resolves Brand + Store + idempotency key and adopts the stored
  operation only after strict
  intent, stored-row, result, Audit / Event and complete effect-bundle digest
  validation. A well-formed same-key changed intent conflicts. A Found but
  malformed, cross-scope or effect-drifted durable bundle is a dependency
  failure and is never re-executed; only an exact NotFound after uncertainty may
  perform the full retry.
- Authorization is repeated before replay so revoked access cannot retrieve a
  historical result.
- Exact replay is available while trusted current time is earlier than
  `replayExpiresAt`, and the persisted expiry must equal `occurredAt + 30
days`. Equality is already expired. After current authorization, RLS installation,
  scoped lookup and strict stored-bundle validation, a key at or after expiry
  returns exact `KITCHEN_WORK_VERSION_CONFLICT` for both same and changed
  intent. It returns no historical result and performs zero source, admission,
  Expo, Domain-clock, stable-reference, mutation, Audit or Outbox call. The
  WP-1404 performs no deletion or compaction: the append-only row remains under
  the approved `KITCHEN_BUSINESS_RECORD` / `audit-security` retention policy,
  and the key is never silently re-executed or reused. Any later authorized
  archive/erasure design must preserve a scope+key non-reuse tombstone while
  minimizing replay result/Actor data; this WP does not invent that legal or
  retention action.

Ticket CAS serializes cross-item mutations. Target Work Items are locked in
lowercase UUID code-unit order. Conditional writes require exact Brand, Store,
Ticket / Work Item identity and expected version, and must affect exactly one
row. A zero or multi-row result is conflict or dependency, never last-write-
wins.

kitchenWorkItemReference, orderItemReference, ticketVersion,
workItemVersion, workItemStatus: "Queued", acceptedAt }`;
2. `KitchenWorkStarted.v1`: `{ kitchenTicketReference,
kitchenWorkItemReference, orderItemReference, ticketVersion,
workItemVersion, fromStatus: "Queued", toStatus: "In Progress",
startedAt }`;
3. `KitchenItemProgressRecorded.v1`: `{ kitchenTicketReference,
kitchenWorkItemReference, orderItemReference, ticketVersion,
workItemVersion, quantityDelta, completedQuantity, requiredQuantity,
fromStatus: "In Progress", toStatus: "In Progress", recordedAt }`; and
4. `KitchenItemCompleted.v1`: `{ kitchenTicketReference,
kitchenWorkItemReference, orderItemReference, ticketVersion,
workItemVersion, quantityDelta, completedQuantity, requiredQuantity,
fromStatus: "In Progress", toStatus: "Completed", completedAt }`.

All three references are canonical lowercase UUIDv7 values. Event versions are
canonical positive decimal strings and are never JSON unsafe numbers;
quantities are bounded integers. Progress requires a positive delta and
`0 < completedQuantity < requiredQuantity`; Completed requires a positive
delta and `completedQuantity == requiredQuantity`. The Event-specific instant
is canonical server UTC and exactly equals the envelope `occurredAt`.

Every envelope is produced by `@rms/kitchen`, uses `KitchenTicket` as aggregate,
binds aggregate ID to `kitchenTicketReference` and aggregate version to the
exact positive-bigint value represented by `ticketVersion`, uses the named User
Actor in the envelope, sets causation to the operation reference and preserves
the trusted command correlation. Exact envelope values are
`tenantId = brandReference`, `storeId = storeReference`,
`actor = { type: "Actor", actorId: trustedActorReference }`,
`correlationId = trustedCorrelationReference`,
`causationId = operationReference`, `redactionClassification = "personal"` and
`replayMetadata = { replaySafe: true }` with that one exact key. Actor,
correlation and causation are envelope-only and are forbidden payload keys.
Payloads contain no display narrative,
Customer note, health / allergen fact, admission / Expo evidence, Audit value,
Payment or Provider data. Because the envelope contains a named User Actor,
the catalog classification is `personal`; retention is `business_record` and
replay is idempotent.

The existing `KitchenWorkCreated.v1` registration is preserved. Four distinct
`ordering: none` registrations are added:

- `kitchen.queue-work-accepted-projection:v1`;
- `kitchen.queue-work-started-projection:v1`;
- `kitchen.queue-item-progress-projection:v1`; and
- `kitchen.queue-item-completed-projection:v1`.

Each name is registered once and maps only to its corresponding Event type at
schema version `1`. All four freeze `consumerVersion: 1`, owner
`@rms/kitchen`, Store tenant scope, `ordering: none`, exact side effect
`replace_kitchen_queue_projection` and `replaySafe: true`. Registrations and
their schema-version arrays are deeply frozen; changed name/type/version/owner/
scope/side-effect/replay metadata is rejected before handler execution.

The public lifecycle `consume` facade accepts only the raw delivery and delegates
it directly to generic Inbox. A completed same-Event Inbox record therefore
short-circuits before any lifecycle parser, authorization, lock, source read or
result hash. Only a first or otherwise non-completed registration handler
strictly parses the named-User envelope, then final-authorizes the internal
System / null-Actor action `ProjectKitchenQueue`, purpose
`MaintainKitchenQueueProjection`, exact Brand / Store, parsed
`sourceEventReference` and trusted observed UTC instant before acquiring the
Store lock or reading source. The immutable authorization input has exactly
those action/purpose/System/null/scope/Event/time fields, and its reply is
strictly parsed as one trusted snapshot. There is no
pre-authorized context or alternate internal-handler capability. The envelope's
User Actor proves the business fact and never grants projection authority. A
definitive authorization denial permanently rejects and parks the delivery;
authorization or dependency throw is retryable. Both roll back the incomplete
Inbox transaction and produce zero source read or generation effect without
revealing Actor or object existence.

After authorization and within that same caller-owned Inbox transaction, the
handler installs the exact server-derived Brand / Store Tenant Context with
System Actor, null Actor reference and purpose
`MaintainKitchenQueueProjection`. It does so before Store lock, source or
repository access. Missing, wrong, leaked or failed context installation is
retryable, rolls back Inbox completion and performs zero generation effect;
transaction-pool reuse can never retain the prior Store context.

After authorization, the handler uses the same Store projection lock and loads
one exact current Ticket group, an authorized Store checkpoint / as-of pair and
a non-empty canonical same-Ticket lifecycle-operation proof set. It validates
and replaces only that verified Ticket group in the Active generation. Only a
rebuild may load the complete WP-1403 Store feed. The proof set contains the
triggering operation and every same-Ticket intermediate needed to prove the
current source advance through the checkpoint. It is sorted by committed Ticket
version and then lowercase operation reference, has no duplicate operation or
committed-version/action pair, and has no arbitrary business-count truncation.
The DTO is never a generic Work Item entity and contains no Customer note,
preparation, admission / Expo details or health data.

Each incremental safe source item carries current positive Ticket / Work Item
versions, closed status, completed / required quantities, nullable per-Work-Item
`acceptedAt` and the immutable original `KitchenWorkCreated.v1` binding. It has
no projectable `orderItemReadyAt`: an eventless Ready proof is validated for
complete-through version history, but candidate rows exact-preserve the Active
generation's prior Ready value and do not compare it with current Ready source.
The complete rebuild DTO additionally carries nullable per-OrderItem
`orderItemReadyAt`, derived only from the unique Ready-result table.

That rebuild DTO never treats a timestamp as self-authenticating. For every
Ticket it includes a canonical, complete-through-checkpoint lifecycle proof
bundle with operation count, Ready-result count and tagged
`lifecycleProofSetDigest` over every normalized proof. Non-null `acceptedAt`
must reconcile to the unique exact Accept operation target/time/projection-proof bundle;
non-null `orderItemReadyAt` must reconcile to the unique Ready result, its
one-entry vector/full quantity and the complete causal manual or parent+auto
projection-proof bundle. Null is valid only when the authorized complete bundle
proves no matching owner-table fact through the checkpoint. The core recomputes
the proof-set digest and all timestamps. Actor, Audit/Event proof and opaque
Kitchen-owner effect anchors remain transient Confidential input and never enter
a queue row or public result. Command-private admission / Expo evidence is not
loaded. Missing, extra, duplicate, cross-scope or forged proof is a
dependency failure with zero generation switch.

The proof is one exact action-discriminated union:

- Event-producing Accept, Start, Progress and Completed proofs bind exact Brand,
  Store, Ticket, Work Item and OrderItem, operation reference, exact
  action/purpose/reason/`KDS_COMMAND` source, named User Actor, expected and
  committed Ticket / Work Item versions, before / after status, applicable
  delta / cumulative / required quantities and occurred instant. Each also
  binds its Confidential Audit reference / semantic digest, operation
  `effectDigest` as an opaque tagged Kitchen-owner anchor, original Outbox Event
  reference and Event-semantic digest over the complete normalized lifecycle
  envelope with only `eventId` excluded.
- An eventless explicit Mark Ready proof binds Brand, Store, Ticket and
  OrderItem, operation reference, exact `KITCHEN_ORDER_ITEM_READY` action,
  `KitchenExpoCoordination` purpose, `EXPO_MARKED_READY` reason, `KDS_COMMAND`
  source channel and named User Actor. It proves expected-to-committed Ticket
  version `+1`, unchanged sole Work Item version / Completed status / full
  quantity, exact one-entry sibling vector / digest, Ready-result reference,
  ready / required quantities, ready instant, Confidential Audit reference /
  semantic digest and opaque tagged operation `effectDigest`. It has null Event fields,
  contains no Expo-policy evidence and has no invented mutated Work Item result.
  It may appear only as an intermediate Ticket-version advance, never as the
  trigger. Wrong action / Actor / version / vector / result / Audit / effect
  binding is source corruption and retries with zero switch.
- An Expo-Disabled automatic Ready proof is a System child paired atomically
  with its final Completed parent at that same committed Ticket version. It
  binds the deterministically derived child reference, parent causation, exact
  `KITCHEN_ORDER_ITEM_READY` action, `KitchenExpoCoordination` purpose,
  `ALL_WORK_ITEMS_COMPLETED` reason, `KITCHEN_AUTOMATION` source, System / null
  Actor, full Ready-result reference / one-entry vector / quantity / instant,
  System Audit reference / semantic digest and opaque tagged child
  `effectDigest`. It has null
  Event fields, cannot be a trigger or independent version advance and is
  invalid without the exact same-scope Ticket / OrderItem parent Completed proof
  and Ready result. All three references must remain pairwise distinct.

Projection intentionally does not load command-private admission / Expo anchors
and does not claim to recompute the full lifecycle-operation `effectDigest`.
Instead every union variant carries a tagged `projectionProofDigest` over all
fixed-order projection-safe fields enumerated for that variant, including the
opaque effect anchor, Audit/Event semantic anchors and explicit null fields,
while excluding private evidence and its own digest. The core recomputes it.
The parent+automatic-child form additionally carries a recomputable
`readyCausalBundleDigest` over parent and child projection-proof digests plus the
full safe Ready-result reference/vector/quantity/time bundle. Rebuild
`lifecycleProofSetDigest` is the lowercase-reference/version-sorted aggregate of
those recomputed projection proofs. Private anchors are forbidden input.
Missing or changed projection-safe proof fields, or any extra proof field, fail
closed.

Every variant forbids fields belonging only to another variant. The source
adapter proves every listed operation, Ready result and applicable original
Event are committed and that its Store checkpoint is complete through the
delivered semantic fact. The consumer selects the event-bearing proof whose
operation / causation and event-semantic digest match the trigger with only
`eventId` excluded. It recomputes that digest from event type/schema, producer,
scope, aggregate/version, Actor, correlation/causation, occurredAt,
redaction classification, replay metadata and complete payload before trusting
the Ticket group. Registration separately fixes Catalog classification
`personal`, retention `business_record` and replay `idempotent`; a reissued ID
cannot select a different contract. The delivered Inbox Event ID may equal the proof's original Event ID or
be a distinct reissued ID; the proof's original Event reference remains the
business binding. Any other field drift parks.

The trusted checkpoint comparator input is exact: it binds the Active
checkpoint / as-of, candidate checkpoint / as-of, delivered Event reference and
semantic digest, and the complete same-Ticket proof set. It has only three
outcomes. `Current` requires exact scope, checkpoint, as-of, complete Ticket
group, rows and header digests equal to Active; it completes this Event's Inbox
with zero generation, clock or reference call. `Successor` means the adapter
proves that interval contains only the represented Ticket-group advance and no
other unprojected Kitchen-queue-relevant Store fact, then permits the exact
generation switch. A cross-Ticket fact, unknown delta, gap, regression or same
checkpoint with changed as-of is `retry_required`; Inbox remains incomplete and
no generation switches.
`ordering: none` removes a broker ordering promise, not the requirement to prove
Store-checkpoint completeness.

Incremental and rebuild time reconciliation is exact. Delivered Event
`occurredAt`, every proof/operation/Audit-safe `occurredAt`, source `updatedAt`,
`acceptedAt` and `orderItemReadyAt` are canonical and satisfy source `createdAt
<= factTime <= candidate asOfUtc`. Candidate as-of is no earlier than Active
as-of. Accept, Start, progress/final completion and Ready facts are monotonic,
with automatic Ready allowed at its parent final-Complete instant; `Current`
must exact-match the same chronology. The builder
finishes all source/proof/row/digest/count preparation before sampling final
`projectedAt`. That one clock value must be no earlier than final-authorization
observation, candidate `asOfUtc`, current Active `projectedAt` and retained
`lastRebuiltAt`; finalization does no further source or digest work before the
atomic switch. Future facts, negative lag or regressed/throwing clock is a
dependency failure with no Inbox completion or generation switch. A `Current`
no-op performs no new clock call. Freshness remains the WP-1403 checkpoint-lag
fact, not wall-clock aging of an unchanged queue.

If current source versions equal the Event result, the current safe row must
match the lifecycle proof exactly. If current versions are greater, each
intermediate operation needed to prove complete-through advancement must be
present in the authorized source evidence and the final row must reconcile to
that history. Lower versions, an unknown same- or cross-Ticket intermediate gap, checkpoint
regression, same checkpoint with changed as-of, or a well-formed Event not
backed by the exact committed operation retries without switching generation.
An Event/operation semantic mismatch is a permanent rejected/parked delivery.
There is no cross-Ticket ordering claim.

A completed same-Event duplicate arriving through either the raw registration
or the raw-only facade short-circuits in generic Inbox before its handler, so it
performs no parsing, authorization or source read and returns no result hash or
object fact. A different Event ID with the exact original operation and
otherwise byte-equivalent
semantic envelope can complete Inbox without a second business effect and
preserves the operation's original Event reference. Same operation with changed
Actor, scope, version, status, quantity, time, correlation or causation parks.
On `Current` it creates no generation; only a separately proven `Successor` may
perform the already defined metadata/source-checkpoint switch.
Dependency, lock, database or commit uncertainty retries without completing
Inbox. Generic Inbox `result_hash` remains null.

Projection row `originalSourceEventReference`,
`sourceEventSemanticDigest` and `sourceEventOccurredAt` remain permanently the
original `KitchenWorkCreated.v1` creation provenance. A lifecycle Event never
overwrites or aliases those fields. Header `sourceEventBindingDigest` continues
to bind only the exact original creation-Event set. Lifecycle authenticity is
proved transiently by the delivery + committed-operation proof; source
checkpoint/as-of and the queue snapshot advance, but no personal lifecycle
Event or Actor reference is copied into the projection.

The queue row gains nullable `acceptedAt` and `orderItemReadyAt`. Neither field
contains Actor or evidence. Both enter the safe queue snapshot digest.
`acceptedAt` is derived from the unique Accept operation. Every lifecycle
consumer and rebuild reconciles it from current authorized source, so Start,
Progress or Completed delivery before the Accepted Event still converges to a
complete safe snapshot. `orderItemReadyAt` is derived only from the unique
Ready result and, until WP-1406, can become non-null only through a complete
authorized rebuild. Incremental WP-1404 lifecycle consumers preserve the prior
Ready value and never introduce one. Null means `Unknown / not yet projected`,
never authoritative `Not Ready`. Queue state cannot authorize or deny Ready,
Start, completion, Fulfillment or handoff.

The dedicated queue-source and stored-row parsers widen Ticket and Work Item
versions from WP-1403's creation-only literal `1n` to any positive Domain
`bigint`, while retaining bigint-safe canonical digest serialization. They
accept only the already closed Work Item status vocabulary and exact quantity
invariants. The original `KitchenWorkCreated.v1` path still requires an Open
version-1 Ticket with version-1 Queued, zero-completed Work Items; only a strict
lifecycle Event plus exact current source can advance a projected row.

existing digest bytes. The migration adds a required internal

replaces `enforce_kitchen_work_queue_generation_transition()` so the marker is

and no service guesses which algorithm produced it. The binding marker exists

other public queue result strip it and do not widen the WP-1403 public contract.

### `rms_kitchen.kitchen_work_lifecycle_operation`

One append-only row represents one successful explicit command or its automatic
Ready child action. An explicit row stores its durable replay result, exact
Brand / Store / Ticket scope, nullable target Work Item / OrderItem references
according to action, independent non-null `idempotency_key`, server-owned

accepted-operation reference for Start, opaque admission or Expo anchors where
applicable, Audit and optional Event references, correlation / causation,
occurred time and 30-day replay expiry.

An automatic Ready child is a second System row in the same Complete
transaction. Its UUIDv7 operation reference is deterministically derived by
the injected stable-reference port with exact purpose
`KitchenAutomaticOrderItemReadyOperation` from the canonical parent Complete operation
and scope; it is distinct from the parent and every observed input / result
reference. Its `idempotency_key` and replay expiry are null; it cannot be invoked
or replayed independently.
Its causation is the parent Complete operation, its action is
`KITCHEN_ORDER_ITEM_READY`, its reason is `ALL_WORK_ITEMS_COMPLETED`, and its
Ready result points to the child row. Resolving the parent operation returns and
strictly verifies the complete parent + child + Ready-result bundle.
Stable-reference throw, malformed output or namespace collision is a dependency
failure that rolls back the complete parent transaction.

The exact action codes are `KITCHEN_WORK_ITEM_ACCEPTED`,
`KITCHEN_WORK_ITEM_STARTED`, `KITCHEN_WORK_ITEM_COMPLETION_RECORDED` and
`KITCHEN_ORDER_ITEM_READY`. The first three use purpose
`KitchenWorkExecution`; Ready uses `KitchenExpoCoordination`. Exact reason codes
are `WORK_ITEM_ACCEPTED`, `WORK_ITEM_STARTED`,
`COMPLETION_QUANTITY_RECORDED`, `EXPO_MARKED_READY` and, for the automatic
System child, `ALL_WORK_ITEMS_COMPLETED`. Explicit commands use source channel
`KDS_COMMAND`; the automatic Ready child uses `KITCHEN_AUTOMATION`.

The migration applies exact action-discriminated CHECK constraints. They close
User versus System Actor shape, allowed target and required-null columns,
expected/result version arithmetic, before/after status, delta/cumulative/
required quantity shape, Event-reference presence for event-producing actions,
admission/Expo anchor presence, correlation/causation, result shape and the
exact independent idempotency-key/operation/correlation shape and 30-day replay
expiry for explicit rows, plus null key/expiry for the automatic child.

vector, full-quantity equality, causal operation shape and no Ready Event.

## Atomic Audit, Outbox and privacy

Every new operation writes one descriptor-safe, validated Confidential Audit
record in the same transaction. An automatic Ready child writes its own System
Audit causally bound to the named User Complete operation. Audit summaries are
limited to action code, safe target type, before / after status and version,
quantity outcome and correlation. They contain no display name, Option text,
Customer note, health / allergen fact, admission / Expo digest, Session / token,
raw request or error detail.

Audit uses the exact action and reason codes above, source channel `KDS_COMMAND`
or `KITCHEN_AUTOMATION`, classification `Confidential`, retention policy
`KITCHEN_BUSINESS_RECORD` version `1`, and target type `KitchenWorkItem` or
`KitchenOrderItem` according to command.

Accept, Start, partial Progress and final Completed Outbox Events are mandatory
for their corresponding committed operation. Mark Ready / automatic Ready has
no WP-1404 Ready Event. A required operation, source mutation, Ready result,
Audit or applicable Outbox failure rolls back all effects.

Errors use one safe message, `kitchen work is unavailable`, and only the closed
codes:

- `KITCHEN_WORK_INPUT_INVALID`;
- `KITCHEN_WORK_PERMISSION_DENIED`;
- `KITCHEN_WORK_NOT_FOUND`;
- `KITCHEN_WORK_VERSION_CONFLICT`;
- `KITCHEN_WORK_PRECONDITION_FAILED`; and
- `KITCHEN_WORK_DEPENDENCY_UNAVAILABLE`.

The mapping is closed: malformed public input is `INPUT_INVALID`; a definitive
User-command authorization denial is `PERMISSION_DENIED`; an authorized absent
target is `NOT_FOUND`; expected-version, changed-idempotency, CAS or semantic
unique races are `VERSION_CONFLICT`; a well-formed but disallowed transition,
Blocked admission or Expo precondition is `PRECONDITION_FAILED`; authorization
provider throw, malformed/corrupt source or durable result, dependency, clock,
digest, transaction, database or commit uncertainty is
`DEPENDENCY_UNAVAILABLE`. None of those technical failures is converted into a
permanent input result. Lifecycle-consumer denial and throw use the separate
rejected/park versus retry mapping frozen above.

Not Found is returned only after authorization. Errors, logs, traces and
telemetry expose no object, Actor, Store, SQL, bind, digest, narrative or
dependency detail. Metrics use only bounded action / outcome / error-class
labels.
