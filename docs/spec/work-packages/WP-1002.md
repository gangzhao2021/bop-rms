## Purpose

Create the smallest provider-neutral `@rms/dining` Phase-1 stub that proves:

1. a bounded compact token has an exact canonical ES256 protected header、payload and 64-byte JOSE
   signature；
2. verification accepts only one exact non-compromised `Current` or `Overlap` key from an explicit
   immutable key-set evidence record；
3. the signed payload proposes one strict public Store reference、optional public Table reference、
   `DineIn` / `Pickup` channel、locale、issued/expiry instants and revocation version；
4. token lifetime is half-open、at most 180 days and evaluated only against an explicit canonical
   UTC instant；
5. verified payload values resolve to one exact active Tenant-owned Store/Table assignment whose
   current revocation version still matches；
6. a verified fixed QR returns only a customer-safe immutable context and never becomes
   authorization；
7. malformed request is distinct from every valid-shaped but unavailable QR outcome, while
   signature、key、expiry、scope、assignment、revocation and dependency failures are externally
   uniform；and
8. telemetry is bounded to stable operation/outcome/reason codes and excludes token、signature、
   `kid`、public/internal references、locale、time and key evidence.

WP-1002 establishes only `ResolveQrTableContext`. WP-1003 owns creation/rotation of the server-side
Guest Session；WP-1004 owns invalid/expired QR HTTP/UI error mapping；WP-1006 owns Staff-started
Dining Session、short-lived join credential and copied-Table-QR abuse behavior.

## Ownership and Domain boundary

Dining owns Dining Area、Table、Table assignment and Table QR context semantics. Because the first
Pilot does not otherwise put the complete Dining module on the Phase-1 critical path, this WP
creates the exact `@rms/dining` Phase-1 stub authorized by Handoff Section 48.5.

- `@bop/tenant` remains the sole owner of Brand/Store identity、scope and lifecycle.
- `@rms/store` remains the sole owner of Store public profile and operating status.
- Dining owns public Table reference binding、Table lifecycle/assignment and QR revocation version.
- signing-key registry、KMS and abuse infrastructure enter only through provider-neutral injected
  ports；Dining never receives private signing material.
- the Dining Domain layer evaluates already validated primitive token/key/context values only.
  Cross-Domain evidence validation and signature-port composition remain in Application.

The result is context metadata, not a Permission、Session、credential or capability to query an
Order or execute a Command.

## Adopted decisions

1. **New bounded package —** create exact RMS package `@rms/dining` with module name `dining` and
   lifecycle `Phase 1`. It is a query-only Phase-1 stub, not the full Phase-2 Dining Aggregate.
2. **Query only —** implement a pure resolver over injected evidence. No Command、mutation、
   expected version、idempotency ledger、Audit append、Event、Outbox or Inbox is required.
3. **Request —** `ResolveQrTableContextRequest` contains one compact `qrToken`、explicit canonical
   UTC `evaluatedAt` and exact purpose `CustomerEntry`.
4. **Bounded compact token —** token is ASCII、at most 2,048 characters and exactly three
   unpadded base64url segments separated by `.`. Empty、padded、non-canonical or extra segments are
   invalid before dependency access.
5. **Protected header —** decoded UTF-8 JSON is a plain closed record in exact canonical field
   order/value form: `alg="ES256"`、bounded `kid` and `typ="BOP-QR"`. `none`、algorithm confusion、
   `crit`、`jku`、`jwk`、`x5u` and unknown fields are prohibited.
6. **Signed payload —** decoded UTF-8 JSON is a plain closed record with exact canonical field
   order/value form:
   - `schemaVersion=1`；
   - strict UUIDv7 `qrReference` and `publicStoreReference`；
   - `publicTableReference` UUIDv7 for `DineIn` and exact `null` for `Pickup`；
   - closed channel `DineIn | Pickup`；
   - normalized BCP 47 `locale`；
   - canonical UTC `issuedAt` and `expiresAt`；
   - positive safe-integer `revocationVersion`.
7. **Canonical bytes —** JSON parser output must serialize back to the exact decoded header/payload
   bytes using the contract field order. Duplicate keys、alternate ordering、whitespace and
   non-canonical escape/number forms fail closed.
8. **Signature —** signature segment decodes canonically to exactly 64 raw JOSE bytes. The
   Application passes only protected-header/payload signing input、signature bytes、`ES256` and an
   opaque public-key reference to the injected verifier.
9. **No private key —** package contracts contain no private key、KMS key ID/ARN、PEM、JWK、X.509、
   Provider response or unrestricted public-key bytes. Signing and key creation are excluded.
10. **Key set —** one injected exact-shape immutable registry contains a bounded sorted list of
    `Current | Overlap` verification keys、registry version/evidence reference and evidence
    validity. Key records contain bounded `kid`、algorithm `ES256`、opaque public-key reference、
    half-open validity and optional compromise instant.
11. **Unique key —** exactly one key must match `kid`; it must be valid at issuance and evaluation、
    remain in the explicit current/overlap set and have no compromise effective at or before the
    evaluation instant. Zero、duplicate、ambiguous or stale registry evidence is unavailable.
12. **Verifier result —** injected verifier returns only `Verified | Invalid | Unavailable`.
    Anything other than exact `Verified` is externally `QrUnavailable`; verifier exceptions are
    normalized identically.
13. **Signature before payload trust —** only compact framing/header/key selection is processed
    before signature verification. Payload semantics and Table lookup occur only after
    `Verified`.
14. **Token timing —** `issuedAt <= evaluatedAt < expiresAt` and
    `expiresAt - issuedAt <= 180 days`. Host clock、clock guessing and inclusive expiry are
    prohibited.
15. **Context evidence —** one injected exact-shape record binds payload public Store/Table/channel
    to exact internal Tenant Brand/Store/Table scope、active Store/Table lifecycles、active Table
    assignment、current revocation version、immutable evidence reference and validity instant.
16. **Pickup/Dine-in shape —** `DineIn` requires one active Table binding；`Pickup` requires no
    Table. `Delivery` and arbitrary channel codes are excluded from this WP.
17. **Immediate invalidation —** inactive Store/Table、Table reassignment、disabled QR state、
    revocation-version mismatch、key compromise or expired evidence returns `QrUnavailable`.
    Store operating-hours closure is composed later through WP-1001 and does not mutate QR truth.
18. **Customer-safe output —** Verified output contains only `qrReference`、public Store/optional
    Table references、channel、locale、issued/expiry instants and revocation version. Internal
    Tenant/Brand/Store/Table IDs、key/registry references and signature are excluded.
19. **Context is not authority —** output grants no Merchant capability、Dining join、Host、
    Participant、Cart/Order write、Order read or Guest Session. Fixed Table QR cannot enable
    `Guest Self-Start` or `Convenience Mode`.
20. **Uniform unavailable —** signature/key/timing/scope/lifecycle/assignment/revocation/shape and
    dependency failures all return the same `QrUnavailable` result without an identifier oracle.
21. **Malformed request —** invalid outer request/token framing/evaluation instant/purpose returns
    bounded `InvalidRequest` before dependency access. WP-1004 may later map UI copy without adding
    an oracle.
22. **Bounded dependency use —** key registry、signature verifier and context lookup are each
    called at most once and only in that order. The service does not retry、read the host clock、
    fetch a URL、perform DNS or mutate evidence.
23. **Telemetry —** labels are limited to `operation=ResolveQrTableContext`、outcome and stable
    reason. Token、signature、`kid`、public/internal refs、scope、locale、time、key/registry and
    revocation values are prohibited.
24. **Privacy classification —** verified public QR context is `Public`; key registry metadata and
    internal scope evidence are `Internal`; raw IP/device abuse evidence is `Confidential` and
    absent. Unknown/unclassified fields fail closed；fixtures are synthetic.
25. **No Guest Session —** no Cookie、Session identifier、CSRF token、server Session store or
    Customer authorization is created. WP-1003 owns that composition after Store/abuse checks.
26. **No abuse infrastructure —** no WAF、IP/device parsing、abuse bucket、rate limiter or copied-QR
    decision exists. WP-1006/2042/2048 own those controls and the accepted budgets.
27. **No persistence/transport/UI —** no schema/table/view、migration、RLS、repository adapter、
    HTTP route、redirect、cache policy、PWA screen or Merchant page is included.
28. **External Evidence —** no real QR、Store/Table、KMS/public key、signature、Customer traffic、
    load、staging or production evidence is available or claimed.
29. **Hard stop —** unsigned/algorithm-confused token、private key material、internal-ID input、
    ambiguous key/context、expired/revoked fact、authorization claim、Guest Self-Start、persistence、
    production API/UI、Provider/resource or allowlist-external tracked file stops implementation.

## Public contract

The implementation candidate defines:

- `ResolveQrTableContextRequest`
  - `qrToken`
  - `evaluatedAt`
  - exact purpose `CustomerEntry`
- `QrVerificationKeySetEvidence`
  - immutable registry version/evidence validity
  - bounded current/overlap ES256 public-key-reference records
- `QrTableContextEvidence`
  - exact active Tenant Brand/Store/Table assignment
  - signed public-reference/channel binding
  - current revocation/evidence validity
- `ResolveQrTableContextResult`
  - `Verified` with immutable customer-safe `QrTableContext`
  - `InvalidRequest`
  - uniform `QrUnavailable`

The service parses bounded framing/header, selects one exact key, verifies the original compact
signing input, then parses payload timing and resolves exact context evidence. It never signs、
persists、creates a Session or reveals why an unavailable token failed.

## Risks、rollback and next action

- Compact-token parsing can enable algorithm confusion or parser differentials；the contract fixes
  ES256、canonical bytes、closed shapes、strict UTF-8/base64url and an exact signature length.
- A static QR can be mistaken for Dining authorization；the output is context only and every
  Session/join/Order capability is explicitly absent.
- Stale key、assignment or revocation evidence can preserve access；exact validity and matching
  current evidence fail closed.
- Rollback before merge is deletion of this brief plus bounded index edits. After merge, correction
  is a forward documentation/implementation change；accepted history is never rewritten.
- Next allowed action is readiness verification followed by exact-head pinned-Linux CI and
  Section 91 review. Implementation starts only from the verified readiness squash on `main`.
