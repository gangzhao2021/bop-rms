## Purpose and boundary

Implement the smallest formal Ordering aggregate created from one still-current Checkout Validation:
one Order, its first Order Batch and stable Order Item identities. The model retains exact Brand,
Store, Order Type, Source Channel, Cart/Version, Quote, validation, Submission and Actor references.
Creation starts at canonical phase `Submitted`, closure `Open`, and a distinct Payment summary of
`NotReported`; it does not infer Payment facts.

## Contract and acceptance criteria

1. Creation consumes a closed, runtime-validated WP-1220 evidence object and fails at the exact
   `validUntil` instant or when submission predates validation.
2. The first Batch preserves the exact Checkout validation, Quote, Cart and Cart Version and the
   supplied unique Submission reference. WP-1224 remains owner of durable replay enforcement.
3. Every validated Cart Item maps exactly once to a stable Order Item identity under the first
   Batch; no missing, extra, duplicate or cross-Batch identity is accepted.
4. Dine-in requires a Dining Session while Pickup forbids one. Source Channel, Created By Actor and
   Submitted By Actor remain explicit and may differ.
5. The aggregate is deeply frozen, begins only at `Submitted + Open`, and cannot claim a Payment
   result. Item payloads deliberately contain no Catalog, Option, Price or Tax snapshot fields.
6. Frozen install, Ordering regression, affected static/build and repository architecture checks,
   final scope/security review and exact-head/exact-main CI pass before Done.
