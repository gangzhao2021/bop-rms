## Purpose

Define the smallest same-origin Customer-entry HTTP and public error contract that proves:

1. a signed QR is submitted only in a bounded POST body, never a query/path、redirect or log；
2. malformed transport input is distinct from a valid-shaped but unusable QR, while expired、
   revoked、copied、unknown Store/Table、signature/key、Store availability、abuse and dependency
   causes remain one non-oracular public outcome；
3. successful server composition establishes an exact WP-1003 Guest Session, emits only the fixed
   `__Host-bop-guest` Cookie plus page-memory CSRF and customer-safe context, and never exposes
   internal Brand/Store/QR/Session references or selector hashes；
4. invalid/expired recovery never guesses another Store and offers only re-scan / Staff-assistance
   guidance until a future accepted safe Store-selection policy exists；
5. every response is no-store、non-indexable and non-reflective, with stable localized message keys
   rather than server-controlled prose or cause detail；and
6. no Menu、Cart、Order、Dining join、Customer Profile、Provider、Service Worker or visual screen is
   implemented in this WP.

WP-1004 owns the public entry transport envelope and invalid/expired error/recovery contract.
WP-1002 remains the owner of QR verification facts. WP-1003 remains the owner of Guest Session
credentials and lifecycle. WP-1006 owns copied-QR abuse policy and Dining admission. WP-1700 owns
the `CUST-ENTRY-CONTEXT` visual screen and browser fragment handoff.

## Ownership and trust boundaries

- `apps/api` is the composition root and owns the same-origin HTTP handler only.
- The handler consumes one injected Customer-entry composition port. That server port composes
  WP-1002 QR verification、WP-1000/1001 Store facts、admission/abuse decisions and WP-1003 Guest
  Session creation. The HTTP layer does not import or query private Domain storage.
- `@bop/identity` remains the source of the fixed Guest Cookie descriptor and raw credential
  boundary. The handler serializes the accepted descriptor without changing its flags.
- `@rms/dining` remains the owner of the static QR context and deliberately exposes only
  `InvalidRequest | QrUnavailable | Verified` to composition. WP-1004 cannot infer the cause of
  `QrUnavailable`.
- `apps/customer-pwa` is not changed. WP-1700 will read a signed QR from a browser fragment,
  remove it from visible history before network use, POST it to this contract and render the
  accepted message keys.
- Request correlation may record only the stable route template and bounded result code. The raw
  QR、Cookie、CSRF、public/internal references、Origin and recovery context are prohibited labels.

The static signed QR is reusable context, not a Guest credential. The HTTP request creates a fresh
server operation/reference and cannot select a Guest Session、Brand、Store、Table、channel or
locale.

## Adopted decisions

1. **Route —** add exact same-origin `POST /bff/customer/entry`. No GET、query-token、path-token、
   redirect-token、form or multipart variant is accepted.
2. **Media type —** require `application/json`; the global `64kb` JSON ceiling remains, while the
   strict body contains only `qrToken` with length `1..2048`.
3. **Browser fragment boundary —** a future QR deep link carries the signed compact value in the
   URL fragment so it is not sent in HTTP requests/referrers. WP-1700 owns fragment parsing and
   immediate `history.replaceState`; WP-1004 neither adds nor accepts a URL transport.
4. **Same-origin proof —** require exact configured HTTPS `Origin` plus Fetch Metadata
   `Sec-Fetch-Site: same-origin` and `Sec-Fetch-Mode: cors`. Missing、ambiguous、cross-site、
   `null` or malformed values fail before the composition port.
5. **No CORS —** emit no `Access-Control-Allow-Origin` or credential-sharing header and register no
   OPTIONS behavior for this route.
6. **Fresh server identity —** the handler injects fresh opaque UUIDv7 entry-request and operation
   references. Client values、existing Cookie and fixation candidates cannot supply either.
7. **Injected composition result —** accept only strict:
   - `Established` with customer-safe public Store/Table、`DineIn | Pickup`、normalized locale、
     Guest Session/CSRF credentials and effective expiry；
   - `InvalidRequest`；or
   - `EntryUnavailable`.
8. **Uniform unavailable mapping —** expired、not-yet-valid、revoked、bad signature/key、
   unknown/mismatched Store/Table、Store closed/unavailable、copied/abuse denied、stale evidence、
   dependency failure and Guest admission denial all map to `entry_unavailable`. No reason or
   retry timing is returned.
9. **Malformed mapping —** invalid JSON/media type/body shape/compact framing maps to
   `entry_request_invalid` only when the failure is established before an existence-bearing
   dependency lookup.
10. **Dependency exception —** an injected composition exception or malformed result maps to
    `entry_service_unavailable`; it contains no upstream name/detail and does not claim the QR is
    invalid.
11. **HTTP statuses —** success `201`；malformed `400`；uniform unusable `422`；service unavailable
    `503`. Status is not used to distinguish invalid from expired or any other QR cause.
12. **Success body —** exact versioned body:
    `schemaVersion: 1`、`status: Established`、public Store/Table、channel、locale、
    `contextExpiresAt` and raw CSRF for page memory. It excludes QR、Guest Session、internal
    Brand/Store、selector/hash、operation and evidence references.
13. **Cookie —** serialize exactly
    `__Host-bop-guest=<43-char value>; Path=/; Secure; HttpOnly; SameSite=Lax` with no `Domain`、
    `Expires` or `Max-Age`. Unknown descriptor/credential shape fails closed.
14. **CSRF —** raw CSRF appears only in the no-store success JSON and is never a Cookie、header、
    URL、log、analytics value or browser-persistence instruction.
15. **Public error body —** exact versioned body:
    `schemaVersion: 1`、stable `code`、localized `messageKey` and closed recovery object. It contains
    no echoed input、identifier、timestamp、dependency/cause or arbitrary prose.
16. **Recovery —** unavailable recovery is exact
    `action: RescanOrAskStaff`、`storeSelection: Hidden`. Malformed recovery is
    `action: Rescan`、`storeSelection: Hidden`. Service-unavailable recovery is
    `action: RetryOrAskStaff`、`storeSelection: Hidden`.
17. **No Store guessing —** WP-1004 never lists nearby/alternate Stores、accepts internal/public
    Store lookup or infers a Store from hostname/location. Safe Store selection requires a future
    explicit public policy contract.
18. **Response controls —** all outcomes include `Cache-Control: no-store`、
    `Pragma: no-cache`、`Referrer-Policy: no-referrer` and
    `X-Robots-Tag: noindex, nofollow`.
19. **Non-reflection —** neither body nor response headers contain the QR、Cookie、CSRF on errors、
    Origin、incoming headers or dependency error text.
20. **Availability behavior —** when the Customer-entry port is absent, the route remains
    registered but returns the same bounded `503` service-unavailable contract. Readiness/health
    semantics are not changed.
21. **Retry semantics —** no `Retry-After` is invented because no accepted capacity/abuse budget
    exists. A later retry uses a new server operation；the static QR remains reusable unless the
    owning verifier/admission policy denies it.
22. **No telemetry oracle —** allowed labels are route template、HTTP status and stable public
    result code only. Do not distinguish expired、invalid、revoked、unknown、abuse or dependency in
    Customer-entry metrics.
23. **Accessibility/localization —** the API returns message keys, not final English copy. WP-1700
    owns a visible heading、instructions、focus placement、screen-reader announcement、non-color
    cues and minimum touch targets.
24. **Offline —** no Service Worker/cache/background replay is added. Customer entry is
    NetworkOnly and offline UI remains a later WP-1700/1707 concern.
25. **No external evidence —** no real QR、Cookie、Store/Table、Customer、Origin、browser、WAF、
    load、staging or production evidence is available or claimed.
26. **Hard stop —** cause-specific QR error、Store guessing、QR in URL/log、client-provided
    operation/scope、loosened Cookie、CSRF persistence、CORS、Service Worker、production adapter、
    Provider/resource、Customer PII or allowlist-external tracked file stops implementation.

## Risks, rollback and next action

- Distinct invalid/expired details create a QR/Store/Table oracle；all valid-shaped unavailable
  causes remain one public outcome.
- A signed QR in query/path leaks through history、referrer、proxy and analytics；the contract is
  POST-body-only and browser fragment handling remains WP-1700.
- CSRF or Cookie mishandling turns entry into a fixation/persistence boundary；serialization is
  fixed and success is no-store.
- Helpful Store recovery can silently guess cross-Store context；Store selection remains hidden
  until an accepted public policy exists.
- Rollback before merge is deletion of this brief plus bounded index edits. After merge, correction
  is a forward documentation/implementation change；accepted evidence history is never rewritten.
- Next allowed action is implementation exact-head pinned-Linux CI followed by Section 91 review.
  Merge remains prohibited until both pass on the immutable reviewed head.
