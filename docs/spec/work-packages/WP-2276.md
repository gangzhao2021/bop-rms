# WP-2276 - Fresh Dining Join Generation After Consumption

## Authority and readiness

Baseline88fb2037a820111beb8f48de63a33cd255b4f09e; branch codex/wp-2276-dining-join-renewal.
The Owner directs continued bounded implementation and verified local commits. Composite Sections0–97,
WP-1006 decisions2/11–18 and WP-2273/2274 require current Staff authority, an Active Session/current
assignment, fresh next-generation identity/hash, one-time use and immutable terminal history.
The current policy only regenerates an unexpired Active capability: after the first Guest consumes it,
or after its15-minute lifetime, Staff cannot issue the next invitation. This contradicts the accepted
multiple-Participant flow without requiring old credential reuse. Replacement also copies the old
pepper version instead of the currently configured hasher's version. Both are implementation defects.

## Bounded transition

Current Staff/Session/Table gates and expected versions stay mandatory. Regeneration creates a new
Active capability with exact next generation, fresh reference/hash, version1 and the existing maximum
15-minute lifetime. The old credential never becomes Active again and its expiry is never extended.
An old Active capability becomes Revoked, including one whose clock lifetime has elapsed. Consumed
or explicitly Expired predecessors remain byte-for-byte equivalent immutable terminal facts; their
consumption/expiry must not be in the future. Explicitly Revoked predecessors stay denied, as do
inactive Sessions, reassignment, future chronology, wrong scope, skipped generation and reused keys.
The new capability records the currently configured pepperVersion; no key material is accessed.

The existing resolveActiveJoin name remains compatible and is documented as the current generation
for an Active Session, which can be Consumed/Expired. No selector lookup/recovery protocol is added.
Tests exercise first Guest -> Staff fresh generation -> second Guest with the same Session and
original Host, distinct Participant/admission, preserved first-operation replay and single-use denial.
The in-memory fixture gains accurate current-generation/history behavior for this concrete scenario;
it is not claimed as database persistence.
