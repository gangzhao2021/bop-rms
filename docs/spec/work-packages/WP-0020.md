## Bounded responsibility

## Closed implementation contract

- Catalog：root `migrations/` only；closed fourteen-band version-`1` namespace registry；namespace is order only and never ownership。
- Name：`<four-digit namespace>_<001-999 sequence>_<closed action>_<snake object>.sql`；global numeric namespace / sequence order。
- Header：exact ordered version、owner、schema、phase、risk、required transaction、bounded lock / statement timeout and recovery fields。
- Bytes：UTF-8 without BOM、LF、final newline；SHA-256 over exact bytes；fully schema-qualified SQL and no templating。
- Bootstrap：`0000_001_create_migration_history.sql` creates only `platform_core` and its exact history table，then records itself in the same transaction。
- History：append-only；same ID / path / metadata / checksum is a no-op；edit、rename、delete、orphan、gap、duplicate and out-of-order fail closed。
- Concurrency：one dedicated `pg` Client；fixed `(1112494162, 1296648018)` advisory key；exclusive apply、shared status / verify、fail-fast busy behavior and explicit release。
- Transaction：one migration per transaction；trusted local search path、finite local timeouts、SQL and history insert commit / rollback together；v1 rejects non-transactional SQL。
- Lifecycle：`status | verify | apply` only；no down、repair、baseline、mark-applied、force、checksum bypass or automatic retry；applied changes are forward-fixed or restored through a separately approved procedure。
- Environment：explicit target identity；password file only；no CLI password / DSN、`DATABASE_URL` or `PGPASSWORD` authority；TLS verify-full outside loopback；safe redacted output。
- Staged enforcement：root catalog and `packages/database` receive exact exceptions；Module-local migration / persistence / Repository / ORM / driver / raw SQL / schema / model / connection / seed remains `UNSUPPORTED_DATABASE_ASSET`。
- Exit：`0` success / help；`1` catalog / ownership / state / lock / apply violation；`2` usage、unreadable / unsafe config、connection / TLS、uncertain lost connection or internal error。

## Acceptance and evidence map

1. **Authority / baseline:** exact fresh baseline、Canonical 0.5.6 / Section 94、ADR-0031 / IDR-0044 and protected Evidence hashes are recorded。
2. **Catalog / namespace:** every legal namespace and name passes；unknown directory、mismatch、duplicate order、case conflict、path escape and symlink fail deterministically。
3. **Metadata / ownership:** exact header and platform owner pass；unknown fields、wrong order / value、foreign schema / owner and namespace-derived ownership fail。
4. **Bytes / immutability:** invalid encoding / BOM / CRLF / missing newline fail；exact checksum is stable；applied mutation、rename、deletion and orphan history fail。
5. **Empty bootstrap:** an isolated empty PostgreSQL database creates only `platform_core.migration_history` and records the first migration atomically。
6. **Repeated execution:** second apply is a successful no-op with no duplicate history or DDL。
7. **Unmanaged boundary:** a pre-existing user / reserved schema or malformed history is rejected without adoption、baseline or mutation。
8. **Transaction:** failing SQL leaves neither its DDL nor history；transaction-prohibited syntax is rejected before execution。
9. **Concurrency:** concurrent apply permits one exclusive owner and returns deterministic lock-busy for the other；shared status / verify behavior is observed。
10. **CLI / diagnostics:** help、status、verify、apply、stable JSON / text、closed codes、sorting、stdout / stderr and exits `0 | 1 | 2` are observed。
11. **Connection security:** wrong confirmation、unsafe host / SSL、unsafe CA / password path、secret symlink / mode and implicit password / DSN authority are rejected。
12. **Redaction:** config、authentication、SQL and connection-loss failures reveal no secret、DSN、SQL body、bind value or sensitive server detail。
13. **Staged coexistence:** legal runner / root catalog passes while every existing Module persistence prohibition and WP-0010–0014 check remains green。
14. **Isolated fixtures:** static roots and uniquely named test databases contain synthetic data only and are removed after success and failure。
15. **Root / CI integration:** `pnpm db:migrate -- --help` and `pnpm migration:check` are discoverable；root `verify` and the sole workflow invoke the finite non-secret migration check。
16. **Scope / security:** final diff contains only the authorized control plane and no WP-0021、business、Provider、production、API / UI or reusable fixture work。

## Risks、rollback、External Evidence and next action

- Risk：bootstrap DDL could become an untracked escape。Mitigation：the first migration is byte-hashed、self-recorded in the same transaction and limited to one shell schema / history table。
- Risk：a broad WP-0013 exemption could admit Module persistence。Mitigation：path- and owner-specific exceptions plus existing negative tests。
- Risk：concurrent or interrupted execution could create uncertain state。Mitigation：session advisory lock、one-client transactions、atomic history and no automatic retry after connection loss。
- Risk：diagnostics could expose SQL or connection secrets。Mitigation：closed safe fields、redaction tests and no raw driver error serialization。
- Rollback：normal reviewed Git revert before integration；applied database changes use forward-fix or separately approved restore，never history mutation。
- External Evidence：production database / role、TLS certificate、backup / restore check、RDS compatibility、real upgrade dataset and production migration results remain external gates，not fabricated acceptance facts。
- Next action after complete local evidence：publish the separately authorized single WP-0020 commit、push and Draft PR，then wait for explicit Owner authorization before any Ready、merge、deploy、production migration or WP-0021 action。
