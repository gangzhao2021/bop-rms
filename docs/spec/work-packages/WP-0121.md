## Purpose

Continue Feature F01.2 with a provider-neutral、synthetic `@bop/media` minimum contract that proves:

1. Media owns Asset metadata、Upload Session、immutable Asset Version and access/reference rules；
2. business Domains store and exchange only validated Asset references, never binary data、
   temporary URLs、credentials、upload grants or storage locators；
3. an Upload Session is Tenant/purpose/scope bound、single use、expires after at most fifteen
   minutes and cannot make unfinished or quarantined content referenceable；
4. finalization reauthorizes the request and accepts only exact server-obtained object evidence
   through an injected Provider-neutral verifier；
5. Asset Versions are immutable, the original is never overwritten and only a clean、ready version
   can resolve；
6. exact Brand/Store scope、accepted Permission and a bounded access purpose are required, with no
   owner-as-grant or cross-Brand reference；
7. Dynamic and Pinned references are distinct, while formal publishing、transaction、evidence and
   compliance uses fail unless Pinned；and
8. state changes compose one atomic next-state plus Audit request and fail closed on ambiguity、
   expiry、reuse、scope mismatch、check failure or persistence failure.

This WP creates no production upload/download endpoint、database object、Provider integration、
scanner、Screen or external resource. WP-0122 owns Publishing Lifecycle；WP-0123 owns reusable
configuration Version/Effective Period；WP-2047/WP-2054 and External Evidence own production media
storage、upload hardening、malware/content processing and operational proof.

## Governing decisions

1. **Exact predecessor —** implementation starts only after WP-0120 exact-head CI、authorized
   squash merge、post-merge exact-main CI and branch/resource cleanup. Baseline
   `71146b9754fccde5a1ab38847f8d0c15c077be03` satisfies that gate.
2. **Domain owner —** `@bop/media` owns Asset、Upload Session、Asset Version、check/processing state、
   access classification and Media Reference. It does not own Tenant、Permission、Audit、Privacy
   Governance、business Aggregate lifecycle、Publishing or Provider resources.
3. **Reference-only boundary —** public business consumption is limited to `MediaReference` and
   bounded resolution/access results. Binary bodies、base64、temporary/signed URLs、bucket/key、
   object-version locator、upload token and credentials are excluded from public contracts.
4. **Opaque identifiers —** Asset、Asset Version、Upload Session and owner references are validated
   opaque UUIDv7 values. Owner type and owner reference are attribution only；they grant no access
   and cannot couple Media lifecycle to another Domain.
5. **Exact Tenant scope —** every Asset and Upload Session is scoped to one Brand or one Store
   within that Brand. Store use requires exact Brand + Store Tenant Context. Cross-Brand direct
   reference fails closed；copy behavior is not implemented here.
6. **Asset metadata —** required metadata is bounded purpose、media kind、declared/sniffed content
   type、positive byte size、checksum evidence、scope、owner attribution、classification and
   positive version. Free text、original filename、contact/identity/payment data and arbitrary
   metadata maps are excluded.
7. **Upload Session —** a session is single use、server-created、purpose/scope/Actor bound and has a
   maximum fifteen-minute UTC interval. Pending、Finalized、Expired and Rejected are closed states；
   reuse or late finalization returns a uniform unavailable result.
8. **Provider-neutral grant —** creation may persist only an opaque upload-grant reference supplied
   by an injected port. The service never constructs a URL、bucket/key、policy、KMS field or claim
   that a real upload exists.
9. **Finalization evidence —** an injected verifier returns exact server-obtained evidence for the
   session-bound quarantine object: opaque object reference、provider object version、size、
   checksum、content type and encryption/check metadata. Caller assertions alone are never trusted.
10. **Quarantine first —** finalization creates an immutable quarantined Asset Version. The exact
    check states are `Quarantined`、`Clean`、`Rejected` and `ProcessingFailed`; processing readiness
    is `Pending`、`Ready` or `Failed`. Only `Clean + Ready` is referenceable.
11. **No scanner claim —** state-transition evidence is accepted only from an injected trusted
    verifier port in synthetic tests. No malware engine、content moderation、GuardDuty、S3 event、
    job、queue or production decision is implemented or claimed.
12. **Immutable versions —** Asset Version content evidence is append-only. Recheck/reprocess creates
    a new result/version under a later WP；neither Asset nor business callers overwrite an original.
13. **Dynamic/Pinned —** `Dynamic` names one Asset and resolves its current clean/ready version；
    `Pinned` names exact Asset + Asset Version. Draft use may accept either. Formal publication、
    transaction、evidence and compliance use require Pinned.
14. **Publishing boundary —** this package validates reference suitability but does not publish、
    schedule、activate、roll back or choose an effective period. Those actions remain WP-0122/0123.
15. **Permission —** Create Upload、Finalize Asset、Authorize Access、Create Variant and Archive Asset
    operations require exact accepted `@bop/permission` decisions for operation and scope. This WP
    implements only Create Upload、Finalize Asset and Authorize Access；the others remain explicit
    unsupported operations.
16. **Access result —** authorized resolution returns only exact Asset/Version references and
    bounded media metadata. Delivery URLs/headers are created later by a private delivery adapter
    after fresh authorization and are never logged or returned by this minimum contract.
17. **Atomic Audit —** each state change constructs a bounded `@bop/audit` append request and passes
    the immutable next records plus Audit request to one injected unit-of-work port. Success is
    reported only if the port atomically commits all of them.
18. **Concurrency/idempotency —** mutations require expected positive version and validated
    idempotency key. Replay may return the identical recorded outcome；key reuse for different
    input、stale version or concurrent session closure fails closed.
19. **Uniform denial —** unknown Asset/session、wrong Tenant/scope/purpose、not-clean、not-ready、
    expired、reused、Permission-denied and verifier mismatch do not expose existence or state to an
    unauthorized caller.
20. **Retention/Legal Hold boundary —** a bounded classification/reference may be carried, but
    retention calculation、erasure、Legal Hold and Privacy rights remain Privacy Governance/future
    work. Media cannot invent or execute those policies.
21. **No persistence change —** no Media table、migration、RLS policy、runtime role、grant、seed、
    repository adapter or production storage is added.
22. **No production API/UI —** `MEDIA-LIBRARY /app/media` remains Phase 1A and later delivery work.
    No route、navigation、frontend state、upload widget or deployment is added.
23. **No external mutation —** no S3、KMS、GuardDuty、scanner、CDN、credential、real Tenant/media、
    Provider account or external resource is created or changed.
24. **Privacy/telemetry —** stable reason/state/result codes may be logged；Tenant、Store、Actor、
    Asset、session、owner、object/checksum references and filenames are not metric labels or logs.
25. **External Evidence remains a gate —** real region/service capability、presigned policy、
    encryption、malware/content detection、retention、Legal Hold、delivery authorization、load、
    recovery、staging and production evidence is `NOT AVAILABLE / NOT CLAIMED`.
26. **Hard stop —** any need for persistence/migration、real upload/delivery URL、Provider SDK、
    scanner decision、Privacy policy execution、cross-Domain private query、production route/UI、
    credential/resource、weakened denial or allowlist-external tracked file stops implementation
    for exact review.
