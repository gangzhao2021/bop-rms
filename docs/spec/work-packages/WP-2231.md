## Implementation and acceptance

1. An injected bounded write transaction runner owns commit/rollback/connection cleanup. Ordering
   locks the exact scoped Cart, checks the expected version and validates the single-item transition.
2. Preserve Cart/Item identity, creator/Participant attribution, immutable lifecycle policy and
   unaffected items. Advance only the accepted idle deadline, content, aggregate version and time.
3. Commit Cart, item and original operation snapshot with Audit's public append in one transaction.
   No SQL accesses foreign private tables. Any write, Audit or verification failure rolls back.
4. Exact repeated persisted commit returns its original record without duplicate writes. Conflicting
   operations/versions fail; service-level retry continues to use the original operation via WP-2230.
   Same-key concurrent business intent converges on the original timestamp and generated Item ID;
   changed business intent remains a conflict. The service verifies that canonical commit result.
5. Real isolated PostgreSQL acceptance covers Add/Update/Remove, operation replay after recreation,
   concurrency, rollback, scope and immutable history. Unit checks bound invalid input/driver errors.
   Exact path/owner/schema/table registration retains driver and unrelated-asset rejection.

This adapter is infrastructure, not an authorization endpoint. The existing service remains the
Session, Participant, Catalog and Audit-input authority. Caller-owned transactions may lend a
read-only query view to existing readers while keeping all writes in the same outer transaction.
No new production grants, migrations, Cart creation, HTTP activation, UI, credentials or Provider.
