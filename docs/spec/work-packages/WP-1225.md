## Purpose

Create Ordering's first rebuildable `ordering_order_status_v1` read model and public query
contracts. It exposes one customer-safe exact-Order view and one Store-scoped merchant queue/detail
view without making the projection a transaction source of truth or joining another Domain's
private tables.

WP-1225 projects only facts currently owned by Ordering: immutable Order/Batch/Item identity and
snapshot summaries, Order Number, source channel/type, submitted time, current Ordering phase and
closure, plus the explicitly separate `NotReported` Payment status. Kitchen, Fulfillment, ETA,
claim, exception, receipt and pickup-proof fields remain typed as unavailable rather than invented.

## Closed execution contract

1. The projection is Ordering-owned, Store-scoped, versioned, generation-switched, rebuildable and
   never writes `order_header`, `order_batch`, `order_item` or other transaction facts.
2. Projection input is one strictly parsed Ordering source snapshot. Replaying the same or an older
   source version is idempotent; conflicting same-version content fails closed; a newer version
   replaces the active generation while preserving checkpoint/freshness evidence.
3. Customer query authorization and a usable Guest Session are checked before any projection read.
   The session must match the exact permanent Submission evidence; Order reference alone grants no
   access. The response excludes actor, Cart, Quote, validation and unrestricted snapshot content.
4. Merchant query authorization is checked before every read and binds Actor, purpose, Brand and
   Store. No cross-Store row, unrestricted customer data or health/personal snapshot field crosses
   the public query boundary.
5. Queue search is limited to exact Order reference/number. Filters are closed to the currently
   representable Order type, channel, phase, closure and Payment status; pagination is bounded and
   deterministic by submitted instant plus Order reference.
6. Every query result declares projection name/version, source checkpoint, projected-at instant and
   `Fresh | Stale | Rebuilding | Failed`. Non-fresh data is explicit and may not authorize a
   mutation or pretend to be current transaction state.
7. `CUST-ORDER-STATUS`, `OPS-ORDER-QUEUE` and the WP-1225 portion of `OPS-ORDER-DETAIL` retain the
   Section 88 routes, placement, permissions, fields and universal state/accessibility contracts.
   This WP supplies backend contracts only; WP-1705 and WP-1803 own UI/realtime composition.
8. Projection tables force Store RLS, grant no runtime access, use synthetic-only fixtures, and
   retain no secret, Provider payload, contact datum, medical narrative or unrestricted object.

## Risks, rollback and residual gates

The main risks are projection-as-authority, leaked transaction snapshots, reference-only customer
access, cross-Store queue reads, stale mutation hints and lost generation/checkpoint ordering.
Closed contracts, authorization-before-read, safe summaries, exact scope, monotonic source version,
generation switching and explicit freshness mitigate them. Rollback is a reviewed Git
revert/forward-fix before WP-1226 depends on the projection; no destructive data rollback is
authorized. Provider, Pilot Store, staging/production and External Evidence remain gated.
