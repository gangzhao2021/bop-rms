## Outcome and closed semantics

WP-1405 adds the concrete Kitchen hint catalog entry and a runtime-inactive publisher boundary for
an already committed `kitchen_work_queue_v1` generation activation. The exact message type is:

`kitchen.work-queue.updated` version `1`.

One successful active-generation switch may produce one lossy Store-scoped hint. The hint is only a
notification that the canonical Kitchen queue Query should be refreshed. It is not a Domain Event,
Audit fact, projection row, command response, checkpoint, replay cursor or source of truth.

The message identifies the complete activated generation rather than a Work Item. This is required
because one incremental or rebuild switch may add, change or remove multiple rows, and the client
must requery the complete authorized projection rather than infer row state from a lossy message.
WP-1405 does not emit one message per Work Item and does not copy Work Item status, quantity,
Station, note, display, Option, preparation, ETA, allergen or readiness facts into realtime.

## Exact message contract

The deeply frozen message has exactly these fields and no `data` bag:

```text
{
  messageId,
  type: "kitchen.work-queue.updated",
  version: 1,
  occurredAt,
  scope: { brandId, storeId },
  resource: { type: "kitchenQueueGeneration", id },
  projectionVersion: 1
}
```

- `messageId` is a server-generated canonical lowercase UUIDv7 with purpose
  `KitchenRealtimeMessage`. It is independent from Event, operation, correlation, checkpoint,
  generation, Brand and Store references and cannot alias any of them.
- `occurredAt` is exactly the committed generation `projectedAt`; no client time or second clock is
  accepted.
- scope is exactly the committed generation Brand and Store.
- resource `id` is exactly `projectionGenerationReference`; resource type is the closed literal
  `kitchenQueueGeneration`.
- `projectionVersion` is the static contract/projection version `1`, not a mutable row version or
  replay sequence.

Every accepted input is the existing strict `KitchenQueueGeneration` contract with projection name
`kitchen_work_queue_v1`, version `1`, status `Active`, canonical scope/references/times/digests,
bounded counts and internally consistent freshness. The publisher never accepts a caller-composed
scope, resource, message type, version, timestamp or arbitrary payload.

## Publication and failure boundary

`createKitchenRealtimeService` exposes one method:

`publishCommittedQueueActivation(value: unknown)`.

The method is called only after the generation switch transaction has successfully committed. The
port name and input contract do not authorize an in-transaction call. WP-1405 intentionally does
not modify the WP-1403 consumer transaction: a realtime failure can never roll back, retry or make
ambiguous the Inbox completion or projection switch.

The service performs this order:

1. strict-parse and deeply freeze the committed generation;
2. reject any non-Active, wrong-name/version or malformed generation without calling dependencies;
3. obtain exactly one server message reference for the accepted attempt;
4. build and strict-parse the minimal concrete hint;
5. call the injected lossy publisher once; and
6. return a deeply frozen bounded result.

The result is exactly `{ outcome, message }`, where outcome is `Delivered`, `NoSubscribers`,
`Unavailable` or `Rejected`. `message` is the exact hint for the first two outcomes and `null` for
dependency failure or rejected input. A non-negative safe-integer delivery count greater than zero
means `Delivered`; zero means `NoSubscribers`. Throwing, malformed or negative publisher output is
`Unavailable`. Invalid message identity is `Unavailable`. Invalid input is `Rejected`. The method
does not throw and calls a low-cardinality metric sink best-effort; metric failure cannot change the
result.

Loss, duplicate delivery, no subscribers and publisher outage are normal realtime outcomes. They do
not create durable retry, Inbox, Outbox, database, Audit or error evidence. Connect/reconnect and
every received Kitchen hint invoke the canonical queue Query; no Command is replayed.

## Security and privacy review

Actors and trust boundaries are: committed Kitchen projection owner → strict Kitchen realtime
service → injected lossy publisher → WP-0036 authorized Store stream → merchant browser canonical
Query. The input and hint are `indirect_identifier` only.

Prohibited fields include Customer note, note-derived digest, health/allergen fact or inference,
localized display name, Option, preparation instruction, Station, status, quantity, ETA, Actor,
Session, permission, Ticket/Order/Work Item reference, Payment, Provider, contact, token, secret,
raw error, URL and arbitrary narrative. These fields are absent from contract, result, metric and
fixtures. Scope/resource/message identifiers are never metric labels, logs or errors.

Abuse and failure tests cover extra/symbol/accessor/proxy input, wrong projection/scope/version,
malformed time/reference/digest/count/freshness, identity alias, mutable dependency output,
publisher throw/malformed count, duplicate attempts, zero subscribers, cross-Store transport
rejection, and sentinel Customer/health/secret fields. Open findings at brief time:

- Blocker `0`
- High `0`
- Medium `0`
- Low `0`

Residual risks are externally gated distributed fan-out loss, capacity, real Session revocation,
browser query recovery and production observability. No risk acceptance or production evidence is
