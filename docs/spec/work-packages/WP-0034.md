This brief resolves and implements the bounded design questions for WP-0034. It does not reopen the accepted Event Envelope、Outbox、Inbox or retry/dead-letter state machines.

## Problem statement

WP-0030 already requires a UUIDv7 `correlationId` and optional UUIDv7 `causationId` on every Domain Event. Outbox persistence stores both identifiers, dispatcher reconstruction preserves both, and Consumer Inbox stores the correlation identifier. The repository does not yet own one transport-neutral context contract that defines:

- how a new root correlation is created;
- when an existing correlation may be continued;
- how immediate causation is derived for Command- and Event-triggered work;
- how retries、replays and commit-unknown reconciliation preserve identity;
- how concurrent work avoids ambient-context bleed;
- which identifiers may be returned or observed without becoming high-cardinality or sensitive-data channels.

Without this contract, later API、logging、trace and Event Catalog work could create competing identity semantics or silently rewrite causal history.

## Intended outcome

WP-0034 delivers:

1. Eventing owns one immutable Correlation / Causation Context value contract.
2. Root creation and child derivation use injected UUIDv7 generation and deterministic validation.
3. Correlation is preserved across Outbox dispatch、Consumer delivery、retry and replay.
4. A newly emitted Event records only its immediate Command or source Event as causation.
5. No context identifier grants Tenant、Store、Actor or object access.
6. No unrestricted context becomes a metric label、URL value、payload field or telemetry baggage.
7. HTTP middleware、structured logging and OpenTelemetry integration remain owned by later Work Packages.

## Existing accepted floor

The following facts are already implemented and are not redesigned here:

- `DomainEventEnvelope.correlationId` is required UUIDv7.
- `DomainEventEnvelope.causationId` is optional UUIDv7.
- `platform_eventing.outbox_event` persists `correlation_id` and `causation_id`.
- the Outbox dispatcher reconstructs both fields without creating new values.
- `platform_eventing.consumer_inbox` persists `correlation_id`.
- retry/dead-letter records do not duplicate payload or unrestricted context identifiers into metric dimensions.
- Brand / optional Store scope、Actor、idempotency、Aggregate identity and Correlation identity are separate contracts.

## Accepted Owner decisions

The Owner accepted all recommendations without modification on `2026-07-24` Toronto time.

1. **WP boundary** — Recommended: WP-0034 owns the transport-neutral in-process context contract and Eventing/Worker propagation proofs only. Express request middleware、public response envelopes and end-to-end Request / Command / Event integration remain WP-0041；structured logging remains WP-0040；OpenTelemetry SDK/export remains WP-0041–0045.
   Impact: closes Eventing identity semantics without pulling observability rollout forward.

2. **Context shape** — Recommended: immutable `{ correlationId, causationId? }` with both values validated UUIDv7 strings；Tenant、Store、Actor、Request、Session、Idempotency、Trace and object identifiers are not embedded.
   Impact: prevents one convenience object from becoming ambient authorization or a data bag.

3. **Root creation** — Recommended: create a new root with an injected application-owned UUIDv7 factory；`causationId` is absent. No database default、timestamp-derived ID or random source hidden inside Domain/Eventing code.
   Impact: deterministic tests and one accepted UUID boundary.

4. **Continuation trust** — Recommended: core code can continue only a context already validated by a trusted server adapter. WP-0034 does not accept raw `X-Correlation-Id`、Provider header、query、body or browser input. WP-0041 must later define trusted-upstream/header behavior.
   Impact: prevents correlation spoofing and avoids prematurely choosing HTTP policy.

5. **Immediate causation** — Recommended: a Command-created Event uses the Command ID as `causationId`; an Event-created Event uses the consumed source `eventId`; a child Command uses the immediate parent Command/Event ID. Correlation remains unchanged.
   Impact: produces a navigable causal chain without copying the complete ancestry.

6. **Retry、replay and reconciliation** — Recommended: retries、lost-ack redelivery、commit-unknown reconciliation and replay preserve the original Event correlation and causation exactly. Scheduling IDs、attempt IDs、lease tokens and operator action IDs never replace them.
   Impact: operational recovery cannot rewrite business lineage.

7. **Manual recovery** — Recommended: an operator retry/discard command has its own Command ID under the continuing correlation context. Only a new Domain Event caused by that command may use the operator Command ID as causation；the original dead-lettered Event remains immutable.
   Impact: preserves both original history and the audited recovery cause.

8. **Ambient context** — Recommended: public Application/Eventing contracts pass context explicitly. No module-global mutable state and no Eventing-owned `AsyncLocalStorage`; a later API/logging adapter may use request-local storage only behind the explicit contract and must prove cleanup.
   Impact: prevents cross-request and cross-Tenant context bleed.

9. **Trace separation** — Recommended: W3C `traceparent`、`tracestate`、OpenTelemetry baggage and X-Ray identifiers are not part of WP-0034 durable context and do not require a migration here. Correlation/Causation are durable business-operational lineage；trace propagation/export is a later, separately threat-modeled observability concern.
   Impact: avoids storing vendor or baggage data and preserves WP-0040–0045 ownership.

10. **Persistence** — Recommended: reuse the accepted Outbox correlation/causation columns and Consumer Inbox correlation column. Create no new table、column、index、migration、Repository or generic context store.
    Impact: the missing capability is propagation semantics, not another source of truth.

11. **Privacy and observability** — Recommended: context IDs are `Restricted` operational identifiers. A stable Correlation ID may appear in a permission-safe error response or allowlisted log/trace field only when the owning later WP implements that surface. IDs are prohibited from metric labels、analytics dimensions、URLs、free text and payload-derived attributes.
    Impact: supports investigation without unbounded cardinality or discovery leakage.

12. **Acceptance and command** — Recommended: add unit/concurrency tests plus one synthetic existing-Outbox round-trip acceptance and root command `pnpm correlation-context:acceptance`. Tests must prove root/child derivation、retry/replay preservation、parallel isolation、invalid-input fail-closed behavior and no sensitive-data capture.
    Impact: makes the contract reproducible without claiming an HTTP、Collector or production trace.

## Accepted contract semantics

### Root

```text
correlationId = new UUIDv7 from injected factory
causationId   = absent
```

### Child caused by a Command

```text
correlationId = parent correlationId
causationId   = parent commandId
```

### Child caused by an Event

```text
correlationId = source event correlationId
causationId   = source eventId
```

### Retry or replay of an existing Event

```text
correlationId = original event correlationId
causationId   = original event causationId
```

Correlation and causation do not imply authorization、Tenant membership、object existence、idempotency or ordering.

## Security and privacy review

| Severity | Risk                                                                                                  | Required control                                                                             |
| -------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Blocker  | A raw external correlation header could be treated as trusted lineage or authorization.               | core accepts only validated server-adapter context；HTTP trust policy stays gated to WP-0041 |
| High     | Mutable/global ambient state could bleed correlation or Tenant-adjacent facts across concurrent work. | immutable explicit context、parallel isolation tests、no Eventing-owned ALS                  |
| High     | Retry/replay could create a new correlation and destroy forensic lineage.                             | exact preservation tests across every recovery path                                          |
| High     | `tracestate`/baggage could persist secrets or PII.                                                    | no trace carrier、baggage or exporter in WP-0034                                             |
| High     | IDs could become unbounded metric labels or discovery channels.                                       | Restricted classification、allowlisted surfaces、label prohibition                           |

These risks are design gates, not evidence that a production incident occurred.
