## Purpose

Provide Ordering's public internal `CreateOrder` application API. One authorized Customer Guest
Session submits one exact Cart Version and Quote under a permanent Submission/Idempotency reference.
The service reuses WP-1220 Checkout Validation, WP-1221 Order identity, WP-1222 immutable line
snapshots and WP-1223 Store Business Date/Order Number allocation, then requires the owning
repository to persist the Order, first Batch, Items, allocation, Submission record and Audit in one
database transaction.

Section 87 supersedes the older shorthand public-route examples: the later `/payment-intents`
command will call this application API and must commit the immutable `Submitted / Payment Pending`
submission before invoking the Provider. WP-1224 therefore does not expose an independent customer
HTTP route, create a Checkout Session or call a Payment Provider.

## Closed execution contract

1. Input is exactly Submission reference, Cart reference, expected Cart Version, Quote reference and
   server UTC request instant. Client Catalog, Option, Price, Tax, total, Actor, Store, status,
   Business Date and Order Number values are rejected.
2. `CreateOrder` authorization and a usable Guest Session are required before Submission lookup or
   business-data reads. The authorized session must match the validated Brand, Store, Order Type,
   source channel and Checkout evidence.
3. Submission intent is the stable Cart/Version/Quote tuple and does not include retry time. The
   Submission reference is permanent: the same authorized intent returns the original complete
   result; changed intent or session fails with an idempotency conflict; no second Order, Batch,
   Item, allocation or Audit is created.
4. New creation generates all internal references server-side, obtains a fresh exact-scope Checkout
   validation, loads only public immutable source contracts, and re-runs the WP-1221/1222 parsers.
   Malformed, extra-field, expired or scope-mismatched dependency output fails closed.
5. Store resolves Business Date from its public versioned IANA-zone contract. The repository owns
   the atomic counter increment and returns the persisted allocation. A rolled-back pre-Order
   transaction consumes neither a durable counter change nor a displayed number.
6. The returned record contains the immutable Order aggregate, first Batch, copied transaction line
   snapshots, permanent Submission evidence and exact Order Number allocation. The result is closed,
   parsed and relationship-checked before it crosses the public application boundary.
7. Audit evidence is `ORDERING_ORDER_CREATE`, System actor, exact Brand/Store/Order target,
   `AUTHORIZED_ORDER_CREATE`, Customer PWA, Restricted classification and the creation instant.
8. Order submission/Batch/Item history is append-only. Header identity and number allocation cannot
   be rewritten. All new tables force Store RLS and grant no runtime access in this WP.

## Risks, rollback and residual gates

The main risks are authorization ordering, replay ambiguity, partial persistence, orphaned numbering,
cross-Store source mixing and snapshot mutation. Closed inputs, session/scope validation, permanent
intent binding, one repository transaction, allocation FK, uniqueness, append-only history and
forced RLS mitigate them. Rollback is a reviewed Git revert/forward-fix before dependent WP-1225+
data exists; no destructive data rollback is authorized. Provider, Pilot Store, legal/tax,
staging/production and External Evidence remain gated and unclaimed.
