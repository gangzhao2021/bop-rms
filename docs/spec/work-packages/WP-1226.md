## Purpose

Publish the stable Store-scoped `rms.ordering.OrderCreated.v1` fact exactly once for a newly
committed Order intent and require its Outbox append to share the WP-1224 Order/Audit transaction.
An Ordering-owned Inbox consumer uses that fact to drive the WP-1225 status projection from an
injected exact public snapshot contract. Duplicate delivery is harmless, Aggregate ordering is
explicit and a projection/consumer failure never rewrites or rolls back the source Order after its
transaction commits.

The earlier Section 52 Phase 1 catalog lists the later commercial fact `OrderConfirmed`; the later
Section 64 capability map, Feature F12.2 title and accepted WP-1224/1225 boundaries explicitly own
`OrderCreated` here. This WP therefore does not publish or alias `OrderConfirmed`.

## Closed execution contract

1. `OrderCreated` schema version `1` is owned and produced only by `@rms/ordering`, uses Store
   Tenant scope, Aggregate type `Order`, Aggregate version from the persisted Order and the Order
   creation instant as `occurredAt`.
2. The payload is closed and contains only stable creation facts required to bind an exact source
   snapshot: Order, first Batch and Submission references, Business Date, source snapshot digest
   and item count. It contains no Guest/Actor reference, contact/PII,
   customer note, option narrative, payment fact, Provider payload or full transaction snapshot.
3. The event reference is generated server-side. Audit correlation is reused; the permanent
   Submission reference is the causation reference. The envelope actor is `System`, classification
   is `indirect_identifier` and replay is safe.
4. A new CreateOrder result composes the validated envelope before persistence and passes it to the
   owning repository. The repository contract must persist Order, first Batch, Items, number
   allocation, Submission, Audit and Outbox in one database transaction. An Outbox failure rolls
   back all of them; an Order transaction rollback leaves no Outbox row.
5. Permanent CreateOrder replay returns the first durable record and emits no second event. Event
   identity, Aggregate identity/version and payload content are stable for that committed creation.
6. Event Catalog metadata, Ordering manifest identities and runtime envelope must agree exactly.
   The Event Catalog remains the schema source and generated AsyncAPI/Markdown artifacts must not
   drift.
7. Consumer `ordering.order-status-projection:v1` uses Store-scoped Inbox idempotency and Aggregate
   ordering. It validates producer, type/version, scope, Aggregate identity/version and every closed
   payload field before any source/projection effect.
8. The consumer loads one exact Ordering public source snapshot, requiring matching Brand, Store,
   Order, source version/checkpoint/digest, first Batch, Submission, Business Date and item count.
   Missing source is retryable; malformed or mismatched content fails closed. Projection replace and
   Inbox completion share the consumer transaction.
9. Duplicate delivery produces no second projection effect. Older/same Aggregate versions cannot
   replace newer content; a same-version conflict remains a hard failure rather than silent success.
10. No new database table, runtime grant, role, Provider call, external transport, realtime hint or
    cross-Domain private-table read is authorized.

## Risks, rollback and residual gates

The main risks are event-name ambiguity, partial Order/Outbox commit, oversized or sensitive payload,
replay duplication, cross-Store consumption, projection from mismatched source and treating creation
as payment/commercial confirmation. The explicit fact name, closed minimal payload, atomic repository
contract, Store scope, Inbox idempotency, exact snapshot digest/checkpoint binding and later-boundary
rules mitigate them. Rollback is a reviewed Git revert/forward-fix before dependent Payment/Kitchen
work; append-only Order/Event history is never destructively rewritten.
