## Purpose

Extend the existing provider-neutral `@rms/store` package with the smallest query contract that
proves:

1. a strict public Store reference can resolve one exact active Tenant-owned Brand/Store scope
   without accepting an internal Store ID or treating the public reference as authorization；
2. one published、currently effective immutable operating-hours configuration is selected at an
   explicit canonical UTC instant；
3. the Store IANA time zone deterministically maps that instant to a local calendar date、weekday
   and wall-clock time, including DST gap and overlap boundaries；
4. a date-specific exception schedule replaces the weekly schedule for that local calendar date；
5. exact UTC temporary-closure intervals can suppress all service modes or a closed subset of
   `DineIn`、`Pickup` and `Delivery`；
6. the customer-safe result reports `Open`、`Closed` or `TemporarilyClosed` plus the sorted allowed
   service modes and immutable configuration evidence；
7. malformed requests remain distinct from every valid-but-unavailable Store/configuration
   outcome；and
8. telemetry is bounded to stable operation/outcome/reason codes and excludes identifiers、
   references、hours、dates、times、time zones and configuration facts.

WP-1001 establishes only `GetStoreOperatingStatus`. It does not create the Merchant
`STORE-HOURS-SERVICE` page or authoring Commands. It supplies a safe Store-owned query for later
composition by `CUST-ENTRY-CONTEXT` and other authorized consumers.

## Ownership and Domain boundary

`@rms/store` owns Operating Hours、Order Channel Enablement、Store time zone、temporary closure
evaluation and Store Operational State query semantics.

- `@bop/tenant` remains the sole owner of Brand/Store identity、scope and lifecycle.
- `@bop/publishing` remains the sole owner of Release status and immutable Release evidence.
- `@bop/effective-period` remains the sole owner of timing metadata validation and unique
  effective-version resolution.
- collaborating facts enter only through public contracts or injected exact-shape ports；Store
  never reads another Domain's private table.
- the Store Domain layer evaluates already validated Store-owned schedule values only. Cross-Domain
  evidence validation and composition remain in the Application layer.

The query grants no Permission、Guest/Customer Session、QR capability、ordering authority、
Merchant access or object-discovery capability.

## Adopted decisions

1. **Query only —** extend the existing `@rms/store` package with a pure query over injected
   evidence. No Command、mutation、expected-version write、idempotency ledger、Audit append、Event、
   Outbox or Inbox is required because this WP changes no fact.
2. **Request —** `GetStoreOperatingStatusRequest` contains strict UUIDv7
   `publicStoreReference`、canonical UTC `evaluatedAt` and exact purpose `CustomerEntry`.
3. **Lookup is not authorization —** the public reference is only a lookup handle. Internal Brand
   ID、Store ID、Store code、name、address、coordinates and unrestricted search are prohibited.
4. **Exact active scope —** injected resolution evidence must bind the requested public reference
   to exactly one active Tenant-owned Brand/Store scope. Mismatch、inactive scope and malformed
   evidence are unavailable.
5. **Immutable candidates —** each operating-configuration candidate contains exact Tenant scope、
   immutable configuration/version/release references、`sha256:` content digest、Publishing
   evidence、Effective Period metadata、one IANA time zone and Store-owned schedule values.
6. **Unique current version —** explicit `evaluatedAt` resolves exactly one published effective
   candidate. Zero、overlap、conflict、future、expired or array-order-dependent selection is
   prohibited and externally unavailable.
7. **Service-mode set —** the only service modes are `DineIn`、`Pickup` and `Delivery`. Source and
   output values are unique and emitted in that canonical order.
8. **Weekly schedule —** each local ISO weekday maps to zero or more half-open wall-clock
   intervals. An interval declares the exact enabled service-mode subset for that time.
9. **Overnight intervals —** a wall-clock interval may cross local midnight only when represented
   explicitly with `endsNextDay=true`. Evaluation checks both the current local weekday and the
   prior weekday's overnight tail without converting the schedule to UTC.
10. **Exception precedence —** at most one exception exists for a local ISO calendar date. When
    present, its interval list fully replaces the weekly schedule for that date；an empty list
    means closed. Exceptions never merge implicitly with weekly values.
11. **Temporary closure —** zero or more immutable half-open UTC intervals can suppress all modes
    or an explicit non-empty subset. A closure never enables a mode that the active schedule did
    not enable.
12. **State derivation —** `Open` means at least one schedule-enabled mode remains after closure
    suppression；`TemporarilyClosed` means the active schedule enabled at least one mode and active
    closure evidence suppresses all of them；otherwise the state is `Closed`.
13. **DST rule —** the supplied UTC instant maps uniquely to local fields through the configured
    IANA zone. The query does not synthesize a UTC instant from an ambiguous/non-existent local
    time and does not calculate future transitions.
14. **Business Date excluded —** Store-local calendar date is an evaluation aid, not Business
    Date. Business Day Start、Business Date resolution、Order Number reset and their DST behavior
    remain WP-1223.
15. **Closed source shape —** candidate、scope、publication、effective-period、weekly、exception
    and closure values are exact closed shapes. Unknown fields、duplicate dates、duplicate modes、
    invalid weekdays、invalid wall times、zero-length intervals、overlapping intervals and invalid
    closure periods fail closed.
16. **Customer-safe output —** Available output contains only operating state、canonical service
    modes、`evaluatedAt`、IANA time zone、local calendar date/time and immutable
    configuration/version/release/digest evidence. Internal Tenant/Brand/Store IDs are excluded.
17. **Uniform unavailable —** missing source、inactive/mismatched scope、unpublished/archived
    Release、non-effective/conflicting version、malformed source and dependency exception all
    return the same `StoreUnavailable` result without existence detail.
18. **Malformed request —** invalid UUIDv7、UTC instant or purpose returns bounded
    `InvalidRequest` without calling dependencies.
19. **Bounded dependency use —** each injected dependency is called at most once. The service does
    not retry、read the host clock、fetch a URL、perform DNS/network I/O or mutate input evidence.
20. **Privacy classification —** public Store hours and operating status are `Public` only after
    approved publication. Unknown/unclassified fields fail closed；fixtures are synthetic.
21. **Telemetry —** labels are limited to
    `operation=GetStoreOperatingStatus`、outcome and stable reason. Public/internal references、
    scope、hours、dates、times、time zone、service modes、digests and exception details are
    prohibited.
22. **No order acceptance claim —** this query does not evaluate capacity、catalog/menu
    availability、inventory、pricing、tax、payment/provider health、Feature Control、Store Live
    Gate or operational incident containment. Later composition must check each owning Domain.
23. **No cutoff/lead time —** fulfillment cutoff、lead time、slot/capacity and promise calculations
    remain later Checkout/Fulfillment/Store authoring work.
24. **No QR/Session —** QR signature/token、Table context、Customer Session、copied-code abuse and
    invalid/expired QR behavior remain WP-1002–1007.
25. **No authoring or event —** weekly/exception/temporary-closure Commands、permission、
    approval、expected version、idempotency、Audit and `StoreTemporarilyClosed` publication remain
    later Store configuration work.
26. **No persistence/transport/UI —** no `rms_store` schema/table/view、migration、RLS、repository
    adapter、HTTP route、CDN/cache policy、Customer component or Merchant page is included.
27. **External Evidence —** no real Store、hours、holiday、closure、Customer traffic、staging、
    production or performance evidence is available or claimed.
28. **Hard stop —** internal-ID lookup、Store discovery、ambiguous effective version、unknown source
    field、unpublished hours、invented Business Date、capacity/order-acceptance claim、persistence、
    production API/UI、Provider/resource or allowlist-external tracked file stops implementation.

## Public contract

The implementation candidate defines:

- `GetStoreOperatingStatusRequest`
  - `publicStoreReference`
  - `evaluatedAt`
  - exact purpose `CustomerEntry`
- `StoreOperatingStatusResolutionEvidence`
  - exact active Brand/Store scope and requested public-reference binding
  - immutable lookup-evidence reference and validity instant
- `StoreOperatingConfigurationCandidate`
  - exact scope、configuration/version/release references and content digest
  - immutable Publishing and Effective Period evidence
  - IANA time zone
  - weekly local wall-clock intervals
  - date-specific replacement exceptions
  - exact UTC temporary-closure intervals
- `GetStoreOperatingStatusResult`
  - `Available` with one immutable `StoreOperatingStatus`
  - `InvalidRequest`
  - uniform `StoreUnavailable`

The service validates request and exact dependency shapes, resolves one current candidate
deterministically, derives local fields from the explicit UTC instant, evaluates Store-owned
schedule rules and returns immutable customer-safe values.

## Risks、rollback and next action

- DST or overnight logic can silently report a wrong state；the contract evaluates only a supplied
  UTC instant in an explicit IANA zone and tests both DST transitions and prior-day tails.
- Ambiguous or malformed Store configuration can overstate availability；exact-shape validation
  and unique-current-version resolution fail closed.
- An operating-hours result can be mistaken for order acceptance；the result is deliberately
  limited to Store-owned hours/service modes and documents every excluded owning Domain.
- Rollback before merge is deletion of this brief plus the bounded index edits. After merge,
  correction is a forward documentation/implementation change；accepted history is never
  rewritten.
- Next allowed action is readiness verification followed by exact-head pinned-Linux CI and
  Section 91 review. Implementation starts only from the verified readiness squash on `main`.
