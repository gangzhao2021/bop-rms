## Problem and bounded outcome

Identity proves who an authenticated Actor is and Tenant owns Brand/Store identity, but neither fact grants a workforce Actor membership in a Brand or assignment to a Store. A client-provided Brand/Store ID、email、Provider subject、route value or active Session must never create that authority.

WP-0102 creates the smallest executable `@bop/membership` Phase 0 boundary:

- one immutable Actor + Brand Membership identity with effective lifecycle and optimistic version;
- independent effective-dated Store Assignments under that Membership;
- fail-closed exact active Membership and Store Assignment resolution;
- atomic suspension semantics that invalidate Store Assignments and identify downstream Session-revocation work without performing Provider operations;
- one owning schema with two forced-RLS tables、explicit ownership and synthetic PostgreSQL evidence.

This WP does not define Role、Permission、Grant、explicit allow/deny、Tenant Context middleware、authentication/invite/MFA/recovery、Session Store、employment/payroll/scheduling、real workforce data、UI/API route、Provider/AWS resource or production action.

## Ownership and boundaries

`@bop/membership` owns the relationship between one workforce Actor and one Brand plus the Actor's explicit Store Assignments. Identity continues to own Actor and Session facts. Tenant continues to own Brand and Store identity. Membership stores only validated opaque public references and never reads or writes either dependency's private tables.

Membership is not Authentication and grants no business Permission. Store Assignment is not a Role. WP-0103 composes server-authoritative Tenant Context from active Membership/Assignment; WP-0104 evaluates decisions; WP-0105 owns Role/Grant/deny/allow. WP-0108 owns invitation、MFA、recovery and Session-revocation policy composition.

## Adopted Recommended Owner Decisions

1. **One owning Module —** create exact Phase 0 module `membership` / `@bop/membership`.
2. **Public dependencies only —** it may depend synchronously only on root public contracts from `@bop/identity` and `@bop/tenant`; both exact roots are classified `domain-safe`.
3. **Workforce Actor only —** Membership creation accepts only an active `User` Actor with `Workforce` account kind and a non-null Actor reference. Customer、Platform、Service and System Actors fail closed.
4. **Immutable relationship identity —** `membershipReference`、`actorReference` and `brandReference` never change. The same Actor may have separate Memberships in different Brands.
5. **Closed Membership lifecycle —** `PendingActivation | Active | Suspended | Ended`. Pending may activate; Active may suspend or end; Suspended may reactivate or end; Ended is terminal.
6. **Effective period —** canonical UTC millisecond `effectiveFrom` and optional exclusive `effectiveUntil`; end must be later than start. Server-authoritative time resolves activity.
7. **Workforce relationship evidence —** Membership carries only an optional opaque `workforceRelationshipReference`. Real employee/contractor/legal classification and evidence are External Evidence; no name、email、address、payroll or HR fact is stored.
8. **Activation evidence boundary —** synthetic contract tests may activate with an opaque synthetic relationship reference. Real activation requires separately verified workforce evidence and invitation policy.
9. **Positive optimistic version —** every Membership and Store Assignment has a positive version; mutation requires the exact expected version and rejects last-write-wins.
10. **Independent Store Assignment —** each assignment has its own immutable ID、Membership、Actor、Brand and Store references、effective period、lifecycle and version.
11. **Closed Assignment lifecycle —** `Active | Suspended | Ended`; Suspended may reactivate; Ended is terminal. Removal is represented by ending/suspending, never hard deletion.
12. **Exact Store ownership check —** application composition must validate the public Store belongs to the Membership Brand before assignment. No cross-Domain private FK or table query is permitted.
13. **Exact resolver —** Actor + Brand + effective instant resolves exactly one active Membership. Actor + Brand + Store + instant additionally resolves exactly one active Store Assignment belonging to that Membership. Zero or multiple matches fail closed with stable safe codes.
14. **Parent dominates child —** a Store Assignment is never active for access when its Membership is not active or outside its effective period, even if the assignment row itself says Active.
15. **Suspension cascade —** suspending Membership atomically suspends every active Store Assignment owned by it and returns a bounded invalidation result containing only opaque references.
16. **Session boundary —** Membership suspension/removal does not mutate Identity private state. The invalidation result is consumed later by WP-0108's idempotent Session-revocation composition using the accepted `MembershipDisabled` / `StoreAssignmentRemoved` reasons.
17. **No Permission fields —** Brand Role、Store Role、Permission Override and business action codes are excluded and owned by WP-0104/0105, notwithstanding older grouped summaries.
18. **No Event widening —** WP-0102 introduces no Event Catalog item or Outbox write. A future integration event requires its own producer/consumer/idempotency authority.
19. **Persistence belongs here —** no later backlog WP owns Membership persistence. Create only `bop_membership.membership` and `bop_membership.store_assignment`.
20. **No foreign private FK —** assignments may reference Membership within the owning schema; Actor、Brand and Store references have no cross-schema FK.
21. **Tenant keys —** both tables carry required `brand_id`; Store Assignment additionally carries required `store_id`. Scope indexes start with Brand and, where applicable, Store.
22. **Forced RLS —** Membership rows require exact Brand and remain visible during an exact Store context so WP-0103 can validate the parent. Store Assignment rows require exact Brand and Store. Missing/wrong scope returns zero rows or denies writes.
23. **Least privilege —** schemas/tables revoke `PUBLIC`; migrations create no role、login、credential、BYPASSRLS or broad runtime grant.
24. **Ambiguity and leakage —** duplicate/overlapping active facts are rejected by the resolver; database conflicts are mapped to generic stable errors so foreign-scope existence is not disclosed.
25. **Privacy —** Actor/Membership/Store/evidence references are at least `indirect_identifier`; workforce relationship evidence is `sensitive_personal`. Raw values are prohibited in logs、URLs and analytics; fixtures are synthetic only.
26. **No real seed —** no Customer、Employee、Contractor、email、Store roster、Provider identity or production relationship is inserted.
27. **Historical facts —** suspend/end and Audit intent preserve stable references; downstream Audit、Order、Payment and workforce history are not rewritten.
28. **Future composition —** Role/profile selection、object authorization、Store switch and cross-Tenant negative flows remain WP-0103–0109 and must consume this public contract without changing ownership.

## Security、privacy、risk and rollback

- **Actor ID becomes authority:** Membership creation requires a validated active Workforce Actor; reference equality alone never authenticates or authorizes.
- **Cross-Brand Store assignment:** public Store/Brand relationship validation plus exact stored keys、resolver checks and RLS fail closed.
- **Suspended parent leaks access:** every resolver re-evaluates parent lifecycle/effective period; no cached child can override it.
- **Assignment overlap:** resolver returns ambiguity rather than choosing by order; later write repositories require transaction/concurrency enforcement.
- **Membership grants Permission:** public contract contains no Role/Permission and returns only membership/assignment facts.
- **PII/workforce leakage:** no names、emails、addresses、payroll or free text; opaque evidence references are prohibited in logs/URLs/analytics.
- **Session remains usable:** this WP returns invalidation evidence only; WP-0108 owns idempotent Identity Session revocation before real integration is accepted.
- **Rollback:** before shared integration, Git revert and a reviewed forward migration may remove empty synthetic-only objects. After migration sharing, never edit applied SQL; use forward-fix/contract after dependency and retention review. No production/data rollback is authorized.
