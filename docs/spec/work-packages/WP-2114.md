## Owning facts and boundaries

Reservation & Waiting owns each Waitlist Entry identity and lifecycle, original Joined At,
append-only controlled revisions / priority changes / estimates, response and ready deadlines, and
Dining / Notification collaboration references. The ordered queue is a rebuildable query projection,
not one shared Aggregate. Dining owns actual Table compatibility, assignment and Session creation;
Notification owns delivery; Customer / Identity own profile truth.

## Acceptance contract

1. Join, check in, call, mark Ready / Missed, restore, revise, cancel, expire, extend Ready once and
   record Dining seating are strict idempotent Commands with Tenant, Brand, Store, Actor, purpose,
   `dining.operate`, exact expected version, append-only Audit and only authority-backed future facts.
2. `Ready` never means seated. `Seated` requires a Dining-issued Session reference; repeated or
   failed seating cannot create or infer a second Session. Notification request / outcome is separate
   and delivery failure never rolls back Waitlist lifecycle.
3. Queue order is computed from compatibility and original Joined At plus explicit policy / Manager
   override evidence. Position is never stored as an immutable fact. ETA is a deterministic min / max
   range with calculation version / time and append-only history, never a promise.
4. `WAIT-BOARD` and contextual `WAIT-ENTRY` implement every Section 88 field, filter, action and
   mandatory state. Contact display/search is permission-minimized and all commands remain visibly
   disabled without an authorized command-capable BFF.
5. Handoff Section 50 authorizes no Reservation / Waitlist schema or migration namespace.
   Persistence, outbox, Dining / Notification adapters and live projections remain injected ports;
   this WP must not invent database or external-service authority.
