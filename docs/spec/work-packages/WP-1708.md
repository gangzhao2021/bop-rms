## Closed cache and update contract

The Customer Service Worker uses a deployment-scoped cache ID and deny-by-default routing. It
precaches only the built static shell and hashed same-deployment JS/CSS/fonts. Navigation uses
NetworkFirst with a static offline fallback and caches only successful basic same-origin documents.
Public runtime JSON is limited to same-origin credential-free `GET /api/v1/public/*`, a successful
`2xx` response and exact `X-BOP-Cache-Class: public`; it is NetworkFirst with a three-second timeout
and five-minute maximum age. Cross-origin assets remain outside Cache Storage.

The existing Menu client deliberately remains NetworkOnly: its current request uses
`credentials: same-origin` and has no authoritative `menuVersion`, so it cannot satisfy the public
cache key. Enabling that cache awaits a future backend/client contract that supplies the accepted
credential-free, versioned request; this WP does not invent one.

`/auth/*`, `/bff/*`, every private Customer/transaction route and all unknown requests are
NetworkOnly. Non-GET requests are never registered for caching. `workbox-background-sync` and any
mutation queue are absent. Cached public data cannot authorize Cart, Quote, Checkout, Payment,
Order, Pickup, allergen-safety or other transaction facts; the WP-1707 shell supplies explicit
Offline/Possibly Outdated/Read-only recovery language.

Update registration uses prompt mode. A waiting worker is never activated automatically. The UI
allows explicit activation only on `/`, `/menu` and `/menu/search`; Cart, item configuration,
Checkout, Payment, Order and Pickup routes remain unsafe. A security-forced activation mechanism is
not invented because no preservation/recovery adapter exists.
