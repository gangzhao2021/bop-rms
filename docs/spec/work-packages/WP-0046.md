## Problem and bounded intended outcome

WP-0042 proves insert-only Audit behavior but explicitly makes no tamper-evidence claim. Database ownership or append-only privileges alone cannot detect an owner-level change、missing row、duplicate sequence、restored stale copy or archive deletion.

WP-0046 establishes the smallest truthful repository integrity increment:

- one ordered SHA-256 chain per existing Brand/Store audit scope;
- versioned RFC 8785 canonical Audit content and deterministic chain preimage;
- transactionally serialized sequence allocation in the caller-owned transaction;
- a daily UTC manifest contract with range、first/last sequence、root hash、gap count and verifier version;
- a KMS ECDSA P-256 signing port and signature verification contract;
- an immutable archive receipt/presence verification contract;
- fail-closed detection of content/hash/sequence/signature/archive faults;
- Security alert classification and high-risk export freeze decision;
- synthetic/local/CI proof without claiming AWS delivery、retention or immutability.

The repository increment does not create a KMS key、AWS account、IAM role、S3 bucket、Object Lock configuration、retention period、daily scheduler or production deployment.

## Ownership and boundaries

`@bop/audit` remains the public technical capability and `shared-infrastructure/audit` remains the sole owner of `platform_audit.audit_record` and its chain-head technical state. Business Domains continue to supply already-authorized Audit facts through the public append contract and never query or write Audit private tables.

The hash is integrity evidence, not authorization、encryption、retention、legal hold or proof of business truth. A valid chain does not prove that a caller was authorized or that the original fact was correct. Correction remains a linked append-only record.

The daily manifest builder consumes an explicitly bounded partition/day record stream supplied by an owning operator/job composition. It does not add an unrestricted cross-Tenant query API. KMS signing and archive storage are ports only; external adapters and resources remain later gated composition.

## Adopted Recommended Owner Decisions

1. **Chain partition —** use exact `(brand_id, scope_store_key)` where `scope_store_key` is existing `store_id` or literal `brand`. This preserves WP-0042 RLS/index scope and never merges Brand-wide with Store-specific history.
2. **Sequence —** use positive `bigint` beginning at `1` independently per partition with no reuse. Gaps or duplicates fail verification.
3. **Concurrency —** maintain one `platform_audit.audit_chain_head` row per partition. The caller-owned transaction initializes then locks that exact row、allocates the next sequence、inserts Audit and advances the head atomically.
4. **No global lock —** never serialize unrelated Brands/Stores. Lock order is one exact partition per append; cross-partition batch append is not introduced.
5. **Recorded time —** the locked allocation query returns a database UTC instant truncated to exact milliseconds; that same instant is inserted and hashed. Caller `occurredAt` remains a separate immutable fact.
6. **Canonical content version —** define `AUDIT_CHAIN_V1` as one closed projection of every persisted Audit fact except generated scope key and chain metadata. Unknown/missing fields fail closed.
7. **RFC 8785 —** implement a local dependency-free canonicalizer using ECMAScript JSON number/string serialization、UTF-16 property ordering and rejection of non-finite numbers、unsupported values、cycles and lone surrogate code units.
8. **Preimage —** hash RFC 8785 canonical JSON of `{content, previousHash, recordedAt, sequence, version}`. `previousHash` is lowercase 64-hex or `null`; `sequence` is a safe positive integer; timestamps are canonical UTC milliseconds.
9. **Hash representation —** SHA-256 is 32 raw bytes in PostgreSQL and lowercase 64-hex at TypeScript/manifest boundaries. No hash truncation or alternate algorithm negotiation.
10. **Genesis —** sequence `1` has `previousHash=null`. Every later entry must reference the immediately preceding record hash in the same partition.
11. **Activation safety —** migration `0000_015_alter_audit_hash_chain.sql` requires `audit_record` to be empty before adding required chain columns. Repository authority records that WP-0042 was never deployed. Any nonempty target is an immediate external hard stop requiring a separately reviewed RFC-8785 backfill plan; no row is silently excluded or assigned a synthetic hash.
12. **Head-state boundary —** the mutable head is technical concurrency state, not retained Audit history. It has forced scope RLS、PUBLIC denial and exact head-vs-chain verification.
13. **Append semantics —** required Audit append still fails the caller transaction on validation、allocation、hash、insert or head-advance failure. No external KMS/S3 call occurs inside a business transaction.
14. **Daily boundary —** manifests use database `recorded_at` UTC calendar day `[00:00:00Z, next day)` and are per exact chain partition.
15. **Manifest V1 —** include manifest/version IDs、partition safe references、UTC day/range、first/last sequence、record count、root hash、gap count、chain verifier version and canonical manifest SHA-256. No Audit summaries、Actor/target IDs、PII or unrestricted provider data enter the manifest.
16. **Empty day —** no manifest is emitted for a partition with zero records. Absence is not represented as a signed empty chain.
17. **Verifier —** recompute canonical content and every hash; detect missing/duplicate/out-of-order sequence、previous-hash mismatch、content mutation、head mismatch、manifest mismatch、invalid signature and archive absence/version change.
18. **KMS contract —** lock signing to AWS KMS asymmetric `ECC_NIST_P256` with `ECDSA_SHA_256`; sign the 32-byte canonical manifest digest using message type `DIGEST`. The repository stores no private key.
19. **Synthetic signer —** local/CI may use an ephemeral Node P-256 key only to test byte/signature/tamper semantics and must label evidence `SYNTHETIC / NOT KMS`.
20. **Archive contract —** verify a versioned object receipt、manifest SHA-256、signature metadata、SSE-KMS state、Object Lock `GOVERNANCE` state and a future `retainUntil` relative to archive time. Never hardcode a legal retention duration.
21. **No bypass —** application/ordinary-admin contracts expose no delete、overwrite、retention-shortening or `BypassGovernanceRetention`. Break-glass/two-person approval remains external cloud evidence.
22. **Failure response —** any verifier failure yields a closed stable code、routes `OBSERVABILITY_REDACTION_FAILED` only for actual leakage/redaction faults and otherwise a dedicated future `AUDIT_INTEGRITY_FAILED` Security route trigger. Until WP-0045 registry expansion is separately accepted, WP-0046 records the Security escalation requirement without changing WP-0045 files.
23. **No new dependency/cloud SDK —** use Node crypto、existing TypeScript/Vitest/PostgreSQL harness and frozen lockfile. AWS SDK、credentials、IaC and `pnpm-lock.yaml` remain unchanged.
24. **Migration lifecycle count —** implementation discovery found the WP-0024 exact migration-count assertion outside the initial candidate allowlist. Owner explicitly authorized adding `packages/database/test/isolated-database-acceptance.mjs` solely to update the expected count from `14` to `15`.
25. **Closed filename grammar —** implementation discovery proved that Migration Runner rejects action word `add`. Owner explicitly authorized replacing the candidate path with exact grammar-compliant `migrations/0000-platform/0000_015_alter_audit_hash_chain.sql`; the catalog validator remains unchanged.

## Security、privacy、risk and rollback

- **Owner-level tampering:** independent recomputation、signed daily root and cross-account immutable receipt; real independence remains external.
- **Concurrency fork:** per-partition row lock and head compare/update in one caller transaction.
- **Canonicalization ambiguity:** versioned exact projection and RFC 8785 adversarial vectors; no native `jsonb::text` hashing.
- **Legacy rows omitted:** migration fails on any existing row; separate backfill decision required.
- **Hash leaks data:** only digest/root appears outside restricted Audit; hash is still classified Internal and not a public identifier.
- **Manifest leaks identifiers:** partition values are safe restricted references and never enter general logs/alerts; no content/Actor/target facts.
- **Signing oracle/private key:** digest-only closed signer port、dedicated KMS key、no application private key. Actual IAM/KMS evidence is external.
- **Irreversible retention:** no bucket or duration is selected. Compliance mode and legal periods remain professional/external decisions.
- **Verifier availability:** verification failure freezes only through an owning authorized control; it never blocks ordinary transaction completion or rewrites Audit.
- **Rollback:** before migration apply, reviewed Git revert. Once applied, append-only chain/history is never rewound；use reviewed forward-fix or separately authorized restore. No cloud rollback exists in this WP.
