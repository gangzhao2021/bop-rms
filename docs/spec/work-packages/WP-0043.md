## Problem and bounded intended outcome

The API skeleton already exposes `/health` and `/ready`, but the behavior is a bootstrap placeholder:

- `/health` returns a structured `200 healthy` response;
- `/ready` always returns `503 not_ready` with database `not_configured`;
- the response is not governed by an explicit state/probe contract;
- API startup and shutdown do not explicitly transition readiness before accepting or draining work;
- dependency timeout、failure classification、bounded disclosure and concurrency behavior are not fixed;
- the Worker has deterministic lifecycle behavior but no separately accepted health transport contract.

The subsequently authorized WP-0043 implementation, after readiness integration, will establish the smallest truthful runtime contract:

1. retain structured `/health` and `/ready` API endpoints;
2. distinguish process liveness from safe-to-serve readiness;
3. derive readiness from explicit startup、draining and injected required-dependency states;
4. fail readiness without causing restart storms for transient dependency failure;
5. mark readiness false before HTTP/SSE drain and bounded shutdown;
6. expose only stable、bounded and non-sensitive status data;
7. supply deterministic unit/runtime acceptance evidence without real Provider、production or cross-Domain access.

This WP does not make the application production-ready. Actual deployment health-check wiring、database credentials、runtime identities、CloudWatch telemetry、alerts、load-balancer behavior and staging/production evidence remain separately gated.

## Domain、Module and runtime ownership boundary

- `apps/api` owns HTTP transport、Composition Root、process lifecycle and the public health/readiness representation.
- A future health/readiness component is runtime infrastructure inside `apps/api`; it is not a BOP business Domain、Aggregate、Projection、Audit source or Event.
- Owning packages expose only narrow injected probes for dependencies they own. The API must not query another Domain's private table or import ORM/Infrastructure into Domain code.
- Liveness does not call PostgreSQL、Queue、Provider、DNS or another downstream dependency.
- Readiness may aggregate only explicitly registered required runtime dependencies. Unknown or unconfigured required dependencies fail closed.
- Dependency probes return bounded technical classifications; they never return credentials、connection strings、hostnames、SQL、stack traces、Provider payloads、Tenant/Store/Actor facts or arbitrary errors.
- `apps/worker` remains a lifecycle Composition Root. A Worker HTTP endpoint、sidecar、job heartbeat、lease health or fake timer is outside this candidate unless the Owner explicitly expands the implementation boundary before authorization.
- WP-0044 owns Error Tracking and Core Metrics；WP-0045 owns Alert Routing and the basic Runbook；deployment WPs own ECS/ALB target-group health checks and rollout alarms.

## Candidate health and readiness contract

Every choice below is `OWNER ACCEPTED — 2026-07-27`. Acceptance fixes the future implementation contract but does not authorize implementation.

### Candidate `/health` contract

- unauthenticated `GET /health`;
- `200` while the process can serve the HTTP handler;
- response fields: `service`、`status: "healthy"` and `checkedAt`;
- no dependency probe and no `degraded`/`unhealthy` branch;
- `Cache-Control: no-store`;
- no request echo、build SHA、version、hostname、PID、uptime、environment details or dependency data.

Liveness ending is represented by process/socket termination, not a dependency-driven non-200 response. A stuck event loop naturally cannot answer and is detected by the deployment platform rather than by self-diagnosis.

### Candidate `/ready` contract

- unauthenticated `GET /ready`;
- `200` with `status: "ready"` only after startup gates pass、the runtime is accepting new work and every required dependency is ready;
- `503` with `status: "not_ready"` during startup、unconfigured required dependency、probe timeout/failure、draining or shutdown;
- response fields are limited to `service`、`status`、`checkedAt` and a closed `dependencies` object;
- each dependency contains only `status: "ready" | "not_ready" | "not_configured" | "timeout"` and `required: boolean`;
- no raw cause、latency、host、port、credential、SQL、stack or Tenant data;
- `Cache-Control: no-store`.

The candidate required dependency set is database only. Queue、Outbox backlog、Consumer、Provider、external broker、CloudWatch、KMS、S3 and alert delivery are not probed by WP-0043. Application/runtime configuration and drain state are top-level readiness gates rather than fabricated remote dependencies.

### Candidate lifecycle and probe behavior

- initial state is `starting / not_ready`;
- readiness becomes eligible only after explicit startup completion;
- the current runtime remains `not_ready / database.not_configured` until a future authorized Composition Root supplies a real database probe;
- shutdown atomically enters `draining / not_ready` before closing HTTP and SSE intake;
- repeated shutdown signals do not reopen readiness or start a second drain;
- required probes are injected functions with a `1,000 ms` per-probe deadline;
- one request never starts more than one probe per dependency;
- concurrent readiness requests share an in-flight probe;
- the last result may be cached for at most `1,000 ms`; timeout/error results may be cached for at most `250 ms`;
- all timers are unref'ed where applicable and are cleared after completion;
- thrown/rejected/invalid/late probe results map to bounded `not_ready` or `timeout`;
- the endpoint does not mutate data、open a transaction、write Audit/Event/Log records or call a Provider.

## Recommended Owner Decisions

**Status for every item: `OWNER ACCEPTED — 2026-07-27`.**

The Owner accepted all seventeen items exactly as written. No item is reopened or inferred beyond its recorded impact.

1. **Owning runtime —** accept `apps/api` as the sole HTTP endpoint owner and keep the health/readiness component transport/runtime-only. Impact: avoids a generic cross-Domain health package.
2. **Worker boundary —** exclude a Worker HTTP endpoint、fake activity timer and job/lease health from WP-0043. Impact: preserves the accepted Worker lifecycle guidance and leaves deployment-specific Worker checks gated.
3. **Liveness semantics —** keep `/health` dependency-free and return `200 healthy` while its handler can execute. Impact: prevents transient downstream failure from causing restart storms.
4. **Readiness semantics —** return `200` only when startup is complete、not draining and every required dependency is ready；otherwise return `503`. Impact: makes rollout safety explicit.
5. **Required dependencies —** make database the only candidate dependency and retain `not_configured` until a real probe is separately wired. Do not add Queue/Provider/Cloud dependencies. Impact: avoids fabricated integration evidence.
6. **Configuration gate —** invalid or missing required runtime configuration fails startup/readiness and is not discovered midway through a transaction. Impact: aligns with Section 87.7.3 without implementing production configuration.
7. **Drain ordering —** fail readiness before stopping new HTTP/SSE work and before socket close. Impact: aligns rollout and WP-0036 reconnect/drain behavior without reopening its accepted contract.
8. **Public representation —** accept the closed response/status schema above and prohibit raw error/dependency details. Impact: provides stable automation behavior without creating an information-disclosure endpoint.
9. **Authentication and cache —** keep both endpoints unauthenticated、read-only and `no-store`, relying on deployment/network controls for public reachability. Impact: health agents need no credential and no Secret enters URLs.
10. **Probe contract —** use injected bounded probes only；no cross-Domain private query、dynamic target、Provider SDK or HTTP fetch from the generic aggregator. Impact: preserves ownership and testability.
11. **Timeout and concurrency —** accept a `1,000 ms` deadline、shared in-flight probe and the proposed positive/negative cache bounds. Impact: limits readiness amplification and response latency.
12. **Clock and timestamps —** emit canonical UTC `Z` timestamps from an injected clock for deterministic tests；never use browser time. Impact: keeps responses deterministic and safe.
13. **Logging —** rely on the accepted WP-0040/WP-0041 bounded request-completion log；do not log probe exceptions or full response payloads. Impact: prevents a high-volume Secret/PII sink.
14. **Metrics/error tracking —** expose no new OpenTelemetry、CloudWatch metric、alarm or error-tracking integration in WP-0043. Impact: preserves WP-0044/0045 ownership.
15. **Local environment —** preserve the accepted WP-0006 truth that the current local API is not ready while database runtime wiring is absent；update only assertions needed for the new stable schema/lifecycle. Impact: avoids falsely claiming local execution readiness.
16. **Deployment boundary —** treat ALB/ECS health-check path、interval、threshold、grace period、task role and alarm behavior as External Evidence owned by deployment WPs. Impact: avoids claiming unperformed cloud configuration.
17. **No new dependency —** implement with existing Node/Express/Vitest capabilities and do not change `pnpm-lock.yaml`. Impact: keeps the candidate bounded and avoids an unnecessary supply-chain change.

## Risks、controls and rollback

- **False healthy signal:** dependency-free liveness is paired with dependency-aware readiness；deployment must use the correct endpoint for the correct purpose.
- **Restart storm:** database/provider failure never changes liveness；readiness only removes the task from safe serving.
- **Probe amplification:** bounded deadline、in-flight sharing and short result cache prevent one probe per caller from exhausting a dependency.
- **Stale positive result:** short cache bounds and immediate drain override ensure shutdown cannot remain ready behind a cached probe.
- **Information disclosure:** closed status values and prohibited details prevent host、credential、SQL、stack and Tenant leakage.
- **Readiness deadlock:** probes cannot mutate、open caller transactions or depend on the endpoint itself.
- **Cross-Domain coupling:** only owning adapters may supply probes；the aggregator cannot inspect private tables.
- **Telemetry cardinality:** no dependency error string、Tenant or target is used as a label or log field.
- **Readiness mistaken for production evidence:** local synthetic tests prove contract behavior only；cloud routing、thresholds and dependency identities remain External Evidence.
- **Rollback:** readiness documentation uses normal Git revert. A future implementation before deployment uses Git revert；after deployment, rollback is the prior healthy immutable artifact plus separately reviewed forward correction. No schema/data rollback is involved because WP-0043 owns no migration.
