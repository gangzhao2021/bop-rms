## Acceptance and design

Add one optional Dining admission configuration to createLocalCustomerRuntime. Assemble both
current-authorized Join and binding handlers with the runtime's fixed scope, actual Guest Session
entry store, explicit Session credential/binding providers, clock and allowed Origin. Caller supplies
existing Dining Join/consumption/current-binding repositories, credentials, recovery/lifetime, current
context resolvers and trusted request-bound abuse resolver. Do not invent provider/default verdict.

No caller sub-configuration may override runtime scope, Session store/credentials, clock or Origin.
Absent configuration leaves both handlers unavailable without reads. Explicit configured but invalid
current Session fails before Dining effects; missing request context denies before Session lookup.
Preserve production-environment rejection, loopback binding and caller-owned resource lifecycle.
API remains composition only: no SQL, Owner policy, cross-domain private reads or runtime grants.

Route the existing actual PostgreSQL Join-to-binding double-lost-ack fixture through this complete
local runtime instead of direct createApp handlers. Existing Guest records/current contexts remain
explicitly synthetic; unrelated entry/menu provider fixture is not exercised and is not new QR/menu
end-to-end evidence. Preserve original-operation history, expiry recovery and resource cleanup.
The existing entry/menu browser lab is separately regressed, not falsely reported as wired Dining UI.
