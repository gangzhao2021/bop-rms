## Problem and bounded intended outcome

WP-0044 now emits three closed operational instruments and stable sanitized error codes, but a signal alone is not an operator response contract. WP-0045 establishes the smallest repository-owned alert-routing and incident-response increment:

- a closed registry of supported technical alert codes derived only from WP-0043/0044 operational signals;
- deterministic severity、role destination、deduplication/grouping and runbook routing;
- a privacy-safe alert envelope with no arbitrary labels、payload or identifiers;
- failure isolation so alert planning/delivery failure can never change a business operation result;
- a versioned basic observability runbook covering detection、triage、containment、escalation、evidence、recovery and closure;
- synthetic tests proving the routing contract and runbook linkage without pretending that an external provider delivered anything.

The package returns a transport-neutral route plan. It does not send email/SMS/chat、publish SNS/EventBridge、call CloudWatch、acknowledge an incident、persist incident state or configure infrastructure.

## Responsibility and ownership boundary

The Platform Observability workspace owns the technical alert schema、closed routing registry and basic operator runbook. It consumes public bounded runtime signals and never reads a Domain's private table. Business Domains remain owners of business meaning and corrective Commands.

Routing destinations are role identifiers only:

- `on_call_primary`;
- `on_call_backup`;
- `security_on_call` only for a closed security/privacy failure class.

Names、emails、phone numbers、chat handles、account IDs、topic ARNs and subscription endpoints never enter source、fixtures、logs or Git. WP-2065/deployment composition owns provider-specific alarms、encrypted SNS topics、least-privilege publish grants、verified subscriptions、actual contacts、staging delivery and acknowledgement drills.

## Adopted Recommended Owner Decisions

1. **Ownership —** keep the alert contract in `@bop-rms/observability` and the operator procedure in `docs/runbooks`; no business Domain owns technical alert transport.
2. **Transport-neutral boundary —** return a frozen route plan only. No network sender、AWS SDK、webhook、email、SMS or chat adapter is added.
3. **Closed alert codes —** accept only a finite registry tied to current Health/Readiness and Core Telemetry behavior. Arbitrary alarm names and free-form provider events are rejected.
4. **Severity —** use exact `warning` and `critical` values. The registry fixes severity; callers cannot upgrade/downgrade it.
5. **Role destinations —** route to closed role identifiers, never personal contact details. Actual primary/backup/security assignments are external operational evidence.
6. **Privacy-safe envelope —** allow only alert code、environment、service、stable result/error code、observed UTC instant、safe grouping key and runbook ID. Reject unknown fields and prohibited identifiers/free text.
7. **No high-cardinality dimensions —** Tenant、Brand、Store、Actor、Session、Request、Correlation、Causation、Customer、Order、object ID、URL/query/header/body、IP、SQL and Provider payload are excluded from routing and deduplication.
8. **Stable grouping —** derive a deterministic grouping key from the closed environment/service/alert-code tuple. Do not include time、identity or raw provider data.
9. **Failure isolation —** invalid input or route-planning failure returns a bounded stable failure result and never throws into the business operation path.
10. **Current signal scope —** cover service not-ready、bounded error-rate、bounded operation-latency and telemetry-pipeline failure classes. Numeric threshold/window configuration remains provider/SLO composition; this WP receives only an already-classified closed alert condition.
11. **Security route —** only the explicit telemetry privacy/redaction failure class adds `security_on_call`. Ordinary availability/latency errors do not disclose payload to Security.
12. **Escalation —** critical alerts include primary and backup roles; warnings include primary only. The registry, not caller input, controls the destination set.
13. **Runbook linkage —** every alert code maps to one existing anchored procedure in one versioned basic runbook. Missing/duplicate links fail tests.
14. **Runbook controls —** require safe evidence preservation、read-only diagnosis、bounded containment、recovery verification and closure. Data deletion、restore、credential rotation and external notification require their own authority.
15. **Legal/privacy boundary —** the runbook never hardcodes notification deadlines or legal conclusions. Customer/regulator notification decisions require current professional guidance.
16. **Synthetic acceptance —** deterministic local/CI injection proves classification、route planning、privacy and runbook coverage only. It is not staging/provider delivery evidence.
17. **No new dependency —** use the pinned TypeScript/Vitest toolchain and platform primitives. `pnpm-lock.yaml` is not modified.
18. **External evidence —** real staging fault-to-alert delivery、encrypted topic、least-privilege publish、verified subscriptions、actual primary/backup contacts and acknowledgement drill remain explicitly blocked until the owning cloud WP has credentials and authorization.

## Basic runbook required content

The implementation runbook must contain:

1. scope、authority and hard stops;
2. severity and role-based routing matrix;
3. safe alert-envelope field list and prohibited-data list;
4. detection and read-only corroboration through Health/Readiness、stable logs、metrics and traces;
5. alert-specific triage anchors for every registry entry;
6. containment that preserves append-only/Audit/Tenant/Store/security boundaries;
7. explicit escalation for privacy/redaction failure and evidence handling;
8. bounded recovery verification and alert closure;
9. provider/route failure fallback that does not block transactions;

The runbook may instruct an authorized operator to stop or isolate intake. It may not authorize production mutation、data deletion/restore、credential rotation、permission expansion、customer/regulator notification or cloud-resource creation.

## Risks、controls and rollback

- **Sensitive data in an alert:** closed schema and unknown-field rejection; tests use synthetic stable codes only.
- **Cardinality/cost explosion:** finite alert/service/environment registries and deterministic grouping; no arbitrary labels.
- **Caller-controlled severity/routing:** registry fixes both; caller supplies no destination.
- **Alert path harms transactions:** route planning is exception-isolated and transport-free.
- **False paging or missed escalation:** table-driven registry/runbook parity tests; numeric provider thresholds require later staging evidence.
- **Runbook causes unsafe mutation:** read-only first、explicit hard stops and separate authority for destructive/external actions.
- **Security signal sent too broadly:** Security receives only the explicit privacy/redaction class and the same bounded envelope.
- **False operational-readiness claim:** repository tests are synthetic; external staging delivery and acknowledgement remain blocked.
- **Rollback:** reviewed Git revert of the contract、tests、script and runbook. There is no schema/data/cloud rollback because this WP creates none.
