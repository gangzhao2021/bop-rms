# WP-2198 — Purpose-bound Support Case and diagnostic access workflow

## Authority and scope

- Handoff Sections 50.7, 87.6, 87.7 and 88.18 define Platform Support access and the canonical
  `PLT-SUPPORT-CASE` `/platform/support-cases` screen.
- Exact local predecessor: verified WP-2197 commit `69ba7e6`.
- `@bop/task` owns the Support Case workflow, assignment, diagnostic-access grant and minimized
  action evidence. Tenant/Store identity, Permission, recent MFA, approval, Audit, evidence bytes,
  production diagnostics and every source Domain fact remain behind owner contracts.

## Acceptance contract

1. Platform Support is never Merchant impersonation or unrestricted database access. Every query
   and command requires a named Platform Actor, exact permission, declared purpose, one exact
   Support Case and one exact Tenant/optional Store scope.
2. A Support Case records only safe references and workflow metadata: type, purpose, requester
   verification evidence, assigned role, due/expiry, status and audit/evidence references. It never
   stores free-form diagnostic commands, query text, secrets, credentials, unrestricted object IDs,
   payment data, health/allergy facts or unnecessary PII.
3. Create, assign, request access, approve/grant, record action, revoke and close use immutable
   versions, expected version, idempotency, exact authorization and append-only operation history.
4. Requester verification and independent grant approval are external evidence gates. Granting
   requires a different approver from requester, owner-validated exact delegated permissions and
   server-validated recent TOTP MFA from the same rotated session.
5. v0.1 applies a conservative maximum of 15 minutes to every diagnostic grant. A grant is bound to
   Actor, Case, Tenant/optional Store, purpose, exact delegated permissions and masking policy; it
   cannot be exported, silently extended or reused after expiry/revocation. Renewal is a new grant
   with fresh approval and MFA.
6. Every allowed diagnostic action records the real Support Actor, grant, exact delegated
   permission, safe target type/reference, reason code, evidence reference and server occurrence
   time. It does not record payloads, commands, queries or returned sensitive data.
7. The public resolver returns active access only when Case, Actor, Tenant/Store, purpose and exact
   permission all match and the Case is not closed and the grant is not expired/revoked.
8. Production ECS Exec, SSH, public debug endpoints and ordinary break-glass execution remain out of
   scope. Exceptional one-shot diagnostic tasks require the separate approved break-glass workflow.
9. Support Case histories use forced Platform-context RLS and bind rows to the exact
   `bop.platform_support_case_id`. The application must authorize before setting database context.
10. `PLT-SUPPORT-CASE` supports safe case/Tenant/Store/type/status/owner/due views plus authorized
    create, assign, grant, record, revoke and close intents with accessible full states.
11. This WP creates no real Case, Actor, Tenant/Store, requester verification, MFA, approval,
    diagnostic session, source access, action, evidence or external mutation.
