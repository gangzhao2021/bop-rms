## Acceptance contract

1. A Role administration version has stable Role identity, Brand/optional Store scope, normalized
   code, display metadata, System/Custom type, lifecycle, exact permission selections, author,
   expected source-policy version and immutable history.
2. Permission selections use active exact action definitions only. Wildcards, prefixes, implicit
   page grants and client-invented actions fail closed. Dependency requirements and explicit deny /
   high-risk warnings are deterministic and visible in compare/impact results.
3. Save draft, duplicate, submit, independently approve/reject, activate/deactivate require exact
   scope, purpose, permission, expected version, idempotency and atomic Audit. System roles cannot be
   edited or deactivated through Custom Role commands.
4. Approval never directly grants authority. Activation revalidates the approved snapshot and exact
   source-policy version, then composes Permission-owned Role/Grant changes atomically. Concurrent
   policy drift fails closed.
5. High-risk additions/removals expose affected assignment count from a bounded public Projection;
   the count is impact evidence, never authorization. Assigned users remain masked and read-only.
6. Persistence is append-only for administration versions, permission selections, decisions and
   operations; forced Brand/optional-Store RLS prevents cross-Tenant access.
7. `IAM-ROLE-LIST` and `IAM-ROLE-EDITOR` expose the canonical fields/actions and complete loading,
   empty, denied, not-found, offline, stale, conflict, validation and command-failure states.
8. This WP creates no real Role, user assignment, Permission Definition seed, approval, policy
   activation, Identity/Membership mutation, Event or external action.
