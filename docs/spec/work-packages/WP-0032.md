## Goal and bounded responsibility

Deliver the smallest transport-neutral Consumer Inbox kernel that can later prove:

1. one registered Consumer applies one accepted Event at most once to its own transactional side effect;
2. the Consumer side effect、any resulting Outbox append and the completed Inbox marker commit atomically in one caller-owned PostgreSQL transaction;
3. duplicate、concurrent、crashed and replayed deliveries have explicit fail-closed outcomes;
4. Brand / Store scope、least privilege、safe diagnostics and bounded observability remain explicit;
5. retry scheduling、dead-letter lifecycle and concrete business Consumers remain owned by later Work Packages.

WP-0032 does not promise exactly-once delivery. Transport remains at-least-once；the Inbox provides transactional effect deduplication for a named Consumer. A committed Consumer effect without its completed Inbox record, or a completed Inbox record without its committed Consumer effect, is forbidden.

## Ownership and runtime boundaries

### `platform_eventing.consumer_inbox`

- Shared technical control data owned by `shared-infrastructure/eventing` in `platform_eventing`.
- It records a Consumer's processing receipt/result；it is not a business Aggregate、Projection、Audit record、transport acknowledgement or API-command idempotency record.
- `@bop/eventing` owns its public Consumer registration and transactional Inbox coordination contracts plus parameterized persistence.
- No business Module may query or mutate this table directly.

### Consumer

- A Consumer is owned by the Module that owns its side effect.
- It may mutate only its owning Module's tables through its public Application Handler / Repository contract.
- It receives the validated Event and a caller-owned transaction context；it must not open an independent transaction、commit、roll back or bypass another Module's public contract.
- Any resulting Domain Event uses the accepted WP-0030 `appendEventInTransaction` contract in the same transaction.
- Concrete business Event schemas and concrete business Consumers remain gated by WP-0035 plus their owning Domain WP.

### `apps/worker`

- Worker is the composition/runtime owner: authorized scope enumeration、transaction creation、server-resolved Tenant Context、registry composition、delivery invocation、transaction commit/rollback、shutdown and later retry handoff.
- Worker does not contain Consumer business rules and does not directly write a Module's private table.
- Cross-Brand work is a sequence of separately authorized Brand / Store transactions, never one bypassing transaction.

### `@bop/eventing`

- Owns transport-neutral types、registry validation、envelope compatibility checks、Inbox begin/complete coordination and stable outcomes/error codes.
- Accepts caller-owned database transactions and uses parameterized fixed SQL.
- Does not own network acknowledgement、broker SDK、polling、retry schedule、dead-letter disposition、business Event semantics or business-table writes.

### Transport adapter

- The adapter delivers an already accepted `DomainEventEnvelope` plus transport-neutral delivery context to Worker.
- Acknowledgement occurs only after the Worker transaction commits successfully or a committed duplicate result is observed.
- Adapter redelivery remains legal. No external broker、pg-boss integration、webhook endpoint or Provider-specific type is selected or introduced in WP-0032.

## Proposed Consumer registration contract

Each in-process registration declares:

- canonical `consumerName` and positive `consumerVersion`;
- exact accepted `eventType` plus exact supported `schemaVersion` values;
- owner Module;
- Tenant scope requirement: Brand-wide or exact Store;
- ordering requirement: `none` or `aggregate`;
- named side-effect classification;
- replay/rebuild safety declaration;
- handler accepting only the validated envelope and caller-owned transaction.

Registry construction rejects duplicate Consumer names、invalid names/versions、duplicate Event/version declarations、undeclared owner Modules and missing ordering/replay declarations before work starts. Runtime dispatch rejects an unknown Consumer、unknown Event type or unsupported schema version before an Inbox write or handler call.

This is a bounded in-process registry, not the WP-0035 Event Catalog、schema generator、AsyncAPI contract、dynamic plugin system or persisted subscription catalog.

## Proposed Inbox persistence contract

`platform_eventing.consumer_inbox` stores:

- `consumer_name text not null`;
- `event_id platform_helpers.uuid_v7 not null`;
- `event_type text not null`;
- `schema_version integer not null`;
- `brand_id platform_helpers.uuid_v7 not null`;
- nullable `store_id platform_helpers.uuid_v7`;
- `received_at timestamptz not null` recorded by PostgreSQL;
- nullable `processed_at timestamptz`;
- `status text not null`;
- `attempt_count integer not null`;
- nullable `result_hash text`;
- nullable `last_error_code text`;
- `correlation_id platform_helpers.uuid_v7 not null`.

The exact idempotency constraint is `UNIQUE (consumer_name, event_id)`, as required by Section 50.16. Tenant-leading operational indexes supplement but do not weaken that global identity:

- `(brand_id, received_at, consumer_name, event_id)`;
- partial failure/operations lookup only if an implementation-owned query exists and WP-0033's boundary is preserved.

`result_hash` is an optional bounded SHA-256 digest of a canonical, explicitly non-sensitive result discriminator. It is not a response body、payload hash、secret、PII fingerprint or authorization input. When no safe stable result exists it remains null.

The table uses `ENABLE ROW LEVEL SECURITY` plus `FORCE ROW LEVEL SECURITY`. Its policy requires `platform_helpers.current_brand_id()` and exact Store semantics through `current_store_id()`:

- Brand-wide rows require transaction Store context to be null;
- Store rows require exact Store equality;
- missing、invalid or cross-scope context denies access.

No runtime role、login、grant、RLS bypass or `SECURITY DEFINER` function is created. Application authorization remains primary；RLS is defense in depth.

## Transaction and delivery semantics

### First delivery

1. Worker resolves one exact registered Consumer and validates the envelope/type/version before starting business work.
2. Worker opens one PostgreSQL transaction and sets server-resolved transaction-local Brand and exact Store context.
3. `@bop/eventing` inserts the Inbox processing marker with `attempt_count = 1` using the fixed unique key.
4. The owning Consumer validates references and ordering, then performs its local side effect using that same transaction.
5. Any resulting Outbox Event is appended using WP-0030 in the same transaction.
6. `@bop/eventing` marks the Inbox row completed with database `processed_at` and optional safe `result_hash`.
7. Worker commits, then returns `processed` to the transport boundary.

### Duplicate delivery

- A committed completed row returns `duplicate_completed`; the handler and side effect are not run.
- The duplicate outcome exposes no stored payload or business result.
- Transport may acknowledge this outcome because the original effect and marker are already committed.

### Concurrent delivery

- Two transactions racing on the same `(consumer_name, event_id)` serialize through the unique constraint.
- Exactly one can create and complete the Inbox row.
- The loser observes the committed completed row and returns `duplicate_completed`; it never executes the handler.
- No application-level check-then-insert race is accepted.

### Handler rejection、failure and crash

- Validation before Inbox insertion returns a stable rejection and produces no attempt.
- A handler error、database error、process crash or shutdown before commit rolls back the Inbox marker、business side effect and generated Outbox Event together.
- Redelivery is therefore a new transactional attempt; before WP-0033 no durable failure attempt is claimed by the Inbox row.
- A commit outcome that is unknown to the Worker must be reconciled by re-running the same key: committed work resolves as `duplicate_completed`; rolled-back work is processed once.
- Worker must never acknowledge a handler failure or unknown commit as successful.

### Replay and rebuild

- Replaying the same Event to the same Consumer identity is a duplicate and cannot repeat the effect.
- A deliberate rebuild requires a separately registered replay-safe Consumer identity and owning-WP authorization；deleting or altering completed Inbox history is forbidden.
- WP-0032 supplies the identity and safety declaration only. Replay orchestration、operator UI、retention and Projection rebuild are non-goals.

## Atomicity invariant

The Inbox coordinator and Consumer handler share one transaction. The following states are impossible after transaction completion:

- committed business side effect with no completed Inbox row;
- completed Inbox row with rolled-back business side effect;
- committed generated Outbox Event with rolled-back Consumer effect;
- duplicate handler execution after a completed record is visible.

The Consumer cannot request early acknowledgement. Worker acknowledges only after commit. `@bop/eventing` never commits or rolls back the caller transaction.

## Ordering contract

- WP-0031 guarantees claim order only within one Outbox Aggregate head. At-least-once transport、multiple Consumers、redelivery and independent Aggregates can still reorder observations.
- WP-0032 guarantees no global order、cross-Aggregate order、cross-Consumer order、Brand order、Store order or wall-clock order.
- A Consumer declaring `ordering = none` must be safe for any delivery order.
- A Consumer declaring `ordering = aggregate` must validate its expected Aggregate version inside the same transaction against state owned by that Consumer's Module.
- Duplicate or older versions resolve idempotently according to the completed Inbox / owning state；a future version gap returns a stable retry-required result without committing a side effect or Inbox completion.
- WP-0032 does not add a generic Aggregate cursor or holdback queue. Scheduling a gap、backoff and terminal disposition belongs to WP-0033；concrete version compatibility belongs to WP-0035 and the owning Consumer.

## `attempt_count`、errors and WP-0033 boundary

WP-0032's successful Inbox record uses `attempt_count = 1`. A transaction that fails or crashes is rolled back completely and therefore cannot safely persist an increment without splitting the atomic Consumer transaction. WP-0032 must not introduce that split.

`last_error_code` is nullable and remains null on a completed WP-0032 record. Stable pre-commit outcomes are returned to Worker, not durably parked in Inbox:

- `CONSUMER_UNKNOWN`;
- `EVENT_TYPE_UNSUPPORTED`;
- `EVENT_SCHEMA_VERSION_UNSUPPORTED`;
- `TENANT_SCOPE_DENIED`;
- `AGGREGATE_ORDER_GAP`;
- `CONSUMER_REJECTED`;
- `CONSUMER_TEMPORARY_FAILURE`;
- `COMMIT_OUTCOME_UNKNOWN`.

The codes are low-cardinality and carry no payload、exception text、identifier or Provider detail.

WP-0033 owns durable attempt history/increment after rollback、backoff、next-at scheduling、maximum attempts、poison-event classification、failed/dead state、dead-letter storage、operator retry/discard、gap scheduling and alert escalation. It may add a forward migration and delivery-attempt record without rewriting WP-0032's completed idempotency history.

## Rollback and recovery

- Before migration application: normal reviewed Git revert of the unintegrated change.
- After migration application: applied migration bytes and completed Inbox history are immutable；recovery uses a new reviewed forward-fix migration or independently approved restore, never down/repair/baseline/mark-applied/checksum bypass/truncate/delete/history reset.

## Accepted Owner decision record

The composite authority did not uniquely determine these implementation-significant choices. The Owner explicitly accepted all thirteen recommendations on `2026-07-23`:

1. **Concurrent claim algorithm** — Recommended: insert the processing row inside the same Consumer transaction and rely on the exact unique constraint to serialize races；on conflict, read only the committed completion outcome. Impact: proves one effect without holding an application lock, but competing deliveries may wait for the first transaction up to the bounded database timeout.
2. **Inbox lifecycle** — Recommended: WP-0032 permits only transaction-local `processing` and committed `completed`; failed transactions leave no row. Impact: preserves atomicity and crash recovery while deferring durable failed/processing recovery states to WP-0033.
3. **Transaction ownership** — Recommended: Worker owns begin/context/commit/rollback；`@bop/eventing` and the Consumer share the provided transaction and cannot independently finalize it. Impact: makes Inbox、effect and generated Outbox atomic and constrains Consumer APIs.
4. **Attempt semantics** — Recommended: a committed WP-0032 Inbox row has `attempt_count = 1`; validation failures and rolled-back attempts are not durable. WP-0033 adds separate attempt evidence if accepted. Impact: avoids a second bookkeeping transaction but does not provide pre-WP-0033 historical failure counts.
5. **Result hash** — Recommended: nullable SHA-256 only over a canonical explicitly non-sensitive result discriminator；default null and never hash payload/full result/PII. Impact: retains the authority's field without creating a fingerprint or false authorization/equality contract.
6. **Consumer identity/version and replay** — Recommended: globally canonical immutable names include a major identity suffix, with positive registry version validated consistently；a rebuild uses a new explicitly authorized replay-safe Consumer identity. Impact: same identity always deduplicates, while a new identity can intentionally process retained Events once.
7. **Ordering gaps** — Recommended: no generic Inbox cursor；an Aggregate-ordered Consumer checks its own expected version in the shared transaction and returns `AGGREGATE_ORDER_GAP`, leaving scheduling to WP-0033. Impact: preserves Module ownership but cannot make progress on a missing predecessor before retry infrastructure exists.
8. **Tenant/Store shape** — Recommended: persist Brand and optional Store scope copied from the validated envelope；forced RLS requires exact transaction-local context, including null Store for Brand-wide work. Impact: supports shared Worker operation without bypass and prevents a Store worker seeing Brand-wide/cross-Store rows.
9. **Unknown/unsupported delivery** — Recommended: registry/type/schema validation occurs before Inbox insertion；unknown or unsupported input fails closed with a safe non-retryable outcome for later WP-0033 disposition. Impact: prevents poisoning Inbox/history, but durable quarantine/dead letter is unavailable until WP-0033.
10. **Consumer registry boundary** — Recommended: static in-process exact registry in `@bop/eventing`, composed by Worker；no persisted registry or concrete business Consumer in this WP. Impact: closes duplicate-name and compatibility behavior without pre-implementing WP-0035.
11. **Observability** — Recommended: low-cardinality registered aliases/type/version/outcome/duration only；no payload、exception text or unrestricted Event/Aggregate/Actor/Tenant/Store identifiers. Impact: safe operational signals now, with end-to-end propagation/export deferred to WP-0034/0040–0045.
12. **Migration/index boundary** — Recommended: one forward migration after `0000_011`, exact unique constraint plus one Tenant-leading received-time index；no speculative failed-status index until WP-0033 owns a query. Impact: minimal write amplification and deterministic ownership, while production plans remain External Evidence.
13. **Dedicated acceptance command** — Recommended: root command `pnpm consumer-inbox:acceptance` backed by a focused isolated Vitest config. Impact: makes concurrency/failure evidence repeatable and CI-addressable without changing the general lifecycle owner.
