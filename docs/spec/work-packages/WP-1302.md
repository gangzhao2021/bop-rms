## Purpose

Create the Payment-owned application contract, aggregate records and persistence schema for one
online-card Payment Intent. The service must prove that Ordering's immutable Submitted / Payment
Pending submission and capacity allocation are already durable, atomically claim one Payment
Intent/Attempt, and only then call the WP-1301 adapter. Browser/client money, status and Provider
objects never enter the command.

## Closed execution contract

1. The public internal command accepts exactly Payment operation reference, Ordering submission,
   Cart, expected Cart version, Quote, optional server-owned tip-selection reference and request UTC
   instant. It accepts no amount, currency, status, Provider reference, metadata or client secret.
2. `CreatePaymentIntent` authorization and a usable exact Brand/Store Guest Session are required
   before any idempotency, Ordering, Payment or Provider read. Denial performs no business read.
3. The operation reference permanently binds the Cart/version/Quote/submission/tip-selection
   intent digest. Same authorized intent returns the original record; changed intent or scope is an
   idempotency conflict and never creates another Attempt or Provider call.
4. Ordering is accessed only through a public payment-preparation port. Its strict evidence must
   prove one immutable Submitted Order/first Batch and exact Quote, `PaymentPending` readiness, and
   a server-owned capacity allocation committed in the same PostgreSQL transaction. Capacity
   expires exactly 30 minutes after Payment Intent creation. Missing, malformed, scope-mismatched or
   expired evidence stops before Payment persistence and Adapter use.
5. Ordering evidence supplies immutable CAD `orderAllocation`, `tip` and `total` Money plus digest;
   total must equal allocation + tip and be positive. Payment recomputes the relationship using the
   public Pricing Money contract. Client values cannot override it.
6. Payment atomically creates one Intent aggregate, canonical Attempt 1 and permanent operation
   record before Provider invocation. A concurrent/replayed claim returns the stored record. An
   already-claimed record with no outcome remains `Processing`; it is never blindly re-created.
7. Online v0.1 is closed to `Stripe`, `OnlineCard`, `Automatic`, CAD and environment `Test | Live`.
   The deterministic Provider idempotency key is bound to environment + Payment operation/Attempt.
8. The service calls only `PaymentProviderAdapter.createIntent`. Its result is strict-parsed and
   must echo exact Provider environment, Brand/Store/Attempt/operation, method, capture mode and
   requested total. Raw Provider data or mismatched results fail closed.
9. Provider observations are append-only. A thrown/invalid/ambiguous result is recorded as safe
   `Unknown / CREATE_RESULT_UNKNOWN`; timeout alone never becomes success or failure. A create
   snapshot never directly creates a Payment Transaction, advances Order or authoritatively marks
   Payment success; WP-1303+ owns verified progression.
10. The creation transaction includes a Restricted audit record with stable action/reason codes.
    Payment tables force Brand/Store RLS, expose no runtime grants, preserve identity/operation/
    Attempt history, use integer minor units and prohibit ordinary deletes.
11. No HTTP route, Stripe SDK, client-secret delivery, browser confirmation, webhook, Transaction,
    Event, Projection, reconciliation job, Kill Switch, refund, Terminal flow, real account fact or
    External Evidence is authorized.

## Persistence model

- `payment_intent`: Aggregate Root; immutable scope/financial/preparation identity and versioned
  current creation lifecycle.
- `payment_attempt`: Aggregate Child Entity; canonical Attempt 1 and deterministic Provider-call
  identity; immutable after creation.
- `payment_intent_operation_record`: append-only permanent idempotency binding.
- `payment_provider_observation`: append-only normalized snapshot/failure/unknown evidence with no
  raw Provider payload.
