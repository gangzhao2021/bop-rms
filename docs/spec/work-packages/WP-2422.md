## R1 — deployable composition root (plan)

Facts recorded on 2026-10-06:

- `apps/api/src/server.ts` started without `--configuration` mounts no business routes, and `/ready`
  returns 503.
- The business wiring is in 149 non-test `tooling/environment/pilot-*.mjs` files, about 17k lines of JS.
  It is outside every `tsconfig` include.
- `pilot-api-entry.mjs` requires `NODE_ENV=development` and port 4300.
- Workspace packages export `src/*.ts` directly, so even `apps/api/dist/server.js` only runs under
  `tooling/environment/register-workspace-typescript.mjs`.
- A lenient `checkJs` probe over `tooling/environment/*.mjs` (strict off, run from a scratch config)
  reports 223 errors. Most come from inference of `unknown` catch variables; port-shape mismatches
  such as `BrowserCredentialHasherPort` need individual review.

Owner decision (2026-10-06): packaging strategy **(a)**. Packages emit `dist` with the existing `tsc`
and use conditional exports; no dependency is added. Strategy (b), bundling the apps, was not selected.

R1a, packaging (done):

- The 32 `packages/bop/*` and `packages/rms/*` modules export
  `{ types: src, development: src, default: dist/<repo path>/src/*.js }`.
- Each module has a `tsconfig.build.json` that excludes tests. It keeps the repository-relative
  `rootDir` already used by `@bop/eventing`, because generated `module.manifest.ts` imports
  `tooling/module-manifest`.
- `@bop/eventing` keeps its existing dist export.
- TypeScript resolves `types`. Vitest resolves `development`, as checked with `@rms/catalog` exporting
  an absent dist.
- `register-workspace-typescript.mjs` adds `development` for `@bop/`, `@rms/` and `@bop-rms/`
  specifiers only, so loader-run dev/pilot processes keep running source. Plain Node resolves `dist`.
- `import-boundary` accepts an unbuilt `./dist/` target only beside an existing source target.
- The module generator emits the same convention for new modules.

Remaining steps, each one usable workflow, starting with the pickup sale:

1. Move composition into `apps/api/src/composition` and `apps/worker/src/composition` as TypeScript.
2. Reduce the `tooling/environment` entries to thin launchers.
3. Add a production start path that does not require `NODE_ENV=development`.

Start them only after the R6 checkpoint commit. The pilot runtime is the only working composition,
and these 149 files must not be moved without a recoverable baseline.

## R2 — reproducible runtime ACL (plan)

Section 95.4 (accepted) constraints:

- Migrations never embed a runtime role name.
- No broad schema-wide future grant.
- Per-object least privilege only after accepted ownership/permission evidence.

Writing GRANTs into migrations would therefore reopen 95.4, and is not selected.

Baseline, measured by a static scan:

- `packages/database/test` and `test-support` issue about 1,855 GRANT statements.
- These cover 494 objects and 1,080 object×privilege pairs, including 167 column-scoped grants and 13
  `ALL TABLES IN SCHEMA` grants.
- The pilot recorded 354 object ACL entries and 16 column grants, applied by hand in approved batches
  (`docs/runbooks/single-store-pilot.md`).

Design:

- A versioned runtime ACL matrix per module, next to the existing `database-access.manifest.ts`: table
  or column → principal class (api/worker/projection) → privileges.
- A generator renders GRANT/REVOKE SQL for role names supplied by the installation.
- A verifier compares an installation's catalog ACL with the matrix.
- Isolated DB tests take their grants from the generator instead of hand-written GRANTs.
- Matrix rows still need the Owner approval that the runbook requires. The matrix makes that approval
  reviewable once instead of per batch.
