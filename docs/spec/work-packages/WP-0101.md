## Problem and bounded intended outcome

Identity now defines who an Actor is, but the repository has no owning Brand、Store or Operating Entity Aggregate. Later Membership、Tenant Context and Permission code must not infer Tenant scope from arbitrary IDs、Provider claims、route/query values or legal-entity data.

WP-0101 establishes the smallest executable Organization foundation:

- a `@bop/tenant` Phase 0 boundary owning Brand and Store identities/lifecycle;
- a separate `@bop/operating-entity` Phase 0 boundary owning Operating Entity and explicit effective-dated Brand/Store assignments;
- strict Aggregate construction and expected-version transitions with privacy-safe failures;
- deterministic fail-closed Operating Entity resolution for exact Store、Business Function and Effective Time;
- Stage DB-1 schemas/tables with explicit ownership、constraints、forced RLS and no default runtime privilege;
- synthetic domain and isolated PostgreSQL evidence.

This WP does not create a Membership、Store Assignment to an Actor、Tenant Context Middleware、Role、Permission、Store Configuration、hours、menu、capability publication、real corporation/Store record、production resource or external integration.

## Ownership and boundaries

`@bop/tenant` owns Brand as the primary Tenant boundary and Store as a child Tenant scope. A Store belongs to exactly one Brand. Brand/Store references identify scope but grant no Actor access.

`@bop/operating-entity` owns the independent entity and its Brand/Store relationship Assignments. It imports only public opaque Brand/Store references from `@bop/tenant`; it never reads or writes Tenant private tables through application code. Database relations retain opaque references without cross-schema foreign keys, preserving Domain ownership.

WP-0102 owns Actor Membership and workforce Store Assignment. WP-0103 resolves server-authoritative Tenant Context and applies transaction-local scope. WP-0104 evaluates permission decisions. WP-0105 owns Role/Grant/explicit deny/allow. Store setup/configuration、hours、service modes、Delivery and real pilot activation remain later Store/Configuration WPs.

Brand is not a Legal Entity. Store is not a Tenant grant. Operating Entity is not a permission scope and cannot authenticate an Actor.

## Adopted Recommended Owner Decisions

1. **Two owning Modules —** create exact Phase 0 modules `tenant` / `@bop/tenant` and `operating-entity` / `@bop/operating-entity`; do not collapse Organization, Identity, Membership and Permission into one model.
2. **Stage DB-1 persistence belongs here —** unlike WP-0100 Session persistence, no later backlog item owns Brand/Store/Operating Entity persistence. WP-0101 therefore materializes only its five owning tables and dedicated acceptance evidence.
3. **Brand is primary Tenant —** every Tenant-owned fact has an opaque lowercase UUIDv7 Brand reference. A code、name、domain、Provider subject or route/query value is never authorization.
4. **Brand Aggregate —** use closed lifecycle `Draft | Active | Suspended | Archived`; store opaque ID、bounded code/display name、default locale/currency、positive version and canonical UTC timestamps. Archive/suspension never rewrites historical references.
5. **Pilot currency boundary —** the accepted v0.1 planning currency is exact `CAD`. Multi-currency Brand activation requires an accepted future decision; no exchange or Money calculation exists here.
6. **Store Aggregate —** each Store has one immutable Brand reference、opaque UUIDv7 Store ID、bounded code/display name、IANA time zone、locale、`CAD` currency、closed lifecycle and positive version.
7. **Store scope cannot widen —** Store mutation requires its exact Brand and expected version. Moving a Store between Brands is prohibited; create a new Store reference under a separately accepted migration/correction workflow.
8. **No Store configuration —** hours、Business Date cutoff、service mode、Table/QR、Dine-in/Pickup/Delivery、catalog source、tax calculation and operational capability are excluded. ADR-0028 remains a planning baseline, not an active Store fact.
9. **Optimistic concurrency —** every mutable Aggregate and Assignment carries a positive version; mutation requires exact expected version and fails closed on conflict. No last-write-wins.
10. **Operating Entity independence —** Operating Entity is its own Aggregate Root and not embedded in Brand or Store. Brand/Store do not store tax、bank、license or legal identity values.
11. **v0.1 entity kind —** construction accepts only `LegalEntity` for this pilot increment. Sole proprietorship、operating unit、franchise and multiple-entity activation remain Future Triggers; the broader historical vocabulary is not silently enabled.
12. **Legal fact boundary —** legal name、registration、jurisdiction、tax、billing and settlement fields are either bounded synthetic values or opaque controlled references. `PendingExternalEvidence` cannot be activated as a real operating fact. No professional verification result is fabricated.
13. **Closed entity lifecycle —** use `Draft | PendingExternalEvidence | Active | Suspended | Archived`. Activation requires an injected verified-evidence reference contract; this WP tests only synthetic evidence and makes no real activation claim.
14. **Explicit Assignments —** own distinct `BrandOperatingEntityAssignment` and `StoreOperatingEntityAssignment` records. An Operating Entity may relate to multiple Brand/Store references only through these records.
15. **Business Functions —** use the closed set `SalesReceiptIssuer | TaxRegistrant | PaymentSettlementOwner | ProcurementBuyer | LicenseHolder | Employer`.
16. **Effective Period —** Assignment uses canonical UTC millisecond `effectiveFrom` and optional exclusive `effectiveUntil`; end must be later than start. No client clock or Business Date resolves legal responsibility.
17. **Exact resolution —** Store + Business Function + effective instant must resolve exactly one active Store Assignment. Zero or multiple matches fail closed with stable codes. Brand Assignment is not an implicit Store fallback.
18. **Cross-Brand boundary —** an Operating Entity may be referenced by more than one Brand only through separately authorized Assignments. That relationship does not permit data access across Brands.
19. **Historical snapshot boundary —** downstream Order、Receipt、Payment、Purchase Order and Compliance owners later persist their own immutable resolved snapshot. WP-0101 only returns a stable snapshot reference/value and never rewrites downstream history.
20. **Correction model —** no hard delete is exposed. Lifecycle/effective-period correction uses expected-version state transition plus Audit intent; append-only Audit/Event evidence is composed later through public ports.
21. **Database ownership —** `bop_tenant` owns exact tables `brand` and `store`; `bop_operating_entity` owns `operating_entity`、`brand_operating_entity_assignment` and `store_operating_entity_assignment`.
22. **No cross-Domain private FK —** `bop_tenant.store` may reference its owning Brand table. Operating Entity assignments store validated opaque public Brand/Store references without a foreign key into `bop_tenant`, avoiding a private-table dependency.
23. **Forced RLS —** Brand and Store rows are forced-RLS Tenant data. Brand access requires exact transaction-local Brand with null Store; Store access requires exact Brand and Store. Operating Entity visibility is derived only from an exact in-schema Brand or Store Assignment matching transaction-local context.
24. **Least privilege —** schemas/tables revoke `PUBLIC`; WP-0101 creates no login、role、credential or broad runtime grant. Later repositories receive only reviewed object-level grants with WP-0103 context composition.
25. **Relationship integrity —** persistence enforces UUIDv7、closed codes/lifecycles/functions、positive versions、canonical effective ordering、unique stable IDs and scope indexes. Domain resolution additionally rejects overlapping effective matches.
26. **No Event Catalog widening —** no new published Event is introduced. Future event/outbox composition requires its owning contract and catalog evidence.
27. **Privacy classification —** Brand/Store business names and references are `Internal`; legal/registration/tax/billing/settlement/evidence facts are `Restricted`. Logs、URLs and analytics prohibit raw values; fixtures are synthetic-only.
28. **Dependency discipline —** `@bop/tenant` has no synchronous business dependency in this increment. `@bop/operating-entity` may depend only on the public `@bop/tenant` contract. No external package is added.
29. **No real pilot seed —** ADR-0023–0028 planning choices are represented only as contract bounds. The synthetic code `CA-ON-TOR-PILOT-001` remains documentation/evidence context and is not inserted into a seed or database.
30. **Future composition —** Membership and Permission consume opaque references only. Neither module imports Identity private paths or decides which Actor may use a Brand/Store.

## Security、privacy、risk and rollback

- **Arbitrary ID becomes authorization:** references carry no permission; WP-0103/0104 must resolve server authority before database context or action.
- **Store crosses Brand:** immutable Store Brand、composite indexes、forced RLS and exact domain checks deny mismatch.
- **Operating Entity leaks across Brand:** entity visibility requires an explicit matching Assignment; no global list or unrestricted Legal Entity lookup exists.
- **Assignment ambiguity:** exact resolver fails closed on zero/overlap and persistence/repository acceptance must prove concurrency handling before activation.
- **Legal/financial data leakage:** Restricted values and evidence references never enter logs、URLs、analytics or fixtures; no bank account or tax identifier is accepted as evidence here.
- **Lifecycle rewrite:** suspend/archive/effective correction uses versioned transition; downstream snapshots and existing Audit/Event history are never rewritten.
- **Cross-Domain coupling:** no Operating Entity application query or FK reaches Tenant private tables; only public opaque references cross the boundary.
- **Rollback:** before shared integration, reviewed Git revert plus forward migration removes only empty synthetic-only schemas. After a migration is shared, never edit applied SQL; use forward disable/contract migration after dependency and retention review. No production/data rollback is authorized by WP-0101.
