## Acceptance and design

Add an independent Customer PWA Dining binding client for the three fixed WP-2300 endpoints.
Preparation takes closed operationReference/csrfToken/admissionReference; activation and completion
retain their exact transport contract. Validate canonical UUIDv7 admission and operation, closed
plain own-data inputs, exact response echoes and finite canonical timestamps without trusting client
clock for server authorization. Capture fields before asynchronous work. Raw Session credentials
remain browser-managed HttpOnly cookies and are never accepted or returned in the client contract.

Require fixed relative URLs, same-origin credentials, cors Fetch Metadata, no-store, redirect error,
no-referrer, a bounded4096-byte UTF-8 JSON body and a finite deadline covering headers and body.
Candidate CSRF/proof are ephemeral caller-memory only. No state replacement, storage, rendering,
analytics, mutation queue, automatic replay or inferred rollback on unavailable/unknown outcomes.
Malformed/offline inputs produce no fetch. Known400/503 remain bounded; wrong-purpose envelopes,
redirects, timeouts and unknown results remain outcome-unknown with no raw reflection.

Use this production client in the existing actual Dining/Identity PostgreSQL HTTP recovery test
through an explicitly synthetic cookie/header boundary. Preserve raw HTTP cookie assertions and
Closing/Move regressions. After lost acknowledgement, complete after preparation expiry using
both staged and already-published main cookies; no duplicate owner or Identity history/Audit.
This is local client/HTTP/PG composition evidence, not actual browser/TLS loss or complete UI.
