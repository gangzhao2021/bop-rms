## Purpose and bounded outcome

WP-1600 establishes the Fulfillment-owned Phase-1 Pickup Aggregate and its idempotent creation
boundary:

1. consume the already registered public `OrderConfirmed.v1` contract through
   `fulfillment.confirmed-order:v1` and independently authorize the exact Brand / Store source;
2. resolve a strict Ordering-owned public source DTO containing only Pickup type, exact Order / Batch
   / Item references, quantities, source version/digests and captured UTC time;
3. create exactly one Store-scoped `Pickup` Fulfillment in `Pending`, aggregate version `1`, with one
   pending Fulfillment Item per exact Order Item and zero handed-over quantity; and
4. atomically persist the Fulfillment, Items, immutable creation operation, Audit and generic Inbox
   completion. Same-Event, semantic redelivery, concurrency and commit-unknown recovery converge;
   conflicting source identity or content fails closed.

No Kitchen Ready consumer, Pickup proof, Complete Pickup Command, Handoff Record,
`FulfillmentCompleted` Event, Ordering completion Projection, Customer/Pickup UI, HTTP/SSE adapter,
live role/grant, Delivery flow, Customer/contact/address snapshot or production activation is
introduced. WP-1601–WP-1605 retain those lifecycle increments.

## Closed Domain contract

- Owner: new `@rms/fulfillment` Module and `rms_fulfillment` schema. Ordering remains owner of Order
  and source evidence; Kitchen remains owner of Ready facts.
- Aggregate identity: stable Fulfillment reference derived from Brand + Store + Order. The database
  enforces one Fulfillment per Order and one creation operation per semantic confirmation.
- Initial lifecycle: `fulfillmentType=Pickup`, `canonicalPhase=Pending`, `aggregateVersion=1`.
  `Ready`, `InProgress`, `Completed`, `Failed` and `Cancelled` are recognized future states but are
  not writable in this WP.
- Item invariant: exact non-empty unique Order Item set, positive ordered quantity, ready and
  handed-over quantities both `0`, state `Pending`; Fulfillment never copies Catalog definition,
  price, tax, Payment, Customer note or Kitchen state.
- Authority: System consumer intent, purpose `CreatePickupFulfillment`; public screen permission
  `fulfillment.operate` remains query/command composition owned by later WPs and is not a substitute
  for consumer authorization.
- Concurrency/idempotency: generic Inbox + permanent Event and semantic Order identities; no
  last-write-wins, no duplicate Aggregate, no replacement of original provenance and no Event
  emitted before a later lifecycle WP authorizes it.
- Time/money: all instants are strict UTC. No Money fact enters Fulfillment in this increment.

## Persistence and privacy

Migration `1700_001` creates `fulfillment`, `fulfillment_item` and
`fulfillment_creation_operation` as Fulfillment-owned forced-RLS Store tables. Aggregate and Item
updates remain closed until their owning lifecycle WPs; creation provenance is permanently
append-only. Cross-Domain references have no private-table foreign keys. PUBLIC privileges are
revoked.

Classification is `indirect_identifier`. The boundary excludes Customer name/contact/address,
Customer note or possible-health text, Pickup proof, allergen narrative, Money, Payment, Provider,
credential and unrestricted object data. Logs, URLs and analytics may contain only bounded outcome
codes and never references or digests.

## Acceptance criteria

- A strict authorized Pickup source creates one exact Aggregate and Item set in one transaction.
- Dine-in, missing/partial/stale/malformed/cross-scope source, changed source digest and unknown
  dependency result fail before an effect.
- Same Event, semantic redelivery, concurrent delivery and commit-unknown recovery return the
  original result without a second Aggregate, operation or Audit record.
- Persistence proves composite scope keys, one-per-Order uniqueness, forced RLS, cross-Store denial,
  immutable creation provenance and exact item quantities.
- Ordering and Fulfillment unit/contract tests, migration/tenant regressions, architecture gates,
  root format/lint/typecheck/test/build, security/privacy review, exact-head and exact-main CI pass.
