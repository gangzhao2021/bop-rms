## Goal

Create independently verifiable API, worker, merchant-web, and customer-PWA application skeletons, plus the smallest shared UI foundation needed to keep semantic tokens and accessibility primitives consistent. Materialize the machine-checkable Section 88 Screen Registry before feature-page implementation.

## Scope and deliverables

- `apps/api`: Express `5.2.1` app factory and process entry, bounded HTTP defaults, structured `/health` and `/ready`, and tests. Readiness explicitly reports required database as `not_configured` and returns `503` until it exists.
- `apps/worker`: deterministic lifecycle and signal-handling skeleton with no jobs, timers, persistence, queue, Outbox/Inbox, or Provider behavior.
- `apps/merchant-web` and `apps/customer-pwa`: React `19.2.7`, Vite `8.1.4`, React Router `8.2.0`, Tailwind `4.3.2`, accessible synthetic shells, visible loading/error/offline placeholders, and smoke tests.
- `packages/ui`: justified by Sections 86.6 and 90.10 to keep BOP Pilot Neutral semantic tokens, focus treatment, reduced-motion behavior, and minimal BOP-owned shell/status wrappers identical across both web applications. Radix remains an approved future primitive layer; no business component or page is created here.
- `docs/product/screen-registry.yaml` and `screen-registry.schema.json`: reviewed, machine-checkable mirror of all 210 current Section 88 Screen IDs, including aliases and contextual/embedded placement.
- Four concise nested `AGENTS.md` files required by Section 89.4.
- Root and package scripts, lockfile, CI, and documentation needed to verify this WP.
