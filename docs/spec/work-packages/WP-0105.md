## Objective and scope

Extend the existing `@bop/permission` owner with the smallest Phase 0 authoritative policy source:

- exact-action Permission Definition lifecycle with an initially empty catalog;
- Workforce Brand/Store Role and Actor Role Assignment;
- Role-to-Permission Grant;
- Actor-scoped Explicit Deny/Allow;
- a Brand policy state carrying an opaque snapshot reference and positive optimistic version;
- deterministic server-side materialization of active facts into the normalized WP-0104 `PermissionEvidence` contract;
- Stage DB-2 schema/table ownership、constraints、indexes、forced RLS、least privilege and isolated synthetic PostgreSQL evidence.

This WP creates no concrete business Permission、wildcard、Workflow/Approval policy、API middleware/route、frontend capability、Platform Administrator authorization、Session/cache/revocation mechanism、Audit write adapter、Event/Outbox、real workforce/Tenant fact、Provider/cloud resource or production action.

## Ownership and boundaries

`@bop/permission` is the sole owner of Permission Definition、Role、Role Assignment、Permission Grant、Explicit Override and policy-state facts. It consumes only public immutable Identity/Tenant/Membership facts and emits only normalized evidence accepted by WP-0104. It never reads or writes another Domain's private table and never accepts client Role/Grant/Override claims as authority.

Membership proves where a Workforce Actor may operate but grants no business action. Role Assignment and Permission Grant prove what an active Actor may do. Business Command Handlers still follow Section 52.6: validate Actor、resolve Tenant、evaluate Permission、validate resource scope、enforce business invariants、then compose Audit/Event.

## Adopted Recommended Owner Decisions

1. **Single owner —** extend existing `permission` / `@bop/permission`; no second IAM、RBAC or policy package.
2. **Workforce tenant increment —** implement exact Brand/Store policy facts for active Workforce Users. Platform Administrator role activation remains a future platform-security WP because WP-0104 has no Platform Tenant Context.
3. **Empty Permission Catalog —** define lifecycle and exact action identity but seed no concrete action. Each future business WP owns registration of its exact action.
4. **Exact action only —** Permission Definition uses the bounded lower-case dot-delimited WP-0104 action syntax. Wildcard、prefix、glob、regex and implicit page/action inheritance are prohibited.
5. **Permission lifecycle —** a definition is `Active | Retired`; retired definitions cannot produce granting evidence and are never repurposed to a different action.
6. **Role scope —** a Role is bound to one Brand and optionally one exact Store. Brand Role may apply in that Brand's Store context；Store Role applies only to that Store.
7. **Role lifecycle —** `Active | Suspended | Retired`; retired is terminal. Changes require expected positive version and monotonic UTC update time.
8. **Role code —** a bounded normalized machine code is unique within exact Brand/Store scope. It is display-neutral, not a Permission action, and never authorizes by name.
9. **Role Assignment —** explicitly connects one Workforce Actor and active Membership to one Role. It is not stored on User or Membership and does not mutate either owner.
10. **Assignment admission —** Brand Role requires the exact active Actor+Brand Membership；Store Role additionally requires the exact active Store Assignment at materialization time.
11. **Assignment lifecycle —** `Active | Suspended | Ended` with half-open effective period. Ended is terminal；all transitions use expected version.
12. **Permission Grant meaning —** a Grant is only Role-to-one-active-Permission-Definition allow evidence. It cannot express deny、Workflow conditions、amount limits、approval requirements or resource filters beyond the Role scope.
13. **Grant lifecycle —** `Active | Revoked`, half-open effective period, expected version and immutable Role/Permission/scope references. Revoked is terminal.
14. **Explicit Override meaning —** an Override binds exact Actor、Brand、optional Store and one exact action with effect `Deny | Allow`.
15. **Override precedence —** WP-0104 remains authoritative: Explicit Deny > Explicit Allow > Role Permission > Default Deny. WP-0105 never implements a second evaluator.
16. **Override reason —** every Explicit Deny/Allow requires an opaque bounded reason reference and correlation reference. Free text is excluded from policy facts、logs and decision explanations.
17. **Override lifecycle —** `Active | Revoked`, half-open effective period and expected version. Revocation/correction creates a new state transition; rows are never deleted or silently rewritten.
18. **Deny-first fail closed —** ambiguous duplicate active facts、foreign scope、inactive dependencies、missing policy state or invalid version produces no allow evidence and returns a stable safe error.
19. **Policy state —** one Brand policy state carries a UUIDv7 snapshot reference and positive version. Every Role/Assignment/Grant/Override mutation must atomically advance it using expected version.
20. **Snapshot semantics —** materialization emits exactly the persisted current snapshot/version. It never derives authority from wall-clock-only cache keys、array order or client input.
21. **Materialization input —** trusted server-side code supplies revalidated Tenant Context plus public active Membership/Assignment and permission-owned policy facts. Raw request headers/body/frontend state are forbidden authority.
22. **Evidence mapping —** active explicit records map to `ExplicitDeny | ExplicitAllow`; active assignments plus active Role+Grant+Permission map to `RolePermission`. Evidence references are opaque UUIDv7 values.
23. **Order independence —** materialized evidence is deduplicated and deterministically sorted. Conflicting duplicate references fail closed rather than picking first/last.
24. **No implicit grant —** Role existence、Membership、Store Assignment、screen visibility or empty catalog never authorizes. Zero evidence remains WP-0104 Default Deny.
25. **UTC/effective periods —** all policy facts use canonical UTC instants and `[effective_from, effective_until)`; browser time is never authoritative.
26. **Optimistic concurrency —** mutable roots use positive version and conditional update semantics. Last-write-wins、force、repair and silent overwrite are prohibited.
27. **Persistence owner —** create only `bop_permission` and its six exact tables: `policy_state`, `permission_definition`, `role`, `role_assignment`, `permission_grant`, `permission_override`.
28. **Relationship modeling —** Role Assignment and Permission Grant are relationship tables; no role/permission arrays or JSONB policy blob exists.
29. **Foreign keys —** local permission-owned references may use same-schema foreign keys. Identity/Tenant/Membership references remain validated opaque UUIDv7 values with no cross-Domain foreign key.
30. **Tenant isolation —** all Actor/Role/Grant/Override/policy rows carry Brand scope；Store-scoped rows also carry Store. Forced RLS uses exact transaction-local Brand and, where present, Store context.
31. **Global catalog boundary —** `permission_definition` is permission-owned and Tenant-neutral. It has no runtime/public grant in this WP; only trusted owner materialization may read it.
32. **Least privilege —** revoke PUBLIC schema/table access and create no role/login、default runtime grant、credential、`SECURITY DEFINER` function or dynamic SQL.
33. **Indexes —** only known exact policy materialization and lifecycle/version lookup paths receive indexes; no unbounded listing query is introduced.
34. **Audit boundary —** commands/materialization expose bounded audit descriptors with action/effect/reason class/correlation and opaque references. Real append composition remains the existing Audit owner and future integration; no successful Audit write is claimed here.
35. **Privacy —** Actor、Membership、Role、Grant、Override and policy references are indirect/sensitive identifiers. Logs、URLs、analytics and screenshots are prohibited; fixtures are synthetic.
36. **No cache/session authority —** no cache、Session snapshot、revocation or token claim is created. WP-0108 owns revocation composition.
37. **No Event/API/UI expansion —** no Event Catalog、Outbox、API route、OpenAPI、screen registry or frontend file is changed.
38. **Forward-only recovery —** migration is immutable and forward-fix only. Before integration, normal Git revert removes code; applied database state is never down-migrated or deleted.
39. **External Evidence —** no real employee、Store、Provider、credential、staging/production database or independent-review evidence is required or claimed.
40. **Future composition —** WP-0106–0109 own real authentication integration、BFF/session security、invite/MFA/recovery/revocation、Store switch、object authorization and end-to-end cross-Tenant negative evidence.

## Risks、security review and rollback

- **Privilege escalation:** exact action/scope、active public dependencies、deny-first compatibility and default deny prevent Membership/Role existence from becoming authorization.
- **Cross-Tenant evidence:** Brand is mandatory and Store is exact where present；foreign facts produce no evidence and forced RLS provides defense in depth.
- **Stale policy:** every mutation advances one optimistic Brand policy snapshot/version；no cache/session claim exists.
- **Deny bypass:** explicit deny is materialized distinctly and the unchanged WP-0104 evaluator remains authoritative.
- **Ambiguity/conflict:** duplicate active references or inconsistent scope fail closed and never use array/query order.
- **Audit gap:** bounded descriptor and mandatory opaque reason/correlation are testable；real Audit append composition is not falsely claimed.
- **Privacy leakage:** no email、name、Provider subject、free text、raw token or real workforce fact enters source、fixture、log、URL、analytics or screenshot.
- **Migration risk:** six new empty Stage DB-2 tables use finite timeouts、one transaction、forced RLS and no runtime grants. Applied bytes are immutable and recovery is forward-fix.
- **Rollback:** prior to shared integration, reviewed Git revert. After migration application, only an accepted forward correction or separately authorized restore/compensation; no down/delete/repair.

Security/privacy readiness finding counts: Blocker `0`、High `0`、Medium `0`、Low `0`. Residual risks are the accepted Process-enforced GitHub Free administrator-bypass risk and future real integration/cache/revocation/Audit wiring; neither is represented as production readiness.
