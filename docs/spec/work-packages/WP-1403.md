## Purpose and bounded outcome

WP-1403 adds Kitchen's first Store-scoped, versioned and rebuildable operational
read model over the immutable Ticket / Work Item facts delivered by WP-1401 and
the deterministic Station assignment delivered by WP-1402. It activates the
already registered `kitchen.queue-projection:v1` consumer contract for
`KitchenWorkCreated.v1`, but does not register a live Worker.

The bounded result is one coherent active Kitchen queue generation per exact
Brand + Store:

- a Store-level set of per-generation headers records lifecycle state, source
  checkpoint, safe source binding, safe queue digest, as-of/freshness evidence
  and an explicit initialized-empty state, while a scoped partial unique index
  selects at most one `Active` generation;
- one projection row exists for every Work Item in the active generation and
  exposes only the safe fields needed for Station lanes, exact reference lookup
  and current quantity/status display;
- duplicate, concurrent, replayed and commit-unknown consumer attempts converge
  without duplicating a row or changing a source Ticket; and
- an authorized rebuild writes a complete shadow generation and switches it
  atomically only after exact count, identity, checkpoint and digest
  reconciliation.

This WP creates no Kitchen lifecycle Command, Ready decision/Event, Customer or
health interpretation, API, UI, realtime message, Worker composition, runtime
role/grant, external resource or production activation. WP-1404–WP-1408 and
WP-1804 retain those responsibilities.

## Resolved authority, precedence and ownership

1. **Canonical identity.** The Handoff contains one Feature F14.1 and names
   `WP-1403 — Kitchen Queue Projection`; it contains no F14.2.
2. **Source ownership.** Kitchen alone owns Ticket, Work Item, Station-routing
   snapshot and current Kitchen state. The projection never becomes the source
   for a status transition and never writes the three WP-1401 transaction
   tables.
3. **Projection ownership.** Section 80.9.2 names `kitchen_work_queue_v1` and
   Section 88 makes `kitchen_*_v1` the authoritative family for
   `KIT-KITCHEN-QUEUE` and `KIT-WORK-ITEM`. The projection write owner is
   `@rms/kitchen.queue.v1`; public readers use only the Kitchen Application
   Query contract.
4. **Reporting boundary.** Section 48.4.9's Operational Reporting Module owns
   later cross-Domain reporting. It does not take ownership of Kitchen's local
   operational queue or gain a Kitchen write interface.
5. **Table-mapping boundary.** Section 26.2 prohibits a second business Ticket;
   it does not prohibit a read model. Section 50.21's three Kitchen tables are
   the Phase-1 source-transaction mapping, not an exhaustive projection table
   inventory. Section 50.20 expressly requires independent, versioned,
   rebuildable Projection tables.
6. **Permission precedence.** The later Section 88 machine mirror fixes the
   Kitchen screens' exact permission reference as `kitchen.operate`, with
   Tenant, Brand, Store, Actor, purpose and field scope. WP-1403 does not revive
   the older `kitchen.work_item.read` spelling or seed a new Permission.
7. **Privacy boundary.** WP-1401's Customer note can be Restricted
   possible-health data. Neither it nor a digest derived from it enters this
   projection. Structured allergen assistance, safety cues and acknowledgement
   remain WP-1407.
8. **Operational boundary.** A non-fresh projection is an explicit read-only
   operational view. It cannot authorize Accept, Start, Hold, Complete, Ready,

## Closed execution contract

### Exact projection schema and safe fields

1. Migration `1500_002` creates exactly two Kitchen-owned projection tables in
   `rms_kitchen`:

   - `kitchen_work_queue_projection_generation`; and
   - `kitchen_work_queue_projection`.

   It neither changes nor backfills `kitchen_ticket`, `kitchen_work_item` or
   `kitchen_action_record`.

2. Each Store-scoped generation header contains exactly these logical fields:

   - projection generation, Brand and Store references;
   - projection name `kitchen_work_queue_v1` and version `1`;
   - generation state `Building | Active | Retired`;
   - required opaque Kitchen source checkpoint reference;
   - canonical `sourceEventBindingDigest` and `queueSnapshotDigest`;
   - non-negative Ticket and Work Item counts;
   - explicit initialized-empty indicator;
   - `asOfUtc`, `projectedAt`, nullable `lastRebuiltAt` and persisted
     `Fresh | Stale` freshness status at projection time; and
   - rebuild reference, canonical `rebuildRequestDigest` and requested UTC
     instant, all non-null only when created by an explicit rebuild, plus the
     expected prior generation, which may be null only for the first authorized
     rebuild; all four fields are null for an incremental generation.

3. A Work Item row contains exactly these logical fields:

   - projection generation, Brand and Store references;

     reference / quantity / localized-name snapshots;
   - Station reference;
   - the row's original `KitchenWorkCreated` source Event reference, independent
     safe source-Event semantic digest and source occurred UTC instant; and
   - the Work Item created UTC instant.

4. WP-1403's creation consumer accepts only a version-1 Open Ticket whose Work

   WP-1401 snapshots. The wider Section 26.4 database status constraint merely

### Safe digests, empty state and concurrency

7. Each strict `KitchenWorkCreated.v1` envelope has an independent
   `sourceEventSemanticDigest`, recomputed through the injected SHA-256 port over
   every exact envelope semantic field except `eventId`. Fixed field order is
   `eventType`, `schemaVersion`, `occurredAt`, `producerModule`, `tenantId`,
   `storeId`, `aggregateType`, `aggregateId`, `aggregateVersion`,
   `correlationId`, `causationId`, System `actor.type`, then the complete payload
   in its strict field order (`kitchenTicketReference`, `orderReference`,
   `orderBatchReference`, `confirmationReference`, `workItemCount`,
   `aggregateVersion`, `createdAt`), followed by `redactionClassification` and
   `replayMetadata.replaySafe`. Every row sourced from that Event repeats the
   original Event reference and this safe semantic digest.
8. Header `sourceEventBindingDigest` is independently recomputed over the
   complete normalized unique per-Ticket/version set of fixed-field pairs
   `originalEventReference` and
   `sourceEventSemanticDigest`, sorted by lowercase canonical original Event
   reference using raw code-unit/ASCII order. A new Event reference with the
   exact same Ticket/version semantic digest produces zero new queue effect and
   retains the first original reference/binding. Any other envelope drift for
   that Ticket/version conflicts and is parked for reconciliation.
9. Header `queueSnapshotDigest` is independently recomputed only over the fixed
   projection name/version, Brand/Store scope, exact Ticket and Work Item counts
   and normalized queue-safe business rows. Those rows use the fixed item-3
   business-field order and raw code-unit/ASCII Work Item-reference order, but
   exclude original Event reference, source-Event occurrence time,
   source-Event semantic/binding digest, checkpoint, `asOfUtc`, `projectedAt`,
   freshness, rebuild and generation metadata. Work Item `createdAt` remains a
   queue-safe business/sort field. Locale collation, insertion order and
   wall-clock-dependent ordering are prohibited.
10. Neither digest layer may reuse or alias WP-1401's source-line,
    execution-snapshot, work-plan or other digest that could bind Customer note,
    preparation narrative or excluded evidence. Exact parsers independently
    reconcile row/source pairs, both header digests, counts, scope,
    checkpoint/as-of and generation metadata; a mismatch fails closed even when
    the mismatched value is intentionally outside `queueSnapshotDigest`.
    `sourceEventSemanticDigest`, `sourceEventBindingDigest`,
    `queueSnapshotDigest`, `rebuildRequestDigest` and the cursor filter/sort
    digest all use UTF-8 bytes of `JSON.stringify` over exact accessor-free
    objects with the field and normalized-array order fixed by this brief;
    bigint versions are canonical decimal strings. Object spread, locale
    collation, insertion-order sets and alternate serializers are forbidden.
    Every stored or public digest has exact lowercase form
    `sha256:<64 lowercase hexadecimal characters>`, enforced by strict parsers
    and database checks where persisted.
11. An initialized-empty Store has one valid `Active` generation, zero row,
    zero Ticket/Work Item counts, the required opaque checkpoint returned by the
    authorized complete Kitchen source feed, the canonical digest of the empty
    source-binding set and the canonical digest of the empty queue. Its
    `asOfUtc` is the authorized rebuild observation/checkpoint instant. Empty
    never means missing, unauthorized, failed or not initialized.
12. The generation table has one header per generation. A partial unique index
    allows at most one `Active` generation per exact Brand + Store + projection
    name/version; shadow headers are `Building` and superseded headers become
    `Retired`. Every consume or rebuild transaction takes a transaction-scoped
    advisory lock keyed only from server-derived Brand, Store and projection
    identity before reading active generation or source, and holds it through
    Inbox completion/switch and commit. Client-provided lock keys are forbidden.
13. Under that lock, the first valid `KitchenWorkCreated.v1` delivery may create
    the first non-empty `Active` generation directly; it must not wait for an
    empty rebuild. Later consume or rebuild writes a complete `Building` header
    and row generation, reconciles it, retires the prior active generation and
    activates the shadow atomically. Lock acquisition/interruption or a
    technical active-generation race is retryable and never poisons Inbox;
    failed switching leaves the previous active generation intact.
14. Every primary key, unique constraint and lookup/order index on both tables
    leads with Brand + Store. Each projection row has a composite scoped FK to
    its generation and to the existing same-Domain Kitchen Work Item; no
    cross-Domain FK or private read is allowed. Both tables force Brand+Store
    RLS, revoke PUBLIC, receive no runtime grant, and require caller-owned
    transaction-local Tenant context. Acceptance uses non-owner `NOBYPASSRLS`
    roles. Rows and completed generation facts are immutable except for the
    exact builder-owned `Building -> Active -> Retired` switch.

### Time, checkpoint and freshness semantics

15. A creation Event is not a Store-feed watermark. On every incremental call,
    the dedicated authorized Kitchen source port returns the strict safe source
    DTO plus required `sourceCheckpointReference`, authoritative `asOfUtc` and
    complete-through-checkpoint evidence. Under the advisory lock, an injected
    trusted comparator accepts only an exact same checkpoint/as-of pair or a
    monotonic successor bound to the current active checkpoint. Unknown gaps,
    regression, same checkpoint with changed as-of, or incomplete coverage fail
    retryably with zero Inbox completion/switch and no `partial: false` or Fresh
    claim. No cross-Ticket sequence is inferred from Event IDs.
16. An authorized complete rebuild feed provides the same required opaque
    Kitchen checkpoint plus authoritative `asOfUtc`; both remain required for
    an empty feed. Their exact scope/completeness postcondition is validated
    outside all digests. The real incremental watermark/comparator and complete-
    feed adapters remain External runtime gates.
17. `projectedAt` comes only from the injected clock after complete generation
    reconciliation and immediately before atomic activation. That transaction
    computes non-negative checkpoint catch-up
    `activationLagMs = projectedAt - asOfUtc` and persists the canonical Section
    50.20 status: `Fresh` iff
    `0 <= lag <= 2s`, otherwise `Stale`; negative lag fails closed. Over ten
    seconds remains `Stale` and requires runtime lag alert/telemetry evidence as
    an External gate. Query parses and returns that persisted checkpoint
    freshness and does not age an unchanged Store from wall-clock time. A
    complete initialized-empty generation activated as `Fresh` remains `Fresh`
    until new builder evidence replaces it.
    `Building` is uncommitted/invisible, failure rolls back to the prior Active
    generation, and v1 never claims `Rebuilding`, `Failed` or partial; without
    an Active generation or on repository failure it returns the closed
    dependency-unavailable error. Future health is `NotAvailable`.

18. Consumer name remains exactly `kitchen.queue-projection:v1` and accepts

    the raw `unknown` envelope, then obtains internal System final authorization
    for action `ProjectKitchenQueue`, purpose
    `MaintainKitchenQueueProjection`, exact Brand + Store and the injected
    observation instant before any source call. This is trusted service
    authority, not a human Permission seed or a bypass of scope validation.
20. The first-delivery parser validates envelope, producer, type/version,
    Brand/Store, aggregate identity/version, occurrence time, correlation,
    causation, System actor, complete minimal payload, classification and replay
    semantics before final authorization or a source/repository call.
21. Because the Event deliberately contains no item, Station or display
    narrative, an injected Kitchen-owned source port returns one strict exact
    safe Ticket / Work Item queue-source snapshot plus the item-15 checkpoint
    assertion. It must bind every shared Event field and exactly
    `payload.workItemCount` unique contiguous Work Items within that Ticket. It
    never loads excluded Work Item columns or reads Ordering, Recipe or another
    Domain's private table.
22. Under the advisory lock, the consumer strictly loads the optional Active
    generation, adds the exact new Ticket group, recomputes row semantic
    digests and both complete header digests and atomically records generic
    Inbox completion, the complete generation and activation in one
    caller-owned transaction. The handler returns no result hash; generic Inbox
    `result_hash` remains `NULL`.
23. A completed same-Event Inbox record short-circuits before this handler and
    produces zero second source call or projection effect. Under WP-0030's
    immutable Event contract, this completed duplicate path does not claim to
    reparse changed content or repeat final authorization. A new Event ID with
    the exact existing Ticket/version semantic digest retains the first source
    Event reference and produces zero new queue row/business effect. If its
    validated checkpoint/as-of pair exactly equals the Active pair, only the
    new Inbox completes. If it is a trusted monotonic successor whose
    complete-through delta contains only that deduplicated fact, the same Inbox
    transaction switches to a metadata-equivalent generation: rows, counts,
    original binding, `sourceEventBindingDigest` and `queueSnapshotDigest`
    remain exact while generation, checkpoint, as-of, projected-at and
    checkpoint freshness advance. Unknown gaps, regression or same-checkpoint
    drift are retryable and do not complete Inbox. Any other same-version
    semantic drift conflicts and is parked. On commit-unknown retry, a completed
    Inbox record is authoritative because Inbox completion and any activation
    were atomic; otherwise the attempt repeats the complete first-delivery
    flow. Generation reference is not a business identity.
24. Missing, extra, duplicate, cross-scope, malformed or mismatched source
    evidence produces zero Inbox completion and zero generation effect.
    Higher/unknown `KitchenWorkCreated` versions and lifecycle Events are parked
    for reconciliation with no projection effect; supporting them requires a
    WP-1404 brief refresh. The machine outcome matrix is closed: Registry
    type/schema rejection uses the matching `EVENT_*_UNSUPPORTED` code without
    entering the handler; permanent strict-envelope, authorization, scope or
    semantic conflict returns `rejected / CONSUMER_REJECTED`, parks the delivery
    and rolls back; unknown/incomplete checkpoint or gap, source/dependency,
    lock/race, clock/digest-port or database failure returns
    `retry_required / CONSUMER_TEMPORARY_FAILURE` without completing Inbox; and
    commit uncertainty is never acknowledged and uses the same-key completed-
    Inbox-or-full-retry rule. Projection processing emits no Audit, Outbox or
    Domain Event.

    contains action `RebuildKitchenQueueProjection`, purpose

    The owning adapter uses trusted service identity to final-authorize before
    the advisory lock and any source read. It is not a human Permission seed,
    public endpoint or UI action.
26. The dedicated source port returns a complete authorized Store feed of only
    the safe fields and `KitchenWorkCreated` bindings allowed by this brief,
    plus required opaque checkpoint and authoritative `asOfUtc`. Rebuild rejects
    scope mismatch, missing/extra Ticket or Work Item, duplicate Event/item,
    count mismatch, unsupported source version, null/malformed checkpoint or
    checkpoint/as-of mismatch. The checkpoint remains required for an empty
    feed.
27. Rebuild writes one complete Building generation, reconciles
    Ticket/item/event counts, both digests, identities and checkpoint, then
    activates it under the common advisory lock. Failure rolls back and leaves
    the prior Active generation readable. Rebuild reference is Store-scoped
    unique and retained with its generation under operational retention; exact
    same reference/digest returns that durable generation even after a later
    switch, while the same key with changed digest conflicts. WP-1403 performs
    no key expiry or generation purge; future expiry/purge needs a brief refresh
    and may never silently re-execute an old key. Concurrent rebuild/consume
    cannot lose a committed Ticket.

## Risks, rollback and authorization boundary

- Risk: the queue becomes mutable Kitchen truth. Mitigation: projection-builder
  ownership, source-table immutability, read-only public contract and mandatory
  source revalidation for every future Command.
- Risk: an Event update loses another concurrent Ticket. Mitigation: one common
  Store/projection lock, expected active generation and atomic complete shadow
  switch.
- Risk: an empty Store is indistinguishable from failure. Mitigation: an active
  zero-row generation with exact empty digests, checkpoint semantics and
  freshness.
- Risk: a digest leaks or transitively binds Customer health narrative.
  Mitigation: two independent aggregate safe-field anchors plus the per-row
  Event semantic digest, and an explicit prohibition on every WP-1401
  note-derived or execution digest.
- Risk: stale queue data authorizes unsafe kitchen work. Mitigation: explicit
  freshness/read-only behavior and future source/Expected Version revalidation.
- Rollback: revert code/docs before integration. An applied migration is never
  edited or removed; use a reviewed forward-fix or independently approved
  restore. Projection rows are rebuildable and never the sole source.
- Authorization boundary: the bounded implementation touches only the exact
  twenty tracked paths. Candidate commit, push, PR, merge, deployment and
  external/non-local actions remain separately gated by task authorization;
  runtime activation is not authorized by this candidate.
