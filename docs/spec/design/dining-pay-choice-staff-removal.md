# DEC-DINING-PAY-CHOICE-STAFF-REMOVAL — 客人选好付哪几道菜后，店员删菜

状态：协调人按商用原则决定（2026-11-11，v15 batch 7 table-pay-by-dish），Owner 可推翻。补充 [DEC-DINING-CHECKOUT-SCOPE](./dining-checkout-scope.md) 第 10–13 条（作为第 15 条）。

## 问题

先付款的桌，手机 A 选了“只付我加的”，还在结账页、没开始付款。店员在桌台页“购物车（还没下单）”里删了 A 的一道菜（客人要求）。原来：删菜成功，A 的选择因购物车变了而结束，B 的菜回到购物车；A 的结账页说“同桌有人改了购物车：加了黄瓜……删了柠檬茶”，唯一的按钮“按新的总额结账”报的是全桌的价。店员那边看不出有人正在选菜。结果是只想付自己菜的客人可能付了别人的菜。

## 决定

1. **店员仍然可以删菜。** 客人当面要求删，或者厨房做不了，都不能等客人的 5 分钟保留（还可以一再延长）过去。只有客人已经开始付款（结账占用）时才拒绝，这条不变。
2. **店员看得到有人在选。** 桌台页购物车面板写明“手机 N 正在选这些菜里要付哪几道，保留到 {时间}。删掉一道菜会结束他的选择，他的手机会请他重新选。”（来源：Ordering 的选菜记录，选在店员看到的这个购物车版本上；手机号不明时说“有位客人”；时间按门店时区。保留时间已过而手机还停在选择上时（付款人自己的手机不会因到期取消选择，见第 13 条），写“手机 N 选了这些菜里要付哪几道，还没付。保留已在 {时间} 到期。……”，不说“正在选，保留到”一个已过的时间。这条提示只是告知：读取失败时不显示，绝不让店员的删菜失败或回滚。）
3. **客人的选择结束后要重新选，不会按旧选择付全桌。** A 的结账页发现自己选的菜已不再保留（购物车变了、读到的付款人不是自己：没人在付，或另一部手机已先选），说“店员已从购物车删除柠檬茶 ×1，你选要付的菜已不再保留。没有扣款。请重新选择要付哪些菜。”（不是店员删的就说“购物车变了，……”），只给“重新选择”，回到购物车重新选；不给“按新的总额结账”。
4. **说清是谁做的。** 别的手机在结账页看到店员删的菜，说“店员已从购物车删除……”，不说成“同桌有人改了购物车”；回到购物车的别人的菜不说成“加了”。依据是购物车自己的店员删菜记录（按菜名对上）。

不需要新的迁移、授权或目录升级：选菜记录、等待区和店员删菜记录都已存在（`2000_520`），店员读的是 API 角色已有的 Store 范围读取。
