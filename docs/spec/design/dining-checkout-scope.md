# DEC-DINING-CHECKOUT-SCOPE — 同桌结账：谁付哪几道菜

状态：**Owner 决定（[DEC-OWNER-DEFAULTS-2026-11-06](./owner-defaults-2026-11-06.md) 同桌结账 M38）**；实现细则按商用原则由协调人作出（2026-11-10，WP-2423 shared-table-checkout），Owner 可推翻。
修订 [DEC-DINE-IN-SPLIT-BILL](./dine-in-split-bill.md)：最后结账的桌，客人可以在手机上按菜付，付过的份数随客人增加（原来只有店员分好的份）；店员分单的规则不变。

## 已实现（最后结账的桌，pay at the end）

1. **客人在手机上选这次付哪些菜：**“付全桌”（有人付过后是“付剩下的”）、“只付我加的”、“选择要付的菜”（每道菜可选份数，也可以替别人付）。门店设置决定一开始选哪一项：默认“付全桌”，店长可改成“各付各加的菜”（`2000_522`，版本化、只追加）。客人随时可以改选。
2. **每道菜只付一次：**每次付款是这桌“客人按菜付”方案里追加的一份，记下这份付哪几道菜（按份数）、谁选的（客人手机或店员）、是不是付完了最后剩下的菜（`2000_524`）。同一道菜的同一份只能在一份“已付或正在付”的份里；两部手机同时选同一道菜，只有一部能开始付，另一部被告知“同桌刚刚有人开始付其中几道菜，请再看一下。”，它的支付在服务商那边被取消。数据库在提交时再查一次。
3. **金额到分（DEC-TAX-WHOLE-RECEIPT）：**每道菜每一份的金额、税前小计和税额，是这道菜的金额按份数用最大余数法分的；一份在某一轮的金额就是它那几份菜的合计，但付完这一轮最后剩下的菜的那一份，付这一轮剩下的全部（包括这一轮分到的整单税额取整）。所以每一轮各份加起来正好是这一轮，各份加起来正好是整桌。小费按这一份的税前小计算。按钮上显示的金额就是扣款金额。
4. **刷卡失败或取消：**这一份在同一个事务里记为“撤回”（只追加，不删除），它的菜回到“还没人付”。
5. **店员在收银处收剩下的：**桌台页列出每位客人付了或正在付哪几道菜、怎么付的；“还没人选 · $x”由店员按现金或刷卡机收，作为方案的下一份记录，经手人是店员。
6. **付清和关台：**有一份付完了最后剩下的菜（之后没有更早的份被撤回），并且所有没撤回的份都已付，这桌才算付清；关台、订单列表、客人本桌页、核销都用同一条规则，数据库的核销检查也一样。客人按菜付开始后，店员不能再改分法，也不能退回点餐。
7. **退款：**按份退，以那一份的实付为上限（现有的按份退款流程）。
8. **接受的限制（2026-11-10 复核）：付过一份之后不再重新记一次整单税额取整。**原因：一旦有一份已付或有手机正在付，账单就不能再变——赠送（`merchant-dining-item-comp.ts`）、删未付的菜（`merchant-dining-unpaid-item-removal.ts`）和退回点餐都会被拒绝；已有的一轮的菜和金额不再变，新加的一轮按同一规则单独算。所以“付完一轮最后剩下的菜的那一份付这一轮剩下的全部”这条规则就让各份每一轮加起来到分。以后如果允许付过一部分后再改账单，必须先按设计 7.5 重新记取整（新版本、只追加），再放开。
9. **客人看到的账单变了：**客人打开付款页时还没人按菜付、点了“付全桌”，这时别人已经开始按菜付，客人被告知“账单刚刚变了，已重新读取”，看到剩下的菜和“付剩下的”，不会看到“暂时无法付款”。店员看到的“还没人选”算不出来时说“暂时算不出还剩多少要付。请刷新账单再试。”，不会说成“每道菜都有人选了”。

## 还没有实现（下一批）

- **先付款的桌（pay first）**：一张购物车一次付一轮。“只付我加的 / 选几道菜”需要把没选的菜暂存（下一轮）、付完后回到购物车，并挡住别人同时结账（迁移号 `2000_520` 保留）。在此之前先付款的桌仍是一人付整个购物车；门店设置注明只用于最后结账的桌。
- **换浏览器或丢了 cookie 的同一部手机重新扫码**仍会成为新手机（`2000_523` 保留）。现在的限制：`dining_identity_admission` 和 `dining_session_join_operation` 对 `participant_id` 唯一，同一参与者不能有第二个入座记录。实现时按下面的设计（协调人决定，2026-11-10）：
  - Identity（`2000_523`，`@bop/identity`）：入座激活时发一个续用令牌（只存 SHA-256），`guest_session_continuity` / `guest_session_continuity_use`，只追加。
  - Dining（同一迁移块，`@rms/dining`）：新表 `dining_participant_readmission`（`readmission_id`、参与者、前一个和后一个 guest session（后一个唯一）、操作号、审计号，只追加，Store RLS）。只在参与者仍是 Active、桌没关、没换桌、二维码版本没变时写入；Dining 的入座检查（`createCustomerDiningSessionBinding`）把“最新一条 readmission 的后一个 session”当作这个参与者现在的手机，前一个 session 从此无效。
  - 入口：没有可用 cookie、带了令牌、令牌对得上同店同桌同二维码版本的有效 session → 发后继 session、写 readmission、回 `AlreadyAtTable`；其余一律走普通入座（含暂停扫码）。读不到 Dining 是 503 重试，不是入座。
  - 验收（受限角色）：丢 cookie 后用令牌回来，“只付我加的”仍能找到之前加的菜；被店员移出的手机、换了二维码、别的门店的令牌都走普通入座；同一令牌并发两次只成功一次。
