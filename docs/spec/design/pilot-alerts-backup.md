# DEC-PILOT-ALERTS-BACKUP — 试点外部告警与定时备份

状态：**Accepted（协调人按商用原则决定，2026-10-15；Owner 可推翻）**。执行工作包：[WP-2423](../work-packages/WP-2423.md)（Q13）。
上位依据：IDR-0039（§87.11.1 运营连续性）、AGENTS.md"运营连续性""超时前提醒""顾客尊重"、
[单店试点运维手册](../../runbooks/single-store-pilot.md)"Store outage procedure"与"Daily backup"（B3）。

## 问题

夜间或营业中宿主、服务、证书或备份出问题时没有人会知道：Webhook/对账/worker 持续失败只写在日志里，
备份需要人手动执行，没有失败或过期提醒，也没有异地加密副本。Owner 需要在几分钟内知道"系统停了或变差了"，
并知道该做什么。

## 决定

1. **独立的运维监控进程**：compose 新增 `ops` 服务（与 `pilot` 同一镜像、独立容器、共享数据库网络命名空间），
   每分钟运行 `tooling/environment/pilot-ops.mjs`。与监督进程分离，监督进程、API 或 HTTPS 入口停止时仍能发现；
   数据库不可用时仍能工作，所以告警状态存放在运行目录 `ops/` 下的私有文件（0700/0600），不放数据库。
2. **告警来源（闭合目录，16 个键）**：经与店员/顾客相同的发布端口（代理 14300/14443）探测 API `/ready`、顾客 HTTPS 页、
   商户 `/app`（以试点证书为唯一信任根）；监督进程每 5 秒写 `supervisor.health.json`（仅服务名与状态），监控据此报
   "需要人处理的服务/工作负载"与"监督进程不再报告"（维护锁存在时不报）；api 角色在 Brand/Store 行级安全下读取：
   死信事件计数（订单/支付更新卡住）、所有者来源中未被退款关闭的支付对账差异（超过 24 小时升为紧急）、日结状态
   （有差异的营业日、收盘 6 小时后仍缺失的营业日）；备份状态（失败、26 小时无成功备份、恢复校验失败、异地副本失败）；
   证书 7 天内到期（2 天内紧急）；运行目录、备份目录、数据库卷与异地目录的剩余空间（低于 15%/5 GB 提醒、5%/1 GB 紧急）；
   外发通道持续失败 30 分钟。任何来源读不到即报"部分检查无法运行"，绝不当作正常。
   **Webhook 说明**：试点没有支付 Webhook 路由（支付结果由轮询服务商取得），"Webhook 失败"在试点对应为死信与
   `paymentWait` 工作负载持续失败；真实 Webhook 接收（P2/Q22）上线后验证失败计数并入同一告警键。
3. **去重、限速与持久化**：探测失败持续 2 分钟才告警；同一问题只发一次，仅在升级（提醒→紧急）或间隔到期
   （紧急 3 小时、当日 24 小时）时再发；连续 2 分钟正常才发"已解决"，期间反复不重发；每个通道每小时最多 6 条
   （失败的尝试也计入，避免短信部分送达后重复轰炸），等待的内容合并进下一条；状态写入 `ops/alert-state.json`，
   重启不重发。
4. **隐私**：消息只由固定目录文本加类型化参数（整数、时长、时间、闭合服务名）构成，来源中的任何自由文本都不会进入
   消息、看板或日志；不含姓名、电话、邮箱、订单内容、令牌、密码。秘密只放在运行目录的 0600 文件中，读取时取用，
   错误只输出固定代码。
5. **通道**：统一接口 `{id, kind, send(message)}`。常开：商户首页"Store system"卡片（Owner 与店长，权限
   `operations.order-exception.manage`，与异常页一致；API 读取先在事务内校验会话、所选门店为本安装门店与权限，再按闭合
   契约投影 `ops/alert-board.json`；监控 5 分钟未写入时显示"监控已停止报告"，从未运行显示"监控未运行"，不显示
   "一切正常"）与 `ops/alerts.log`。外发（默认关闭，须 Owner 提供真实账户）：SMTP 邮件（仅 TLS 或 STARTTLS，校验证书）、
   Webhook（`json`、`slack`、`pushover`、`twilio-sms`）、心跳（死人开关：定期访问外部在线监测服务的 URL；整台宿主
   或网络断开时由外部服务发现并通知 Owner——宿主内告警对此无能为力）。`test-alert` 命令逐通道发送测试消息并报告结果。
6. **定时备份**：监控在门店时区的配置时刻（默认 04:30，营业日结束后）每日执行一次 B3 的 `pilot-backup.sh backup`
   （新增 `--client local`：使用镜像内与服务器同版本的 PostgreSQL 18.4 客户端，Dockerfile 从固定摘要的 postgres 镜像复制
   `pg_dump/pg_restore/psql` 与 libpq，以包装脚本隔离库路径），随后 `drill` 恢复到临时库逐表比对行数并删除临时库，
   再写异地副本；失败 30 分钟后重试，每个门店日最多 3 次；宿主当时关机则在下次启动时补做（在线备份不影响营业）。
   密码文件末尾换行现被忽略（此前会让恢复校验失败）。
7. **异地加密副本**：在本机用 AES-256-GCM（文件名作关联数据）加密后才写出，接口为 `put/list/remove`；试点实现
   目录目标（外接盘或会被同步客户端上传的文件夹），拒绝位于运行目录或备份目录内的目标；`decrypt-backup` 解密并认证，
   篡改或错误密钥时不写任何输出。密钥由 `generate-offsite-key` 生成，Owner 必须另存一份（否则宿主丢失时副本无法读取）。
   S3 兼容对象存储（托管密钥）为 P4 外部关口，配置为 `s3` 时明确拒绝而不是假装可用。

## 更正 1（2026-10-18）：计划内更新窗口

**问题**：每次部署重建 `pilot` 容器时，顾客页、员工端与监督进程会停几分钟，监控照常在 2 分钟后报紧急
"Customer ordering page is not loading"（v15 alerts.log：01:41:48 报警、01:46:45 解除，监控 01:43:30 停、
01:43:36 起），计划内更新被当作故障通知店员与外发通道。真实故障仍须及时报警。

**决定**：

1. 部署流程在重建前用 `pilot-ops.mjs maintenance start <runtime> --reason <说明> [--minutes 1–15] [--by <名字>]`
   写入 `ops/maintenance.json`（0600：`schemaVersion`、`startedBy`、`reason`、`startedAt`、`expiresAt`，窗口不超过
   15 分钟，再次 start 覆盖），页面恢复后用 `maintenance end <runtime>` 删除。说明与名字只留在该文件与 `status`
   输出中，不进入看板、消息或日志（日志只记 `maintenance_started/active/ended/expired/stopped` 与到期时刻）。
2. 监控每轮读取标记；仅当格式正确、已开始、未到期且不超过 15 分钟时生效（格式错、超长、未来开始、读不到均不生效，
   照常报警）。生效期间 `entry.api`、`entry.customer`、`entry.merchant`、`supervisor.silent`、`service.attention`
   **尚未报出的**不报出，但仍从首次出现起计时；付款、结算、备份、证书、磁盘等其余告警从不暂缓；窗口前已报出的
   告警保持显示，不被清除也不发"已解决"。
3. 窗口结束（`end` 或自动到期）后，仍在失败的检查**立即**报出（其 2 分钟已过），不再等 2 分钟；窗口内恢复的不发任何消息。
4. 看板新增 `maintenance: {startedAt, expiresAt} | null`；API 投影为 `plannedUpdate`（仅在未到期且监控在报告时给出，
   兼容不含该字段的旧看板）；商户首页"Store system"卡片显示非紧急提示"System update in progress — ordering may
   pause for a few minutes."、开始时刻与"到期后仍不能点单则显示紧急告警"，不显示"Everything is working."。
5. 顾客端不加提示：重建期间顾客页由正在重启的同一进程提供，页面本身无法打开；已打开的页面遇到的是现有的
   "couldn't load / try again"重试提示，没有能自然显示"正在更新"的位置，不为此新增接口或占位页。
6. 运行手册部署步骤：先 `build`（旧版本继续服务），再 `run --rm --no-deps ops … maintenance start`（用新镜像，
   首次部署也可用），然后 `up -d pilot ops`，API 与顾客页返回 200 后 `exec ops … maintenance end`。
   非计划重启（故障恢复）不开窗口。

**否决**：按时间段静默（部署时刻不固定，且会掩盖真实故障）；延长全部探测的报警延迟（真实故障报警变慢）；
由监督进程的 `maintenance.lock` 推断（那是停止/恢复租约，部署重建时并不存在，且没有到期上限）。

**验证**：`pilot-ops-maintenance.test.mjs`（标记校验；部署几分钟不发送且显示提示；超过窗口立即报警；提前结束立即报警；
无标记/超长/读不到照常 2 分钟报警；付款告警不暂缓、窗口前告警保留；文件 0600 与参数拒绝；CLI start/status/end，Linux 镜像内）、
API 投影与商户卡片单元测试、商户 `operations-alerts` 生产浏览器规格。

## 否决的方案

- 告警状态放数据库：数据库宕机时恰恰最需要告警，且需要迁移与授权，收益只是多店场景（扩张时再建 Operations 投影）。
- 在监督进程内告警：监督进程本身停止时无人报告。
- 宿主 cron/systemd 定时备份（B3 原文）：Owner 的宿主是 macOS，每台机器各配一次且失败无人知；改为随 compose 一起运行。
- 只做通用 JSON Webhook：Pushover/Twilio 需要各自字段，Owner 无法直接使用；四种格式各十余行，无额外依赖。

## 外部关口（不阻塞仓库工作）

SMTP/Pushover/Twilio/Slack 账户、外部在线监测（心跳）账户、可公开访问的运维手册地址、异地目标（P4 S3 桶与托管密钥，
或 Owner 指定的外接盘/同步文件夹）、密钥另存、v15 部署 `ops` 服务（见 WP-2423 记录行）。

## 验证

单元测试：规则、去重/提醒/清除、升级、重启不重发、每通道限速、脱敏（敌意输入不进入消息与看板）、SMTP（脚本化服务器）、
Webhook 格式与秘密文件、心跳间隔、配置拒绝、调度（门店时区、重试、每日次数）、加解密与篡改、异地保留、备份周期各阶段；
