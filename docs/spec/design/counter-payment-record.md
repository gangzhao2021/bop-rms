# DEC-COUNTER-PAYMENT-RECORD — 柜台刷卡机收款记录

状态：**Accepted（Owner 2026-10-13 选择"记录柜台收款"，门店"有自己的刷卡机"，不收现金）**。执行工作包：[WP-2423](../work-packages/WP-2423.md)（Q7）。
本决定为试点解除 WP-2116 "No cash / 只经 Terminal" 非目标中与门店自有刷卡机相关的部分；现金仍不在范围内。

## 决定

1. 员工代客点单（取餐或堂食）与断网后补录的订单，可由员工记录"门店刷卡机已收款"：付款领域所有的只追加记录，方式固定为门店刷卡机，金额固定为服务端报价总额
   （含税与小费选择），记下操作员工、刷卡机交易参考号（小票末段，选填）、可选的实际收款时间与原因"断网后补录"。
2. 该收款视为已确认付款，订单照常进入接单与厨房；同一操作编号重放不重复记账。
3. 日结页把门店刷卡机收款与线上（Stripe）收款分开列出，供店员与刷卡机批次总额核对。
4. 此类付款的退款由员工在刷卡机上办理后在系统中记录"已在刷卡机退款"（同样只追加、记员工与参考号），仍受 Q5 升级审批规则约束；不经 Stripe。
5. 现金不支持；Stripe 读卡器（Terminal）待 Stripe 账户与读卡器就绪后另做。

## 实现决定（2026-10-13，第一步：柜台取餐与断网补录，按商用原则作出）

1. **顾客路径原样复用**：柜台为不会用手机的顾客开一个"到店顾客"会话（经门店取餐二维码进入，与顾客扫码相同的身份所有者流程），之后的购物车、
   菜品与选项（售罄/下架）、报价（含税）、营业门、取餐产能、提交、小费记录与付款计时全部走顾客端同一组所有者端口；会话凭据只在本次店员请求的内存中，
   不返回浏览器、不写日志。购物车渠道为 `Pos`（柜台）；Ordering 只对取餐放行 `Pos`（堂食店员点单是后续一步）。
2. **店员与幂等**：Ordering 新增只追加的柜台点单记录（`counter_order_entry`：店员、柜台购物车、到店顾客会话、小费选择编号、是否断网补录、审计）；
   同一操作编号重放返回同一订单，不会再建第二单。
3. **两步收款**：先"发送订单"——服务端返回要在刷卡机上收取的金额（报价含税 + 小费选择）与放单时间；刷卡机批准后店员"已在刷卡机收款"（可填小票末段，
   ≤40 字符且最多 12 位数字，因此不能存卡号）。付款领域只追加记录 `card_machine_payment`，按服务端准备金额、与线上付款相同的付款准入（订单仍可付、
   产能计时未到、库存预留完好）在同一事务写记录、`PaymentSucceeded` 事件与审计，订单随后经原有消费者进入接单与厨房。柜台点单收款后自动接单；
   断网补录的订单同样自动接单（纸单已在断网时被店里接下），页面提示店员在订单页将其标为已做好/已交付。
4. **断网补录**：订单标记"Recorded after outage"，付款记实际收款时间（72 小时内）与原因 `RecordedAfterOutage`；日结按实际收款时间计入当天。
5. **退款**：店员取消（Q6）刷卡机付款的订单时，退款方式为"在刷卡机退款"，补偿任务不会把它当作服务商退款；店员在刷卡机退款后记录
   `card_machine_refund`（整笔剩余含小费，权限同取消）。按菜品取消对刷卡机付款拒绝（请取消整单）。
6. **日结**：刷卡机收款、小费、补录笔数与刷卡机退款单列，不计入线上合计与服务商对账。

已知限制（后续步骤）：Q5 普通退款（部分退款、升级审批）尚不支持刷卡机付款，订单页对这类订单不显示线上退款入口并说明做法；柜台点单无打印小票
（顾客取刷卡机小票）；线上暂停接单时柜台点单同样被拒；补录订单仍需经接单/厨房/交付流程收尾；未付款的柜台订单只能等付款窗口结束自动释放。
