# Ordinary Product publication scope proposal

WP-2421 milestone128 implements an explicit proposal in the existing CAT-PRODUCT-EDIT publication panel, under accepted Sections68.9/68.10 and88.8. The current Merchant components, labeled controls, responsive layout and recovery pattern supply the authorized design baseline; no unavailable Figma or external rule input is required. This is a scoped software/UI decision, not whole-project design closure.

The initial Draft explicitly proposes the current authenticated Store. An editor can instead choose the entire Brand for Validate. The Brand command uses the existing owning scope shape (Brand, null reference, empty channel/order-type filters); Store uses the captured current Store reference. Both are intent, never authority, module activation or sale eligibility. The owning backend retains current scope admission, twelve independent checks, policy, source barriers, permissions, CAS, Audit/Outbox and actual System activation revalidation.

An existing Draft defaults to its recorded scope unchanged, preserving all tuples and channel/order-type filters. Choosing a different Store/Brand proposal disables SubmitReview until Validate and an explicit current refresh. InReview/Approved/Scheduled versions expose recorded scope summaries and use those original tuples without an editable scope control. No new Region, StoreGroup, Channel, OrderType or arbitrary Store picker is synthesized. Scope summaries expose level/filter counts rather than raw object identities. Rescheduling changes time through the existing workflow and retains recorded scopes. Partial scope supersession/overlap administration remains separate unfinished work.

The control has a visible label, shared result/help association, existing touch-target styling, keyboard access and normal narrow reflow. Expiry, offline, hidden context and denied reads remove current proposal controls while preserving unsent edits for explicit recovery. Current capability/management reads still precede preparation and dispatch. Unknown outcomes remove new intent controls, retain the exact original scope in the existing scoped IndexedDB journal and require explicit retry under current capability and native permission admission. Reload/retry cannot change the original period, scope, root, operation, digest or bytes.

CurrentSku supplies Brand-owned lifecycle facts and explicitly separates Store applicability/publication; Catalog Inventory Draft-SKU references mark applicability Unavailable. Neither these sources nor registered Tenant Brand/Store identity proves target-scope publishable SKU or operational topology. The new entire-Brand choice does not fill that independent owning source gap. Known or unknown scope still needs the actual current backend producer; unavailable facts fail closed.

Acceptance runs the actual production-built ordinary route in Chromium, with controlled synthetic HTTP responses, business identity/permission/capability facts and native-shaped receipts. It proves UI interaction, original bytes, keyboard/narrow/mobile-width/zoom, expiry/offline/current denial and explicit recovery. It is distinct from milestone127 actual isolated native HTTP/IAM/Postgres. It does not prove real approval, complete validation, provider/store qualification, actual scheduled activation, UAT or formal release. Exact checks, failures and final input hashes are recorded in [WP-2421](../work-packages/history-WP-2421-01.md#milestone128-plan--explicit-ordinary-draft-publication-scope-proposal).
