# Full Option Draft content storage

WP-2421 supplies forward Catalog1102 storage for the [full Option content contract](./option-set-editor-content.md). Migration1102_003 preserves both applied1102 migration files and all existing Draft/version/lifecycle semantics. It adds nullable additional `editor_content_json` to the owning current version; a legacy NULL stays missing and never becomes empty full content.

`option_set_draft_content_snapshot` is an append-only original full Draft result, not a Published version. It preserves the core root/Draft plus all additional fields and source/content/configuration fingerprints. Exact version/set/Brand foreign keys and an exact original operation/action/intent/result revision/time composite foreign key prevent borrowing another operation result. Unique Brand/set/root revision forbids alternate original results. Create and ReplaceDraft results are supported; Archive and publication have different lifecycle/results and cannot be disguised as a full Draft snapshot.

The table has forced Tenant and Brand RLS, requires no Store context, has no public grant, and classifies its data as ConfigurationMetadata with indirect identifiers retained as configuration/audit history. Identity/profile/size/digest syntax are SQL constraints; full field semantics and recomputed fingerprints remain the owning runtime parser's responsibility. Update/delete suppression preserves history. Changing the current mutable Draft cannot reconstruct or overwrite its original result. A legacy operation lacking a full snapshot remains unavailable for full recovery.

The forthcoming writer must hold actual current Actor/action/field/purpose/Brand authority, lock the owning root/version, verify expected revision and exact current input, save complete current details and original operation snapshot, CAS the root, and append Audit/required events in the same outer transaction. It must verify the stored result with the public full parser, recheck authority/deadlines after writes and roll back late failures. Original recovery uses the exact stored result, retains current permission and refuses altered intent without acquiring today's references. This migration provides none of those application decisions by itself.

Actual isolated SQL acceptance uses controlled Draft/operation seeds. It covers complete field persistence, exact operation/version binding, immutable history after current edits, duplicate/identity/profile/digest-format refusal, scope isolation, denied writes and observed tentative storage writes followed by rollback. Direct SQL is storage evidence, not an owning application writer, CAS/Audit/Outbox, independent approval, CurrentPublished qualification, HTTP/UI or production release evidence. Complete immutable publication and successor/current-source storage follow separately once their held validation/approval contracts are implemented.

The accepted old OptionSet identity suppression RULE disallows UPDATE RETURNING. The writer must hold the root lock, check the conditional UPDATE affected count and explicitly reread the new root in the same transaction; it must not remove the identity guard merely to use RETURNING. The isolated rollback case observes this reread before rollback. This is a database execution constraint, not permission to rewrite immutable identities.
