# DEC-DINING-TABLE-MERGE — 并桌

状态：**Owner 决定（2026-10-28 取舍 3：并桌排在分单之后；WP-2423 剩余工作 8 ⑨）**，细则由协调人 2026-10-30 给出，
实现方式按商用原则由实现者作出（2026-10-30），Owner 可推翻。延续 [DEC-DINE-IN-PAY-LATER](./dine-in-pay-later.md)、
[DEC-DINE-IN-SPLIT-BILL](./dine-in-split-bill.md) 和换桌（WP-2423 item 8 ⑧）。

## 决定

1. **入口：**单桌详情（桌台页）加“并到…”，把这一桌（来源桌）的客人并进另一张已入座的桌（目标桌）。只列其他已入座的桌；
   不能选的桌写明原因，不能选。
2. **只允许：**两张桌都是“吃完再付”、都还在点餐（没有开始结账）、都没有任何付款（整桌、分份、线上、刷卡机按轮）、
   都没有核销、都没有分单方案。目标桌必须已经点过单，或者来源桌还没点过单（只并人）；来源桌点过单而目标桌还没点单时，
   写明“X 桌还没点单：先在 X 桌点单，或把 X 桌并到这桌”。
3. **一次并桌，一个事务：**
   - 来源桌的这次用餐结束（`Closed`），来源桌转为待清洁（和关台、换桌相同）；它的入桌码和邀请随之作废。
   - 人数：目标桌记一条新人数 = 两桌相加（经手人记录）；茶位按新人数走现有的茶位同步。来源桌的茶位行在同步时一起取下
     （记录的删菜，原因“并桌”），整桌茶位只按合并后的人数收一次。
   - 账单：来源桌的订单记为“并入”目标桌的订单（只追加）。目标桌的账单 = 它自己的订单 + 并入的订单。来源桌订单的轮次、
     菜品、价格、免单、删菜都保持原样，只是从此在目标桌的账单上，按原来的点单人归属，所以“各付各点”分得清两桌各自的轮次。
   - 购物车：来源桌还没送出的购物车不能自动搬（它属于来源桌的那次用餐）；并桌时如有未送出的购物车，提示店员让客人先送出或清空。
4. **记录：**只追加的并桌记录：操作号、谁、什么时候、哪桌并到哪桌、两边会话和两张桌的版本、合并前后的人数，写审计
   `DINING_SESSION_MERGE_TABLE`。同一操作重试返回同一结果；两位店员同时并桌（或一个并、一个换）只有一个成功，
   另一个得到“桌台已变化，请刷新”。
5. **付款与关台：**之后目标桌照常结账：整桌一笔，或按现有分单分开付。付款记录里每一行仍记它那一轮真正所属的订单；
   Payment 自己记下“这张账单包括哪几张订单”（并桌时同一事务写入），它的约束据此检查，不读取 Ordering 的表。
   目标桌关单时，并入的订单一起关单；关台到 `Closed`。
6. **后厨：**未完成的单显示目标桌号，并注明“由 X 桌并入”。后厨记录、上菜进度仍按原订单记，不重做、不重发。
7. **客人手机：**来源桌的手机刷新本桌页看到“你们这桌已并到 X 桌”，扫 X 桌的码可加入（不需要桌主）；加入后看到整桌账单。
8. **不做“拆回”。**并错了：按分单“各付各点”分开结账即可（运行手册写明）。
9. **断网：**在纸单上写明“X 桌并到 Y 桌”和时间，单子随客人走；恢复后在“并到…”补录。

## 数据（只追加）

- Dining：`rms_dining.dining_session_merge_operation`（来源会话、目标会话、两张桌、命令、两边快照、审计、事件）。
- Ordering：`rms_ordering.order_merge`（来源订单 → 目标订单、两边会话、并桌操作号、时间）。
- Payment：`rms_payment.dining_table_bill_order`（账单订单 → 成员订单），结算行、分单片、线上付款和核销的“同一订单”检查改为“同一账单”。

## 证据（付款与关台，完整证据）

受限角色验收先对有缺陷的代码报错：并桌成功；不满足条件被拒；旧码作废；并发只有一个成功；并桌后两边的桌主都能扫码重新加入；
整桌结账（及按分单各付各点）、关单、关台到 `Closed`。浏览器测试按真实顺序：开两桌、各自点单、并桌、来源桌手机刷新看到提示、
扫码加入、结账关台。
