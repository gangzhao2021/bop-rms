# DEC-STORE-PHONE-BEFORE-PICKUP — 有门店电话才能提供自取（M109）

状态：已接受（Owner 2026-11-06 “全部按推荐”，M109 推荐默认）。协调人按商业运营定具体做法（2026-11-11）。

## 为什么

自取客人不在店员面前下单：问过敏、晚到、改时间、门店提前打烊（M46），都要打电话。真实餐馆的外带单、外卖平台都要求门店电话。堂食客人身边有店员，所以只有自取需要电话。

## 一条规则

门店对客资料（“向顾客显示的名称和联系方式”）里有电话，才能提供自取。电话只有一个来源：已发布的对客资料 `businessPhone`。收据、订单页、入口页读的都是它。

## 每个打开自取的地方都挡住，并说明原因

| 哪里                              | 做法                                                                                                                                             |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| 门店功能：打开自取                | 没有电话时拒绝（409 `store_features_phone_required`），页面写明先在门店设置里加电话（已有，`6f19b6dc`）                                          |
| 门店设置（分步）第 8 步的发布检查 | 新检查 `StorePhone`：这份设置开始提供自取（在用的配置没有自取，或还没有配置）而没有电话时不通过，送审挡住；写明在哪里加电话，或在第 3 步去掉自取 |
| 新店一页（开业）的检查            | 同一个 `StorePhone` 检查；这一页本来就要求填电话，万一不通过，写“自取客人要打电话……请填写电话，或取消勾选自取”                                   |
| 对客资料：清空电话                | 门店开着自取时拒绝（409 `store_phone_required_for_pickup`），写明先关掉自取（已有）                                                              |

- **检查列表版本：**发布检查从 `StoreConfigurationPublicationChecksV1`（8 项）升到 V2（末尾加 `StorePhone`）。读取两种都接受：浏览器里保存的旧回答仍能读。发布证据里固定的 `storeConfigurationValidationCheckCodes`（运营读取要求一模一样）不变：`StorePhone` 在送审时和其他检查一起跑，不通过就不送审。
- **已经提供自取的店不被挡：**在用的配置已有自取时 `StorePhone` 通过，所以老店改营业时间（只改时间的修改也走这些检查）、改其他设置都不受影响；缺电话由 Home 提醒。
- **同时保存：**“打开自取”和“清空电话”各自读对方的事实。两个人同一时刻保存时，两条命令先拿同一把门店锁（`pg_advisory_xact_lock`，键 `StorePickupPhone:品牌:门店`），再读对方；打开自取在锁后按当前时间读电话。所以第二个人一定看到第一个人已提交的结果，不会出现“开着自取却没有电话”。只有这两条路径拿锁，其他门店功能修改不受影响。

## 已经在接自取单、却没有电话的老店

- **不自动关掉自取：**正在下单的客人和等着取餐的单都照常；突然关掉比缺电话伤害更大。
- **Home 列一条设置步骤**（只给能改的店主）：“添加门店电话 · 方便自取客人就过敏或订单问题联系你”，状态写“设置步骤”，排在眼前客人的事之后，链接到对客资料。不是报错，也不是红色。
- 读不到门店功能或对客资料时，这一条不出现：故障时不说“缺电话”。

## 客人看到的

- 订单页和收据的“联系门店”：有电话时“对这单有疑问？打电话给门店”和可点的“拨打 (416) 555-0123”；老店没电话时写“取餐时在柜台问”，不说“门店可以帮你”。
- 入口页的门店卡片显示电话；自取入口的帮助写“过敏请先打电话或在柜台说”。
- 电话只在客人看得到的页面上显示，不进日志、链接参数或分析。

## 断网、主机或设备出问题

- 门店功能或对客资料读不到时，保存回答 503“再试一次”，不说没有权限；Home 不显示缺电话。
- 客人手机上订单页读不到时照常重试；收据上也有同一个电话。断网时客人到柜台问，店员按 runbook 的 Store outage procedure 处理。

## 差距（已知）

- 开店工具写的第一份配置已带自取。新店走新店一页时必须填电话；如果改走折叠的“所有设置（分步）”，`StorePhone` 把它当作已提供自取，不挡。这时门店功能的自取默认开着，Home 照样列“添加门店电话”。真实开店流程定下来（DEC-STORE-FIRST-OPENING 的 B2）时，第一份配置应不带自取，再由店主打开。

## 不做

- 不给电话发验证短信：试点阶段店主自己填写、自己负责；格式按国际号码校验，北美号码另查区号和局号。
- 不按点单方式再细分（例如只接现取单也要电话）：自取客人都不在店员面前。

## 验收

- 单元：发布检查（开始提供自取没电话失败、第一份配置也失败、堂食通过、已有自取通过、V1 仍可读）、商户端解析 V1/V2、检查文字、新店一页的说法、Home 设置步骤。
- 数据库（受限 NOBYPASSRLS 角色、渲染后的试点 ACL）：`vitest.store-phone-before-pickup.config.ts` 三个用例：两个并发（第一个在没有锁时失败：资料被发布成没有电话），一个按试点组合跑发布检查（只堂食的门店加自取：没电话不通过，发布电话后通过）；`vitest.store-setup-publication.config.ts` 已提供自取的店 `StorePhone` 通过。
- 浏览器 390/1024/1440：门店功能拒绝打开自取并说明原因，第 8 步检查写明缺电话，Home 列设置步骤。
