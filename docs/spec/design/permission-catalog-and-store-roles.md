# DEC-PERM-CATALOG — 权限目录对齐与门店角色模板

状态：**Accepted**。2026-10-07，Owner 在会话中选择方案 A，并确认角色模板（“选A，模板按你的建议做”）。
执行工作包：[WP-2423](../work-packages/WP-2423.md)。

## 背景

- 门店权限定义（`bop_permission.permission_definition`）与角色目前只由测试脚本写入：只有一个合成角色，没有库存等权限。
- 代码实际检查约 100 个权限名；Section 88 页面表明确写出的权限名只有 77 个（主要是 Catalog 与 Inventory），其余页面只以文字描述
  （如 “work-item read / execute”、“exception permissions”）。两者部分不一致，如规格 `kitchen.work_item.read`，代码 `kitchen.operate`。
- 数据库权限名格式不允许下划线，此前以逐个例外放行（`0300_005` 等）。

## 决定

1. **以规格为准的细粒度权限（方案 A）**：形如 `模块.资源.动作`。规格写明的名字原样采用（含下划线）；规格未写明的，按同一惯例补齐；
   代码中合并的权限（如 `kitchen.operate`、`dining.operate`、`ordering.operate`、`fulfillment.operate`、`inventory.manage`、
   `catalog.manage`、`organization.manage`）按读/建/改/执行/审批拆分。
2. **单一权限目录**：在 Permission 模块内维护一份带版本的权限目录（权限名、所属模块、说明、风险等级），作为数据库权限定义、
   角色模板与代码检查的唯一来源；附旧名 → 新名对照表。数据库格式规则统一允许下划线段，不再逐个放行。
3. **门店角色模板**（店主可在模板基础上增删）：
   - **Owner 店主**：全部门店权限，包括角色与员工管理、财务与退款审批。
   - **Store Manager 店长**：订单与异常、退款（规格限额：当日累计 CAD 100 以内，超出需更高授权）、厨房、取餐、
     配料与库存（盘点、损耗、调拨、进货）、商品与 SKU 上下架。
   - **Front of House 前台/咖啡师**：查看与接受订单、代客下单、取餐交付、记录损耗。
   - **Kitchen 厨房**：厨房看板操作（与具名厨房操作员会话配合，见 IDR-0039）。
   - **Inventory Manager 库存管理员（可选）**：配料主数据、进货、盘点、调整、损耗；小店可由店长兼任。
   - 商品/菜单编辑与审批、分析、审计等角色单店一般由店主兼任，模板暂不单列。
4. 分步迁移：先建立目录与对照表；各模块在接通后台功能时把代码检查改为细粒度权限，同时保留对照，直至旧名全部退役。

## 落地与审批（2026-10-07，Owner 选方案 A）

现有约束：任何角色（含系统角色）的提交人与批准人必须不同（`role_administration_approval_separation`），
首位店主依靠签名初始化计划（执行人 + 独立批准人）。据此：

1. **权限目录发布**：Permission 拥有的同步操作随版本部署执行，按权限名只增不删；目录版本 + 摘要记入
   `permission_catalog_revision`（只追加，执行人 ≠ 批准人，库内约束同样拒绝自批），并写平台审计
   `PERMISSION_CATALOG_INSTALLED`。目录内容变化必须提升目录版本，否则拒绝；已退役的权限不会被同步悄悄恢复。
   批准依据为版本发布审批（代码评审 + 发布批准记录），不另设签名。
2. **门店开通建模板角色**：5 个模板以系统角色在门店开通时由签名开通计划一次建立，执行人为平台运营人员、
   批准人为平台另一人；店主不能修改系统角色的权限，只能停用/启用。
3. **店主日常改角色**：自定义角色按现有流程“提交 → 另一人批准 → 生效”；批准人可以是店内第二位管理员
   （如店长），也可以是平台客服。单人店因此仍能使用自定义角色。
4. 不允许店主自批（方案 C 已否决）。
5. 实现（2026-10-07）：开通计划 `StoreRoleProvisioningPlanV1` 逐项列出每个角色与全部权限（审批人签的就是实际授予的内容），
   必须与已安装目录版本的模板完全一致；审批 `StoreRoleProvisioningApprovalV1` 为 Ed25519 签名，绑定计划摘要、门店、执行人，
   信任文件可撤销、有有效期，写入前与提交前各核验一次。模块仍检查的旧合并权限，只在角色持有其全部替代权限时一并授予，
   不会多授。每店只开通一次（`store_role_provisioning` 只追加，库内拒绝自批）；之后的调整走角色管理流程。
   发布工具 `tooling/environment/store-role-provisioning.mjs`：`keygen`（审批人，私钥只存本人文件）、`prepare`（执行人）、
   `sign`（审批人）、`apply`（执行人；序列化冲突有限次重试）。
6. 模板升级与店主指派（2026-10-07）：目录摘要涵盖角色模板，模板内容变化必须提升目录版本（v2：店长可批准角色变更，
   使单店主门店也有第二位批准人）。已开通门店按新的签名计划（`previousCatalogVersion` = 门店当前版本，只能向前）升级系统角色：
   保留角色标识，补授新增权限、撤销移除的权限，新增一版角色管理记录。计划可附店主指派，仅当门店当前没有在职店主时接受
   （开业，或店主离开后由平台客服指派），被指派人须为该店在职成员。同一目录版本内更换店主属于后续的员工角色指派流程。

## 角色管理接通（2026-10-07）

- 页面 `IAM-ROLE-LIST` / `IAM-ROLE-EDITOR` 接真实数据；读取需 `identity.role.read`（菜单原用的 `identity.manage` 不在目录中，已更正），
  每个命令由领域服务按确切权限再次授权。
- 自定义角色：从任一角色“复制”生成草稿（角色暂停、无授权）→ 编辑 → 提交 → **另一人**批准（提交人永远不能批准）→ 生效时
  按批准内容落地授权并推进品牌策略版本；停用时角色暂停。模块仍检查的旧合并权限按与模板相同的规则自动附带，不能直接勾选。
- 系统模板角色：不可编辑，只能复制、停用、重新启用。
- 生效不再要求策略版本等于起草时版本（否则任何其他角色变化都会使已批准变更永远无法生效）：批准后内容不可改，生效时按当前策略
  重新校验依赖并记录当前版本。
- 角色仍有在职员工时拒绝停用，须先改派。
- 代码中的权限名格式规则与数据库统一（同一正则），取消逐个放行。

## 员工与角色分配（2026-10-07）

- 员工页面 `IAM-USER-LIST` `/app/organization/users`、`IAM-USER-DETAIL` `/app/organization/users/:id`；读取需 `organization.staff.read`。
- 员工姓名：Membership 拥有的员工资料（版本化、只追加、个人数据分级），由有 `organization.staff.manage` 的管理员维护；
  审计只记录“谁改了谁的资料”，不记录姓名。
- 分配角色是提权：管理员（`organization.staff.manage`）发起 → 另一位持有 `identity.role.approve` 的管理员批准后生效；
  发起人与被授权人都不能批准（代码与数据库触发器双重拒绝），发起人可撤回。撤销角色是降权，立即生效并留记录。
  不能给自己分配或撤销角色；门店至少保留一位在职店主。每次生效都推进品牌策略版本。
- 店内无人可批时（如只有一位店主）：平台客服对该条待批申请做签名批准（`ROLE_ASSIGNMENT_APPROVAL` 用途的密钥，
  绑定申请编号、门店、被授权人、角色与发起人，可撤销、有有效期），发布工具 `prepare-assignment` → `sign-assignment` →
  `apply-assignment`；审计记录批准凭证编号。
- 并发：权限读取会对权限表持共享锁直到请求结束，管理写入需要更强的锁。事务封装把锁超时、序列化冲突、死锁统一报告为
  可重试冲突（不暴露 SQL 细节），角色与员工命令整笔重试（最多 4 次、短退避），不加长锁等待以免阻塞点单与厨房请求。

## 不改变

不改变 Section 88 已写明的权限名与页面契约；平台级权限（平台管理员）保持现有机制；具名厨房操作员会话的最小权限档案继续生效。
