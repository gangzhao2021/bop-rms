## 问题（v15 只读 SQL 确认）

两道 $12.50 的菜分两轮下单，13% HST：每轮报价各收税 $1.63，整张账单按
[DEC-TAX-WHOLE-RECEIPT](tax-whole-receipt.md) 只取整一次，税 = 25.00 × 13% = $3.25，账单 $28.25（税额取整 −$0.01）。
两道都免单时，按钮写“免单 $28.26”，`order_item_price_reduction` 记了两行 1250 + 163 = 1413，共 2826（税 326），
账单从 $28.25 变成 $0.00。客人欠款和收据没错，但免单记录比它清掉的账单多一分：报表的“免单/折让（含税）”、
日结的“经理减免”、税额减免合计都会多一分，要靠“税额取整”那一行补回来。

原因：每条减免记录按这道菜自己报价的税（按比例、半分进位）记；而账单的税是整张账单一起算的。减掉菜以后整张
账单的税变动可能比这些菜自己的税多或少一分，这一分以前落在账单的“税额取整”里（−$0.01 变成 $0.00），不在减免记录里。

## 决定：减免记录 = 账单真正减少的钱

1. 一次减免（一次“免单/折让”，或一次积分抵扣）记下的金额合计，恰好等于账单因此减少的钱。
   **每次减免之后，账单的税额取整与减免之前相同**；整张账单的税因减免而多变或少变的那一分，记在这次减免的菜的税上。
   所以任何时候：**各次减免合计 + 账单还欠的 = 减免前的账单，到分**。报表、日结、Ordering 的计价总额、客人收据读的都是这些记录，自然一致。
2. 每道菜先按原规则取它自己的税（整道免单取全部税；按比例取，半分进位），数据库照旧逐分核对。整单那一分（正或负）
   从这次减免里按菜的编号**最后一道开始往前**一分一分放（通常只有一分，落在最后一道）；只放在按税率计税的菜上，
   不会让一道菜的减免税变成负数，每道菜最多 ±$0.09。并桌的账单先放在持有账单的单（取整所在的单）的菜上。
3. 那一分单独记在新列 `tax_rounding_minor`（`tax_minor` 已含它），审计时能看出哪一分来自整单取整；数据库校验
   `tax_minor − tax_rounding_minor` 就是这道菜自己的税份额，`tax_rounding_minor` 只能在有税率的菜上、在 −9…9 之间。
   金额由系统算出，浏览器从不发送金额。
   为什么是 ±9（b16 复核）：数据库的行触发器算不了整张账单，只能核对菜自己的份额和这一分的上限。减掉菜时整单取整
   每种税最多变动约一分（加拿大最多两种税），复合税再多一分，一次减免又是一分一分分给它的每道菜，所以一道菜实际最多一两分。
   上限 9 留有余地，同时保证即使程序有错，一道菜的减免税最多多记 $0.09，而不是 $0.99。系统里同一上限为
   `billTaxRoundingShareLimitMinor`，读记录时超出即视为不可用。
4. 只追加：已有记录不改（新列默认 0）。

例（v15 那张桌）：一起免两道 → 第 1 道 1250 + 163 = $14.13，第 2 道 1250 + 162 = $14.12（整单一分 −1），合计 **$28.25**，
账单 $0.00，税额取整仍为 −$0.01。先免一道 → $14.12（账单 $28.25 → $14.13），再免另一道 → $14.13（→ $0.00）；
或再打五折 → 625 + 82 = $7.07（→ $7.06 = 6.25 + 整单税 0.81）。

整单的税原先就比各轮多收了一分时（如三轮各 $3.80：各轮税 0.49，整单 1.48），全部免单要减掉 $12.88，比各菜自己的价格
多一分；这一分同样记在最后一道菜的税上（这道菜的减免税比它自己的税多一分，所在轮的税额取整再补回 +$0.01，这一轮仍是 $0.00）。

b16 复核修正（两轮各 $3.80，账单 $8.59，全部免单记 429 + 430 = 859）：这张单自己的菜只有 858，Ordering 的计价总额以前要求
“减掉的不超过单上的菜”，于是全部免单的这桌读不出计价总额，关台、核销、日结都会变成“暂时不可用”。现在规定：减免合计可以比
单上的菜多，但只能多出这些减免记下的正的整单分（`tax_rounding_minor` > 0 之和），这一分由这张单记下的税额取整还回，
计价总额 = 858 − 859 + 1 = $0.00；不带已记取整读（尚未付款的账单读法）时最低可到 −这几分，带上取整永不为负。

并桌（b16 复核）：B 单并入持有账单的 A 单，各一轮 $12.50，账单取整 −$0.01 在 A。只免 B 的菜时，这一分只能放在 B 的菜上
（B 记 1250 + 162 = $14.12），以前 B 这一轮按规则 v2“并入的轮照点的收”会剩 $0.01 税要付，B 单计价 $0.01，按轮分账会出现 $0.01 的一份。
现在并入的轮“照点的收”是指：它被收的税加上它的减免记下的那一分（还回去），所以 B 这一轮记一行 −$0.01 取整，
这一轮 $0.00、B 单计价 $0.00，A 仍是 $14.13，账单取整总额仍为 −$0.01。没有这一分的账单算法和摘要都不变。

## 员工看到什么

- “免单/折让”面板的按钮写**真正会减掉的钱**：选好菜和方式后，服务端按记录时完全相同的算法（含整单那一分）算出金额
  （`POST /merchant/orders/comp-items/preview`，同样的权限和检查，不记录、不要员工 PIN）。算出之前按钮写“正在算减多少…”且不能按；
  算不出（断网、服务忙）时写“没能算出减多少。请检查网络，然后重试。”，按钮改为“重新算减多少”，绝不显示估算的数。
- 按下时把按钮上的金额一起发给服务端（`expectedTotalMinor`）；这期间桌上账单变了、金额不同，就拒绝为“这桌已变化，请刷新后再试”，
  员工看到新金额再确认。旧页面不带这个字段时照旧记录。
- 免单列表每行就是记录的金额（例中 −$14.13、−$14.12），加起来等于账单减少的钱，不再需要“减免后整单重算的税差”一行来解释多出的一分。
- 免单时用到了整单那一分、而这张账单还没记过税额取整时，同一事务里把取整记下来（系统规则，只追加），所以全部免单、
  不付款就关台的桌，报表也读得到那一分在哪一轮。报表把“全部免单的轮次”判断为“这一轮的菜减免后 + 这一轮分到的取整 = 0”。

## v15 上已有的 TEST 记录

v15 有 68 条减免记录（43 张单，全部为 TEST 数据）。它们不改、不补记：这些桌的欠款、付款、收据都是对的（多出的一分
当时由账单的税额取整抵消），没有为免单设计的“补偿记录”可用，也不需要动钱。上线后这些行 `tax_rounding_minor` = 0；
只有整单取整在免单时变动过的那几张旧桌，按记录相加的“免单（含税）”会比账单减少的钱多或少一分，报表的税额取整行仍使总数正确。
新的免单、折让和积分抵扣从上线起都对到分。

## 断网与故障

没有新做法。断网时不能免单（本来就要连服务端记录）；预览算不出时按钮不能按，页面说明原因并可重试，员工也可以按断网指引
先收账单上最后看到的金额，恢复后再处理。服务端故障时按钮从不显示估算金额，也不会把故障说成没有权限。
