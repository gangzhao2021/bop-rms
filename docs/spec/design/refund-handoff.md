# DEC-REFUND-HANDOFF — 退款停做后的交付、收银员的退款说法与厨房单上的退款人

状态：已决定（协调人 2026-11-11，按 Owner 规则 [DEC-OWNER-DEFAULTS-2026-11-06](owner-defaults-2026-11-06.md) 第 2、4 项，M10/M14）。适用：试点与 InternalTest。来源：v15 第五批实测（Test Merchant 2 第 24 单、DEMO Store 第 7、8 单）。

## 问题

1. 自取单一道菜点 3 份、退 1 份并勾“也停做”，做好后取餐卡和对话框都写“交付 2 份 · 1 份已退款，不在袋里”，但交付命令仍发 3 份，服务器拒绝（422），这单卡在“已做好”，客人拿不到餐。
2. 客人已付、还没人接的自取单，收银员只看到“接单”，没有“做不了”：读模型给了这个按钮，BFF 只在自动接单时才转给页面。
3. 收银员退一道菜，复核页写“确认后即退回原付款方式”、按钮“退款 $X”，按下其实只记录申请；“审批”页对收银员写“等你发送”；首页同样写“等你发送”。收银员整单退还没接的单，页面让他用“拒单并退款”，这是店长和店主才有的按钮。
4. 店主退款停做一道菜，厨房单只写“1 份已退款 · 不要做 · 做 2 份”，没写谁退的：店主在员工名录里没有名字，读不到名字就什么都不写。

## 决定

1. **交付按还欠客人的数量**：已做好，减去已交付，减去已退款不交付。取餐卡、对话框和交付命令用同一个数（`pickupLineToHandOver`）；全部退款的那道菜不交付。服务器本来就只收这个数（受限角色验收 `staff-item-cancellation` 中“交 2 份被拒、交 1 份成功”）。
2. **“做不了”给所有能接单的人**：BFF 在没有自动接单信息时，也把 `canCantMake` 原样转给页面（只在为真时发送）。店长另有“拒单并退款”，页面仍只给他一个（`acceptanceCloseControl`）。
3. **收银员从不被说成“由你发送”**：
   - 不能发送退款的人，复核页不写“确认后即退回”，按钮是“记录退款申请”，说明“记录这笔申请还不会退款：由店长或店主在‘审批’里发出”；刷卡机付的款也一样，不让他自己去刷卡机上退（复核页与记录后的提示一致）；
   - “审批”页对他写“{name} 提交，等店长或店主发送”；首页和审批角标只算读者自己能做的：待批准只算他能批准的那笔（`canApprove`），已批准未发送和未发送的申请只在他能发送时才算，所以收银员的首页和角标不出现“待批准”“已批准未发送”；
   - 整单退还没接的单被拒时，告诉收银员“没有记录任何内容……请在这单上用‘做不了’……看不到就找店长”；店长和店主仍看到“拒单并退款”。
4. **厨房单写退款人；没有名字就写角色**：先写名录里的名字；读不到名字的人，写他提交这笔退款时记录的退款角色（店主、店长、店员，来自 `ordinary_refund_requester_role`，api 角色已有 SELECT 授权）；两样都读不到才不写。不编名字，不显示编号。真实门店里店主常常没给自己填名字，厨房仍需知道是谁拍板不做的。

## 不做

- 不新增迁移、授权、目录或角色升级。
- 停做的数量、退款金额和交付记录都照原样追加，不改历史；没有任何隐藏或删除销售的路径。
