# Product publication client transport

WP-2421 milestone90 uses the accepted native Merchant publication command wire.
It admits User Validate, SubmitReview, Approve, Reject, Publish, SchedulePublish,
ReschedulePublish and CancelScheduledPublish. Actor/Tenant/current field and action
permissions, complete validation/approval/topology/policy and actual activation
remain owning server facts. System ActivateScheduled and Supersede are excluded.

The closed browser parser preserves the original IDs, expected versions, hashes,
canonical scope set, UTC instants/IANA local boundaries/offsets, reason, schedule
and successor identity. It mirrors structural/time rules without importing Domain
runtime or asserting source admission. The8192-byte request ceiling remains the
native ordinary BFF limit; responses are bounded65536 and finite15000ms. Explicit
re-execution uses the same frozen command, exact bytes and original occurredAt.
There is no automatic retry, operation creation, renewed authority or hidden merge.

Applied/Replayed confirms that original action, root/publication version increment,
state, effective start and successor identity. Native receipt contains no Brand,
Store, complete validation outcome or permission receipt; the existing scoped
server session/command binding supplies authority. Receipt is never today's usable
publication or sale qualification. The command contract lacks an expected schedule
counter; this transport requires a positive counter for scheduled operations and
leaves exact current-counter binding to the following management source/controller.
Independent approval remains a current authorized server decision.

Protocol tests use synthetic Response objects with real frontend transport and
parser. Normal runtime import, current management sources/controller, ordinary
publishing page and actual native HTTP replay are following milestones. No browser,
SQL, IAM, scheduling activation, UAT, legal or external release proof is implied.

## Physical native transport proof (milestone91)

The isolated acceptance bridge uses the same frontend preparation once, forwards
original CSRF/scope/body to physical BFF/native Catalog SQL and observes actual
headers/receipts. Losing an Applied response after commit must produce client
OutcomeUnknown; explicit identical replay must bind native Replayed. Current
permission revocation denies recovery; restoring permission permits original
replay. Validate, SubmitReview, SchedulePublish, ReschedulePublish and
CancelScheduledPublish use this bridge in the existing first native SQL case.

This case retains synthetic validation/topology/field declarations and an
approval-not-required policy fixture. Independent approval and owning System
activation retain their separate protected acceptance evidence; neither is
inferred from this bridge. Ordinary publishing UI/current complete sources remain
open. No persistent schema, permission source, policy or publication gate changes.
