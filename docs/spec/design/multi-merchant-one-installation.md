# DEC-MULTI-MERCHANT-ONE-INSTALLATION — 一套部署服务多个商家

状态：**Owner 2026-11-04 同意按建议做（原话“按你建议做”）**，实现细则由会话按商用原则作出，Owner 可推翻。
是 [DEC-BRAND-MULTI-STORE-ONE-INSTALLATION](./brand-multi-store.md) 的下一步：那里是一套部署服务一个品牌的几家店，这里是服务多个商家。

顺序：① 本文（一套部署服务多个商家）→ ② 平台商家总览 → ③ 老板自助开通。

## 现状（2026-11-04 查明）

- 数据库已按商家、品牌、门店隔离（RLS），一个数据库放多个商家不需要改表结构。
- 运行时是**每家店一套完整组合**：HTTPS 入口和客人 API 共用进程、按门店各组装一份，后台是每家店 5 个独立进程。前面的路由层决定请求属于哪家店。
- 只允许一个商家的地方：`servedStoresOf`（所有门店取同一 Tenant、Brand）、`pilot-https-entry.mjs` 的 `PILOT_HTTPS_SCOPE_CHANGED`、Cognito 的 `isActiveStoreMember`（固定用安装的品牌）、会员密钥（放在安装根目录，因为“这些店是一个品牌”）。
- **容量（v15 3 家店实测）：**容器 3.0 GiB，每家店约 1 GB；每店连接最少 16 条，按角色上限 80 只能放 4 家店（`pilot-connection-budget.mjs`）。

## 决定

1. **同一数据库、同一套进程，商家之间靠数据库隔离。** 不选“每商家一套部署”：第一批客户是 1–3 家店的小餐厅，每家一台主机的运维和成本撑不起这门生意。
   - 锁也按商家分开：一个商家的写只挡它自己的读，不用整张共用表的锁（[DEC-MERCHANT-LOCK-SCOPE](./merchant-lock-scope.md)）。
2. **绝不把一个商家的请求落到另一个商家。** 现在“找不到门店就回第一家店”的做法在单品牌内无害，多商家时不允许：
   - 客人端：没有会话、桌码或门店编号对不上时，回中性的拒绝，不经过任何商家的组合；
   - 员工端：未登录的请求只能到达不含商家数据的登录流程；
   - 单店安装的行为不变。
3. **每家店的门店范围来自它自己的运行目录**（Tenant、Brand、Store 三项都由服务端记录决定），从不来自请求。员工只看到自己有成员身份和门店分配的门店，切换门店仍按现有规则审计。
4. **一个人可以属于几个商家。** 用现有 `membership_brand_discovery_read` 找到这个人的品牌，登录后默认进入第一家有效门店；不同商家之间切换走同一个有审计的切换操作。
5. **商家之间不共用会识别人或能冒充门店的密钥：** 桌码签名按门店目录分开（新商家由工具新生成，不复制）；会员手机号的密钥由安装密钥按品牌派生，安装自己的品牌沿用原密钥，现有会员不受影响。平板设备哈希和客人会话哈希保护的是随机值，不能跨商家识别人，可以共用。数据库账号、平台基础密钥可以共用。同一个手机号在两个商家是两个互不相通的会员。
6. **后台改为共用进程。** 每种后台任务一个进程，按门店依次处理；一家店出错不影响其他店。这样内存和连接数不再随门店数线性增长。没有这一步，“多商家”只是能放 4 家店。 代价：这个共用进程崩溃时，第一家店之外所有门店的后台任务会暂停到监督进程把它重启（几秒内）；后台单线程，门店很多时可能要拆成几个进程，等实测再定。
7. **运营连续性：** 一套部署是所有商家共同的故障点。部署、数据库或主机故障时，各店按现有纸单流程营业并各自补录；运行手册要写明通知所有商家的做法。
   告警（2026-11-05）：每家店有自己的告警板，商家只看自己的店，BOP 看根看板，见 [更正 2](./pilot-alerts-backup.md)。真实商家在 `stores/<name>` 下运行前，心跳或 Webhook 必须打开，支持电话必须配好。
8. **备份恢复：** 整库备份照旧。恢复整库会影响所有商家，所以单个商家的数据导出和删除列入第 ② 步，正式接第二个真实商家前必须有。

每段的门槛都包括：v15 现有 3 家店行为不变；受影响的数据库配置和工具测试通过。跨商家隔离按权限与数据分级类，走完整证据。

| A2  | 去掉跨商家的“回第一家店”，改中性拒绝                            | 路由测试：未知桌码、未知门店、未知会话都不进入任何商家的组合       |

已知缺口（2026-11-04 查明）：

- **Stripe 回调：** 一个回调地址，请求不带客人会话。多商家时路由层认领不了这种请求，回 404，Stripe 会重试，付款不会丢，但入不了账。接第二个真实商家收款前必须完成 A7。内部测试用模拟服务商，不受影响。
- **Stripe 公钥：** 客人端在进店前读一次付款配置，来自第一家店。接 Stripe 时要么全平台一个公钥（Connect），要么进店后重读，放在 A7。
- **客人会话查找：** 没有缓存的会话要逐家门店查询，门店多时要改成一次查到。放在 A5 一起做。

## 暂停商家（Owner 2026-11-05“就按这个做”）

**规则：** 平台暂停一个商家后，不再有新客人能进店，员工照常工作，已有的单照常做完、结账、退款。恢复后马上可以接新客。

- **拦什么：** 该商家所有门店的新访问：桌码和自取码扫码进店、柜台新单、新开一桌。
- **不拦什么：**
  - 已经在店里、手机里有访问的客人，照常加菜和付款；
  - 员工登录和所有员工操作：接单、后厨、上菜、结账、退款、日结；
  - 后台进程照常运行。
- **不隐藏任何东西：** 订单、付款、小票都照常记录。暂停不改、也不删任何销售记录（AGENTS.md 禁止隐藏销售）。
- **谁能做：** 平台支持人员，且持有单独的 `platform.merchant.pause` 权限（不是查看或代改设置的权限）；必须写原因。
- **记录：** 每次暂停和恢复都写一条只增不改的记录（谁、何时、为什么），以 `bop_tenant.brand_guest_intake` 最高版本为当前状态；按商家行级隔离。每家门店的支持访问日志都记一条“Changed”，老板能看到。
- **客人看到的：** 一句话，说餐厅暂时不接新订单，请联系店员；不出现内部代码，不说原因。
- **员工看到的：** 首页一条横幅：平台已暂停接新客，什么时候起，已有的单照常完成。柜台新单和新开桌被拒时说明原因。
- **为什么不用品牌状态 `Suspended`：** 品牌 `lifecycle` 改成 `Suspended` 会挡住员工找门店和登录，违反“员工做完单和退款”。所以这件事单独记录，不碰品牌状态。
- **为什么不走旧的租户审批流程：** `platform-tenant-administration` 是早期的租户开通审批模型，试点商家都没有走过它。它没有“恢复完成”这一步，也没有接到客人入口。真实上线前如果要两人批准，在这条记录上加一个审批步骤即可，不用换模型。
- **断网或云端故障：** 暂停只是一条数据库记录，入口每次进店时实时读取。读不到时入口照常报“暂时不可用”，不会把暂停当作开着。
