# DEC-MIGRATION-RELEASE-ORDER — 迁移按发布批次排序

状态：**Accepted**（2026-10-07，按 Owner 的商用原则由执行 agent 决定并记录；不改变 Section 94 的完整性与顺序保护）。
执行工作包：[WP-2423](../work-packages/WP-2423.md)。

## 问题

Section 94 规定迁移按 `(命名空间, 序号)` 全局排序，任何低于已应用最高位的新迁移在执行前一律拒绝
（`MIGRATION_OUT_OF_ORDER`）。命名空间原本按模块划分（0000 平台 … 1900 库存）。数据库一旦上线运行，
除最高命名空间外，任何模块新增的迁移都会排在已应用最高位之下，升级被拒绝。试点库 v14（93 项）与 v15
（`0300_011`、`0300_012` 低于 `1900_014`）均因此无法升级。

## 决定

1. **模块命名空间封闭**：0000–1900 各模块命名空间封闭在当前最后序号（迁移目录校验以
   `MIGRATION_NAMESPACE_CLOSED` 拒绝新增），既有文件不变、不改校验和。
2. **发布批次命名空间**：此后所有新迁移，无论属于哪个模块，都放入当前发布批次命名空间
   `2000-release-001`、`2001-release-002` …（四位命名空间单调递增，目录登记在 `migrations/namespaces.json`）。
   全局执行顺序因此等于发布顺序，所有环境执行顺序完全相同，可重现、可审计。
3. **归属不变**：迁移的归属仍由文件头 `owner` 与 `schema` 决定并按模块清单校验；命名空间不决定归属
   （与 Section 94 原文一致）。每个迁移仍只改一个归属 schema。
4. **开新批次**：某批次部署到正式环境后，下一次变更开新批次命名空间；尚未部署到正式环境前，变更追加到当前批次。
   已应用最高位保护照常生效：误把迁移加到已部署的旧批次，执行前即被拒绝。
5. 本次把尚未在任何库执行过的 `0300_011`、`0300_012` 移为 `2000_001_alter_permission_catalog_identifiers`、
   `2000_002_create_permission_catalog_revision`。

## 未选方案

按模块各自排序并显式声明跨模块依赖：不同环境可能得到不同的执行顺序，跨模块外键、授权、触发器依赖容易在
部分环境出错，执行器与校验需大改；正式运营的数据库管理通常要求单一全局顺序，故不采用。
