# DEC-PAPER-SEND-IDEMPOTENT — 纸质订单发送从头到尾只记一次

状态：**Accepted（按商用原则作出，2026-11-11；v15 batch-9 bundle paper-send-idempotency）**。执行工作包：
[WP-2423](../work-packages/WP-2423.md)。在 [DEC-PAPER-ORDER-PAID-AT-SEND](paper-order-paid-at-send.md) 与
[DEC-PAPER-ORDER-NEVER-RELEASED](paper-order-never-released.md) 之上补齐“没收到答复后再发送”的路径；不改变两者已有的决定。

## 问题（v15 实测 L5）

纸质订单发送时同一请求里下单并录入付款。订单和付款都已记上、页面却没收到答复（断网一下）时，员工按提示用同一操作编号再发送：

- 2 分钟内服务端答“还在发送”，之后答“这单没有发出去，也没有收款，请再发送”——这句话是假的；
- 页面随即丢掉操作编号，下一次点击下了一张新的纸质订单并再次录入付款：同一张 $3.67 的纸质单在当天营业额里出现两次（订单 77、80）。

原因：再次发送时服务端从“等待付款的付款准备”重建原订单；订单一旦付款，这份准备就不存在，于是已付款的纸质单被当成“没完成”。
另外两条相同后果的路径：没收到答复后员工改了付款时间（页面把它当成新订单），或改了菜品再发送。

## 决定

1. **同一次发送永远只对应一张订单**：再次发送（同一操作编号、同样的菜品/小费/纸质标记）时：
   - 订单还在等付款：照旧返回这张订单与应收金额；
   - 订单已付款（纸质单随发送入账，或之后在柜台/订单页录入）：返回同一张订单、它的订单号，以及付款记录里保存的金额（菜品、小费、合计、付款时限），任何时候都可以；
     同一请求里的付款用同一付款操作编号再录一次时答“已录入”（不再新增记录），改过签购单号或付款时间的新付款答 `already_paid`，页面显示“这张纸质订单的付款已经录入并计入当天营业额”；
   - 订单存在但既不在等付款也没有刷卡机/现金付款记录（时限已过的纸质单、已取消的柜台单）：2 分钟内答“还在发送”，之后答“已下单，订单 N。这次没有新的扣款。请在“订单”中查看。”，从不再下一张；
     柜台现金（现场或纸质，带 `tenderedMinor`）也记在同一个刷卡机付款记录里，所以“没有付款记录”不会漏掉现金付款的订单；
   - 只有确实没有生成订单时才答“没有发出去，也没有收款”。
2. **同一操作编号带着改过的菜品或小费再发送**（员工没收到答复后改了单）：第一次发送已生成订单时答“已下单，订单 N”，不下新单、不收款；
   可能还在进行时答“还在发送”；确实什么都没生成时答“没有发出去”，员工再发送即为新订单。
3. **订单可能已存在后的系统故障答“还在发送”**：从提交订单那一步起，意外失败不再答“系统没能下单，什么都没收，请再发送”（页面会换新的操作编号），
   而答“还在发送”，页面保留同一操作编号，再发送时找回这张订单。与店员加轮已有的做法一致。
4. **柜台页在答复未知时保留操作编号**：没收到答复或“还在发送”后，改菜品、小费或纸质标记都沿用同一操作编号（交由第 2 条判断）；
   付款时间属于付款而不是订单，改它从不换订单操作编号（只换付款操作编号）。收到确定答复、发送成功、返回修改或重新开始后恢复为“改单即新订单”。
5. **店员为桌台补录的纸质轮次**同样适用第 1 条中“已付款”的情形：再次发送返回同一轮次与付款记录里的金额。
   轮次存在但既不在等付款也没有付款记录（付款时限已过、已被撤下）时，2 分钟内答“还在发送”，之后答 `staff_round_already_sent`，
   带订单号和桌台：“{桌台}的这一轮之前已经发送，在订单 N 里。付款时限已过，这一轮已撤下，没有收款。这次没有发送新的菜品。请在“订单”中查看。”，与柜台点名订单一致。
6. **订单页列表行与详情顶部**：纸质单付款还没录入时写“纸单已付款 · 付款还没录入”“停电/断网时已付款 · 请在 {时间} 前录入”“付款未录入”，
   操作按钮为“录入纸单付款”；不再写“等待柜台收款 · 请在 … 前收款 · 未付款将释放”或“收款”。

7. **再次发送时读出“已付款”**（复审补充）：再次发送（`AlreadyPlaced`）时总会读一次这张订单/轮次的付款记录，有记录就在答复里带 `paid: true`。
   柜台单在接单前付款窗口仍显示为打开，桌台轮次的付款时钟付款后也不会关闭，所以不能只在“窗口已关”时才读付款记录。
   页面收到 `paid: true` 就进入“已付款”，写“订单 N 已经付款，付款已录入。不要再向客人收款；可在订单页查看。”（纸质单写“已经录入并计入当天营业额”），
   不再进入收款步骤（以前会让员工对一张已从订单页收过款的现场单再刷一次卡，且显示已过去的付款时限）。第一次发送不多读。
8. **页面重新载入后仍是同一次发送**（复审补充，商用原则：平板卡住后重新载入很常见）：柜台发送没有收到答复或“还在发送”时，
   页面把这次发送按门店保存在本浏览器（`localStorage`，键 `bop.counter.unansweredSend.v1.{门店}`，读写都在 try/catch 里）：
   订单操作编号、发送时间、是否纸质单、纸质付款的操作编号和付款内容的摘要（FNV-1a，**不保存签购单号本身**）。重新载入后：
   - 页面顶部提示“这台平板上次发送的纸质订单（{时间}）没有收到答复，可能已经录入。按同一张纸质单填写后发送：会找回已录入的订单，不会多记一笔。也可以先到订单页查找。”；
   - 下一次柜台发送沿用保存的订单操作编号；付款时间、方式、签购单号和原来一样时也沿用同一个付款操作编号（服务端答“已录入”），改过则是新的付款操作（答 `already_paid`）；
   - 收到确定答复（下单成功、已下单 N、没有发出去等）、返回修改或重新开始后清除；超过 3 天（纸质单可录入的范围）自动丢弃；
   - 浏览器存储不可用时行为与以前一样（只在当前页面记得）。
     店员桌台轮次不保存：它的意图里包含客人购物车的决定，换了内容再发送答冲突，保存编号帮不上忙；桌台轮次的重复由桌台订单页可见。
9. **另一台平板**：页面无法知道另一台平板上没有答复的发送。纸质单表单写明“在另一台平板上发送过这张纸质单但没收到答复？先到订单页按时间和金额查找（停电/断网后补录），再在这里录入。”，
   运行手册第 4 步同样要求先在订单页查找。

10. **被撤下的轮次再次发送**（b11 实测，按商用原则补充）：付款时限过后系统撤下（`PAYMENT_NOT_STARTED`）或员工取消的未付款轮次，它的付款时钟仍是“待付款”，
    以前再次发送时仍按“待付款”返回这一轮，页面显示“在刷卡机上收 $2.83”和可点的“已用刷卡机付款”，员工会给一轮永远不会做的菜刷卡。
    现在再次发送（`AlreadyPlaced`）时，没有付款记录、且这一轮已被撤下或付款时限已过（尚未被撤下也算），直接答 `staff_round_already_sent`（不经“还在发送”的 2 分钟），
    显示第 5 条的“{桌台}的这一轮之前已经发送，在订单 N 里……”；已付款的轮次仍按第 1 条读作已付款。是否已撤下由 Ordering 的轮次记录读出（结账取消或员工取消）。
11. **一张纸质签购单只录入一次**（b11 实测：同一张签购单 TESTSLIP6D 记在订单 29 和 30 上，当天营业额多出一笔）：
    - 柜台页收到“已下单，订单 N”且这次是带纸质付款的发送时，清空纸质勾选、付款时间和签购单号，并说明这张签购单属于订单 N、这里已清空、不会重复录入。
    - **购物车（b11 复审）**：收到“已下单，订单 N”时，订单 N 里的菜从购物车拿掉，不会随下一次发送再下单、再收款（以前整车重发，$3.67 的菜按 $7.35 再收一次、厨房做两次）。
      本页记得这一操作编号每次没收到答复的发送内容（菜品、选项、备注、数量）：都相同时就按数量拿掉，说明“已在其中的菜已从清单中拿掉，剩下的请作为新订单发送并另外收款”（全部在订单 N 里时清单清空）；
      几次发送内容不同或本页不知道（重新载入后）时，不猜：说明“这台平板分不清哪些菜在订单 N 里”，发送按钮要等员工核对订单 N、拿掉其中的菜并勾选“我已把订单 N 里已有的菜从这份清单中拿掉”后才可用。
    - 服务端：纸质（停电/断网后补录）的刷卡机付款，若同一门店在付款时间前后 72 小时内已有**另一张订单**的纸质付款用了同一签购单号（忽略空格和大小写），
      在下单前的检查里就拒绝（`slip_already_recorded`，带持有它的订单号，什么都不下、不录），录入付款时再按同一把签购单锁检查一次（并发的两次录入只有一次录入）。
      同一次发送再发（同一订单操作编号）不受影响，仍按第 1 条找回原订单。现金纸质单没有单号，不检查。
    - **同一订单的其他轮次（b11 复审）**：每轮付款的桌台停电时两轮纸质单用一次刷卡付清，是真实情况。同一订单（同一桌台同一次就座的订单）的其他轮次可以带同一签购单号：
      录入付款时只和别的订单比较；下单前的检查对桌台轮次按发送里写明的桌台和就座（`expectedDiningSessionReference`）认出同一订单，没写就座时（员工从“这桌再点一单”发送，b12 起）按桌台当前的就座认出同一订单，不问员工；见文末 b12。
    - **员工确认，不是静默拒绝（b11 复审）**：签购单号已录在另一张订单上时，页面在拒绝说明下给两个回答：“同一张签购单，也付了这单”（一次刷卡付了两张柜台单）、
      “另一张签购单，参考号相同”（两台刷卡机 72 小时内打出相同的号）。员工核对签购单后回答，这次发送（或录入）随回答再发一次：服务端放行，付款照常入账，
      付款审计（`PAYMENT_CARD_MACHINE_RECORDED` 的 afterSummary）记下 `slipConfirmation` 和另一张订单 `slipAlsoRecordedWithOrder`，操作人即回答的员工。
      回答不是付款身份的一部分（不进 intentDigest）：没回答时被拒的那次什么都没写。同一笔销售录了两次则不回答、不再发送。柜台点单、柜台“已发送、未付款”列表和订单页的录入纸单付款都有这两个回答。
    - **这次发送自己的付款操作编号已录在另一张订单上**（订单操作编号是新的）：下单前就拒绝，员工回答也不放行。那个付款操作编号只能录在它随之发送的订单上，
      放行会下一张永远录不上付款的纸质单（`CARD_MACHINE_IDEMPOTENCY_CONFLICT`），所以以前“同一付款操作编号即同一次发送”的豁免取消；真正的重发由订单操作编号认出。
    - **两台平板同时发送同一张签购单（b11 复审）**：下单前检查的锁在检查自己的事务结束时就释放，两台平板可能都通过检查、都下单。现在同一进程内，带同一签购单号的纸质发送
      （检查、下单、录入付款）一个接一个执行（最多等前一个 15 秒），第二台在第一台录入后才检查，下单前就被拒。多个 API 进程之间仍由录入付款时的签购单锁保证只录一次。
    - **已下单但付款因签购单被拒**（多进程同时发送，或较早发送的订单付款当时失败、重发时签购单已录在别处）：页面不再说“没有再录入”，而说“这张订单已经下单，但付款没有录入：
      签购单已录在订单 N……如果是同一笔销售录了两次，请不要录入，告诉店长，等录入时限过后由店长在订单页按‘已重新录入’关闭，关联到订单 N”（桌台轮次：在订单页撤下这一轮）；
      也给出上面两个回答。
    - 只比较纸质付款之间：现场刷卡的签购单号由员工照机器小票录入，不会与补录混淆；把现场付款也纳入会误拒同一订单两轮用同一张小票号的既有记录。
12. **已付款面板的金额标签**：已付款（或再次发送时读作已付款）的柜台单，金额一栏写“已付金额”，不再写“应收”。
    本页看到已付款的订单，“已发送、未付款”列表在读数落后的几秒内也不再列出它（不再出现“收款”按钮）。

## 为什么不是别的做法

- **按金额和时间去重**：现金纸质单没有单号，同一分钟同金额的两杯豆浆是真实的两笔；按金额和时间去重会误拒真实销售。
  同一次发送的操作编号才是“同一笔”的可靠依据，所以从操作编号入手；签购单号只在填写了时作为第二道检查（第 11 条）：
  刷卡机每笔交易的授权码/参考号不同，同一门店 72 小时内两张纸质单用同一个号，就是同一张签购单录了两次。
  同一门店 72 小时内两张纸质单用同一个号，多半是同一张签购单录了两次，但也有真实的例外（一次刷卡付两张单、两台机器打出相同的号）。
  所以不提供无记录的“仍然录入”开关，而是要员工核对签购单后明确回答并记录回答人（b11 复审）；静默拒绝会让真实销售无法入账，违背“每笔销售都入账”。
- **把“还在发送”的 2 分钟缩短**：正常发送有十几个步骤，负载高时可能超过 30 秒；缩短会让仍在进行的发送被当成失败而重下一单。保持 2 分钟，并让已存在的订单在窗口后被点名。
- **只把操作编号放在页面内存里**：员工没收到答复后重新载入页面再录入，会生成第二张订单（复审指出，等同实测 L5 的 $3.67 记两次），所以按第 8 条按门店保存在本浏览器。
- **用 `sessionStorage`**：关掉标签页或浏览器重启就丢了；平板上“关掉重开”和重新载入一样常见，所以用 `localStorage`，并在答复后清除、3 天后丢弃。

## 停电/断网时

本决定处理的正是“发送时网络断了一下”。员工看到“系统没有答复”时直接再发送（无需改动），即使改了付款时间或菜品，也不会多记一笔；
若答“已下单，订单 N”，到订单页查看这张订单，不要按纸质单再录一次。

## 仍然存在的边界

- 多个 API 进程同时收到同一签购单的发送时，第二张订单可能已下单而付款被拒：页面按第 11 条说明怎么关闭它；若它恰好比持有签购单的订单晚发送，
  “已重新录入”的关联（要求新订单不早于旧单）不能用，需要店长按运行手册处理（试点只有一个 API 进程，同进程内已逐个执行）。

- **另一台平板**上没有答复的发送：本页不知道，只能按第 9 条先在订单页查找；系统不按金额/时间自动拒绝（会误拒真实的两笔相同销售）。
- 同一台平板上**换了员工登录**后再发送保存的编号：服务端按操作人答冲突（不会多记一笔），页面清除保存的发送，员工应先到订单页查找再录入。
- 浏览器存储被禁用或清空时退回到只在当前页面记得。

## b12 同桌同一张签购单（DEC-PAPER-SLIP-SAME-TABLE，2026-11-13，第十二批实测发现，协调人按商用原则决定，Owner 可推翻）

实测：停电后同一桌第二轮纸质单用付第一轮的同一张签购单，从“这桌再点一单”发送，被拒为“签购单已录在订单 9……不要再发送”。
照这句话做的服务员会丢掉一轮真实销售（不进厨房、不入账）。原因：没有待定的就座时，页面不带 `expectedDiningSessionReference`，
下单前的检查没有就座可比，同桌豁免不生效。

1. **同一桌、同一次就座的各轮用同一张签购单是正常的**（每轮付一次、一张小票）：下单前的检查在发送没写就座时，读这张桌台当前的就座；
   签购单已录在这次就座的订单上时直接放行，不问员工。发送写了别的就座、别的桌台、柜台单或另一张订单时，仍要员工回答两个问题之一。
2. **每笔付款各记一次，审计写明**：同一订单后面一轮的付款照常记一条，付款审计记下 `slipAlsoRecordedWithRound`（先录这张签购单的那一轮）；
   旧页面仍问、员工答了“同一张签购单，也付了这单”时，回答 `slipConfirmation` 一并记下（以前这种回答在录入时丢掉，没有归属）。
3. **超过 3 天的重发**：已下单的纸质单在付款时间超过 3 天后用同一次发送再发，先认出“之前已发送”，答“已下单，订单 N”，
   页面显示这张订单，员工不会再下一张；它的付款仍受 3 天补录时限约束，超出时在这张订单下说“请核对签购单参考号和付款时间”，
   不再只答“付款时间超出范围”而不说订单已经在。
