# DEC-DINING-CART-TIMEOUT-CONTINUATION — 堂食共享购物车超时后继续点餐

状态：**Accepted（协调人按商用原则决定，2026-10-11，待 Owner 知悉）**。
执行工作包：[WP-2423](../work-packages/WP-2423.md)（授权变更由协调人在 WP-2423 记录）。

## 问题

v15 实测：一桌的共享购物车（策略 `idle_timeout_seconds` 3600）在最后一次修改一小时后由过期任务记为
`Expired`（`IDLE_TIMEOUT`）。用餐会话仍为 Active，但此后同桌每位顾客：

- `POST /api/v1/carts` 返回 409 `cart_expired`（选择购物车时遇到已过期的购物车）；
- `GET /bff/customer/cart` 返回 404（当前购物车读取只返回未过期的 Active 购物车）；
- 菜单显示“购物车已过期……请找店员”，店员“重新生成入桌码”也无效。

已有的替换能力（`POST /api/v1/carts/:cart_id/replacement`、购物车页“开一个空购物车”按钮）只允许**桌主**使用，
而且顾客根本到不了那个按钮。结果是饭后一小时想加甜点的整桌顾客无法点餐，商用上不可接受。

## 决定

1. **谁可以替换**：上一辆购物车为 `Expired`（`IDLE_TIMEOUT` 或 `ABSOLUTE_TIMEOUT`，且过期已由过期任务记录）时，
   该用餐会话中**任何当前在座（Active）的参与者**都可以替换；已离开的参与者、已关闭的会话一律拒绝。
2. **Abandoned 不变**：上一辆购物车为 `Abandoned`（顾客主动放弃）时，仍只允许桌主替换，与现状完全一致。
3. **走现有所有者路径**：替换仍由 Ordering 的替换命令完成——同样的身份与 CSRF 校验、Dining 围栏（按“桌 → 会话 → 参与者”
   加锁）、结算检查（旧购物车没有进行中的结账/付款）、每个会话只有一个后继购物车、版本冲突检测、审计，按操作编号幂等。
   **不复制任何菜品**，不触碰已提交的订单与付款。
4. **自动继续**：顾客在菜单加菜时，服务器选择购物车若遇到已过期的桌购物车，就以由该次选择操作编号确定性派生的替换操作编号
   自动替换，然后选中新的空购物车，加菜照常成功。两位顾客同时触发时只产生一个后继购物车：后到者遇到版本冲突，直接重新
   选择即可。到期但过期任务尚未记录（数秒窗口）时返回“稍后重试”（503，`Retry-After` 5 秒），顾客端自动重试一次。
5. **告知顾客**：旧购物车里还有未下单的菜品时，触发替换的那位顾客在“已加入购物车”处看到一次提示：
   “Your table's earlier cart timed out, so items that hadn't been ordered were cleared. Orders already placed are not
   affected.” 旧购物车为空时不提示。已提交的轮次会清空购物车，所以留在过期购物车里的都是未下单的菜品。
6. **页面文字**：购物车页对过期购物车说明“同桌任何人都可以开一个空购物车继续点餐，未下单的菜品不会被复制”；
   对 Abandoned 说明只有开桌的人可以重新开；菜单不再出现“请找店员”的死路。

## 不在本决定范围

- 过期时长本身（策略 3600 秒）不变。
- 不由 API 代替过期任务记录过期；记录前的短暂窗口只做重试。
