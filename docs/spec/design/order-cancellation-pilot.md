# DEC-ORDER-CANCELLATION-PILOT — 试点订单取消流程

状态：**Accepted（Owner 批准）**。2026-10-10 Owner 在会话中回复“批准订单取消流程”。
执行工作包：[WP-2423](../work-packages/WP-2423.md)（扫码点餐痛点核对 Q6；能力缺口 `BatchCancellationWorkflow`）。

## 决定

1. **系统取消未付款的堂食批次**：现有 InternalTest 工作流（付款失败且厨房未接单、未开始的加单批次 → 取消，订单阶段按剩余批次
   重新汇总；权限 `order.batch.cancel.expired`；无副作用、无规则覆盖）按原样发布为 Pilot 工作流版本，在 Pilot 环境安装，
   并从 `pilotCapabilityGaps` 删除 `BatchCancellationWorkflow`。
2. **店员取消已付款、厨房尚未开始的菜品或订单**：
   - 权限 `ordering.order.cancel`（门店经理、Owner）；须选原因（顾客要求、售罄、门店差错、重复下单）。
   - 只允许厨房未开始的菜品；已开始的菜品走普通退款。
   - 退款走“已付款无法履约”的补偿路径，原路退回被取消菜品对应的金额（含税，按快照分摊），不受普通退款额度约束；
     服务商结果未知时只查询、不重复提交。
   - 同一事务撤下厨房待做项、释放库存预留（与 Q12 同一释放机制），写只追加的取消记录与审计。
   - 顾客状态页显示已取消的菜品与退款状态。
3. 取消不删除任何订单、付款或厨房记录；更正只经补偿操作。

## 待实现时核实

- 补偿路径目前是否只支持整单；若只支持整单，先交付整单取消，再补按菜品取消，两者都在本决定范围内。
- Pilot 工作流版本的发布与安装方式须与现有工作流定义存储和 v15 安装一致，不手工改库。

## 实现决定（2026-10-11，按商用原则作出，Owner 回复“继续”）

1. **顺序**：先做店员取消（第 2 项），后做系统取消的 Pilot 工作流版本（第 1 项）。
2. **店员取消第一步——整单/整批**：一个批次（取餐单即整单）的全部厨房工作项都未开始（Queued；店员已“接单”或 Held 均算未开始，开始制作是不可逆点）
   才可取消；同一数据库事务内：权限与原因 → 围栏（订单版本、厨房工作项行锁且仍未开始、付款已确认）→ Ordering 只追加的店员取消记录、修订与审计 →
   厨房工作项置为 Cancelled（新厨房命令与事件）→ 库存整单释放（新系统原因 `STAFF_CANCELLED_BEFORE_PREPARATION`）→ 付款补偿案件。
   向服务商退款在事务外由现有补偿任务执行（租约、先查询再退款、结果未知只查询）。
3. **退款金额**：门店取消整单时退还该付款尚未退的全部金额，**含小费**（门店原因取消，顾客不应承担）。
4. **第二步——按菜品取消**：Ordering 按菜品记录、厨房只取消该菜品、库存按订单行释放（仅 schema-2 预留）、退款走普通退款的按菜品分摊并新增
   `Cancellation` 类型（不计入 CAD 100/24 小时/跨营业日门槛与普通退款累计，由取消记录自动批准）。
5. **系统取消 Pilot 版本**：Pilot 环境使用新的、与环境无关的用途码 `UnpaidDineInBatchCancellation`（新工作流族，六个迁移与 InternalTest 相同）；
   InternalTest 保留 `InternalTestBatchCancellation`；新增仓库内的工作流起草与发布工具（经 Publishing 与 Workflow 所有者命令，可按操作编号重放）；
   发布后从 `pilotCapabilityGaps` 删除 `BatchCancellationWorkflow`。
6. **发布方式（2026-10-11 实现）**：工作流内容是平台定义的产品规则，由平台发布步骤 `workflow-release-install.mjs` 安装到品牌（与权限目录安装同类：
   操作人与独立批准人、批准证据、按操作编号重放）；版本无到期，内容变更只能发新版本。单人门店规则（DEC-SOLE-OPERATOR-APPROVAL）不适用于这一平台级批准。
