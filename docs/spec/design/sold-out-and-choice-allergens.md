# DEC-SOLD-OUT-CHOICE-ALLERGENS — 刚售罄的菜与选项过敏原

状态：**Accepted（实现决定，2026-11-11，按商用原则与 Owner 授权作出）**。
执行工作包：[WP-2423](../work-packages/WP-2423.md)（B08 sold-out-and-allergen-safety 的 v15 第 5 批实测问题，b7 包）。
依据：Owner 默认决定 [owner-defaults-2026-11-06](owner-defaults-2026-11-06.md) 第 16 项（M76）与 M23、M154、M166。

## 决定

1. **刚售罄就说刚售罄（M154）**：客人在菜品页或购物车“+”时，菜刚被标“今天售罄”或库存做不出，服务端回
   `CATALOG_ITEM_SOLD_OUT`，页面标题直接是“这道菜刚卖完。”并给“返回菜单”，不再出现“请检查你的选择”。原因在服务端：
   外带加菜服务丢了 Catalog 的单行判断（`explainMany`），桌台加菜服务把拒绝原因抹成只剩错误码；两处都改为原样传递。
   购物车里已标“现在不可点”的一行只留“删除”，“+”“−”不可按（服务端本来就会拒绝）。
2. **选项的过敏原只挂在那个选项上（M166 与 M77）**：员工在已上架的菜上回答“炒蛋饭 加：蛋”，Inventory 立刻按新选项配方用料，
   所以客人和后厨必须马上知道。员工过敏原变更记录（`sellable_allergen_change`，只追加）保留原来的“整道菜连同所有选项”的合集
   （不认识选项的读取方仍不会漏报），并新增 `choices_json`（迁移 `2000_680`）分开记“菜本身”与“每个已回答选项加什么”，
   且带上这道菜所有已回答的选项（不只本次保存的）。客人：菜的过敏原列表标“（所有选择）”，“加：蛋”出现在炒蛋饭下面，
   每组选择只含它真正包含的；后厨：只在点了炒蛋饭的那份菜上提示蛋；选项未知时仍按合集（宁多勿漏）。保存提示如实说
   “顾客和后厨已经能看到各选项新增的过敏原；其他改动在菜单上架后显示”。
3. **没回答的选项从不当作“不含”，回答了“不加”就不再提醒**：只要某个可选选项从没回答过自己的过敏原、且这道菜没有逐组合的
   过敏原，客人在选项下方看到一行“选项可能会加入这里没列出的过敏原。如果你有过敏，请下单前先问店员。”员工编辑菜时看到
   哪些选项还没回答“加过敏原吗？”，以及“回答前顾客会被提醒先问店员”。员工回答“不加”后这句话对该选项就停止：
   “不加”也让选项配方加上该选项的员工申报替身（申报内容为空），上架后的菜单因此能把“回答了不加”（空列表，从不写成“不含”）
   和“从没回答”（缺省）分开；同一替身答案改了（先“蛋”后“不加”）会重新保存选项配方，让它指向现在的答案；已上架的菜上回答
   “不加”时立刻记一条员工过敏原变更（各选项连同空答案），不显示“刚更新”。客人收到空列表只在这道菜没有逐组合过敏原时
   （有时页面本就不提醒）。一条变更最多说 600 个选项（菜编辑器一道菜最多 12 组×50 个）；超过时只记整道菜合集，读到旧的超量
   记录也按合集读，菜单不会因此读不出。不拦截保存或上架：现有菜单的每个选项都未回答，拦截会让商家连改价都上不了架；
   按 M76 的做法，新菜必须答全，旧数据提示而不阻断。
4. **切换语言不丢正在填的菜**：切换语言会重新加载页面。编辑中的菜有未保存内容时，先用员工当前语言问“这里填写的内容还没保存。
   切换语言会重新加载页面，内容会丢失。仍要切换吗？”；选“取消”留在原页，语言选择不变。刷新或关闭标签页由浏览器询问。
   不把草稿跨重载保存：草稿含价格与过敏原答案，静默恢复旧草稿比明确询问风险更大。
5. **首页提醒下单后售罄的订单（M23）**：等待接单、且含下单后售罄或下架菜品的订单，在首页“需要处理”第一项单独列出（标题“有菜在下单后售罄或下架的订单”，与订单页一致），
   说明在“订单”里请客人换菜或取消该菜并退款（不自动退款）。

## 断网与故障

- Catalog 出错时绝不说售罄或“没有权限”：加菜本身读不到按“暂时无法添加，请重试”；只是拒绝原因读不到时，按一般的“不能按所选下单”说。
- 后厨读不到选项信息时按合集提示（宁多勿漏）；纸质流程仍按 runbook 的桌台过敏勾选与“选项售罄”纸面做法。
