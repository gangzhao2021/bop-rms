# DEC-TABLE-ROUND-STATES-B5 与 DEC-STAFF-ROUND-SPEED：桌台轮次的金额、说法与店员加轮速度

状态：协调人按商用原则决定（2026-11-11，WP-2423 v15 第 5 批实测 shared-table-staff-round），Owner 可推翻。
依据：[DEC-STAFF-DINE-IN-ROUND](staff-dine-in-round.md)、[DEC-TABLE-CLOSE-GUESTS-LEFT](table-close-guests-left.md)、
[DEC-TAX-WHOLE-RECEIPT](tax-whole-receipt.md)、Owner 默认值 2026-11-06。

## 决定

1. **整单都已取消的桌台仍按轮列出（金额以分计）**：一桌的所有轮次都"未付款取消"（客人停付、到时取消、店员以"客人已走"取消）后，
   店员读单仍列出每一轮，状态为已取消、不收费；合计只算应收的（0），"已取消的未付款轮次 · 不收费"单列。原因：v15 上三轮共 $38.91
   被当成合计显示，而实际一分没收。只读显示，不改任何命令。
2. **店员加轮在客人手机上的说法**：店员加的一轮写作"店员正在用刷卡机收第 n 轮的款"，不是"同桌有人正在付款"；只有这一轮里确有
   本手机加的菜时才加"你的菜也在里面"。被店员拿出购物车的菜，即使购物车空了也照样告诉该手机"店员把 X 从购物车里拿出来了"。
   依据是 Ordering 自己的记录（店员加轮记录、订单菜品上的加菜参与者），读不到时按旧说法（不比以前更差）。
3. **客人停付的轮次**：桌台页对未付款取消的轮次不显示税和合计，合计行写"未扣款"；客人自己停付的轮次写"这一轮在有人付款前停了，
   菜回到了本桌购物车，没有人被扣款"。旧付款页面在停付后再按确认，服务器立即回答"这一轮已停付"（409 `round_returned`），页面
   直接转到结果页说明同样的话并给"去购物车"，不再等 30 秒后说"没有按时完成"。判定来自 Ordering 的退回记录
   （`dining_round_cart_return`），读不到时按原来的说法。
4. **店员看到的等待原因**：未付款轮次的菜不再写"等待员工"：店员加的一轮写"等刷卡机收款"，客人的一轮写"等客人付款"；已付款
   待接单的仍写"等待员工"。关桌说明里同一轮只说一次（刷卡机收款），不再同时让店员"请客人在手机上付完"。点单页、桌台页、订单页
   的收款截止时间统一为该轮真正被取消的时间（付款窗口：容量链接时间 + 30 分钟），不会出现 07:40 与 07:39 两个说法。
5. **少一道菜写"1 道菜"**；购物车每个"删除"按钮的读屏名称带菜名（"删除 柠檬茶"）。

## DEC-STAFF-ROUND-SPEED（M35 < 2 秒）

慢在哪里（容器数据库实测，三次店员加轮，每次两道菜）：总 3.6–4.3 秒，几乎全部是数据库往返：付款准备 1.3–1.9 秒、结账
0.6–0.9 秒、报价 0.45 秒、每道菜加入购物车 0.2 秒。CPU 有八成时间空等数据库。付款准备一次要约 1,600 条语句、约 110 个事务，
原因是客人身份在每一步前后都重新核对（结账服务每步 4–6 次，付款准备里结账核对、小费、下单、加轮各走一遍，共约 30 次），
而每次核对又分成约 7 个事务（会话、桌码、桌台上下文两次、参与关系……）。

本次决定：**一次核对只用一个事务**——同样的读取、同样的顺序、看到同一时刻的数据（与 WP-2423 第 4 项"入口绑定一次核对一个
事务"同一做法），不减少核对次数，不放宽任何写入前的围栏。已在调用方事务里的核对（`identity(tx)`）不另开事务。效果：付款准备的
事务数约减半，整轮 3.1–3.5 秒（同一台机器、同一测试）。

仍未达到 2 秒：剩下的是核对次数本身（约 30 次 × 约 10 条语句）。要再快，需要"一次请求内的客人核对结果在最终写入围栏前复用"
这一类授权设计变更，属于付款与授权的完整证据范围，另立一项，由协调人与 Owner 确认后再做。在那之前：店员按"发送"后按钮显示
正在发送，答复丢失时以同一操作号重发，不会重复下单。

### 第二步（2026-11-11，staff-round-speed，协调人按商用原则决定，Owner 可推翻）

重新实测（受限 NOBYPASSRLS 试点角色，真实店员加轮从"发送"到刷卡机金额）：开新桌的一轮 8,088 条语句、约 2.9 秒（本机负载约 5）。
其中约六成是同一位客人的同一组核对读取被重复执行，另有每个事务单独一次往返设定门店范围、每次核对在"门店/品牌"范围之间来回切换。
真实餐厅里店员按"发送"后要等的是数据库往返，不是核对本身；所以这一步**不复用核对结果、不减少核对次数**（上面那项授权设计变更
仍不做），只去掉不改变任何答案的往返：

1. **事务开始只走一次往返**：BEGIN、事务时限和门店范围一起发送。范围值只在通过 UUIDv7 校验后写进语句文本（只含十六进制和连字符），
   其它值在取连接前就被拒绝。
2. **范围设定随下一条语句发送**：同一事务里写了又改回的门店/品牌范围不必发送；只有真正要执行的下一条语句前，范围与数据库里不同时才发。
   只由试点事务执行器这样做；自己逐条发送的调用方（测试里的事务包装）照旧。
3. **同一事务内重复的"稳定读取"直接作答**：只针对所属领域在 SQL 前标了 `-- bop:stable-read` 的纯读取（客人会话、桌码、品牌/门店、
   桌台、参与关系、重新入座记录）。同一范围、同一参数的再次读取，中间没有任何写入、新加锁、所属领域函数调用或保存点回滚时，
   直接用第一次的结果（每次给一份副本）；任何写入或新锁之后重新读取。已在本事务加了行锁（FOR SHARE）的品牌/门店读取，锁在事务
   结束前一直持有，别的事务改不了这一行，所以新加锁、加行锁的纯读取之后仍可作答；但本事务自己的写入能改这一行（行锁挡不住自己），
   所以**任何可能写入的语句**（INSERT/UPDATE/DELETE、带写入的 WITH、所属领域函数调用等，也包括写别的表而由触发器改到这一行的情况）
   之后，带行锁的读取也一并忘掉、重新读取。这与"同一事务里先后两次读取之间，别人的提交恰好落在第二次读取之后"等价；凡是要按锁
   排序的再读（写入围栏）仍然真正执行。
4. **购物车的一次客人核对（会话、本机在桌上的位置、会话再查一次）放进一个事务**（`runTogether`），与付款准备的"一次核对一个事务"
   同一做法：核对之间的加菜、报价等写入仍各自提交。顾客端同样受益。**要说清的一点**：合用一个 READ COMMITTED 事务后，第二次查会话
   如果与第一次之间没有任何写入或新锁，会直接用第一次的结果（第 3 条），**不再真正重读**；因此在这两次读取之间被结束或被替换的会话，
   这次核对看不出来。兜底的是：随后在自己事务里的 `authorize()`，以及写入前的围栏（桌台锁与重读、版本号、操作号幂等）仍会拒绝；
   风险小，但不是"重读照旧"。限制：`runTogether` 里的读取必须一个接一个，不能并发；同一连接池上所有普通事务（不论哪个执行器、
   什么范围）都并入这一个事务，它们各自的时限和连接预算不再生效；并发启动会得到 `TENANT_DATABASE_TRANSACTION_CONCURRENT_QUERY`，
   客人看到"暂时不可用"。现有路径是顺序执行，部署后看 api 日志里有没有这个代码。
5. **已发出的桌码每个进程只读一次**：桌码记录只能追加、不能修改或删除；换码、停用是桌台上的新事实，每次核对仍读桌台本身。

效果（同一测试、同一台机器）：开新桌一轮 8,088 → 约 4,160 条语句（−49%；带行锁的读取在写入后也重读，比初版 4,141 多约 15 条），
后续加轮约 4,150 条。本机（负载 5–6）复测 1.7–2.4 秒，有一次复审测得 2,153 毫秒，**已在 2 秒边上甚至超过**。容器上原 3.1–3.5 秒，
按条数估算约 1.6–1.9 秒只是估计，**M35（< 2 秒）未证实，不能记为已修复**，以部署后 v15 实测为准。回归护栏：`staff-dining-round`
验收里真实店员加轮（开新桌、后续加轮）各不超过 4,400 条语句（约比现在多 6%；4,400 × 0.33 毫秒 ≈ 1.45 秒数据库时间），
旧代码 8,088 条时失败。

不变的：店员的身份与权限在命令开始和提交前各核一次；每一步发起的客人核对次数、顺序和写入前围栏（桌台锁与重读、各版本号、
操作号幂等、审计）都不变，但核对内重复的稳定读取可能由第一次的结果作答（见第 3、4 条）；不新增迁移、授权、目录或角色。

### 第三步（2026-11-12，staff-round-speed-and-rounds，协调人按商用原则决定，Owner 可推翻）

v15 实测：安静时 1.85–3.9 秒，且随桌上已有轮次增长（1.9 → 9.4 秒，最长 22 秒）。原因有二：每轮约 4,150 条语句里大半是同一位
客人、同一张桌的同一组核对在一次请求里被反复执行；另外桌上每多一轮，读每轮"是否已接单"多 3 条语句（逐轮各读一次）。决定：

1. **一次请求内复用已做过的核对，直到写入围栏**（`withVerifiedChecks`，只包住店员加轮这一个请求）：只针对所属领域标了
   `-- bop:stable-read` 的读取、只在尚未写入或加锁的读写事务里、同一范围同一参数，最多 10 秒；快照读取和跨请求都不复用。
   事务在**第一条可能写入或加锁的语句之前**，把这次借用的每条读取按原范围真正重发一遍，结果必须与借用时一模一样，否则整笔事务
   以可重试冲突失败（重来时按当前事实重新决定）。所以凡是要写入的事务，仍在自己的锁下按最新事实决定；只有只读核对才用本请求
   早先的答案。任何可能写入的语句会忘掉它可能改到的那些模式里记住的答案（不认识的语句则全部忘掉）。全部被作答的只读事务不取
   连接、不发任何语句。店员身份与权限、门店范围、各写入围栏（桌台锁与重读、版本号、操作号幂等、审计）一条不少。
2. **桌台订单的各轮接单情况一次读出**，后续加轮的成本与桌上已有几轮无关。
3. 结果（受限 NOBYPASSRLS 试点角色、真实 `createTenantTransactionRunner`、同一张按轮付款的桌连续 12 轮、每轮刷卡并接单）：
   每轮约 2,200–2,330 条语句（原 4,136），从第三轮起每轮条数相同；护栏：每轮 ≤ 2,500 条、第三轮后增幅 ≤ 3 条。耗时护栏：12 轮
   中位数 < 2 秒（本机，受负载影响；v15 以部署后实测为准）。

**`runTogether` 的提交范围**：合并成一个事务的多次运行里，第一个写入的运行所属的门店/品牌范围就是"写入者"；别的范围之后只能读、
不能写（写会使整笔事务失败），COMMIT 前把写入者最后写下的范围补发，延迟约束触发器在写入者范围下检查（之前在最后写入的范围下，
RLS 看不到行而 23514）。

**批量自动取消不再"一轮卡住整页"**：某一轮的系统取消失败时，同页其余轮次照常取消、游标照常前进，失败在本页处理完后报告一次
（worker 记录并重试），失败的那一轮在下一轮扫描从头开始时再试。

**旧单不上新客的账**：店员点单页记住"第一道菜放进来时坐在这张桌的那桌客人"（桌台的就餐会话），随单发送。那桌客人已离开（桌台
已关、或已换了一桌）时服务器拒绝，什么都不发、不收款；店员可以"替现在这桌客人发送"（作为新的一单，重新确认现在的会话）或
"重新点单"。点单时桌台是空的，则照旧由这一单开台。

**一次取消多轮看得到进度**：逐轮取消（每轮会改变订单版本，必须一个接一个），按钮显示"正在结束第 n 轮，共 N 轮"，并提示留在本页；
离开页面前浏览器会提醒；中途读不到桌台时明确说"无法确认是否都已结束"，"重试"从剩下的轮次接着做，不会静悄悄停下。
