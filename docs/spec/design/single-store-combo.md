# DEC-SINGLE-STORE-COMBO — 单店套餐（第 ⑥ 项第 4 段）

状态：**Owner 2026-10-28 确认做法 B；第 1 切片已实现**（见 WP-2423）。依据：Owner 2026-10-28 功能取舍 10（“固定价套餐 + 套餐内可选……客人看到一个套餐价，后厨看到一道道单独的菜，报表能看到套餐卖了几份。现有套餐底层复用，不另起一套”）、取舍 12（后厨每道菜单独完成，服务员每道单独“已上”）、[DEC-SINGLE-STORE-MENU](./single-store-menu.md) 第 7 条。

## 现状（查过代码）

- `/app/commerce/bundles` 背后是 Catalog 的套餐聚合（`rms_catalog` 迁移 1107，`bundle.ts`、`bundle-service.ts`、商家页 `BundlePages.tsx`）：固定价或计算价、若干“组”（每组最少/最多选几样、可选哪些菜、可加价），草稿 → 发布。试点里这两个地址重定向回首页。
- 套餐聚合**只到商品目录为止**。下游没有一处认识套餐：
  - 菜单与客人菜单投影（`published_menu_projection_*`）只有可售规格和规格组；
  - 购物车、报价、下单快照（Ordering 的 `order-item-snapshot`、`order-item-option-lines`）只有“规格 + 选项”一种行；
  - 定价只给规格和选项定价；
  - 后厨按订单行和该行配方的制作步骤排工作；
  - 出餐进度、收据、退款、日报都按订单行。
- 所以“复用现有套餐”在今天只能复用**录入和数据**这一层；从客人下单开始每一层都要新做。

## 取舍：套餐在订单里是什么

两种做法都满足“一个价进账、报表数一份”。区别在后厨和出餐要不要拆开。

**做法 A：订单里新增“套餐行”，下带各道菜的子行。**

- 后厨和出餐天然一道道分开。
- 但菜单投影、购物车、报价（含按道菜分摊税）、下单快照与其数据库校验、后厨接单、出餐进度、收据、退款与取消、日报这九处都要加第二种行。每处都碰钱或订单历史，都要完整证据。
- 估计 8–10 个切片，Ordering 与 Payment 改动最大。

**做法 B（建议）：套餐录在现有套餐聚合里，上架时编译成一道“套餐菜”给订单用。**

- 编译方式：套餐编译成一个可售规格（价格就是套餐价，税类取套餐的）。每个组编译成一个规格组，例如“汤（3 选 1）”，组里每个选项指向一道已上架的菜（`选项 → 菜品规格` 对照，Catalog 所有、只追加）。
- 客人、报价、付款、收据、退款、日报不用改：它们本来就处理“规格 + 选项”，套餐计一份、按套餐价进账。
- 后厨：接单时，遇到这种对照过的选项，就按每个选中的菜各开一个工作项。每个工作项用那道菜自己的中文名、配方步骤和档口，标“套餐”。
- 出餐：服务员按这些工作项一道道点“已上”。
- 过敏原：每个选项的加料配方是“加上那道菜的员工申报物料”，客人按所选的菜看到过敏原（沿用现有的“按选项披露”）。
- 库存：同一机制，选中的菜的配方随选项计入。
- 改动集中在 Catalog（编译和对照）、Kitchen（接单拆分）和出餐进度（工作项级“已上”）。
- 估计 4–5 个切片。

**建议做法 B。** 理由：

- 进账和报表路径不变，风险最低。
- 满足取舍 10 和 12 的每一句。
- 套餐的录入和数据仍是 `/app/commerce/bundles` 那套聚合，没有另起一套。

**需要确认的一点：** 做法 B 里，订单这一层用的是编译出的“套餐菜 + 规格组”，不是一种新的“套餐行”。如果 Owner 说的“复用”是指订单里也要有真正的套餐行（做法 A），请告知。

## 协调人 2026-10-28 对第 2–5 切片的决定

第 1 切片已接受，但不单独部署：整个套餐流程可用后一起部署。原因是“上架”后客人能带着默认菜下单、看不到所选菜的过敏原，后厨也只收到一项套餐价的菜。

1. **客人端必选组：**必选组在客人页一开始不选任何菜（底层规格组仍有默认）。每个必选组都选好之前，“加入购物车”不可用，按钮上写明还差哪一组。绝不能替客人送出他没选的菜。
2. **过敏原：**客人在每组里看到每道可选菜的过敏原；购物车和订单显示实际所选菜的过敏原。做到这一点之前，客人看不到套餐。
3. **后厨和出餐：**每道所选菜各是一条后厨项，中文名在前，挂在套餐名下；每道可单独做好、单独上菜；全部上完才算套餐完成。
4. **钱：**付款、税、当晚汇总、报表都按套餐价加加价计一份。退款和作废对整份套餐执行，是有记录的冲正操作；第 5 切片不按菜拆价，除非某个报表需要（需要时要说明）。
5. **权限：**沿用 catalog.product.update 与 pricing.price_book.approve，已接受，记入 WP-2423 决定清单。
6. **旅程测试：**客人每组都选 → 送单 → 后厨显示每道菜 → 上菜 → 现金付款 → 当晚汇总显示套餐一份；涉及持久化的部分在受限角色下运行。

## 第 2–5 切片的实现（2026-10-29）

- **第 1 切片的缺口（已修）：**选项配方要求套餐菜本身有已发布配方，第 1 切片没有，v15 上保存套餐会在选项配方这一步失败（当时测试用替身没发现）。现在保存时给套餐菜申报“无自身过敏原”（生成配方，含一个后厨步骤），每个选项的配方是“加上那道菜的员工申报物料”（数量 1，不计库存）。套餐里的菜必须已由店员申报过敏原；用真配方的菜暂不能放进套餐（选项还不能带配方与库存，已列为限制）。
- **客人（决定 1、2）：**门店数据告诉客人页哪些选项代表套餐里的菜，这样的组标为“套餐组”：一开始不选任何菜，按钮写“请选择{组名}”，每组选好前不能加入购物车。每道菜旁显示它的过敏原：取所有含这道菜的已发布组合共同含有的过敏原。其他组有不含该过敏原的菜时结果精确，否则可能多列一个每种组合都有的过敏原；“按你的选择”一行始终精确。购物车和桌上已点的轮次显示所选菜名及其过敏原。
- **客人菜单契约（v15 2026-10-29 修正）：**套餐组按商品绑定发出，可能是数量形式（semanticsVersion 2，带绑定的默认）；客人端和点单台都接受，条件是每道菜最多 1 份（选 N 道），并清掉默认。客人端按菜逐项读取菜单，读不懂的菜只略过那一道；店员的一页菜单用同一读取模块（`apps/customer-pwa/src/menu/menu-contract.ts`）检查客人现在的菜单，并列出客人看不到的菜。
- **后厨和出餐（决定 3）：**套餐仍是一个后厨工作项、一条订单行，所以就绪、上菜、库存、付款、报表都不变。后厨卡片在套餐名下按所选菜各列一行，中文名在前，每道单独点“做好了”（后厨的只追加记录，2000_116，数据库核对这道菜确实是该工作项的选项）；最后一道做好后，看板用原有命令完成套餐，在此之前不显示原“完成”按钮。上菜页同样按道菜列出，厨房做好的菜可单独点“已上”（用餐的只追加记录，2000_117）；最后一道上完后，用原有命令把整份套餐记为已上。试点只有一个档口，所以不按道菜分档口。
- **钱（决定 4）：**套餐是一条订单行，按套餐价加所选加价计一份，付款、税、当晚汇总、报表的路径都没有改；退款和作废沿用对整行的冲正操作，没有按道菜拆价。

## 切片（按做法 B）

1. **单店录入与上架**（2026-10-28 已完成）
   - 一页菜单新增“套餐”分类和套餐编辑：中英文名、套餐价、税类、各组（中英文组名、选几样、可选的菜、单项加价）。
   - 保存到套餐聚合；“上架”时把套餐编译成套餐菜、规格组和对照，单店直接上架，记录 `SingleStoreListing`。
   - 套餐发布的单店例外同样有数据库核对和咬合测试（协调人条件 4）。
2. **客人点套餐**：客人页显示一个价，分组选；未选够不能加入购物车。尽量复用现有规格组界面。
3. **后厨按道菜**：
   - 接单时按对照拆成每道菜一个工作项，中文名在前，标“套餐 · 二人套餐”，各走各的档口。
   - 套餐行本身不进后厨。
4. **出餐按道菜**：服务员每道点“已上”，全部上完才算这个套餐已上。
5. **旅程测试与日报核对**：
   - 一页菜单做套餐 → 上架 → 客人点 → 后厨每道一个工作项 → 付款；
   - 当晚汇总与报表中，套餐计一份、按套餐价。

## 验收（协调人 2026-10-28 要求）

- 单店在一页菜单做套餐、点“上架”生效，无审核。
- 客人每组选一样（或规定的数目）。
- 后厨看到套餐里的每一道菜，中文名在前。
- 付款、报表、当晚汇总把套餐算一份、按套餐价。
- 旅程测试：做套餐 → 上架 → 客人下单 → 后厨 → 付款，先证明在改动前失败。
