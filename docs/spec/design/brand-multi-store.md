# DEC-BRAND-MULTI-STORE — 多分店：品牌页、区域经理、品牌层菜单

状态：**Owner 决定（2026-10-28 功能取舍 14，原话“其他的按建议即可”），WP-2423 剩余工作 8 ⑥ 之后一项**；
实现细则由会话按商用原则作出（协调人 2026-10-30“your call … no Owner questions”），Owner 可推翻。
不改现有五个门店角色模板（老板、店长、前厅、后厨、库存），不改 [DEC-SINGLE-STORE-MENU](./single-store-menu.md) 的单店做法。

## 现状（2026-10-30 查明）

- 数据模型已支持多店：一个人在品牌下有一个成员身份，每家店一条门店分配（`packages/bop/membership`）；品牌角色作用于品牌所有门店
  （[DEC-PERM-BRAND-ROLES](./brand-role-templates.md)）。员工端会话列出“可用的门店”并能“切换门店”（`persistent-merchant-bff.ts`
  按每家店重新核对成员身份、门店分配和 `merchant.access`）。价格已能按品牌、区域、门店组、门店分别定价（`price-resolution.ts`）。
- 但试点是单店安装：`tooling/environment/pilot-merchant.mjs` 的工作区只列出安装时的那一家店，`targetScope` 拒绝其他门店；
  堂食、自取、后厨、付款等组合也都绑定这家店（`resources.scope`）。报表、当晚小结只读当前这一家店。
- 开真实的第二家店要走受治理的品牌/门店初始化（B2，平台操作员身份与审批），WP-2423 记为外部关口；内部测试的第二家店按下文条件 3 用产品自己的开店路径开。v15 上能实测的前提是
  先有第二家 TEST 门店。

## 决定

1. **品牌页 = 报表页的“各门店”视图。** Section 88 的 RPT-OPS-DASHBOARD 本来就有“Store / Brand”范围与“change scope”，
   不另起屏幕编号。报表页加一个“各门店”标签（只在会话列出同一品牌两家及以上门店时出现；只有一家店时不显示，不留空壳）：
   - 每家店一行：店名、营业日状态（营业中 / 已打烊 / 暂停）、今天到现在的净销售、税、小费、实收、还没结账的桌数和金额、
     是否和日结对得上；每行有“打开这家店”（切换门店后到“今晚”）。
   - 底部是这些店的合计，注明“N 家店中的 M 家”（看不到某家店报表的人，那一行写“你没有这家店的报表权限”，不计入合计）。
   - 每家店单独读取、单独核对权限（该店的成员身份、门店分配和 `reporting.sales.read`，和切换过去再打开报表完全一样）；
     一家店读不出来只影响那一行（“这家店现在读不出来，请刷新”），其他店照常。数字和该店自己的“今晚”完全相同（同一来源与计算）。
2. **区域经理：** 新增门店角色模板 `area-manager`（显示名“Area Manager / 区域经理”，角色码 `area_manager`），权限与店长模板相同，
   按店分配：给一个人在他管的每家店各分配这个角色。用独立模板而不是复用店长，是为了在员工页看得出“管几家店的人”，
   以后区域经理的权限需要和店长不同时能单独调整。权限目录 v20（只增模板，不增权限码）。
3. **员工分到一家或几家店：** 员工页给一个人增减门店分配，每家店的角色单独选；切换门店后看到的是该店给的角色。
4. **试点多店运行：** 一个安装服务同一品牌的几家店：工作区列出这个人有分配的、同品牌的、已上线的门店；`targetScope`
   接受这些门店；每个请求按会话选中的门店取门店事实（营业时间、功能开关、税、付款账户），不再固定用安装时的那一家。
5. **品牌层菜单：** 多店品牌在品牌层编一次菜单，走原有审核发布；各店在自己的“菜单”页只改本店价格（门店价格条目）和售罄，
   一点就生效（价格要确认“原价 → 新价”）。单店仍用一页菜单。

## DEC-BRAND-MULTI-STORE-ONE-INSTALLATION（协调人 2026-10-30，依 Owner 常设授权）

一个安装服务品牌的所有门店（方案 A）。不选“每店一个安装”（B）：真实的多店餐饮集团不会让员工和区域经理每换一家店就换一台主机，
商用原则不允许因为改动小而选它；也不推迟（C）：本产品面向多商户，留下已知的架构缺口不可接受。条件：

1. **门店由服务端决定，从不信任客户端。**员工端：选中的门店必须是这个人当前的门店分配，每个请求重新核对；切换门店是有审计的明确操作；
   没有分配的门店回 403/404，不带任何数据。客人入口和后台任务：门店来自桌码或订单记录，从不来自查询参数。每条命令照常明确带
   Tenant、Brand、Store；数据库 RLS 的门店范围不变。
2. **每段都能单独上线：**每段之后 v15 现有的这一家店行为与今天完全相同；单店实测路径和受影响的数据库配置是每段的门槛。
   不一次改完 79 个组合文件，按层分段，每段有受限角色数据库证明。
3. **第二家门店：**内部测试阶段，用产品自己的路径开一家明确标注的 TEST 门店（“DEMO Store 2 – not production”，测试专用税与地址），
   绝不用 SQL。产品现在没有开店路径（只有测试夹具直接写表、WP-2421 品牌门店拓扑只到草稿），所以本项包括做出最小的开店路径
   （老板权限、审计、只追加）。B2 只管真实的第二家店。
4. **付款：**每家店有自己的服务商账户、自己的日结和报表；品牌数字是各店数字之和，绝不混在一本账里。
5. **营业连续性：**一个安装现在是所有门店共同的故障域。安装不可用时每家店的员工各自按纸单流程营业（运行手册已有单店流程，
   扩展为每家店各一份：各店自己的纸单、各店自己补录）；一家店的门店事实或任务出错不影响其他店的请求。

## 分段（按层；每段的门槛都包括：v15 单店照常——商户 production-fail-closed 0 失败、客人端套件全过、受影响数据库配置全过）

1. **区域经理模板**（决定 2）：已完成（`82124569`）。
2. **员工端门店选择：**工作区列出这个人在本品牌有效分配的、已开业的门店；`targetScope` 接受这些门店并每个请求重新核对；
   切换门店写审计；员工端各组合按会话选中的门店取门店事实（营业日、营业时间、功能开关、税、收据、服务商账户配置），
   不再用安装时固定的那一家。门槛：受限角色验收——两家店都有分配的人看到两家、切换写审计、各店读写互不串；只在一家店
   有分配的人看不到也进不了另一家（403/404，无数据）；RLS 门店范围不变。
3. **开店路径**（按已查明的缺口再分四小段：3a 门店记录与开店人的门店分配；3b 新店的第一份门店配置与 TEST 上线核对；
   3c 新店的菜单、库存地点、桌台（各领域现有命令，切换到新店后做）；3d 签发新店的运行目录并由本安装服务。
   开店需品牌级 `organization.manage`（品牌老板），门店角色仍由平台签名的角色安装工具装上。注意：品牌有第二家店后
   单店一页菜单的“上架”例外即停止（DEC-SINGLE-STORE-MENU），所以 v15 开第二家 TEST 门店会让第一家店改菜单回到审核流程，
   直到第 9 段品牌层菜单完成。）品牌老板（`organization.manage`）在“门店”页开一家新店：门店记录、品牌关联、营业时间与税务草稿、
   门店角色（含老板分配）、服务商账户绑定、上线核对，全部经各领域现有命令，审计、只追加。门槛：受限角色验收（无权限被拒、
   重放幂等、记录只追加）；之后在 v15 开 “DEMO Store 2 – not production”（测试专用值）。
   3c（新店在产品里的设置）：不需要新代码——切换到新店后，“门店设置”从第 1 版配置开始（地址、联系方式、收据、税、付款都是未设定，
   由老板逐步填写并发布下一版，上线核对沿用 3b 的那一个），库存地点、桌台用各领域现有命令，都在新店自己的组合里执行；
   证明放在最后 v15 一次实测的旅程里。菜单属第 9 段。
4. **客人入口：**（做法：客人 API 进程也按门店各自组装；前面一个分发层按服务端自己的记录决定请求属于哪家店——客人会话 cookie
   按各家店的会话记录核对（RLS 按店，安装只服务 1–3 家，逐店核对），扫码入口按桌码属于哪家店的桌台，带公开门店编号的公开读取按
   各店安装资料里的公开门店编号，付款回调按付款记录；都找不到的回第一家店（即单店现状）；单店安装不经分发层。）扫码、取餐码、客人会话按桌码或订单记录决定门店；菜单、报价、购物车按该店。门槛：受限角色验收——
   第二家店的桌码只在第二家店下单、第一家店照常；客人端浏览器套件全过；v15 两家店各扫一次。
5. **后台任务：**业务任务、后厨、购物车过期、自动取消、日结、告警等按安装下每家店各跑一遍，一家店出错不拦其他店。
   门槛：受限角色验收两家店各自完成；v15 两家店的日结各自记录。
6. **每店的服务商账户：**付款、退款、对账、日结、报表都按该店自己的账户。门槛：两个账户的受限角色验收，
   两本账互不混；v15 第二家店用 TEST 服务商。
7. **各门店视图**（决定 1）：报表页“各门店”，品牌合计是各店之和。门槛：验收合计 = 各店之和、无权限的店不显示数字。
8. **员工分到几家店**（决定 3）：员工页增减门店分配、每店选角色（含区域经理）。门槛：受限角色验收与浏览器测试。
   把别家店的人加到本店只给店主与品牌老板（本店 `organization.staff.manage`）：调人到店会改变谁能在这家店操作，是 Owner 的决定；
   店长、区域经理需要人时请 Owner 加（协调人 2026-10-31）。
9. **品牌层菜单与门店改价、售罄**（决定 5）。门槛：受限角色验收（价格是钱，完整证据）与浏览器测试。

每段完整证据（受限角色验收、会咬），每段一行 WP-2423。

## 修订取舍 7：多店品牌的菜单（协调人 2026-10-31，依 Owner 常设授权；Owner 可推翻）

原话：“Segment 9 decision: B, narrowed as below. I'm deciding this as coordinator under the Owner's standing authority. Record it as a revision of trade-off 7, quoting this message, and state that the Owner can overrule it.” 规则：

1. 店长、区域经理、老板在各店直接改本店价格、今天售完、本店隐藏；改价先显示“原价 → 新价”确认，记录是谁改的。
2. 品牌层菜单改动（菜名、规格、新菜、套餐、过敏原）只有持有品牌老板权限的人上架才直接生效，每次上架记录是谁（与单店上架相同，记为 BrandOwnerListing）。
3. 没有品牌老板权限的店长或区域经理改品牌菜单，存为草稿等品牌老板审核；品牌老板在自己的页面一次操作上架。绝不允许非老板自己批准。
4. 单店路径不变。

“品牌老板权限”= 在品牌层（不限门店）持有 `organization.brand.manage`（品牌老板模板特有）。数据库对 BrandOwnerListing 记录同样核对（`bop_permission.actor_holds_brand_owner_authority`）。

### 第 9b 段落地方式（2026-10-31）

门店价格是该店自己那本已发布价目表里的门店范围条目；报价、顾客菜单、小票照旧读门店当前价目表（门店范围优先），
所以钱的计算与证据路径没有新分支。店长改价 = 以该店当前价目表为底另发一本只改这一项门店价的价目表并指派给该店，
`rms_pricing.store_price_change` 记原价→新价与人；品牌老板上架品牌价目表时发往每家未归档门店，各店门店价原样带过去。
数据库保证一家店的改动碰不到品牌价和别家店。单店品牌只有品牌价（一页菜单照旧），店长的本店隐藏也只在多店品牌开放。
