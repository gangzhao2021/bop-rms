# DEC-TABLE-ONLINE-REFUND — 退还客人手机付的整桌款

状态：已实现（WP-2423 已知不足 ⑪）。Owner 2026-11-02 “开启长时间任务，按你建议做，无需问我”批准排期；下列规则由协调人按商用原则决定，标 **[可推翻]** 的 Owner 可改。

## 问题

客人在手机上付了整桌或分单的一份后，店员退不了款，付款面板还误报“还没有已付款的付款”，积分也不会扣回。真实门店里，上错菜、多收是日常，必须当场能退。

## 决定

1. **谁能退 [可推翻]：** 和现金退款一样，经理（`payment.refund.approve`）PIN 确认，填金额和原因（菜品问题、客人要求、多收、门店失误）。按金额退，不按菜品；要取消菜品的走现有取消流程。
2. **先记录后发送：** 批准先落库，同时固定服务商幂等键 `table-online-refund:<operation>`，然后才调用服务商，调用不在数据库事务内。同一键重发不会重复退款。
3. **三种状态：** 正在退回（服务商还没答复）、已退到卡上、发卡方拒绝。“正在退回”的金额占用可退余额；只有服务商明确拒绝才释放。记录只追加，原付款不改不删。
4. **断线与服务商故障：** 没有答复就保持“正在退回”，后台任务 `business-table-online-refund` 每 30 秒重发超过 1 分钟的未答复退款，直到有答复。店员不用再按，面板 15 秒刷新一次。
5. **入账日：** 按服务商创建退款的时间归营业日，与日结、服务商对账单同一规则。未答复的退款不计入退款额，报表显示待确认笔数；日结 worker 会等它们有答复后再结算（与普通退款相同）。
6. **分单：** 每份付款单独显示、单独退，不能超过这一份付的金额。
7. **积分：** 积分扫描任务对比账本的退款事实，按比例扣回赚到的积分、退回抵扣的积分，不需要另外调用。
8. **小费和税：** 退款金额先抵菜品，再抵小费，和现金退款相同；不拆到菜品，报表记为未拆分的退款。

## 没有做

- **刷卡机结整桌的退款（已知不足 ⑤）：** 面板写明“暂时不能在这里退款，请找店主”，另列为后续项。
- **Stripe 真实环境：** 只用模拟服务商验证。真实 Stripe 账户是外部关口，到位后要实测拒绝和待处理（pending）路径。
- **通知客人：** 由店员当面告知；收据不单独发退款通知。

## 操作连续性

| 故障                     | 店员怎么做                                                         |
| ------------------------ | ------------------------------------------------------------------ |
| 店里断网                 | 恢复后再按一次，同一笔不会重复记录；提交前断网的什么都没发生       |
| 云主机或服务停机         | 恢复后后台任务继续发送已批准的退款；未批准的重新操作               |
| 服务商不答复             | 面板显示“正在退回”，告诉客人已提交；后台持续重发                   |
| 发卡方拒绝（如卡已注销） | 面板显示拒绝，金额释放；重新退一次，仍被拒绝时由店主联系服务商处理 |

## 数据

新表 `rms_payment.dining_table_online_refund`、`dining_table_online_refund_outcome`（迁移 `2000_149`，只追加，RLS 按品牌和门店）。数据库触发器保证只能退手机付款、总额不超过这笔付款。审计动作：`PAYMENT_DINING_TABLE_ONLINE_REFUND_APPROVED`、`_CONFIRMED`、`_REFUSED`。
