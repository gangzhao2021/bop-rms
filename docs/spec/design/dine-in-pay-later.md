# DEC-DINE-IN-PAY-LATER — 堂食先点后付

状态：**Owner 决定（2026-10-26，WP-2423）**。原话：“同意先点后付，按这个顺序做”。
来源：[堂食晚市走查](../work-packages/WP-2423.md)（订单 8，DEMO-02）以及 WP-2423「产品定义」中的第一批客户：加拿大华人独立餐厅，堂食优先。

## 和已接受内容的关系

- Handoff §44（Phase 1 限制）和 §27 的 Pilot override 把 “manual pay-later” 列为“以后单独批准的增量”。本决定就是 Owner 对这个增量的批准，只覆盖堂食。
- 现金：Owner 2026-10-26 决定加入本增量。原话：“要支持现金，加进先点后付一起做”。规则见下文“现金”一节。分单付款、礼品卡和离线收款仍按 §87.9 不在范围内。
- Handoff §25.2 的 Session `Closing`（“已请求结账”）是本决定的结账阶段。§25.3 的 “Session Closed → Table Needs Cleaning” 一并恢复。
- 本决定不改变“每一笔都有记录”的原则（`AGENTS.md`）：未付款的金额不会被删除或隐藏。

## 决定

1. **门店设置“堂食付款时机”有两个选项：**
   - **先付**：现在的做法，每一轮先付款，再送到后厨；
   - **先点后付**：先吃，最后按桌一起结账。

   店型模板的默认值：正餐用先点后付，快餐和咖啡店用先付。DEMO 试点门店改为先点后付。设置只对新开的桌生效，已经开着的桌保持开桌时的方式。

2. **点单：**先点后付时，客人提交的一轮直接成为订单批次，不用付款，送到后厨后由后厨在自己的屏幕上接单。前台不用再接单一次。防乱点单仍然靠 §6.7：员工开桌，客人凭入桌码加入。店员可以取消某一轮，取消会被记录、署名，是一项补偿操作。
3. **结账：**由客人在手机上点“结账”，或由店员在桌台页发起。桌子进入 `Closing`，购物车锁定。需要加菜时取消结账，回到 `Active`。账单显示整桌的菜品、税和合计，小费只选一次。付款方式有两种：
   - (a) 客人在手机上线上付清整桌；
   - (b) 店员用店里的刷卡机收款，再按现有的柜台收款记录方式记下来（见 [counter-payment-record](./counter-payment-record.md)）。

   分单付款以后再做。

4. **关台：**余额为 0 才能关台。客人没付钱就离开时，由经理选择“客人未付离开”并填写原因。这笔未收金额会留在当天的营业小结和对账里，订单和销售记录不会被删除。
5. **超时：**已经上桌的轮次永远不会自动取消，也不会自动退款。桌子开得太久时，在桌台页提醒店员（AGENTS.md：超时前先提醒）。
6. **断网和设备故障：**网络或云端中断时，店员照常用刷卡机收款，恢复后再补记（这是已有的柜台收款记录方式）。后厨断网时，按现有的纸单流程做。

## 现金

1. **适用范围：**用于堂食结账，作为第三种付款方式，另外两种是手机付款和刷卡机收款后补记。叠加阶段，柜台单的现金仍由商家原来的收银机处理。
2. **收款：**店员选择“现金”，输入实收金额，系统算出找零。每一笔现金收款都记录金额、找零、收款员和时间，并写入订单的付款记录。现金收款不需要支付平台。
3. **分币取整：**加拿大已停用 1 分硬币。现金付款的应付总额按加拿大规则取整到 5 分：尾数 1、2 舍为 0，3、4 进为 5，6、7 舍为 5，8、9 进为 10。卡付不取整。取整差额单独记一行，不改动商品价格、税额和销售金额。
4. **退款：**现金退款要经理批准，记录退款金额、经手人和原因，是一项补偿操作。原来的收款记录不会被修改或删除。
5. **打烊：**当天小结和结算页单独显示“现金收款”“现金退款”“现金净额”和“取整差额”，老板可以拿来和钱箱对账。叠加阶段，钱箱里也有商家原来收银机收的现金，所以 v1 不做钱箱清点和差异登记，只给出我们这边应收的现金金额。整套取代收银机以后，再加备用金、清点和差异记录。
6. **不做销售隐瞒：**现金收款和其他付款方式一样，进入每一份报表、导出和对账。不能删除，不能“不入账”，也没有任何隐藏现金收入的设置或角色（`AGENTS.md`）。
7. **断网：**断网时现金照收，在纸上记下桌号、金额和时间，恢复后补录。补录的记录带有“补录”标记，并保留真实的收款时间。

## 证据要求

本决定涉及付款、订单状态和对账，按 WP-2423 的规定，必须保留完整证据：

- 在受限角色下做验收测试，并先证明测试能对有缺陷的代码报错；
- 在 v15 上按 TEST 数据实测一遍：开桌 → 两轮直接进厨房 → 呼叫店员 → 结账（线上付款和刷卡机各一桌）→ 关台 → 当日对账；
- 实测中还要试一桌“客人未付离开”。
- 现金：测一桌现金结账，应付总额尾数需要取整，确认找零正确；做一次现金退款，由经理批准；最后确认当天小结里的现金金额和取整差额都对。

## 实现决定（2026-10-27，按商用原则作出，协调人同意）

分四段交付，每段带受限角色验收测试：S1 设置与轮次直接进后厨；S2 整桌结账（刷卡机、现金）、关台、客人未付离开、待清洁；S3 现金退款与日结；S4 顾客手机付清整桌。S1+S2 完成后部署实测一次，S3+S4 后再一次。

1. **设置归属：**“堂食付款时机”归 Dining 所有，按门店只追加版本记录（谁改、何时改）；店长和老板可以改。开桌时把当时的设置记到这张桌上（只追加），之后改设置不影响已开的桌。
2. **先点后付的轮次：**提交照常走点单的所有检查（菜单、库存、产能、价格），但不建立付款计时。提交后由 Ordering 记一条“先点后付确认”（只追加，不是付款），这一轮就和已确认的轮次一样送进后厨，并自动记为前台已接单。没有付款计时，所以不会被“未付款超时”取消。前台仍可按补偿操作取消某一轮，取消会记录经手人和原因。
3. **整桌付款的拆分：**整桌结算有一个结算编号。一笔整桌付款（刷卡机、现金或线上）在付款领域里按轮拆成每轮一条付款记录，每条的金额是这一轮报价的含税合计，全部用同一个结算编号串起来。小费和现金取整差额只记在一轮上（编号最大的未付轮），所以整桌合计 = 各轮合计 + 小费 + 取整差额 = 实收。现有的按轮退款、按菜退款和日结因此照常可用。
4. **对账：**线上整桌付款在支付平台只有一笔交易。对账按结算编号汇总这次结算的各轮记录，再与那一笔交易核对，不逐条核对。
5. **收据：**顾客拿到的是一张整桌收据，列整桌菜品、税、小费、取整差额、合计和付款方式，不按轮拆开。
6. **现金取整：**只对现金付款，按应付总额的分位：1、2 舍为 0；3、4 进为 5；6、7 舍为 5；8、9 进为 10。取整差额单独一行，可正可负，不改动价格、税和销售额。

### S1 的实现补充（2026-10-27）

7. **自动接单走已发布流程：**先点后付的一轮在提交后，由系统按门店已发布的堂食流程的“接单”一步记为已接单（只允许流向“已接单”、权限 `order.accept`、不允许越权），记录接单原因 `PAY_LATER_SENT_TO_KITCHEN`，审计保留期按财务合规。同一轮再送一次只返回原来的记录，不会重复接单或重复进厨房。
8. **付款窗口：**提交时 Dining 仍按原样封存这一轮的结账记录（带付款窗口），但这一轮已接单，所有“未付款超时”的查询都排除它；另外数据库触发器直接拒绝给先点后付的轮次写“未付款取消”。前台页面和顾客页面都不显示截止时间。
9. **桌上不能按轮付款：**一张按“先点后付”开的桌，顾客在手机上不能再按轮付款（服务器拒绝，提示“这桌最后一起结账”）；结账页不显示小费，按钮是“送厨房”。店员替桌下单时也不选小费、不出现刷卡步骤。小费在整桌结账时选一次。
10. **店员怎么知道这桌怎么付：**桌台列表给每张桌带上付款时机：已开的桌按开桌时记下的，空桌按门店当前设置（下一次开桌会用的）。
